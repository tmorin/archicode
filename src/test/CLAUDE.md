# Tests

Integration tests, Java coverage, the unit and end-to-end suites of the page, and the byte-identity harness.

## Integration tests (`*IT`)

- Failsafe is skipped by default (`skipITs=true` in `pom.xml`) unless run with `-DskipITs=false`, `-Dnative` or on the `native` profile (which also skips Surefire: the unit tests are the job `Java`'s).
- They are the `*IT` classes of `src/test/java/io/morin/archicode/it` (`@QuarkusMainIntegrationTest`). Each launches the packaged application as a process, the jar or the native runner, on copies of the shipped examples (`src/doc/examples`, the Brightcart and bookshop fixtures) in a temp folder, and checks what it prints, its exit code and the files it writes: `views generate`, `query views|schemas|graph`, `diff`, `diff --fail-on`, `--against`, `--only-changes`, a TOML manifest, `editor serve` (started on a free port, one request, stopped), and `--version` (`VersionIT`: `archicode <version>` with the version of the pom, which the build hands to the tests as the property `archicode.version`).
- A test must talk to the application through its command line and its HTTP port only. A change to the checks is a change to those classes, not to the workflow; a new class that the application reads by reflection goes to `reflect-config.json`.
- The Native job runs them on the native image, on each target it builds, and keeps the runner: after the tests `.github/scripts/native-collect.sh` finds the one `target/archicode-<version>-runner` (it fails unless there is exactly one), checks that its `--version` is `archicode <pom version>` (and, for a release, that the pom is the version of the tag), and uploads `native-dist/archicode-<version>-<target>` with its `.sha256` as the artifact `archicode-<version>-<target>` (7 days; it is a zip that loses the executable bit, so `chmod +x` it).

## Java coverage

- `./mvnw verify` measures `src/main/java` from every test it runs and fails below the floors. The plain JUnit tests are counted by the agent of `jacoco-maven-plugin`, the `@QuarkusTest` ones by the `quarkus-jacoco` extension (the agent leaves the classes of Quarkus' own class loader to it, `exclClassLoaders`), both into the one file `target/jacoco-quarkus.exec` (`quarkus.jacoco.reuse-data-file` in `src/test/resources/application.properties`; `maven-clean-plugin` deletes the file at the start of a build, so a previous build never adds its lines).
- `jacoco:check` fails `verify` when the line, the instruction or the branch coverage of the bundle is below 0.90 (three floors). The report is `target/jacoco-report` (`index.html`, `jacoco.csv`, `jacoco.xml`), written by the same build locally and in the job `Java` of CI.
- The only code outside the measure is what a compiler writes: Lombok (`lombok.addLombokGeneratedAnnotation = true` in `lombok.config` marks it `@Generated`) and `io/morin/archicode/viewpoint/kernel/ViewpointKernelModule*` (no source; excluded in the plugin config). The `*IT` classes run the packaged application in a process and are not in the figure. The `native` profile sets `jacoco.skip`, so it neither measures nor checks.
- A test written for the figure asserts what the code returns, writes or throws; a line the tests cannot reach because it is dead is deleted, not excluded. When the kernel has to be made to break its contract (a version, a duplicate id), a test replaces `ViewpointKernel.getInstance()` with `Mockito.mockStatic`.

## The JavaScript suites

```bash
npm run test:unit                                        # = node --test "src/test/javascript/**/*.test.js": kernel and standalone editor vs. the views the CLI generates (loads the page in Node, with no DOM)
npm run test:e2e                                         # = playwright test: a real browser against `archicode editor serve` on the packaged jar; needs `./mvnw verify` (or `package`) first, and `npx playwright install --with-deps chromium firefox webkit` once
scripts/byte-identity.sh                                 # the jar of an earlier tag (built outside the repo from `git archive`) and the working tree run the commands on every shipped workspace; files, stdout, stderr and exit codes must be identical but for the sentences of scripts/byte-identity-exceptions.txt
```

- The unit suite is `src/test/javascript/`, plain `node --test`, with the page and the kernel loaded in Node. A test that reads the stylesheet of the page reads it parsed, through `loadStylesheet(html)` of `viewpoint-kernel/stylesheet.js`: its `rule`, `decl`, `has` and `order` answer by selector, at-rules and source order, so that Prettier's layout of `style.css` does not decide the verdict. `npm run test:coverage` runs the same tests with the editor-script floor (see `src/main/editor/CLAUDE.md`).
- The end-to-end suite is `playwright test` (`@playwright/test` pinned exact in `package.json`, config `playwright.config.js`): `src/test/e2e/*.spec.js`, a real browser, in three projects. `chromium` and `firefox` run every spec; `webkit` runs six of them (`open-and-pages`, `browser-workspace`, `sample`, `hosted-acceptance`, `workspace-menu` and `diagram-toolbar`, the anchored `testMatch` of `playwright.config.js`): the six-page sweep, the folder kept in the browser, the sample, the acceptance of the hosted editor, the Workspace menu of a browser workspace and the toolbar of a diagram: on five surfaces its groups, keys and toggles, the dot on the three groups a view keeps, Reset (disabled, then enabled and restoring), the keys a named view writes, Unfold all on the page of a Map view, and at 360 by 740 the height, the group buttons with their counts, the panel that Escape closes and the zoom in Frame. The other specs test the served-folder path, which is the same code in every engine, and each starts a JVM, so they stay out of WebKit. Playwright's WebKit is a build of the engine, not Safari, and needs system libraries the other two do not (`--with-deps` installs them).
- A spec runs `archicode editor serve` started from `target/quarkus-app/quarkus-run.jar` on a free port, on a COPY of a shipped example (or of a small workspace the spec writes, `workspace.js`) in a temp folder: one server and one copy per test (`harness.js`, `fixtures.js`). The `serve` fixture stops the server and deletes the copy whatever the verdict. The automatic fixture `pageErrors` fails a test whose page says an error on the console or throws, judging the page at the end of the test body, before the server of `serve` stops (it lists `serve` among its parameters, so that a request the page sends as the server stops is no error of the test; `teardown.spec.js` holds that order). The files a test asserts on are read back from the disk of the copy (the editor's output is its contract).
- The flows the specs cover: open a folder (the error card of a folder without `.archicode.yaml` and *Try again*), the six pages of a shipped example with no console error, the address (a link, a reload, an unknown route, Back and Forward), the line-preserving save of a name and a description (two lines change, the comments and quotes of the rest stay), the two-click save and the dialog of a layered workspace, the confirm boxes of Cancel and of leaving a form with typed text, a created child, a rename followed in every file, a view drawn with its boxes and the click on a box, the comparison of two plateaus with its Changes panel and the keys `j` and `k`, and the story player (keys, menu, Tab, Escape, focus back on *Play*, Back and Forward, a link to a step), and the claims of the stylesheet that only a computed style shows (`stylesheet-claims.spec.js`: the key of a comparison folded and capped, the header of an element page at three widths, a styled box's fill and its own stroke, the story player on a phone). Not covered by a spec: a rename that the dialog of sibling plateaus questions (it needs two plateaus that do not stack; the unit suite proves it, `move-sibling-plateaus.test.js`).
- The acceptance of the hosted editor is `src/test/e2e/hosted-acceptance.spec.js`, in all three projects. A visitor whose browser has no folder picker opens the sample, changes it, reloads, exports, deletes and imports it back, with the same bytes. A visitor whose browser has a picker, which the test replaces by a stub that counts its calls, makes none, and the page sends no write request. The button of the presentation page is clicked, then clicked again, and the one workspace keeps the change. It runs on the page that `startHostedPage()` serves from Node, with no JVM (the helpers are in `hosted.js`, the routes in `harness.js`).
- One worker and no retry (`workers: 1`, `retries: 0`): a test starts a JVM and a browser, parallel files time out on a busy machine, and a retry hides a flake. A flow that cannot be made stable is dropped with its reason, not retried. A failure keeps its trace, screenshot, video and `error-context.md` (a snapshot of the page for an agent) under `target/e2e/test-results/<test>/` and the report under `target/e2e/report` (`npx playwright show-trace <trace.zip>`; `npx playwright show-report target/e2e/report`).
- `ARCHICODE_E2E_JAR` runs the suite on another build of the application (a copy of `target/quarkus-app` with the page broken on purpose is how the suite is shown to fail); the spawn line of `harness.js` is the one place to change for the native runner. `JAVA_HOME` names the JDK (the shell's `java` may be older than 25).
- In CI the job `E2E` builds its own jar (`./mvnw package -Dmaven.test.skip -Dplugin.asciidoctor.skip=true`, step "Build the packaged application", with a Maven cache of its own), caches the browsers keyed on the Playwright version and the names of the three browsers, installs them (`npx playwright install --with-deps chromium firefox webkit`), runs "Run the end-to-end tests" and, only when they failed, uploads `target/e2e` as the artifact `e2e-results` (7 days). `format:check` and `lint` cover `src/test/e2e/**/*.js` and `playwright.config.js` (`globals.node` and `globals.browser`, the second for the callbacks handed to the page); the unit suite's glob and the coverage floor do not see the specs, and the e2e suite is not in the Java figure.
- What the e2e suite does not test: the browser's own folder picker (`showDirectoryPicker`) and what hangs on it (the remembered folders of IndexedDB, the native `createWritable`; the suite tests the served-folder handle, the second implementation of the same interface, and the picker stub only shows the page does not call a picker when it should not); the real Safari (a pass in Playwright's WebKit is not a pass in Safari); the stock Firefox (Playwright drives its own builds); Windows and macOS; the packaged native runner (the Native job's `*IT` classes run that); and the real GitHub Pages (the hosted specs serve the page from Node the way the website serves it, so only the tag run proves the base path and the assembly of the website, `/editor/samples/`).

## The byte-identity harness

- `scripts/byte-identity.sh` builds the base program from a release tag outside the repository and runs `views generate`, `stories generate`, `query graph`, `query views`, `diff`, `plateau list` and `query schemas workspace` (and the `--plateau` forms, once per plateau) on every folder that holds a `.archicode.yaml` under `src`, with both programs on fresh copies. It compares the files written, stdout, stderr and the exit code.
- The only accepted differences are the lines of `scripts/byte-identity-exceptions.txt` (a regular expression of the base's sentence, a tab, a regular expression of the new one; error sentences only), and the files `stories generate` writes that differ by design, listed in `scripts/byte-identity-new-files.txt`. A self-check proves that a changed sentence is found without the exceptions. A second file, `scripts/byte-identity-stdout-changes.txt` (`--stdout-changes`), declares a change of standard output: one rule per line, a regular expression of the label (`<workspace>: <command>`), a tab and a `sed -E` script; a pair is accepted when only stdout differs and the script, run on the new output, gives the base output byte for byte. The self-check proves that a rule accepts its change, that no rule or another label or a change beyond the declared one is reported.
- A change to what a command prints or writes on a shipped workspace is a decision: add the exception with the reason, or the new file to the list, in the same commit.

## The command reference of the manual

- The block between the BEGIN and END lines of `[[command-reference]]` in `src/doc/README.adoc` is generated by `CommandReferenceTest` from the live command line and checked against it; `manual-howto.test.js` pins only its shape. To regenerate it after a change to a command or an option: `ARCHICODE_MANUAL_REGENERATE=1 JAVA_HOME=<jdk 25> ./mvnw test -Dtest=CommandReferenceTest`, then commit the manual.
