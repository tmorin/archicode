# Tests

Integration tests, Java coverage, the unit and end-to-end suites of the page, the byte-identity harness. Moved from the root `CLAUDE.md` with its wording unchanged; the root file says where each area lives.

Integration tests (Failsafe) are skipped by default (`skipITs=true` in pom.xml) unless run with `-DskipITs=false`, `-Dnative` or on the `native` profile (which also skips Surefire: the unit tests are the job `Java`'s). They are the `*IT` classes of `src/test/java/io/morin/archicode/it` (`@QuarkusMainIntegrationTest`, wave 015 run 0105, #62): each launches the packaged application as a process, the jar or the native runner, on copies of the shipped examples (`src/doc/examples`, the Brightcart and bookshop fixtures) in a temp folder, and checks what it prints, its exit code and the files it writes (`views generate`, `query views|schemas|graph`, `diff`, `diff --fail-on`, `--against`, `--only-changes`, a TOML manifest, `editor serve`: started on a free port, one request, stopped, and `--version`, `VersionIT`: `archicode <version>` with the version of the pom, which the build hands to the tests as the property `archicode.version`). They are what the Native job runs on the native image, on each target it builds (and the job keeps the runner, wave 021 run 0155, #149: after the tests `.github/scripts/native-collect.sh` finds the one `target/archicode-<version>-runner` (it fails unless there is exactly one), checks that its `--version` is `archicode <pom version>` (and, for a release, that the pom is the version of the tag), and uploads `native-dist/archicode-<version>-<target>` with its `.sha256` (the format of `sha256sum -c`) as the artifact `archicode-<version>-<target>`, `actions/upload-artifact@v7.0.2`, 7 days: a contributor finds it under Actions, the run of the pull request, Artifacts; it is a zip that loses the executable bit, so `chmod +x` it), so a test must talk to the application through its command line and its HTTP port only. A change to the checks is a change to those classes, not to the workflow; a new class that the application reads by reflection goes to `reflect-config.json`.

Java coverage (wave 023, run 0171, W-8): `./mvnw verify` measures `src/main/java` from every test it runs and fails below the floors. The plain JUnit tests are counted by the agent of `jacoco-maven-plugin`, the `@QuarkusTest` ones by the `quarkus-jacoco` extension (the agent leaves the classes of Quarkus' own class loader to it, `exclClassLoaders`), both into the one file `target/jacoco-quarkus.exec` (`quarkus.jacoco.reuse-data-file` in `src/test/resources/application.properties`; `maven-clean-plugin` deletes the file at the start of a build, so a previous build never adds its lines). `jacoco:check` (execution `check` of the pom) fails `verify` when the line, the instruction or the branch coverage of the bundle is below 0.90 (three floors at 0.90, wave 023 run 0177: the branch floor was a guard-rail at 0.88 until then). The report is `target/jacoco-report` (`index.html`, `jacoco.csv`, `jacoco.xml`), written by the same build locally and in the job `Java` of CI (which runs `./mvnw verify`; no server and no token). At the end of run 0171 the figure is 98.5 % of the lines, 98.6 % of the instructions and 92.9 % of the branches; before it, the only report that existed said 47.8 % of the instructions because it counted the classes the chicory compiler writes from the WebAssembly. The only code outside the measure is what a compiler writes: Lombok (`lombok.addLombokGeneratedAnnotation = true` in `lombok.config` marks it `@Generated`) and `io/morin/archicode/viewpoint/kernel/ViewpointKernelModule*` (no source; excluded in the plugin config). The integration tests (`*IT`) run the packaged application in a process and are not in the figure. The `native` profile (the Native job: Surefire skipped, only the `*IT` classes) sets `jacoco.skip`, so it neither measures nor checks. A test written for the figure asserts what the code returns, writes or throws (wave 023, T10); a line the tests cannot reach because it is dead is deleted, not excluded. When the kernel has to be made to break its contract (a version, a duplicate id), a test replaces `ViewpointKernel.getInstance()` with `Mockito.mockStatic`.

```bash
npm run test:unit                                        # = node --test "src/test/javascript/**/*.test.js": kernel and standalone editor vs. the views the CLI generates (the unit/integration suite, the first of the two JavaScript suites: it loads the page in Node, with no DOM; the second, `npm run test:e2e`, is below)
npm run test:e2e                                         # = playwright test (wave 023 run 0175, W-13, T11): the end-to-end suite, a real browser against `archicode editor serve` on the packaged jar; needs `./mvnw verify` (or `package`) first, and `npx playwright install --with-deps chromium firefox webkit` once
scripts/byte-identity.sh                                 # V-C (wave 023): the jar of the tag archicode-0.19.0 (built outside the repo from `git archive`) and the working tree run the commands on every shipped workspace; files, stdout, stderr and exit codes must be identical but for the sentences of scripts/byte-identity-exceptions.txt
```

End-to-end suite (wave 023, run 0175, W-13, T11; the framework was chosen by run 0174, Q7): the JavaScript tests are of two kinds. The unit/integration suite is `npm run test:unit` (and `npm run test:coverage`, which runs the same tests with the editor-script floor): `src/test/javascript/`, plain `node --test`, the page and the kernel loaded in Node with no DOM. The end-to-end suite is `npm run test:e2e` (`playwright test`, `@playwright/test` pinned exact in `package.json`, config `playwright.config.js`): `src/test/e2e/*.spec.js`, a real browser, in three Playwright projects: `chromium` and `firefox` run every spec, and `webkit` runs five of them (`open-and-pages`, `browser-workspace`, `sample`, `hosted-acceptance` and `workspace-menu`, the anchored `testMatch` of `playwright.config.js`, wave 025 run 0194 and wave 028 run 0205, DEC-2): the six-page sweep, the folder kept in the browser, the sample, the acceptance of the hosted editor (#162) and the Workspace menu of a browser workspace (#182). The other specs test the served-folder path, which is the same code in every engine, and each starts a JVM, so they stay out of WebKit. Playwright's WebKit is a build of the engine, not Safari, and it needs system libraries the other two do not (`--with-deps` installs them); `showDirectoryPicker` is Chromium-only, so the hosted acceptance replaces the picker by a stub, against `archicode editor serve` started from `target/quarkus-app/quarkus-run.jar` on a free port, on a COPY of a shipped example (or of a small workspace the spec writes, `workspace.js`) in a temp folder, one server and one copy per test (`harness.js`, `fixtures.js`: the `serve` fixture stops the server and deletes the copy whatever the verdict; the automatic fixture `pageErrors` fails a test whose page says an error on the console or throws, judging the page at the end of the test body, before the server of `serve` stops (wave 024, run 0181, W-10: it lists `serve` among its parameters, so that a request the page sends as the server stops is no error of the test; `teardown.spec.js` holds that order)). The files a test asserts on are read back from the disk of the copy (the editor's output is its contract). The specs are the flows of Q8: open a folder (the error card of a folder without `.archicode.yaml` and *Try again*), the six pages of a shipped example with no console error, the address (a link, a reload, an unknown route, Back and Forward), the line-preserving save of a name and a description (two lines change, the comments and quotes of the rest stay), the two-click save and the dialog of a layered workspace, the confirm boxes of Cancel and of leaving a form with typed text, a created child, a rename followed in every file, a view drawn with its boxes and the click on a box, the comparison of two plateaus with its Changes panel and the keys `j` and `k`, and the story player (keys, menu, Tab, Escape, focus back on *Play*, Back and Forward, a link to a step). The acceptance of the hosted editor (#162, wave 025 run 0194) is `src/test/e2e/hosted-acceptance.spec.js`, in all three projects: a visitor whose browser has no folder picker opens the sample, changes it, reloads, exports, deletes and imports it back, with the same bytes; a visitor whose browser has a picker, which the test replaces by a stub that counts its calls, makes none, and the page sends no write request; the button of the presentation page of the site is clicked, then clicked again, and the one workspace keeps the change. It runs on the page that `startHostedPage()` serves from Node, with no JVM (the helpers are in `hosted.js`, the routes in `harness.js`), and the browser workspace it relies on is the one of the paragraph Browser workspace above. Cut from Q8, with the reason: a rename that the dialog of sibling plateaus questions (needs two plateaus that do not stack; the unit suite proves it, `move-sibling-plateaus.test.js`, and the example has none). One worker and no retry (`workers: 1`, `retries: 0`: a test starts a JVM and a browser, parallel files time out on a busy machine, and a retry hides a flake; a flow that cannot be made stable is dropped with its reason, not retried); a failure keeps its trace, screenshot, video and `error-context.md` (a snapshot of the page for an agent) under `target/e2e/test-results/<test>/` and the report under `target/e2e/report` (`npx playwright show-trace <trace.zip>`; `npx playwright show-report target/e2e/report`). `ARCHICODE_E2E_JAR` runs the suite on another build of the application (a copy of `target/quarkus-app` with the page broken on purpose is how the suite is shown to fail); the spawn line of `harness.js` is the one place to change for the native runner. `JAVA_HOME` names the JDK (the shell's `java` may be older than 25). In CI, the job `E2E` (it builds its own jar, `./mvnw package -Dmaven.test.skip -Dplugin.asciidoctor.skip=true`, step "Build the packaged application", with a Maven cache of its own, rather than wait for the jar of `Java`): the browser cache keyed on the Playwright version and the names of the three browsers, `npx playwright install --with-deps chromium firefox webkit`, "Run the end-to-end tests", and, only when they failed, the upload of `target/e2e` as the artifact `e2e-results` (7 days). The format (`format:check`) and the lint (`lint`) cover `src/test/e2e/**/*.js` and `playwright.config.js` (`globals.node` and `globals.browser`, the second for the callbacks handed to the page); the unit suite's glob and the coverage floor do not see the specs, and the e2e suite is not in the figure. What it does not test: the browser's own folder picker (`showDirectoryPicker`) and what hangs on it (the remembered folders of IndexedDB, the native `createWritable`: the suite tests the served-folder handle, the second implementation of the same interface; `hosted-acceptance.spec.js` replaces the picker by a stub that counts its calls, so it shows that the page does not call a picker when a visitor opens the sample and sends no write request, and never that a picker works), the real Safari (a pass in Playwright's WebKit is not a pass in Safari), the stock Firefox (Playwright drives its own builds), Windows and macOS, the packaged native runner (the Native job's `*IT` classes run that), and the real GitHub Pages: the hosted specs serve the page from Node the way the website serves it, so only the tag run proves the base path and the assembly of the website (`/editor/samples/`).
