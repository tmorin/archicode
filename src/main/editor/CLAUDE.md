# The editor page

How the standalone editor page is built, checked and covered, and what its parts do. Moved from the root `CLAUDE.md` with its wording unchanged; the root file says where each area lives.

**The editor page is generated** (wave 024, run 0183, W-5; design: run 0182 RFC-001, the run's DEC-2, DEC-4, DEC-6, DEC-8): `src/main/resources/editor-webapp/standalone.html` is still the one file the jar, the native image, the website, the node harness, the coverage script, the lint extraction and the Java tests read, at the same path, but it is the output of `scripts/build-editor.mjs` and is not edited by hand. The sources are in `src/main/editor/`: the skeleton `page.html` (its `<!--@include FILE-->`, `<!--@parts-->` and `<!--@wasm FILE-->` lines are replaced, every other line is copied), `style.css`, `theme-boot.js`, `codemirror-loader.mjs`, and the main script cut in 69 parts (about 29,800 lines in all, none over 1,600) under the six layer folders `core`, `model`, `persistence`, `application`, `presentation` and `composition`, in the order of `layers.json` (wave 024, runs 0183 to 0187: there is no `unsorted` folder and no `unsorted/script.js` any more; RFC-002, `docs/wav/wav-024-fixes-and-editor-modules/rfc/`). A part is a run of whole top-level declarations of the one classic script, with no `import` or `export`: the parts share one global scope, so a name is used by the parts that come after it in `layers.json` (or inside a function, at call time). The rule between layers is that a layer uses the layers before it (`core`, then `model`, then `persistence`, then `application`, then `presentation`, then `composition`; downward only, RFC-002 rule 1, and the pairs that still go up are the ratchet below). **Redraw contract (RFC-002 rule 2, run 0187):** `modelsChanged()` (in `model/app-state.js`) bumps the version counter of the caches and draws nothing; a part below the composition that needs the page drawn again calls `requestRedraw()` (`model/app-state.js`), never `render()`; the composition registers what draws once, `onRedraw(() => render())` in `composition/render.js`, late-bound, and the request is carried out at once in the caller's turn, so the order of what is drawn, written and put back does not move (`redraw-requests.test.js`). `render()` is called in `composition/` only. The page is committed, so a change to a part is committed with the page it builds. To find the part of a line of the page: `node scripts/build-editor.mjs --where <line>` (`--map` prints every part with its lines).

```bash
npm run editor:build   # = node scripts/build-editor.mjs: writes the page from src/main/editor (no write when the bytes are the same); needs Node, no npm install
npm run editor:check   # = build-editor.mjs --check && check-editor.mjs --layers: the page is the assembly (else "standalone.html is generated: edit src/main/editor and run `npm run editor:build`"), then the three lists and the ratchet below; needs `npm ci` (acorn, eslint-scope)
scripts/check-editor-moves.sh <base> <head>   # the commits of base..head: `refactor: move ...` must leave the page byte for byte the page of its parent, `refactor: relocate ...` its declarations and comments; other subjects are not looked at
```

The hooks are the npm `pre` scripts and nothing else: `npm run lint`, `npm run test:unit` and `npm run test:coverage` run `editor:build` first (`prelint`, `pretest:unit`, `pretest:coverage`), so those three never test a stale page. They are not git hooks, and a command that does not go through those scripts does not build: `node --test` or `npx playwright test` run by hand, `./mvnw` (Maven does not assemble the page; `embed.sh` does, in write mode, after it writes the WebAssembly) and `npm run test:e2e` read the committed page as it is, so run `npm run editor:build` first after a change to `src/main/editor`. The guard against a stale committed page is the first step of the job `Page` of CI, "Check the editor page is the assembly of its parts" (`npm run editor:check`), run before the format check; on a pull request the step "Check the move commits" (`check-editor-moves.sh`) follows. Both are checks, they write nothing, and neither runs on a developer machine unless it is asked for.

`editor:check` stops at the first of its checks that fails, in this order. The three lists are files of `src/main/editor/`: `names.json` (the top-level names of the main script: a name added, removed or renamed is a change to the list, and the check prints which), `java-names.json` (the names that Java sources, comments and tests, say are in the page, each with the Java files that name it, and `pathOnly` for the files that name the path only: a name removed from the page, a listed Java file that no longer holds it, or a Java source that names `standalone.html` and is in no list fails) and `layers.json` (the layers in order, the parts in load order with their layer, and `ratchet.max`). Then the load order (a declaration that runs at load must not use one defined after it) and the ratchet: the count of upward pairs, a declaration that names a declaration of a higher layer, may not be above `ratchet.max` (99 today, lowered by run 0187 from 162; the 99 left are not redraws but helpers and state that a lower layer reads from a higher one, to be relocated; `node scripts/check-editor.mjs --list` prints them by name) and `max` is lowered by hand as parts are cut (nothing stops a commit from raising it; the failing line says to give the reason when it is raised). The ratchet counts names between parts; it does not prove that a part works, which the node suite and the end-to-end suite do. The commits that change the sources say which kind they are in their subject, and `scripts/check-editor-moves.sh` judges the first two: `refactor: move <part> to <path>` leaves the page byte for byte the page of its parent, `refactor: relocate ...` leaves its declarations and comments (a declaration moved to another part, only the order of the lines changing), `refactor: change ...` is a change of behaviour or of contract that the node suite and the e2e suite guard (a `style:` commit of formatter output is none of the three and is not looked at). `node scripts/check-editor.mjs --write-names` rewrites `names.json` from the page; `java-names.json` is written by hand.

`embed.sh` (the kernel) writes the WebAssembly and then calls `build-editor.mjs`, so the block of the kernel in the page is written by one place; its `--check` mode (the Kernel job) compares the committed WebAssembly and the page's block and needs no Node.

Editor script coverage (wave 023, run 0173, W-10, Q6): `npm run test:coverage` (= `node scripts/editor-coverage.mjs`) runs the node unit suite, `node --test` on `src/test/javascript/**/*.test.js`, with `NODE_V8_COVERAGE` and measures how much of the editor page's script (the first `<script>` of `standalone.html`, about 22,000 lines in one script; since run 0183 the page is assembled from `src/main/editor`, and the lines reported are those of the assembled page, which `--where` maps to a part) those tests run, by area and in total, as lines of code (blank and comment lines are not counted; a line is covered when V8 ran its first character) and as functions (every function V8 reports, called at least once), merging the ~110 test processes that load the page (any one running a line covers it). The harness (`harness.js`) runs the page of the repository under the file name `standalone.html-script.js` and any other page (a released one, `ARCHICODE_EDITOR_HTML`) under another, so only the first is counted; the script extracts the page with `scripts/extract-editor-script.mjs`, so a line of the report is a line of `standalone.html`. The areas are sections of the script, each started by a marker line that must match once (`SECTIONS` of the script: a renamed heading fails it, naming the marker): `yaml-and-save`, `layers-and-plateaus`, `workspace-and-files`, `editing`, `pages`, `diagram`, `stories`, `story-player`, `other` (what is none of them: the start of the script, the landing screen, the bootstrap), so that they add up to the total. The floor is `scripts/editor-coverage-floor.json`: for the total and for each area, the lines and the functions, the figure rounded down to a tenth and never above 90 (a total above 90 has the floor 90); the command fails (exit 1) below any of them, or when a test fails, and it prints "it could be raised" when the figure is a tenth above. The floor only goes up: `node scripts/editor-coverage.mjs --write-floor` writes it from the measure and refuses to lower one (`--lower` lowers it, as a decision). The figure at the end of run 0173 is 92.7 % of the lines (15,469 of 16,692) and 96.2 % of the functions (2,015 of 2,095); the weakest area is `pages` (83.9 % of the lines: the delegated click handler `handleAppClick`, the diagram's pointer and keyboard handlers, which the harness has no DOM to drive); the areas above 90 are held at 90, so raising the page's figure further is a matter of tests per area (and of the later steps of wave 024, which cut the page into parts). Since wave 024, run 0188, the page is built from formatted parts (Prettier puts a ternary or a long call on several lines, and a line counts as covered when its first character ran), so the page is 31,000 lines and the figure is 92.8 % of the lines (22,610 of 24,356) and 96.3 % of the functions; the floors did not go down, `pages` went up to 87.1 % and `other` to 76.4 % of its functions, and the `SECTIONS` markers are heading comments of the parts, which the assembled page still holds once each. The report is `target/editor-coverage/` (`report.json`, `report.txt`, `uncovered-functions.txt` and `uncovered-lines.txt` with HTML line numbers; the CI step "Cover the editor script" keeps them as the artifact `editor-coverage-report`, 7 days). The CI step is THE run of the node unit suite (same tests, same output, plus the figure): it replaced `npm run test:unit` in the job `Page`, which stays the command to run the tests alone (two to three minutes on a developer machine; with coverage on 40 to 50 % more, measured 161 s against 257 s back to back, and 1 to 2 s to read ~60 MB of V8 data). `--reuse` reads the coverage of the last run without running the suite; a list of test files after the options runs only those (a subset, so the floor fails: that is how the floor is shown to fail). The one test of the node suite that judges a time, the ratio of the first `quiet` and of `apply_patches` at 591 elements to 82 (#125, `performance-budget.test.js`), is skipped in the suite and runs alone as `npm run test:timing` (CI step "Check the time budget of the kernel", about 5 seconds): under the suite's 70 files at once, and under the coverage, the large pair reads 17 times the small one where the same kernel reads 10 to 13 on a quiet machine (the quadratic kernel of before #125 about 19), so no limit separates them there; it was the node suite's load-sensitive test (it failed once in several full runs, and in 2 of 5 full runs with the coverage on). The test judges the fastest of four warm runs per size, the limit is 16.

```bash
npm run test:coverage                                    # = node scripts/editor-coverage.mjs (wave 023 run 0173, W-10): the same suite with V8 coverage; the share of the editor script it runs by area, 92.7 % of the lines at the end of the run, and a floor in scripts/editor-coverage-floor.json that CI enforces (step "Cover the editor script", which is the job `Page`'s run of the unit suite)
```

Browser workspace (wave 025, run 0192, W-4, #162; TDD `docs/wav/wav-025-hosted-editor/run/run-0192-browser-workspace/tdd-0192-browser-workspace.md`): where the browser has no folder picker (or the reader does not want one), the editor keeps a workspace in the browser. The store is `src/main/editor/persistence/browser-store.js`, a third implementation of the directory-handle interface (after the browser's own and `serverDirectoryHandle`), in its own IndexedDB database `archicode-browser-workspaces`, version 1, one object store `records` with string keys: `workspace:<id>` (name, `createdAt`, `openedAt`, `lastExportAt`, `origin`), `file:<id>/<path>` (`bytes` as a `Uint8Array`, `modified`) and `last` (the pointer to the workspace the browser reopens); directories are implicit, a record of an unknown kind is ignored and never deleted, and the remembered folders' database `archicode-standalone-editor` is never opened by it. The handle is the interface of the other two: `createWritable().close()` is ONE transaction that reads the workspace record and the previous file record and writes the whole file or nothing (a quota or abort failure rejects with the browser's own name and a sentence that says nothing was changed, the old bytes stay), `modified` is `max(Date.now(), previous + 1)` so a rewrite always changes it (the stale check needs that), and a write, a create or a removal whose workspace record is gone (deleted in another tab) is refused with `NotFoundError` and stores nothing (DEC-6: no orphan file record, the workspace is not brought back). The pointer rule: `last` is written only for a workspace that exists, and deleting a workspace removes its record, its files and `last` when it points at it, in one transaction; closing a workspace clears `last` and keeps the workspace. Names are one rule (`browserWorkspaceNameProblem`: trimmed, 1 to 80 characters, no control character, unique without regard to case), checked again inside the transaction that stores them. The flows are `application/browser-workspaces.js` (landing card, create, open, rename, delete, close, export mark; `model/settings.js` and `model/app-state.js` hold `browserStoreState`, `browserStorageAsked`, `browserStoragePersisted` and the drafts of the card); `askForPersistentStorage` asks `navigator.storage.persist()` once per page session and never waits for it. Support floor (ASM-7): Chromium 111, Firefox 121, Safari 16.2; `showDirectoryPicker` is the one Chromium-only API and lives in `persistence/folder-access.js` only. Tests: `browser-store.test.js` (the contract on a fake IndexedDB, the harness option `withFile` and the `navigator.storage` stub of `harness.js`), `browser-workspaces-flows.test.js`, `browser-landing.test.js`, `browser-workspace-equivalence.test.js` (a browser workspace reads and saves as a served folder), `browser-apis.test.js` (a deny list of APIs and CSS newer than the floor, run on `ARCHICODE_EDITOR_SRC` when the sources are elsewhere) and the hosted-style e2e spec `src/test/e2e/browser-workspace.spec.js` (the page opened with no folder picker, a workspace kept across a reload). The run's record shows the store broken three ways on purpose (the record check, the monotonic `modified`, a write before the check) and each caught by a test. The Workspace menu of a browser workspace (wave 028, run 0205, #182): each item of the menu is a box of its own, with its label and its note inside it, and the bar and the menu stay inside the window at five widths from 1280 to 360 pixels, in the light and the dark scheme; `src/test/e2e/workspace-menu.spec.js` proves it (seven tests in each of Chromium, Firefox and WebKit), and `src/test/javascript/workspace-menu-layout.test.js` guards three declarations of `style.css` without a browser (the height of an item, the wrap of `.top-actions`, the position of the menu under 40 rem). Neither covers the *Back to the served folder* button of a served page nor the anchor of the help menu, which is cut off on the left at 360 pixels (out of scope of #182).

Bundle I/O and the Brightcart sample (wave 025, run 0193, W-5, #162; TDD `docs/wav/wav-025-hosted-editor/run/run-0193-import-export-and-sample/tdd-0193-import-export-and-sample.md`): a browser workspace leaves the browser as one YAML text and comes back from one. The codec is the page's own bundle format (`persistence/bundle.js`: one YAML document per file, each opened by a `--- # file: <path>` line); `persistence/browser-transfer.js` reads the files of a workspace (`readBrowserWorkspaceFiles`, a copy) and replaces them in ONE transaction (`replaceBrowserWorkspaceFiles`: the files not in the new set go, the record keeps its `id`, `name`, `createdAt`, `lastExportAt` and `origin`, all or nothing), `persistence/bundle-io.js` is the edge (the file picker, the download named `<name>-bundle.yaml`, the 10 MB limit, UTF-8 refused when invalid, `fetchSampleBundle` with `cache: 'no-cache'`, `BROWSER_SAMPLES`), and `application/bundle-flows.js` holds the flows (export, import, open the sample, reset it, back to the served folder) and names no presentation or composition function: the test of `countUnsavedChanges() > 0 || draftTyped` lives in the menu (`top-panel.js`, `events.js`), so *Export* is refused while changes or a draft are pending and allowed from the card. *Import* only creates a new workspace (a taken name gets ` 2`, `settings.name` is the name when it is valid, else the file name; nothing is created on a refusal); *Export* records `lastExportAt`; *Reset to the sample* names the workspace and the loss, fetches and unbundles BEFORE it replaces anything, and keeps the same record. A workspace made from the sample has `origin: 'sample'` and `sample: '<id>'` and is found again by that property, never by its name (a visitor may have a workspace called Brightcart; the sample then becomes `Brightcart 2`). The sample is `src/main/resources/editor-webapp/samples/brightcart.yaml`, GENERATED by `scripts/build-sample.mjs` from the 61 files of `src/test/resources/brightcart/layered` with the page's codec (`npm run sample:build` writes, `npm run sample:check` is the step "Check the Brightcart sample is the bundle of its fixture" of the job `Page`; a fixture file the bundle skips is an error); it is committed, in the jar (covered by the `editor-webapp/**` native include) and served by `EditorHttpServer` as `GET /samples/brightcart.yaml` (a table of one entry, `SAMPLES`; the token header or the session cookie like the page, otherwise 403; any other name 404), and the step "Assemble website" of the job `Build` copies it to `/editor/samples/` on a tag (proved only by the tag run; the extracted block was rehearsed locally). The visitor reaches it by the button of the presentation page (`#/timeline/applications?plateau=marketplace&compare=past&sample=brightcart`: `sample=` is read before the first render and dropped from the address), by the card, and by the *Workspace* menu of the top bar, which a served page (`editor serve`) also has: served-mode rule, the flows never hold the handle of the served folder while a browser workspace is open, so opening the sample, saving, exporting, resetting and *Back to the served folder* send no write to `/api/fs/` (`workspaceIsServedFolder()` replaces `isServedByArchiCode()` in the close slot and the help sentence only), and choosing the sample from a served page with unsaved changes asks the same confirm as *Back to the served folder*. Tests: `sample-brightcart`, `build-sample-script`, `browser-transfer`, `bundle-io`, `bundle-flows`, `sample-served-mode` and `sample-landing` (node), `EditorHttpServerTest`, `EditorServeIT` and `BrightcartSampleTest` (Java), `src/test/e2e/sample.spec.js` (Chromium and Firefox, against `startHostedPage()` at `/editor/`). Not proved by the run: the tag run, the native runner, WebKit and the real Safari. Since run 0194 the sample spec also runs in WebKit, and the acceptance of the hosted editor is `src/test/e2e/hosted-acceptance.spec.js`: see the paragraph End-to-end suite for the projects and for what the suite does not test.

**The links in the editor** (wave 026, run 0199, #143, W-5): the page Applications lists the relationships under its tree (`presentation/map-links.js`, entries in `model/map-links.js`: source, destination and trimmed label, the kernel's rule) and ticking some is the `links` of the Map. `mapLinks` is view state, no `modelsChanged()`: it is in the diagram cache key, in the address as `rel=<JSON [source, destination, label?]>` once per entry (an entry no model has is dropped), restored by a saved view and written back into `properties.links` by the view form and *Keep as named view*; a view with a highlight never matches the screen (DEC-7). The panel of a selected link has a check box per relationship and *Draw only this link*; a chip over the diagram clears the choice. Rename and move rewrite `links` and `highlight` of views and steps (`application/story-entries.js`, the label never changes). The technology Map has none. Limits: the load check of `links` in a layered workspace is declined (DEC-10, DEF-1). Run 0200 gave the guide its bullet on a story of a flow. Tests: `map-links-*.test.js` (node, with the shared contract file `src/test/resources/map-links/expected-boxes.json`, also drawn by the command line in `MapLinksSharedTest`) and the end-to-end spec `src/test/e2e/map-links.spec.js` (Chromium and Firefox).

**What a link carries** (wave 027, run 0203, #143 follow-up, RFC-001 DEC-2): the address of a diagram page is the whole say of the diagram. The rule: an option is in the address when it changes which boxes and links are drawn, or where; never when it changes only the surroundings. Written by `currentRouteHash` (`composition/address-routing.js`) on the page of an element (diagram tab), both Maps and the page of a selected saved view: `layout=N` (the toolbar's `diagramColumns`, 1 to 20, element and Maps; never the view's or the workspace's value, which are files; nothing on the page of a saved view, whose toolbar edits the file), `compare=<choice>` (every diagram surface of a layered workspace, empty for none; a workspace with no plateau writes none), `changes-only=1` (only with a comparison; never `=0`), `open=` and `hide=` (Maps; sorted lists of references like `pin`, `hide=` being an assumption derived from the rule, DEC-5), after `facet`, `pin`, `rel`, `hl`, then `compare`, `changes-only`, `plateau`. Absent means: no layout, folded, none hidden, and `changes-only` off when `compare=` is present (else the flag is left as it is, so an older link without `compare=` changes nothing). The reader resets what the address does not say on a diagram page (DEC-6) and never calls `rememberFlag` for `changes-only`: the reader's remembered flag survives; `drawPlateau` does remember an addressed comparison (`rememberLayerChoice`). The three exceptions: the wording-only toggle, the open or folded key, zoom and pan (and the selection of a box). `diagram-address-audit.test.js` holds each input of the drawing to a parameter or a reason. Tests: `diagram-address.test.js`, `diagram-address-audit.test.js`, `src/test/e2e/diagram-address.spec.js`; the manual says it in `[[editor-link-carries]]`.

**The highlight in the editor** (wave 026, run 0200, #143, W-6): the editor draws the highlight the kernel marks (`renderDiagramSvg` in `presentation/diagram-layout.js`: `dg-hl` on the heavy link, `dg-calm` on the others, the marker `dg-arrow-hl` only in a diagram with a highlighted link; the kernel's `highlighted` flag is the one source, the editor adds no match of its own), and it writes and plays it. `mapHighlight` is view state beside `mapLinks` (`model/ui-state.js`: in the cache key and in the address as `hl=`; `snapshotWriteState` and `resetUiState` know it). Its controls are the *Highlight* box of a link's panel and its chip (`presentation/map-links.js`), the *Highlight* field of a saved view (`setViewHighlight`, `presentation/view-edit.js`) and of a story step (`setStepHighlight`, `application/story-actions.js`, which writes the step's own key: the one place of a step's highlight, which replaces the view's, `stepViewForDrawing`). *Add to story...* writes the live highlight as the step key with the links in `properties.links`, and *Keep as named view* writes it as `properties.highlight`; `canonicalViewProperties` writes `highlight` sorted and without duplicates after `links`; `rewriteSavedViewReferences` (`application/story-entries.js`) rewrites both on rename and move. The player draws each step with `storyStepScene`, which reads the step's highlight, and announces it (`presentation/story-scene.js`, `storyStepAnnouncement`) without writing to the editor. The shipped story `order_flow` (the layered Brightcart's `shared/story.order_flow.yaml`, also in the sample) is the one written form of a story of a flow; `scripts/byte-identity-new-files.txt` lists the files that `stories generate` writes and that differ from the 0.19.0 jar by design, and `scripts/byte-identity.sh` reads it (DEC-8). The tests are `map-highlight-*.test.js`, `story-player-highlight.test.js`, `map-links-shared.test.js` (with `src/test/resources/map-links/expected-boxes.json`, also read by `MapLinksSharedTest`) and the e2e spec `src/test/e2e/story-flow.spec.js`; the manual says it in `[[map-highlight]]`, `[[editor-map-links]]`, `[[editor-stories]]`, `[[editor-story-player]]` and `[[story-of-a-flow]]`.

**The boxes per row in the editor** (wave 027, run 0202, #178, W-2): `layout: {columns: N}` (N a whole number from 1 to 20), in `properties` of a view and in `settings.views.properties.<viewpoint>`, is read by the editor only; the command line reads neither (`KernelViewpointFactory` reads `properties` by name, `views.properties` is carried and acted on by no Java code, ASM-2). `resolveDiagramColumns({ toolbar, view, settings, viewpoint })` in `model/diagram-columns.js` is the one place that knows the four levels (toolbar, then view, then workspace, then none; the first level that is set decides, and an invalid one gives `columns: null` and its sentence from `columnsProblem`; `viewpoint` is `'map'` for both Maps; `DIAGRAM_COLUMNS_MAX` and `DIAGRAM_COLUMNS_CHOICES` live there). `mainDiagramRecipe`, `viewDiagramRecipe` and `libraryDiagramRecipe` (`presentation/diagram-page.js`, `application/view-recipe.js`) carry `columns` and `layoutProblem`; `computeDiagramScene` returns the error panel for a `layoutProblem` before it lays anything out, and passes `columns` to `buildElkGraph` (`presentation/diagram-layout.js`), which sets `elk.layered.layering.strategy: COFFMAN_GRAHAM` and `coffmanGraham.layerBound` on the root and on each compound node, and adds nothing when `columns` is unset, so the graph is the one of before, key for key. `diagramColumns` is view state (`model/ui-state.js`, reset by `resetUiState`, not in `snapshotWriteState`); `diagramCacheKey` adds `cols:<n>` only when it is set; `applySavedView` takes the valid value of the view. A saved view keeps `layout` in its canonical form (`canonicalViewProperties` writes `{columns: N}`, `canonicalViewDefinition` drops the value the workspace gives, `VIEW_PROPERTY_ORDER` in `presentation/view-edit.js` puts it after `hide-unlinked` and before the texts; `setViewLayout` writes it; `currentViewDefinition` writes the toolbar's value only; `viewProblem` says an invalid one). The *Columns* list is `renderColumnsToolHtml` (`presentation/diagram-controls.js`, `data-action="set-columns"`, handled by `chooseColumns` in `presentation/view-edit.js`, which does not call `pushDiagramHistory`: the address is W-3's), and the form of a view has the same list (`presentation/stories-pages.js`, `layout:columns`). `readSettingsDraft` (`model/form-validation.js`) refuses an invalid `layout` for `overview`, `detailed` and `deep`; `map` is not in `VIEWPOINT_IDS`, so a Map's workspace value is checked when a Map is drawn (the sentence replaces the diagram). Tests: `diagram-columns.test.js`, `diagram-columns-elk.test.js` (the graph with no `columns` deep-equals a copy of the builder before the run, `diagram-columns-reference.js`) and `diagram-columns-view.test.js`. ELK does not run in the node suite (CON-5), so the rows it draws are for the end-to-end suite to show.
