# The editor page

How the standalone editor page is built, checked and covered, and the browser workspace and samples. What each layer does is in the `CLAUDE.md` of its folder: `persistence/` (YAML and the save), `application/` (reading and writing layers, dialogs) and `presentation/` (the band, the Changes panel, stories, Maps and the address). The decisions behind these rules are in `docs/wav/`.

## The page is generated

- `target/editor-webapp/standalone.html` is the page the jar (as `editor-webapp/standalone.html`), the native image, the website, the node harness, the coverage script, the lint extraction and the Java tests read. It is built by `scripts/build-editor.mjs` (Maven runs it in `generate-resources`, `npm run editor:build` runs it by hand) and is not in git: no file of the page, of its `assets/` or of its `samples/` is, and the folder `editor-webapp` of `src/main/resources` is ignored.
- The sources are in `src/main/editor/`: the skeleton `page.html` (its `<!--@include FILE-->`, `<!--@parts-->` and `<!--@assets-->` lines are replaced, every other line is copied), `style.css`, `theme-boot.js`, `codemirror-loader.mjs`, and the main script cut in parts (none over 1,600 lines) under the six layer folders `core`, `model`, `persistence`, `application`, `presentation` and `composition`, in the order of `layers.json`.
- CodeMirror, ELK and the kernel are not in the page: `assets.json` lists them as classic scripts beside it (`assets` are bundled by esbuild as an IIFE from an entry in `bundles/` and set a global, `encoded` are files written as the base64 string of a global, read from `target/kernel` for the kernel's `viewpoint_kernel.wasm`, which `viewpoint_kernel.js` carries), `<!--@assets-->` in `page.html` writes one `archicode-asset:NAME` meta per script with a hash, and `codemirror-loader.mjs`, `loadElk` and `loadViewpointKernel` add a `<script src>` for `./assets/NAME?v=hash` (`loadClassicScript`) and read the global it set. A script, never an `import()` or a `fetch` of the file: a page opened from a disk (`file://`) may load a script but not import a module or fetch a file, and `remote-import.test.js` fails on any `import(` and the spec `editor-offline.spec.js` opens the page from a disk. `editor:build` writes the scripts to `target/editor-webapp/assets/` with a notice file, and `EditorHttpServer`, the website step and the jar serve that folder (`/assets/NAME`, a table of three names, all `text/javascript`). The page loads nothing from a remote address, and works from the network, from a served folder and from a disk.
- A part is a run of whole top-level declarations of the one classic script, with no `import` or `export`. The parts share one global scope, so a name is used by the parts that come after it in `layers.json` (or inside a function, at call time). The rule between layers: a layer uses the layers before it, downward only; the pairs that still go up are the ratchet below.
- Redraw contract: `modelsChanged()` (in `model/app-state.js`) bumps the version counter of the caches and draws nothing. A part below the composition that needs the page drawn again calls `requestRedraw()` (`model/app-state.js`), never `render()`. The composition registers what draws once, `onRedraw(() => render())` in `composition/render.js`, late-bound, and the request is carried out at once in the caller's turn, so the order of what is drawn, written and put back does not move (`redraw-requests.test.js`). `render()` is called in `composition/` only.
- To find the part of a line of the page: `node scripts/build-editor.mjs --where <line>` (`--map` prints every part with its lines).

```bash
npm run editor:build   # = the kernel (embed.sh), then node scripts/build-editor.mjs and node scripts/build-sample.mjs: writes the page, the assets and the samples into target/editor-webapp from src/main/editor (no write when the bytes are the same); needs Node, rustup and `npm ci` (esbuild bundles the assets)
npm run editor:check   # = build-editor.mjs --check && check-editor.mjs --layers: the sources assemble, then the three lists and the ratchet below; writes nothing; needs `npm ci` (acorn, eslint-scope)
scripts/check-editor-moves.sh <base> <head>   # the commits of base..head: `refactor: move ...` must leave the page byte for byte the page of its parent, `refactor: relocate ...` its declarations and comments; other subjects are not looked at
```

- The hooks are the npm `pre` scripts and nothing else: `npm run lint`, `npm run test:unit` and `npm run test:coverage` run `editor:build` first (`prelint`, `pretest:unit`, `pretest:coverage`), so those three never test a stale page. A command that does not go through them does not build: `node --test` or `npx playwright test` run by hand, `./mvnw` (it builds the page in `generate-resources`, so what it packages is current) and `npm run test:e2e` (it drives the jar) read `target/editor-webapp` as it is, so run `npm run editor:build` first after a change to `src/main/editor`.
- CI guards a stale page with the first step of the job `Page`, "Check the editor sources assemble" (`npm run editor:check`), run before the format check; on a pull request the step "Check the move commits" (`check-editor-moves.sh`) follows. Both write nothing.
- `embed.sh` (the kernel) builds the WebAssembly into `target/kernel` and needs no Node; `editor:build` runs it and then `build-editor.mjs`, which reads that file and writes `viewpoint_kernel.js` and the hash in the page's meta, so the hash is written by one place.

## The checks of `editor:check`

`editor:check` stops at the first check that fails, in this order:

- The sources of `src/main/editor` assemble into a page.
- The three lists, files of `src/main/editor/`: `names.json` (the top-level names of the main script; a name added, removed or renamed is a change to the list and the check prints which; `node scripts/check-editor.mjs --write-names` rewrites it), `java-names.json` (the names that Java sources, comments and tests say are in the page, each with the Java files that name it, and `pathOnly` for files that name the path only; written by hand; a name removed from the page, a listed Java file that no longer holds it, or a Java source that names `standalone.html` and is in no list fails) and `layers.json` (the layers in order, the parts in load order with their layer, and `ratchet.max`).
- The load order: a declaration that runs at load must not use one defined after it.
- The ratchet: the count of upward pairs (a declaration that names a declaration of a higher layer) may not be above `ratchet.max`, 99 today. The 99 left are helpers and state that a lower layer reads from a higher one, to be relocated; `node scripts/check-editor.mjs --list` prints them by name and by pair of layers. `max` is lowered by hand as parts are cut; nothing stops a commit from raising it, and the failing line says to give the reason. The ratchet counts names between parts; it does not prove that a part works, which the node suite and the end-to-end suite do.
- The subject of a commit says what kind of change it is, and `scripts/check-editor-moves.sh` judges the first two: `refactor: move <part> to <path>` leaves the page byte for byte the page of its parent; `refactor: relocate ...` leaves its declarations and comments (a declaration moved to another part, only the order of the lines changing); `refactor: change ...` is a change of behaviour or of contract that the node suite and the e2e suite guard. A `style:` commit of formatter output is none of the three and is not looked at.

## Coverage of the page script

- `npm run test:coverage` (= `node scripts/editor-coverage.mjs`) runs the node unit suite (`node --test` on `src/test/javascript/**/*.test.js`) with `NODE_V8_COVERAGE` and measures how much of the page's script (the first `<script>` of `standalone.html`) the tests run, by area and in total, as lines of code (blank and comment lines are not counted; a line is covered when V8 ran its first character) and as functions. It merges the many test processes that load the page. The lines reported are those of the assembled page; `--where` maps them to a part.
- The harness (`harness.js`) runs the page of the repository under the file name `standalone.html-script.js` and any other page (a released one, `ARCHICODE_EDITOR_HTML`) under another, so only the first is counted. The script extracts the page with `scripts/extract-editor-script.mjs`.
- The areas are sections of the script, each started by a marker line that must match once (`SECTIONS` of the script; a renamed heading fails it, naming the marker): `yaml-and-save`, `layers-and-plateaus`, `workspace-and-files`, `editing`, `pages`, `diagram`, `stories`, `story-player`, `other` (what is none of them), so that they add up to the total. The markers are heading comments of the parts.
- The floor is `scripts/editor-coverage-floor.json`: for the total and each area, the lines and the functions, the figure rounded down to a tenth and never above 90. The command fails (exit 1) below any floor or when a test fails, and prints "it could be raised" when the figure is a tenth above. The floor only goes up: `--write-floor` writes it from the measure and refuses to lower one (`--lower` lowers it, as a decision). `--reuse` reads the coverage of the last run without running the suite; a list of test files after the options runs only those (a subset, so the floor fails).
- The report is `target/editor-coverage/` (`report.json`, `report.txt`, `uncovered-functions.txt` and `uncovered-lines.txt` with HTML line numbers; CI keeps it as the artifact `editor-coverage-report`, 7 days). The CI step "Cover the editor script" is the run of the node unit suite (same tests, plus the figure); `npm run test:unit` stays the command to run the tests alone (two to three minutes; with coverage 40 to 50 % more).
- The one test that judges a time (the ratio of the first `quiet` and of `apply_patches` at 591 elements to 82, `performance-budget.test.js`) is skipped in the suite and runs alone as `npm run test:timing` (CI step "Check the time budget of the kernel", about 5 seconds): under the suite's many files at once the large pair reads 17 times the small one, where a quiet machine reads 10 to 13, so no limit separates them there. It judges the fastest of four warm runs per size; the limit is 16.

## The browser workspace

- Where the browser has no folder picker (or the reader does not want one), the editor keeps a workspace in the browser. The store is `persistence/browser-store.js`, a third implementation of the directory-handle interface (after the browser's own and `serverDirectoryHandle`), in its own IndexedDB database `archicode-browser-workspaces`, version 1, one object store `records` with string keys: `workspace:<id>` (name, `createdAt`, `openedAt`, `lastExportAt`, `origin`), `file:<id>/<path>` (`bytes` as a `Uint8Array`, `modified`) and `last` (the workspace the browser reopens). Directories are implicit, a record of an unknown kind is ignored and never deleted, and the remembered folders' database `archicode-standalone-editor` is never opened by it.
- `createWritable().close()` is ONE transaction that reads the workspace record and the previous file record and writes the whole file or nothing (a quota or abort failure rejects with the browser's own name and a sentence that says nothing was changed; the old bytes stay). `modified` is `max(Date.now(), previous + 1)`, so a rewrite always changes it (the stale check needs that). A write, a create or a removal whose workspace record is gone (deleted in another tab) is refused with `NotFoundError` and stores nothing: no orphan file record, the workspace is not brought back.
- The pointer rule: `last` is written only for a workspace that exists; deleting a workspace removes its record, its files and `last` when it points at it, in one transaction; closing a workspace clears `last` and keeps the workspace. Names are one rule (`browserWorkspaceNameProblem`: trimmed, 1 to 80 characters, no control character, unique without regard to case), checked again inside the transaction that stores them.
- The flows are `application/browser-workspaces.js` (landing card, create, open, rename, delete, close, export mark); `model/settings.js` and `model/app-state.js` hold `browserStoreState`, `browserStorageAsked`, `browserStoragePersisted` and the drafts of the card. `askForPersistentStorage` asks `navigator.storage.persist()` once per page session and never waits for it. Support floor: Chromium 111, Firefox 121, Safari 16.2; `showDirectoryPicker` is the one Chromium-only API and lives in `persistence/folder-access.js` only.
- The Workspace menu of a browser workspace: each item is a box of its own with its label and its note inside it, and the bar and the menu stay inside the window at five widths from 1280 to 360 pixels, in both schemes. `src/test/e2e/workspace-menu.spec.js` proves it (Chromium, Firefox, WebKit) and `src/test/javascript/workspace-menu-layout.test.js` guards three declarations of `style.css` without a browser (the height of an item, the wrap of `.top-actions`, the position of the menu under 40 rem). Neither covers the *Back to the served folder* button of a served page nor the anchor of the help menu, which is cut off on the left at 360 pixels.
- Tests: `browser-store.test.js` (the contract on a fake IndexedDB, the harness option `withFile` and the `navigator.storage` stub of `harness.js`), `browser-workspaces-flows.test.js`, `browser-landing.test.js`, `browser-workspace-equivalence.test.js` (a browser workspace reads and saves as a served folder), `browser-apis.test.js` (a deny list of APIs and CSS newer than the floor, run on `ARCHICODE_EDITOR_SRC` when the sources are elsewhere) and the e2e spec `src/test/e2e/browser-workspace.spec.js`.

## Bundles and the samples

- A browser workspace leaves the browser as one YAML text and comes back from one. The codec is `persistence/bundle.js` (one YAML document per file, each opened by a `--- # file: <path>` line). `persistence/browser-transfer.js` reads the files of a workspace (`readBrowserWorkspaceFiles`, a copy) and replaces them in ONE transaction (`replaceBrowserWorkspaceFiles`: files not in the new set go, the record keeps its `id`, `name`, `createdAt`, `lastExportAt` and `origin`, all or nothing). `persistence/bundle-io.js` is the edge: the file picker, the download named `<name>-bundle.yaml`, the 10 MB limit, UTF-8 refused when invalid, `fetchSampleBundle` with `cache: 'no-cache'`, `BROWSER_SAMPLES`. `application/bundle-flows.js` holds the flows (export, import, open the sample, reset it, back to the served folder) and names no presentation or composition function: the test of `countUnsavedChanges() > 0 || draftTyped` lives in the menu (`top-panel.js`, `events.js`), so *Export* is refused while changes or a draft are pending and allowed from the card.
- *Import* only creates a new workspace (a taken name gets ` 2`; `settings.name` is the name when it is valid, else the file name; nothing is created on a refusal). *Export* records `lastExportAt`. *Reset to the sample* names the workspace and the loss, fetches and unbundles BEFORE it replaces anything, and keeps the same record. A workspace made from a sample has `origin: 'sample'` and `sample: '<id>'` and is found again by that property, never by its name (a visitor may have a workspace called Brightcart; the sample then becomes `Brightcart 2`).
- Two samples, `BROWSER_SAMPLES`: `brightcart` (the layered Brightcart, 61 files of `src/test/resources/brightcart/layered`) and `archicode` (the ArchiCode model of ArchiCode, `docs/architecture`). Each is `target/editor-webapp/samples/<id>.yaml`, built (not in git) by `scripts/build-sample.mjs` with the page's codec (Maven runs it in `generate-resources`, `npm run editor:build` and `npm run sample:build` run it by hand, `--only <id>` for one; a file the bundle skips is an error), so a sample follows `docs/architecture` and the Brightcart fixture with nothing to commit.
- The samples are in the jar (covered by the `editor-webapp/**` native include) and served by `EditorHttpServer` as `GET /samples/<id>.yaml` (a table, `SAMPLES`; the token header or the session cookie like the page, otherwise 403; any other name 404). The step "Assemble website" of the job `Build` copies them from `target/editor-webapp` to `/editor/samples/` on a tag (proved only by the tag run).
- The visitor reaches a sample by the button of the presentation page (`#/timeline/applications?plateau=marketplace&compare=past&sample=brightcart`: `sample=` is read before the first render and dropped from the address), by the card (*Open the Brightcart sample*, *Open the ArchiCode model*), and by the *Workspace* menu of the top bar, which a served page (`editor serve`) also has. Served-mode rule: the flows never hold the handle of the served folder while a browser workspace is open, so opening a sample, saving, exporting, resetting and *Back to the served folder* send no write to `/api/fs/` (`workspaceIsServedFolder()` replaces `isServedByArchiCode()` in the close slot and the help sentence only). Choosing a sample from a served page with unsaved changes asks the same confirm as *Back to the served folder*.
- Tests: `sample-brightcart`, `sample-archicode`, `build-sample-script`, `browser-transfer`, `bundle-io`, `bundle-flows`, `sample-served-mode` and `sample-landing` (node), `EditorHttpServerTest`, `EditorServeIT` and `BrightcartSampleTest` (Java), and the e2e specs `sample.spec.js` and `hosted-acceptance.spec.js` (see `src/test/CLAUDE.md` for the projects and for what the suite does not prove). Not proved: the tag run, the native runner, and the real Safari.
