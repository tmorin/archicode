# Editor: reading and writing layers

How the editor reads plateaus and writes into them, and its rename, move and delete dialogs. The line-preserving save is in `src/main/editor/persistence/CLAUDE.md`. The rules of the command line are in `src/main/java/io/morin/archicode/workspace/CLAUDE.md`.

## Reading layers and the pages

- Every open workspace has the layer state `AppState.layers` (the plateau drawn, the comparison). A plateau is drawn as its chain, resolved layer by layer with the kernel's `apply_patches` (`resolveLayerStep`, `layerModelOf`, kept in `layerCache` for one tree of plateaus and one text of the manifests; the sentences of the checks are `LayerLoader`'s). The model of a plateau is `AppState.index`; the plateau compared with is `AppState.baseline` (the plateau drawn is the base only with the future). Each record says where it comes from (`declaredIn`, `patched`).
- The editor builds the same tree with the same sentences (`buildPlateauTree`; `READ_SCHEMA` for the kind) and tells the checks of a layer in the same order, but draws the plateau all the same, so that it can be repaired. `resolveLayerStep` tells the rule of the root with `rootProblem` when `context.layered` (K43 to K49 of `layer-checks-cases.json`, N88 of `negative-cases.json`).
- The perspectives are Timeline (the pages Plateaus, Applications, Environments, Elements), Stories, Files and Settings. `PERSPECTIVES` gives each page its `group` and its `route`; `PERSPECTIVE_GROUPS`: the button Timeline of the top bar opens Applications. `pageIdFromHash` names the page an address opens and `currentPerspective` is the page on screen (the same ids). The page that lists and edits the plateaus is `plateaus`, route `#/timeline/plateaus`.
- The routes are `#/timeline/plateaus`, `#/timeline/applications`, `#/timeline/environments`, `#/timeline/elements`, `#/stories` and `#/stories/views`, `#/files` and `#/settings`; `pageIdFromHash` reads nothing else. `#/map`, `#/elements`, `#/library`, `#/diagram`, `#/applications`, `#/plateaus`, `#/environments` and `#/timeline` alone are no routes: like any unknown address they open Applications, and the page writes `#/timeline/applications` (`editor-structure.test.js`).
- The code still calls `map` the page Applications and `library` the page Stories. Environments (`environments`) is a Map of the technology layer as Applications is the Map of the application layer: one code with the layer as its parameter (`mapIsShown`, `mapLayer()`, `mapStateOf(layer)`). The pins, hidden elements and open boxes of the application layer are `mapPinned`, `mapHidden` and `mapOpened`; those of the technology layer are `technologyMapState`. `buildKernelInput('map', '', { layer })` gives a technology Map the application layer too (`app_elements`) and says `applications: false` or `relationships: false` only when it leaves one out. A saved view with `viewpoint: map` and `layer: technology` is the page Environments (`applySavedView`, `currentViewDefinition`, `viewProblem`). The page Elements keeps its own tree of both layers.
- The `layer` of a view, of a step that carries its own recipe and of a view definition is read in any case, as the command line reads it (`View.Layer`: `layer: Technology` and `TECHNOLOGY` are the technology layer, anything else the application layer). `viewLayerOf` is the one place the page does it, over `entryLayerOf`, which the plateau-free check uses too; `setViewLayer` writes only a change, so a view is never rewritten because of the case of its layer (N86, `view-layer-any-case.test.js`).
- The stories and views of a page are the same whatever plateau is drawn (`manifestEntries`, `entriesOf`, `savedViews`, `storiesList`). A new one is a manifest with no `plateau:` in the first folder of `manifests.paths` (`createManifestEntry`); `filePlateauOf` is null for them, so Files puts them in the group *No plateau*.
- Files lists every file, always, in a group per plateau (`filesGroups`, `filesGroupOf`; the plateau of a file is `filePlateauOf`; the files of no plateau are the group `none`, last, and it is generic: it holds whatever `filePlateauOf` says is null). A group folds and unfolds (`filesFolded`, kept while the editor stays open on the same folder, never written in the workspace; opening a file unfolds its group, `unfoldGroupOfOpenFile`). A workspace with no plateau keeps the flat list. The page warns of a plateau that disagrees with a folder named like another plateau (`filePlateauFolderWarning`).
- The page Settings has the field *Current plateau* (`renderCurrentPlateauSettingsHtml`, `commitCurrentPlateau`, `chooseCurrentPlateau`): a list of the plateaus in the order of the band and *None*, shown when there are at least two plateaus (or the file already has a `current`) and disabled while the plateaus have mistakes. It writes `settings.current` through `commitSettingsEdit` into the raw `settings` of `.archicode.yaml` (a file with no `settings` block gets one with that line alone; *None* takes the line out and leaves `settings: {}` when it was the only one) and refuses a plateau that is none with the sentence of the load (`layersOfSettingsCurrentProblem`). It is not under `guardedLayerWrite` and does not redraw the plateau on screen: the key is read when the folder is opened with no address and no plateau remembered by the browser (`openLayers`; `settings-current-plateau.test.js`).
- The page derives `childKindOptionsForLevel` and its check from `READ_SCHEMA`. A facet the kernel refuses (the Jayway dialect, a path it cannot read) is the error of the view, with its one sentence, on the page of a saved view and of an element: `facetRemovesElement` takes the error and answers no for every sentence the kernel says of a facet it refuses (`saved-view-jayway-facet.test.js`).

## Writing into a plateau

- Anything that changes a model ends in `rebuildIndexAndRender()` or calls `modelsChanged()`: the comparison cache, the diagram cache and the cache of the quiet references are keyed on that version counter (plus the small parts that vary: facet, viewpoint, options), not on the serialised models or the kernel input.
- The plateau drawn is the one a write goes to (`writingPlateau()`, null for a workspace that writes no plateau, which saves exactly as before). `commitElementEdit` writes a field the plateau declares to its manifest and a field it inherits to a patch of its `Kind: Plateau` manifest (`writePatchChange`, `patchFor`: `SET`, `ADD`, `MERGE`, `SET` with `where`, and `REMOVE` of the `field` for a text or a number that is cleared; a list or tags that are emptied are still a `SET` of the empty one). There is one patch per target and field, found again by the next edit and changed in place from `SET` to `REMOVE` and back; new patches go at the end of the list. Tests: `field-removal-cases.json`, `FieldRemovalCasesTest`, `field-removal.test.js`. `commitDeleteElement` writes a `REMOVE` for an inherited element.
- `commitCreateTopLevelElement` (`plateau:` in the header), `commitPlateauCreate` and `commitPlateauEdit` run under `guardedLayerWrite`, which resolves every plateau again, keeps the write only if the plateau written gives back the edited value and no plateau is refused that was not, asks first (`layer-confirm` dialog) when other plateaus inherit what was written, and otherwise restores everything (`snapshotWriteState`). The element and plateau writers of a layered workspace go through it. The view and story writers do not (they belong to no plateau), nor does *Write replaces* (it writes the key on the new element in the manifest that declares it), nor the text editor of Files.
- A rename, a delete and a move rewrite only the files of the plateau drawn and of those that stand on it (`writeScopeHas`). The one thing a plateau is not written for is a kernel that refuses its patches (`readOnlyPlateauMessage`).
- A move goes one of four ways (`moveRouteUnder`, `moveTopVerdict`). `header`: an element with a manifest of its own, only its `header.parent` changes (at the top level the line goes). `inline`: a nested element and a parent of the same file. `paste`: a nested element and a parent of another manifest of the plateau written; the block is cut out of one file and pasted into the other with its comments, quotes and flow lists (`cutBlockFromText`, `pasteBlockInText`, both files marked modified; the ordinary patch writes a file whose layout they cannot follow). `extract`: a nested element that goes to the top level or under a parent of a plateau whose files the plateau drawn does not write gets a manifest of its own (`manifestTextFromBlock`, `plateau:` and `parent` in its header, next to the file it leaves). Every move of a layered workspace goes through `guardedLayerWrite` and a refused one changes nothing.
- Manual: `[[editor-elements]]`, `[[plateau-limits]]`, `[[editor-move]]`.

## Rename, move and delete dialogs

- *Move* puts an element under another parent or at the top level; children follow and references are rewritten in every file. The top level is offered for the kinds the layer holds at its root, read from `READ_SCHEMA` (`topLevelKindsOf`: person, solution and system; environment), which is also what the creation form allows blank (`TOP_LEVEL_BLANK_ATTACH_ALLOWED`); a container, a component or a node is never a root in the editor. The dialog lists the places offered and, under it, one sentence for each element of the layer that is not offered (`moveParentVerdict`: itself, inside it, its parent now, a kind that cannot hold it, an id already held, declared twice) and for the top level, and it says that *Move* writes no `replaces`: the key is written by *Write replaces* of the Changes panel.
- *Delete* of a plateau: `plateauDeletion` says, before anything goes, what `commitPlateauDelete` does under `guardedLayerWrite`. Any plateau but the root can be deleted. Its `Kind: Plateau` manifest and the manifests whose header names it are queued in `pendingFileRemovals`; a `settings.current` that names it is taken out of `.archicode.yaml`; the plateau it overrode is drawn when it was the one drawn. A leaf is deleted byte for byte as before (`delete-plateau-in-the-middle.test.js`).
- A plateau that others override is deleted in the same step. The plateaus that override it go under its parent, their `override` rewritten line by line in their `Kind: Plateau` manifest (taken out when the parent is the root; a plateau over another than the root always has that manifest, so none is made), and what it declares and patches is lost to every plateau that stands on it. `plateauDeletionAbove` resolves each of them again without it (`resolveLayerStep` over `layerStateOf`, kept in `layerCache`), and the dialog lists, for each, its new parent and the elements it loses, gets back (the deleted plateau removed them) and reads differently. The past of a plateau that overrode it follows it to the new parent. The dialog's yes is the yes to those plateaus (`confirmedFor` of `guardedLayerWrite`; a change of any other plateau is still asked).
- The delete is refused, with the sentence, when a plateau above would no longer resolve (a patch that selects nothing, a relationship or a parent that is gone: `plan.breaks`, a mistake to repair and not a loss; nothing is pruned), or when a view or a step that would name a plateau or an element that is gone: a step told `at` a plateau above, or compared `against` one when the plateau it is told at does not keep the element either (the comparison is drawn from the plateau the step is told at: `survivesWhereTold`), or a saved view drawn in one, that would lose the element it draws (`stepsLosingTheirView`, `viewLosesInPlateauAbove`: ``... step n is compared with `q`, which would no longer have `x` ``, ``the view `v` (`file`) is drawn in `q`, ... which would no longer have `x` ``, one sentence per view naming every such plateau). The check is the editor's alone: the command line does not look at the plateau of a step. Nothing is offered instead of a refusal. A delete that passes is written byte for byte as by `archicode-0.17.0` (`delete-plateau-as-released.test.js`).
- Rename and the sibling plateaus. The views and stories a rename rewrites belong to no plateau, so a rename follows them everywhere. When a plateau beside the one drawn (or standing on such a plateau) still has the old reference in its resolved model (`layerModelOf`, declared or only inherited) and a view or a story step names it, saving the form of the element with a new id opens a dialog first (`commitElementWithDraft` → `renameSiblingImpact`, `renderRenameSiblingsDialogHtml`) that names those plateaus and the views and steps that could no longer be drawn there. *Rename anyway* writes exactly what a rename wrote before; *Cancel* writes nothing. With no sibling, no name at risk, no plateau, or a rename in baseline, no such dialog opens (`commitElementEdit` itself asks nothing).
- *Move* asks the same question: `submitMoveDialog` calls `renameSiblingImpact(reference, plan.newReference, layer)` once the parent is chosen and valid, and opens the same dialog (`rename-siblings` with `moving: true`; the buttons are *Back to Move* and *Move anyway*). The Move dialog waits behind it as `dialog.back` with its parent chosen and its search typed; *Back to Move*, Escape and a click beside the dialog (`closeAppDialog`) give it back, writing nothing. *Move anyway* is `commitMoveElement` (the dialog of the plateaus that inherit what is moved may follow, as for a rename). With no sibling, no name at risk, a move in baseline or no plateau, nothing new opens and the same files are written byte for byte (`move-sibling-plateaus.test.js`).
- Cancel keeps the typed form. This dialog and `layer-confirm` leave the form as it was typed when cancelled (Cancel, Escape, a click beside the dialog), because the redraw that opens the dialog, and the one `guardedLayerWrite` makes when it puts a tried write back, would give the fields afresh from the model. `openAppDialog` keeps the values of the form on screen (`keepElementForm`, `keptElementForm`; `guardedLayerWrite` takes them before it writes and hands them over as `typedForm`) and `render()` puts them back (`restoreElementForm`) while the dialog is open and once more when it is gone. It is view state only (no `modelsChanged()`), dropped by a yes (the write is the draft read before the dialog), by another element or mode, and with the folder (`cancel-keeps-the-typed-form.test.js`).
- A refused write (`Not written: ...`) and an error in `writeElementDraft` keep the form too. `writeElementDraft` takes `keepElementForm()` before it writes, because `guardedLayerWrite` has already redrawn the form from the model when it restores a write it refuses, and hands the copy to `keptElementForm` in its `catch` before the redraw that shows the sentence; no dialog is open, so `render()` puts the values back and drops the copy. The success path keeps nothing. `confirmLayerWrite` does the same: it takes `keepElementForm()` before the write the yes runs again and hands the copy over in its `catch`, so a write the second dialog fails on gives the typed fields back.
- *Write replaces* several layers apart. `replaces` is read against the plateau the manifest builds on, so when the comparison is several layers apart (`replacesChainBetween` is not null) and a layer in between removed `from`, the entry would name nothing in the layer it is written in. `replacesLayerProblem` says it in one sentence that names the element, the plateau it builds on and what to do (compare the plateau with the one below, or write the entry in the layer that still has it); `acceptLayeredCandidate` refuses with it and writes nothing, and the Changes panel shows the button off, with the sentence as its title and under the pair. A split or a merge is written one pair at a time and each `from` is checked; a merge (the open pairs of one layer and one `to`, two `from` or more) is checked for all its pairs before the first is written and refused as a whole, every button of it off with the sentence (`candidateLayerProblem`, `replacesMergeProblem`; set aside with *Not related* a pair that is no part of it). A comparison one layer apart, siblings one layer above what they share, a workspace without plateaus and an undrawable plateau below are not looked at. The field *Add replaces* of the inspection is checked the same way when the plateau drawn is the more recent plateau of the comparison on screen (`addReplacesLayerProblem`: the sentence under the field, nothing written). Tests: `write-replaces-refuses.test.js`, `replaces-and-delete-checks.test.js`.
