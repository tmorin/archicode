# Workspace, plateaus and the discovery of manifests

Rules for finding the manifests, building the tree of plateaus, loading a plateau in layers and comparing plateaus. The editor's behaviour is in `src/main/editor/application/CLAUDE.md` and `src/main/editor/presentation/CLAUDE.md`. The decisions behind these rules are in `docs/wav/`.

## Where the manifests are

- An entry of `settings.manifests.paths` that ends in `/**` is read recursively; any other entry reads the files directly in its folder. `..` and absolute paths are refused, and so is a reference declared twice.
- One rule for both tools: `manifest/ManifestDiscovery` and `readManifestFolder` (in the page), run on `src/test/javascript/viewpoint-kernel/discovery-cases.json` by `ManifestDiscoveryTest` and `discovery.test.js`. A change to the rule is a change to the cases file.
- Files are sorted by their path from the folder of `.archicode.yaml`, by Unicode code point. Below a `/**` path there is no hidden file or folder, no link to a folder, no folder of generated views (`views.path` at its depth and the folders beside it that begin with its name and a dash), and no folder that holds both `gap.json` and `gap.md` (`ManifestDiscovery.holdsComparison`, `holdsComparisonFiles`; a lone `gap.json` is read). `**` anywhere else in an entry is a one-line error (`ManifestDiscovery.pathProblems`, `manifestsPathProblems`).
- A manifest is YAML, JSON or TOML on the command line (`ManifestParser` reads the file with the mapper of its extension, then its `content` as JSON; `TomlManifestTest`, case D36). The editor reads YAML only and lists `.toml` and `.json` files as files it does not read.
- The kinds are the seven elements, `view`, `story` and `plateau` (`ManifestKind`, `ARCHICODE_KIND_MAP`, `READ_SCHEMA.manifestKinds`). `group` is no kind in either tool: a nested `kind: group` gives ``unknown kind `group`, a group is no kind any more: write its children in the `elements` of its parent (known: ...) at `elements[0]` ``, and the headers `archicode.morin.io/group`, `container-group`, `solution-group` and `system-group` are `unrecognized header.kind` with the same words (`ArchiCodeException.GROUP_IS_GONE`, `GROUP_IS_GONE` in the page; N89, N90 and N56 to N58 of `negative-cases.json`).

## The tree of plateaus

- A plateau is a layer. A manifest of an element or of a plateau says `plateau: <id>` in its header (none: `baseline`, the implicit root). A manifest of kind `archicode.morin.io/plateau` is optional (`resource/plateau/Plateau`: `id`, `name`, `horizon`, `override` and `patches`); `override` names one plateau, absent means `baseline`; `patches` are read by `Patch` and carried to the kernel's `apply_patches`.
- `ManifestParser.parse` builds `resource/plateau/PlateauTree`: ids in `[a-z0-9_-]`, declared once, a known `override`, no cycle (one `error:` line each). `PlateauTree.redeclared` refuses a reference declared in a plateau and again in its ancestor; two plateaus that do not stack may each declare it. A warning (`Warnings`) is given for a plateau that only headers name, for two ids one letter apart when one of them only has headers to name it (two plateaus with a manifest each, `p1` and `p2`, give none), for two `SET` of one field of one target in one plateau (the last wins) and for a horizon earlier than the parent's.
- `settings.plateaus`, `plateau add` and `--baseline` no longer exist. A workspace file that has the key fails every command with the one `error:` line of `WorkspaceFactory.REMOVED_KEY` (`RemovedPlateausKeyTest`); the editor says the same sentence (`REMOVED_PLATEAUS_KEY`; M50 to M53, N41). `Settings` has no `plateaus` property and `READ_SCHEMA` no entry for it.
- `--plateau` names the plateau and is looked at before `settings.current`, so it gets past a `current` that names a plateau that is gone; the default is `settings.current`, else the last plateau when the tree is one line; a tree that forks needs `--plateau`. `--against` names the plateau to compare with (default: the one it overrides; the root has none). `plateau list` lists the tree. The folders are `views-<plateau>` and `views-<plateau>-vs-<against>`.
- An id with a dot is a one-line error in both tools (`ManifestParser.dottedId`, `dottedIdProblem`; M81 to M83). The cases are `plateau-model-cases.json`, read by `PlateauModelTest` and `plateau-model.test.js`.

## Loading a plateau in layers

- `WorkspaceFactory` loads one plateau per call. `tree.chain(id)` is the chain, root first. `workspace/LayerLoader` adds the elements of `Parsed.ofPlateau(id)` for each plateau of the chain, hands the elements of the two layers and the patches of the plateau to the kernel (`apply_patches`; a plateau without patches does not leave the model), then checks the layer: a relationship, a `uses` entry, a hosted application, a parent. Each mistake is one `error:` line naming the plateau, and the first wrong plateau ends the load.
- The checks of a layer are the cases of `layer-checks-cases.json`, read by `LayerLoaderTest` and `layer-checks.test.js`. The command line stops at the first wrong layer and draws nothing; the editor (`layerProblemsOf`, `resolveLayerStep`) tells the same sentences in the same order and still draws the plateau, so that it can be repaired.
- A `REMOVE` with a `field` takes that field out of the selected elements (any field but `id`, `parent`, `elements` and `kind`); a field the element lacks is already gone, no error. Its report has `matched` and `touched` and no `removed` or `dropped`, so `LayerLoader` lists no `Removal` for it. A `REMOVE` without a `field` removes the element with a cascade, and what it took besides what it names is listed after the table of changes (`Removal`, from the kernel's `removed` and `dropped`; `GapReport`, `gap.md`, `gap.json`). See `[[plateau-patches]]` and `[[editor-writing]]`.
- Which kind a parent holds is written once, in the model: `Parent#elementType()`, read by `resource/element/application/Nesting`. `ElementIndexFactory` refuses an element declared with `header.parent` under a parent that cannot hold its kind, with or without patches (one sentence per element, sorted by reference, naming the file: `unknown kind x under p (known: ...) at header.kind`). The table `nesting.holds` of the cases is compared with the classes by `EditorReadSchemaTest`.
- The root of a layer holds fewer kinds. In a workspace that has plateaus, a manifest with no `header.parent` of a kind its layer does not hold at its top (`Application` holds person, solution and system, `Technology` an environment; `Nesting.holdsAtTheTop`, `kindsHeldAtTheTop`, `topLevelKindsOf` in the page, the table `nesting.top`) is one `error:` line, ``unknown kind `container` with no `header.parent` (known: person, solution, system) at `header.kind` ``. A container, a component or a node is held by an element, never by a layer, so a patch could not select it. `ElementIndexFactory.indexLayers` tells it with the nesting mistakes (one list, by reference, application layer first) and `LayerLoader` passes `layered = true`. A workspace with no plateau is untouched (K48). `WorkspaceFactory.load` takes this path when the manifests are layered.

## Views and stories, which belong to no plateau

- Only elements, patches and plateaus are layers. `Parsed.placedViews` and `Parsed.placedStories` hold views and stories with their file and no plateau; one is declared once in the whole workspace (`declared twice`, even across plateaus that do not stack). `plateau:` in their header is accepted and means nothing, with no warning and no error (`ManifestParser.parse` skips the key for these two kinds; `buildPlateauTree`, `isPlateauFreeManifest`; M01, M84 to M87, N79).
- One check is plateau-free and told once, after the layers (`LayerLoader.entryProblems`, `entryProblemsOf`; K04, K05, K32 to K36, N80): every element a view or a story step names must be declared by a manifest or `.archicode.yaml` in some plateau (`Parsed.declared`), else ``the view `v` (`file`) names `x`, which exists in no plateau``. Patches are not resolved for it. Only a workspace that has plateaus is checked.
- A name that another plateau has and the plateau drawn lacks is no mistake of the view. The command line leaves it out of a map (`KernelViewpointFactory.mapLists`) with a warning, and skips, with a warning, a map none of whose pinned elements is there and a view whose element is not there (`GenerateViewsCommand.canBeDrawnInPlateau`; N81, N82). The page says the view cannot be drawn in this plateau (`viewProblem`, `viewLacksInPlateau`). See `[[plateau-views-lacking]]` and `[[plateau-untied]]`.
- A story step may be told at a plateau and compared with another one: the keys are `at` and `against`, not the header's `plateau:` (`Story.Step#at`, `#against`). None: the plateau drawn, no comparison. `against` with no `at` is told at the plateau drawn. An empty text names nothing. Each must be a plateau of the workspace and the two cannot be one plateau, else one `error:` line with the story, the file and the number of the step, told with the plateau-free check, step by step, before the names the step carries (`LayerLoader.stepPlateauProblems`, `stepPlateauProblems` in the page; K37 to K40, N83 to N85), also for a workspace with no plateau (`WorkspaceFactory.requireNoPlateauInSteps`, `StepPlateausTest`).
- `archicode stories generate [--story <id>]...` draws stories (`views generate` does not): `cli/GenerateStoriesCommand`, `StoriesGroup`, `ViewInPlateau` (shared with `views generate`); `GenerateStoriesTest`, `StoriesGenerateIT`; `[[stories-generate]]`. Each step is drawn like a view of the plateau it is told at (`at`, else `--plateau` or `settings.current`; a plateau is loaded once, a comparison made once) and, with `against`, like the views of a comparison (same `compare` and union as `views generate`; `GapFiles`, `GapReport.render`). Facets are drawn as `views generate` draws them: the global views in the step folder unless `global-enabled` is false, one folder per facet named `<NN>-<view>-<facet>`, on the union for a compared step. A step with `against` also gets `gap.md` and `gap.json` in its step folder, none in a facet folder. Files go to `<views.path>-stories/<story>/<NN>-<view>/` (`step_NN.puml`; `<view>` is the view the step names, else the viewpoint of the view it carries), a map is drawn.
- Skips and errors of `stories generate`: a facet that removes the element the step names gives ``skip <story>/<n> in the facet `f`: it names `x`, which the facet removes`` and that folder only is skipped. A name the plateau lacks gives ``skip <story>/<n>: it names `x`, which the plateau `p` does not have`` and the step is skipped (N84), as are a step compared with the plateau it is told at, an undeclared view and a viewpoint the command line does not generate. A story with no step is a warning, an unknown `--story` one `error:` line (exit 1), and stories are drawn in the order of their ids.
- Shipped examples: the story `migration` of `domain_plateaus` (`StepPlateausTest`, `story-steps-plateaus.test.js`), and on the fork of the layered Brightcart `fork_tour` (steps told at `saas` and `inhouse`, which override `baseline` and do not stack, compared with `baseline`, with each other and with `marketplace`'s ancestry), `order_journey` (no step names a plateau) and `seller_journey` (every step told at `marketplace`), read by `brightcart-views-and-stories.test.js`. The Brightcart fixture ships only its layered form, `src/test/resources/brightcart/layered/`, written by `generate.mjs`; the folder `shared/` that no plateau owns holds seven views and three stories (`ENTRIES` of `description.mjs`, `expected/entries.json`), read by `BrightcartViewsAndStoriesTest`; the tests that delete an element or a plateau start from the fixture without `shared/`.
- No step of a shipped story draws nothing: `StoriesNotEmptyTest` and `story-steps-not-empty.test.js` apply one rule (`diagramHasNothingToDraw`: one box or none and no link) to every step; steps that are empty on purpose are listed with their reason in `src/test/resources/stories/empty-steps.json`.

## Comparing plateaus

- A comparison loads its two plateaus once each (the manifests are parsed once for each); `createUnion` is made from a copy of the target. The kernel's `compare` takes two plateaus and gives the union, with a `change` on every element and relationship, and a sorted table of changes; `compute` takes that `change` back.
- An element of the more recent plateau may say `replaces: [ref, ...]` (references of the plateau it is compared with; never guessed; read by `compare` only, kernel contract 4): it is then `moved`, `split` or `merged` and the replaced ones are no longer `removed`. `compare` also lists candidates (same kind and a name that no other removed and no other new element of that kind has, a close description, or a lone sibling, the last only when one plateau is the past of the other: the host passes `on_one_chain`, required since kernel contract 5), never applied. The command line prints them only for a plateau that already uses `replaces`; the editor proposes them for any comparison. The command line writes no `replaces`.
- States: `new`, `changed`, `removed`, `moved`, `split`, `merged` and, for a box that only contains changes, `contains-changes` (stereotypes added last to the box, with a default style that `styles.by-tags` overrides property by property, given only to a box that has the state computed). The kernel says so with `contains_changes` on the item and on the elements of `compare`'s union, and `contains_more_than_wording` for the editor's wording toggle; `compute` removes both keys from its input so a facet does not see them. `StateTags.stateOf` and the page's `comparisonStateOfElement` read the key and derive nothing from the references. A hand-written state word that disagrees is only the author's stereotype, and the command says so on the error output, as for the warnings of `replaces`.
- `archicode diff` and `views generate` write the table (`gap.md`, `gap.json`, with the identity and the candidates) and `views-<plateau>-vs-<against>`. `diff --fail-on <state>[,<state>...]` (the seven words of `KernelStates` and `any`, `cli/FailOn`, repeatable) exits with 3 when the table holds a change of a listed state, otherwise 0, and prints the table as without it; with `--no-wording` a row that is wording only does not count; an unknown or empty state is one `error:` line, exit 1, before anything is loaded. `diff --width <columns>` wraps the text table (a cell at its spaces, a reference or list after its dots, slashes and commas, then where the line ends; the columns share the width, short ones keep theirs, counts and sentences wrap too; `rendering/gap/TextWrap`, `cli/Width`); a value that is not a whole number above zero is one `error:` line, exit 1, before loading; without the option the text is byte for byte that of `archicode-0.14.0`; `markdown`, `json` and the `gap.*` files are never wrapped; `TextWrapTest`, `DiffWidthTest`, `PlateauComparisonIT`; `[[diff]]`. `views generate --only-changes` passes the kernel's `only_changes` to the views of the comparison only and is an `error:` line when nothing is compared.
- `PlateauComparer` leaves out of a layered target the `replaces` that the base writes the same way for the same element. It is decided when the kernel's graph is built (`KernelGraph.of` takes the test), not by editing the JSON afterwards: an inherited element keeps the `replaces` of the layer that declared it, which would warn once per element; whether an entry is news depends on the plateau compared with, so against the root the `replaces` of `inhouse` are kept.
- A comparison several layers apart composes the `replaces` of the layers in between, so that a move made in two steps is a move. The host hands over the plateaus and the kernel rewrites: `compare` takes an optional `chain` (additive to contract 5; rule 8 of `compare.rs`; the kernel's README), the plateaus the target stands on, oldest first, from the base (between siblings: the last plateau they have in common, `PlateauTree.standsOn`) to the plateau the target overrides, each as `reference` and the `replaces` its layer wrote. With two plateaus or more the kernel reads an entry of the target that names an element of the plateau just above through the step that made it, down to the first plateau: a move then a move is a `moved` from the first plateau's element; a move then a split or a merge is a split or a merge; an element created in a layer in between and moved by the next is `new` and the entry is no mistake; one that a layer in between removed ends its chain; an entry the last step cannot explain is left as written, so the usual warning of rule 6 tells it, and `warnings` and the `replaces` of the union say the composed words. The command line builds `chain` in `PlateauComparer` from `Workspace.getSteps()` (`LayerLoader` keeps one `PlateauStep` per plateau of the chain); a comparison with the plateau a plateau overrides sends none. Cases: `compose-replaces-cases.json`, read by `ComposeReplacesCasesTest` and `compose-replaces.test.js`.
- The converted fixtures of the old plateaus (`plateau-comparison`, `plateau-state-*`, `split-relationships`, `replaces-large-pair`) keep their first state as root manifests with an empty layer over it. P4 of the Brightcart fixture is verified by `archicode diff` and by the editor.

## The kernel

- Six entry points: `compute` (views), `apply_facet`, `apply_patches` (the patches of a layer), `states` (the seven state words, said once; `KernelStates` and the page read it), `quiet` (which elements of a layer have nothing to draw, all in one call; the editor greys them in its tree; the command line does not use it and `ViewpointKernel` does not expose it) and `compare`.

## Other rules of both tools

- The command line reads a BOM in a manifest and in `.archicode.yaml` and never writes either, so no case is shared. `settings.facets.customs` keeps the order of the file. A workspace without plateaus is byte-identical to before.
- The manual's example `domain_plateaus` (the bookshop of the tutorial) has a root named `As is` by its own `Kind: Plateau` manifest (`id: baseline`) and one layer `to-be`. It is loaded by `ManualExamplesTest`, `ShippedFilesTest`, `PlateauComparisonTest`, `FacetRemovesElementTest` and, in the editor, `shipped-files.test.js` and `example-identity.test.js` (every plateau but the root is compared with the one it overrides when its views are generated, and `diff` ends with the cascade of the removals).
- To know what a change to an element touches in a workspace, run `archicode query impact <element>` (`workspace/Impact`) instead of reading `query graph` by hand; it follows the relationships, and the deployments with `--through deployments`.
- The limits and the differences between the tools that stay pinned are in the manual, `[[plateau-limits]]`. The breaks of past releases are told in `[[plateaus-upgrade]]`, `[[upgrade-0-17]]`, `[[upgrade-0-18]]` and `[[upgrade-0-19]]`; the release notes link to these anchors, so their names stay. Other anchors: `[[facets]]`, `[[errors-and-warnings]]`, `[[editor-open]]`, `[[manifest-schema]]`, `[[guide]]`, `[[init]]`, `[[install]]`, `[[version]]`, `[[map-technology]]`.
- Not planned: `--baseline-ref`, the phone, folding a plateau from the editor (the refusal stays; `[[fold-by-hand]]` in `[[editor-plateau-delete]]` tells how to fold by hand), an anchor or a tag on a mapping key (read by the command line, refused by the editor) and the merge key `<<` (refused by both).

## Plateau fold

**`archicode plateau fold <id> [--dry-run]`**: folds a plateau into the one above it, or says in one `error:` line why it cannot, and `--dry-run` runs everything but the write. `workspace/Fold` holds the refusals and the plan in plain Java (no Picocli, no CDI), `FoldReport` prints it (present tense for the dry run, past with `(written)`), `PlateauFoldService` reads the facts through `WorkspaceFactory.facts`, loads the plateau above once, and drives the rest; `FoldRewrite` changes the manifests in memory (the header of those that name the folded plateau, the `override` and the patches of the plateau above, the `replaces` composed; each keeps its format, YAML, TOML or JSON, and loses its comments, quotes and layout), `FoldCheck` folds on a temporary copy and compares the model of each plateau that stays and the table of every pair before and after (only the PLATEAU and PATCH columns of the cascade may differ; the check runs in the dry run too, and nothing forces it), `FoldFiles` writes all its files or none (`FoldFiles.commit`: re-read the bytes, stage `<file>.archicode-fold`, move over the targets, delete the folded manifest last, put back from memory on a failure; `DiskFoldFiles` is the disk, a test double fails each step in `FoldFilesTest`; the guarantee is for a failed write, not a killed process), `FoldSnapshots` holds the snapshots, `cli/FoldCommand` is the command. The deleted manifest's `name` and `horizon` are not kept and the report says so. The sentences are the cases of `src/test/javascript/viewpoint-kernel/fold-cases.json` (F01 to F08, F20 to F27, with `expect.files`), read by `PlateauFoldServiceTest` and `PlateauFoldCommandTest` (`FoldTest`, `FoldRewriteTest`, `FoldCheckTest` hold their own data) and by `fold-workspace.test.js`, which opens the folded workspaces in the editor; `ManifestRoundTripCorpusTest` holds the round trip of the manifests the repository ships; the manual says it in `[[plateau-fold]]`, `[[fold-by-hand]]` and `[[plateau-limits]]`.
