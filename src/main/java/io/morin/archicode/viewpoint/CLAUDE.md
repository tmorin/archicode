# Viewpoints and the Map

The Map of both layers, its links and its highlight. Moved from the root `CLAUDE.md` with its wording unchanged; the root file says where each area lives.

The Map of the technology layer draws the applications and the relationships (wave 016, run 0114, #107; the author, 2026-10-20: *the Environment map must show the application elements and the relationships; both can be hidden or shown from the toolbar*). What is drawn is settled once, in the kernel's `map` (contract 5, additive keys: the number does not move; `applications` and `relationships` are optional booleans of the input, absent or null meaning drawn, and `app_elements` is the application layer the map was not given before; an input of a technology map that gives no `app_elements`, and the Map of the application layer whatever it is given, are drawn exactly as before): (1) **the applications** are the `applications` of the nodes of the layer, a box each inside its node, drawn only when that node is open (`opened`, or encloses a pinned element) and visible, and, when the map is pinned, only inside what it is pinned on; their ids are the ones the deep viewpoint gives (`<last segment of the node>_<application>`, or the whole path of the node when that is ambiguous or is the reference of an element), settled over the whole layer so that opening or hiding a box renames none; a node that hosts applications is `expandable` while it is closed (it was only the nodes with children), an application box has nothing to open, and a pin or a hidden element names technology elements only (an application is not pinned, hidden or opened on its own: hide the node, or turn *Applications* off); (2) **the relationships** are the ones the elements of the layer declare, as before, and the dependencies between environments that the deployed applications give, the ones the overview, the detailed and the deep viewpoints draw (`derived_dependencies`: an application whose environment does not host the destination, found in an environment or a node that environment `uses`; `uses` stays a scope, never a link of its own; the dependencies inside one environment stay out, as they are "secondary" in those viewpoints), as a link between the boxes of the two applications when both are drawn, else between the boxes the nodes that host them land on, grouped under the first closed box as every relationship of the map is (a link whose ends are the applications or the nodes themselves is natural, one brought up to a closed box above is grouped); the dependency uses the relationships of the deployed element and of everything inside it (wave 018, run 0133, #124, decision D7: a relationship of `shop.app.payments` is a dependency of the node that hosts `shop.app`, in the three viewpoints and the Map alike, `relationships_of_deployed` in the kernel; the relationship of the link says who declares it; one that ends inside the deployed application itself is internal and gives nothing; the kernel contract stays 5; wave 019, run 0140, #139, decision T5: the other end counts too, a relationship whose destination is inside a deployed application (a component of `shop.app`) is a dependency towards the node that hosts it (`deployed_application_of`, the nearest deployed application; the link is drawn between the boxes of the deployed applications and the relationship of the link says what it ends on), the destination must still be inside a deployed application, and one that ends inside the deployed application it starts from stays internal (a loop on the box of the container is gone from the comparison of the flow views); the secondary links inside one environment, drawn for a flow only, read the relationships of everything inside the deployed element on both ends as the primary links do; on the layered Brightcart only the views of the facets (flows) change, and the fixture `viewpoint-kernel/workspace` has the golden views of its four faceted folders regenerated; `DestinationDependenciesTest`, `destination-dependencies.test.js`, the kernel's `the_secondary_links_read_what_is_inside_the_deployed_element_on_both_ends`); (3) **the toggles**: the properties of a Map view are `applications` and `relationships`, booleans, drawn when absent (the editor writes `false` only, after the lists and `facet` and `hide-unlinked`, `VIEW_PROPERTY_ORDER`, `canonicalViewProperties`; a value that is not the boolean `false` is no choice, in both tools; they mean nothing in a Map of the application layer and `canonicalViewDefinition` takes them out of anything else), read by `KernelViewpointFactory.mapParts` and by the page (`mapPartsOf(view)`), who both only pass them to the kernel; on the page Environments the tools of the diagram have the group *Applications* / *Relationships* (`renderMapPartsToolHtml`, action `toggle-map-part`, `aria-pressed`, no key), also on the page of a saved view of the technology Map, where they edit the view like the texts do (`setViewMapPart`; the form of the view has the two boxes, `part:applications`, `part:relationships`); the state of the page is `technologyMapParts` (reset with the folder, `MAP_PARTS`, `mapPartsShown()`), kept in the address as `applications=0` and `relationships=0` (only what is left out), read back by `applyDiagramParamsFromHash`, part of the key of the diagram cache (`diagramCacheKey`, for the technology Map only; issues #32 and #37), view state and never model state (no `modelsChanged()`), and a toggle asks the Map to drop a selection it no longer draws (`mapSelectionCheck`); (4) **an application box** is an element of the other layer: its `data-ref` is the application and its `data-layer` is `application` (on the Map only; `renderDiagramSvg`), a click selects it in the application layer, the panel does not say "the map draws the technology layer" for an application that is deployed on some node (`applicationIsDeployed`, `mapElementIsOnMap(reference, layer)`, `scene.drawnApps`), and `mapBoxesIfOpened` counts the applications of the nodes it would open. A saved view of the technology Map that says neither key draws both, which changed the output of the saved technology maps of a workspace that has applications deployed on its nodes and dependencies between its environments (accepted by the author: the command line has drawn saved maps since 0.14.0, released the same day): on the layered Brightcart the `environments_map` and `cloud_map` of every plateau, comparison and facet folder gain the link `prod.dc --> partners` (or `prod.cloud.k8s --> partners`) and, when pinned, the `partners` box; the example `domain_technology_map`, which deploys no application, draws what it drew; every other file `views generate`, `query graph` and `diff` write, on every example and fixture, is byte-identical to the jar of `archicode-0.14.0` (run 0114).

**The `links` of a Map** (wave 026, run 0197, #143): a saved Map view of the application layer may say which relationships it draws, `properties.links`, a list of mappings `{source, destination, label}` (`label` optional; `MapLinks`, `KernelViewpointFactory.mapLinks`; the kernel's `map` reads the key `links` of its input, additive, contract 5 unchanged; the editor reads, ticks, sends and keeps it since wave 026 run 0199, W-5, see the next paragraph but one; no shipped example or fixture has `links`: CON-5, ASM-3, DEC-9). The match is exact on the source, the destination and the label (`RelationshipLabel.same`, no label is not a wildcard); relationships of one triple that differ by qualifiers are drawn together; the boxes are the ends of the matched relationships, the pinned elements and their ancestors, `hidden` and `pinned` filter the relationships as before, and `links` absent, `null` or `[]` is no selection. An entry of another shape is one `error:` line (``the view v: `links[n]` is a mapping with `source`, `destination` and optionally `label`, and ... is not one``), an entry that names no relationship another (``the view v: `links[n]` names a relationship from `a` to `b` with the label `x`, which does not exist``, `with no label`), an unknown end `dangling reference`, and `links` on a map of the technology layer is refused, all exit 1. In a workspace with plateaus or a facet the adapter drops an entry the plateau lacks and `ViewInPlateau` warns (``the view `v` is drawn without the link `a -> b`, which the plateau `p` does not have``) or skips the view (``skip `v`: none of its links is in the plateau `p` ``), so a typo is only a warning there; the load check was declined by run 0199 (DEC-10, DEF-1) and stays a follow-up. The cases are `src/test/javascript/viewpoint-kernel/map-links-cases.json`; the manual says it in `[[map-links]]`.

**The `highlight` of a Map** (wave 026, run 0198, #143, W-4): a Map view of the application layer, and a story step, may name relationships to draw heavy, `properties.highlight` on a view and the key `highlight` on a step (`Story.Step#highlight`), a list of the same `{source, destination, label}` entries as `links` (`MapLinks` reads both keys: shape, exact match, `existsInUnion` in a comparison; sentences with `highlight[n]`; the cases are the `highlight` section of `map-links-cases.json`). The kernel's `map` reads the optional input `highlight` and marks `highlighted: true` on an output link that stands for a highlighted relationship (a grouped link when any of its relationships is; absent otherwise; marked after `merge_links`; `only_changes` drops the mark with the link; additive, contract 5 unchanged); `KernelViewpointFactory` forwards it for `viewpoint: map` only (other viewpoints ignore it; the technology layer refuses it), `Link#highlighted` carries it. `rendering/plantuml/HighlightMarks`, called by `LinkRenderer`: a view is highlighting when one link is; a highlighted link is `thickness=5` (`#D55E00`, or the arrow of its state at that weight), with the glyph U+25B6 and a bold label; a link with no state and not secondary is calm (`-[#A6A6A6]->`, label in grey); a link with a state that is not highlighted, and a secondary link, are drawn as before; a view with no highlighted link is byte for byte as before. On a step, `GenerateStoriesCommand.viewOf` replaces the `highlight` of the view it draws (a copy of the saved view, which is untouched; `[]` switches it off; the step wins over its own `properties.highlight`). Plateau rule: a missing entry is an `error:` without plateau or facet, and in a workspace of plateaus or facets `ViewInPlateau` warns (``... is drawn without the highlight `a -> b`, which the plateau `p` does not have``) and the view is still drawn, never skipped for it (unlike `links`). The editor keeps `highlight` as written (view recipe, saved view, story step) and follows its references in a rename and a move; run 0200 made it draw and play it (see the paragraph of run 0200 below). The manual says it in `[[map-highlight]]` and `[[stories-generate]]`, the guide in its table of view properties, its stories paragraph and its bullet on a story of a flow.
