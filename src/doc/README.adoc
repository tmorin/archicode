== Introduction

Welcome to the ArchiCode Command Line Tool Documentation. ArchiCode is a powerful tool designed to assist architects in creating models and generating views using an efficient as-code approach. Drawing inspiration from both the C4 Model and the ArchiMate Standard, ArchiCode provides a data model and a command line interface to streamline your architectural workflow.

With ArchiCode, architects can easily design models and produce views while adhering to the principles of the C4 Model. Our built-in viewpoints handle various levels of abstraction, ensuring your architectural vision is accurately represented in your projects.

Incorporating concepts from the ArchiMate Standard, ArchiCode's model is rooted in the structural Aspect and spans the Application and Technology layers. This integration adds depth and clarity to your architectural creations.

This documentation will guide you through the features, domain, commands, and best practices for utilizing ArchiCode in your architectural projects. Let's explore how ArchiCode can elevate your architecture-as-code journey.

== Availability, License, and Deliverables

ArchiCode is an open-source software hosted on GitHub, fostering transparency and collaboration. It operates under the MIT license, granting users flexibility in its use and modification. The software is distributed as a Maven Artifact and an OCI Image (Docker Image), simplifying integration.

- Source Code: ArchiCode's source code is hosted on GitHub at https://github.com/tmorin/archicode, providing access for developers to explore, contribute, and collaborate.

- Licensing: ArchiCode is licensed under the permissive MIT license, enabling users to freely utilize, modify, and distribute the software.

- Deliverables: ArchiCode is conveniently available as a Maven Artifact and an OCI Image, facilitating easy integration into development workflows.

- Access to Deliverables: The practical deliverables can be accessed through the dedicated packages repository at https://github.com/tmorin/archicode/packages.

This accessibility, licensing, and practical distribution emphasize ArchiCode's commitment to fostering an open and collaborative architectural community.

The ArchiCode domain serves as the foundational framework for your architectural endeavors, encompassing essential elements that facilitate and enhance your architectural work:

- Workspace: ArchiCode's workspace provides the supportive backdrop for all your architecture projects, offering an organized and collaborative environment.

- Application Layer: Within the ArchiCode domain, the Application layer hosts a rich array of elements coming from the C4 Model, enabling you to meticulously design and model application components with precision and clarity.

- Technology Layer: Embracing the Technology layer of the ArchiCode domain empowers you to delve into the realm of deployment nodes, strategically configuring your architecture's technological aspects.

[[workspace]]
=== Workspace

In ArchiCode, a workspace is a fundamental construct that orchestrates the foundation of your architectural endeavors. It acts as a cohesive hub, streamlining the definition and configuration of your architecture work. Key aspects of the workspace include:

- Plain Text Format: A workspace is represented as a plain text file, allowing you to choose between YAML, TOML, or JSON formats. This flexibility ensures that the workspace aligns seamlessly with your preferred configuration style.

- Centralized Definition and Configuration: The workspace serves as a central repository for defining and configuring your architecture work. This consolidation streamlines your workflow and provides a clear reference point for all aspects of your project.

- Enrichment with Manifests: Workspaces can be enriched through the inclusion of manifests. A manifest, also presented as a plain text file in YAML, TOML, or JSON format, further refines and specifies architectural details within the workspace.

- Manifest for Enhanced Organization: The concept of manifests introduces a structural layer that enhances source code organization. By encapsulating architectural components, manifests contribute to a cleaner and more comprehensible separation of concerns.

- Collaboration Support: Embracing the manifest concept not only refines source code organization but also provides enhanced collaboration capabilities. Manifests facilitate clearer communication among team members by offering a well-defined structure and purpose.

- Optional Name: a workspace can be given a name with `settings.name`. The editor shows it in place of the name of the folder (see <<editor-workspace-name>>); the command line does not need it. A workspace without a name stays valid.

- Optional Plateaus: a workspace can list the states of the architecture, each a complete folder of manifests, with `settings.plateaus` (see <<plateaus-overview>>). A workspace that does not, keeps the one set of manifests it always had.

[[duplicate-references]]
A reference is declared once. The reference of an element is its `id` placed under its parent, whether that parent is the element that contains it in its file or the `parent` of the manifest's header, so `shop.web` is the same reference for an element nested in `shop`'s file and for a manifest with `parent: shop` and `id: web`. When two declarations share a reference, in two files, in a file and in a manifest placed under its parent, or twice in one file, the command line stops with an error that names the reference and the files, and generates nothing; two identical copies are as much an error as two different ones, because nothing says which file is meant. The same goes for two views, or two stories, that share an `id`. A reference may exist in both layers (an application and a node of the same name): they are not the same element.

----
the reference `shop` is declared twice: in `manifests/a.yaml` and `manifests/b.yaml`
----

The editor reports the same thing, in the same words (see <<editor-folders>>).

Incorporating workspaces and manifests into your architectural workflow within ArchiCode empowers you with an efficient and organized foundation for your projects. Let's explore further as we navigate through the various dimensions of the ArchiCode domain.

[[plateaus]]
==== Plateaus

An architecture goes through states: how it is today, how it should be next year. (<<plateaus-overview>> tells the story in one place, with a tutorial.) A _plateau_ is one of these states, kept as a complete folder of manifests. `settings.plateaus` lists the plateaus of the architecture in one `workspace.yaml`, and the commands and the editor draw the one you choose.

.The folders of that workspace
----
- project_dir/
    - plateaus/
        - 10_as-is/ <1>
            - customer.yaml
            - shop.yaml
        - 20_to-be/ <2>
            - customer.yaml
            - shop.yaml
    - workspace.yaml
----
<1> The manifests of the plateau `as-is`.
<2> The manifests of the plateau `to-be`: a complete folder, not a list of differences.

A plateau has these keys:

[cols="1,3"]
|===
| `id` | Required. What `--plateau` and `current` name. Unique; letters, digits, `.`, `_` and `-`, starting with a letter, a digit or `_`, because the identifier is also used in folder names.
| `path` | Required. The folder of the manifests, relative to the folder of `workspace.yaml` and below it: no `..` segment, not absolute (no leading `/` or `\`, no drive letter). Unique among the plateaus. `.`, the folder of `workspace.yaml` itself, is accepted for a single plateau and refused with several, because it would hold the others.
| `name` | Optional. The name shown to people; the `id` when absent.
| `horizon` | Optional. A free-text label for when the plateau is meant to hold, such as `2027-Q1`. ArchiCode never parses nor interprets it.
| `baseline` | Optional. The id of the plateau this one is compared with (see <<plateau-comparison>>): another plateau of the list. Without it, the baseline is the plateau before this one in the list, and the first plateau has none.
| `from` | Reserved. It will mean "an increment on top of another plateau" in a later version and is refused for now, with a message.
|===

The list is ordered, and the order is the one you wrote: it is the order of the states, the last one is the latest. The numbers in the names of the folders (`10_`, `20_`) are only there to sort them in a file browser; they mean nothing to ArchiCode. `settings.current` is optional and names the plateau that is drawn when none is asked for; without it, it is the last plateau of the list. A reference is declared once *in a plateau* (see <<duplicate-references>>); the same reference in two plateaus is no duplicate, since it is the same element at two moments.

To draw another plateau than the default one, the commands that load a workspace (`views generate`, `query views` and `query graph`) take `--plateau <id>`; the editor has a selector in its header (see <<editor-plateaus>>).

[source,shell]
----
archicode views generate --plateau as-is
----

The views of a plateau are written in a folder of its own, named after it: `views-as-is` (and `views-as-is-<facet>` for each facet, as the `directory-name-template` of the facets says), `views-to-be`, and so on, so that drawing two plateaus never writes one over the other. With `--output out`, the folders are `out-as-is` and `out-to-be`. A workspace that has no plateaus keeps the folders it always had (`views`, and one folder per facet).

`settings.manifests.paths` stays the short form of a workspace that has a single set of manifests, a workspace with one implicit plateau. Writing both `manifests.paths` and `plateaus` is an error: with plateaus, remove `manifests.paths` and give each plateau its own `path`. The ordered list of plateaus is not a set: the order of `settings.manifests.paths` has never mattered, the order of `settings.plateaus` does.

----
the plateau `to-be` has a `from`: it is reserved for a later version of ArchiCode, [...]
the path `../shared` of the plateau `to-be` contains `..`: it must be a folder below the one of workspace.yaml, [...]
the plateaus `as-is` and `to-be` share the path `plateaus/10_as-is`: each plateau needs a folder of its own
----

Every rule is checked before anything is read or written, and every problem is reported, one per line.

The same later version reserves two more names, in the manifests: `kind: archicode.morin.io/plateau` and a `plateau` key in the header of a manifest are not recognised and are refused for now, by the command line (an `error:` line, exit code 1) and by the editor, with one sentence that names the key, says that layered plateaus are not supported yet and points at issue #30 (`tmorin/archicode`).

IMPORTANT: *Breaking change* (see <<plateaus-upgrade>>). A path of `settings.manifests.paths` may no longer leave the folder of the workspace (`../shared`) nor be absolute (`/srv/manifests`, `C:\data`): the same rule as for the folder of a plateau, so that one folder holds a whole workspace, and so that the editor, which only reaches the folder it opened, reads what the command line reads. A workspace that used such a path stops with an error that says which path and what to change: move the folder below `workspace.yaml`, or move `workspace.yaml` up to a folder that holds both, and change the path to match. A path that stays below the folder (`manifests`, `node_modules/<module>/manifests`) is not affected, and neither is a workspace without `plateaus`: it is read, and generates its views, exactly as before.

[[plateau-comparison]]
==== Comparing two plateaus

A plateau is a complete folder, so what a plateau _changes_ is the difference between two folders: ArchiCode compares a plateau with its _baseline_ and tells what is new, what changed and what was removed, elements and relationships. The baseline is, in this order, the plateau `--baseline` names, else the `baseline` key of the plateau, else the plateau before it in the list. The first plateau has no baseline, and so nothing to be compared with unless one is named. The baseline must be another plateau of the list; a `baseline` that names an unknown plateau or the plateau itself is an error that lists the plateaus.

[source,yaml]
----
settings:
  plateaus:
    - id: as-is
      path: plateaus/10_as-is
    - id: to-be
      path: plateaus/20_to-be
    - id: later
      path: plateaus/30_later
      baseline: as-is  # not `to-be`, the plateau before it
----

Two commands show the comparison: `archicode diff` writes the table of changes (see <<diff>>), and `archicode views generate` draws the views of the comparison (see <<generate-views>>).

*What counts as a change.* An element is the same element in both plateaus when it has the same reference (a reference includes the path of the element, so an element that moves under another parent is a removed one and a new one, unless the new one says that it replaces the old one, see <<plateau-replaces>>). It is _new_ when its reference is only in the plateau, _removed_ when it is only in the baseline, and _changed_ when something differs in the element itself or in the relationships it declares: its kind, its name, its description, its qualifiers, its tags (the `rendering-*` ones do not count), its deployment (`applications` and `uses`), or a relationship that was added, removed or changed. A child is judged on its own: a system whose only change is a new container is not _changed_, it _contains changes_. The table lists what changed in each element (`natures`) and tells a change of wording apart: an element whose description is the only thing that differs is _wording only_. A relationship is identified by its source, its destination and its label; it is _new_ or _removed_ when it is only on one side, and _changed_ when its qualifiers, its tags or, when it is the only one between the two elements, its label differ. The order of a list and the order of the keys of a file are no change.

*How the views say it.* The views of a comparison draw the union of the two plateaus (what was removed is drawn too), and every box and every link says its state with the same marks, never by colour alone (the last three are for an element that says what it replaces, see <<plateau-replaces>>, and are only in the legend of a view that has one):

[cols="1,1,2,2"]
|===
| State | Mark | Box | Link

| new | `+` | thick solid outline | thick solid line
| changed | `~` | dotted outline | dotted line
| removed | `−` | long dashes with narrow gaps, grey outline, grey and struck title | dashed grey line
| contains changes | `±` | thin dashed outline | (none)
| moved | `→` | long dashes with wide gaps, blue; the title ends with `(from <the reference it replaces>)` | (none)
| split | `⋔` | medium dashes, purple; the title ends with `(from <the reference it replaces>)` | (none)
| merged | `⊕` | short dashes far apart, light blue; the title ends with `(from <the references it replaces>)` | (none)
|===

The mark is written in front of the title of the box and of the label of the link. A box that did not change is drawn as it always was, and so is a link. `contains changes` is for a box that did not change by itself and holds something that did (a system whose container is new, for instance): the reader can see where to look inside. A link between two boxes that are drawn as one group (a view draws the relationships of the elements below it as one link) is new when all of them are, removed when all of them are, changed when they are mixed, and unchanged when none changed. A view that says at least one change has a legend that explains the marks.

The states are stereotypes of the boxes (`new`, `changed`, `removed`, `contains-changes`, `moved`, `split` and `merged`), so a `styles.by-tags` entry of the same name gives them your own look, as it does for every stereotype (see <<stereotypes-and-styles>>). ArchiCode brings a default style for a state only when the workspace has none, and the style you write wins property by property: write `new` with a `background-color` and the box keeps the thick outline of the default.

The default look of a state belongs to the boxes that _have_ the state, computed: it is never given to a box because of a word it carries. If you wrote `rendering-stereotypes: "new"` (or `changed`, `removed`, `contains-changes`, `moved`, `split`, `merged`) on an element that does not have that state, the box is drawn with your own `styles` entry named `new` and nothing else, no thick outline, no mark, no struck title, in a view that has something new as in one that has not, and the command says so (see <<plateau-state-tags>>).

[source,yaml]
----
styles:
  by-tags:
    new:
      background-color: "#DAF2E6"   # the outline stays the default one
    removed:
      line-color: red
----

A facet can read what changed: in a comparison, every element and every relationship has a `change` (`none`, `new`, `changed` or `removed`, and, for an element that says what it replaces, `moved`, `split` or `merged`) that a JSONPath selects like any other field, such as `$..relationships[?(@.change == 'removed')]`. The other facets work as they always did.

==== Using other environments

An application rarely lives alone in its environment: the development environment of a platform talks to an identity provider, to a mail relay, to the integration environment of a partner. Those are environments too, each with the nodes that host the applications modeled for them. An environment says which ones it depends on with `uses`.

.The manifest of an environment that uses another one, and a node of a third one
[source,yaml]
----
header:
  kind: archicode.morin.io/environment
  version: "1"
content:
  id: dev
  name: Development
  uses:
    - integration
    - idp.production.openid
  elements:
    - kind: node
      id: cluster
      applications:
        - shop.api
----

`uses` is not a relationship and it draws nothing by itself. It tells where to look for what the applications of the environment depend on:

- When an application deployed in the environment has a relationship towards another application, ArchiCode looks where that other application is deployed. If the environment hosts it, nothing leaves the environment.
- Otherwise, it is looked for in the environments, or the nodes, listed in `uses`, and nowhere else. An application deployed in several environments is reached in the ones the environment uses. That is how `dev` reaches the `integration` instance of an application, and not the `production` one.
- The dependency is then drawn, in the deep view of the technology layer, between the two deployed applications, with the label, the qualifiers and the tags of the relationship of the application. It folds with the nodes: when they are collapsed, the dependencies between them are grouped in one link.
- The overview and the detailed view of an environment, or of a node, show the same dependencies grouped on the nodes that host the applications: an environment is linked to the environments it uses.
- The view of an environment shows what it depends on, and the view of a used environment shows who depends on it.

An entry of `uses` is the reference of an environment, to use all of it, or of one of its nodes, to use a part of it. It has to exist, or the views are not generated.

As the dependencies are derived from the relationships of the applications, a facet that removes some of them removes the dependencies that rest on them. Through a facet, the deep view of an environment also draws the relationships between the applications deployed in it, with their label and qualifiers: a facet that keeps one flow (an authentication, the audit events) shows that flow as it is deployed, on the nodes that host the applications. Without a facet these relationships are not drawn, there would be too many. The overview and the detailed view lift them to the nodes the view is made of. A facet that sets `hide-unlinked: true` also leaves out, in these views, the elements none of its links goes through, the element the view is about staying; in the editor it is a check box of the facet, in the Settings. The entries of `uses` can also be selected by a facet, as any other part of the workspace.

[[stories]]
==== Stories

A story puts views in order, with a sentence for each, to tell how a part of the architecture works. It does not draw anything on its own: each step shows a view, and the editor draws that view live from the model, so a story stays true as the architecture moves.

Stories and views are manifests, like the elements: one file each, in the manifests folders, with the kinds `archicode.morin.io/story` and `archicode.morin.io/view`. The editor writes them for you (see <<editor-stories>>), but they are plain YAML:

.manifests/story.order_flow.yaml
[source,yaml]
----
header:
  kind: archicode.morin.io/story
  version: "1"
content:
  id: order_flow
  name: How an order travels
  description: From the shop to the payment provider.
  steps:
    - view: shop_overview          # a view that has a name: see below
      text: The shop receives the order.
    - viewpoint: map               # or a view written right in the step
      layer: application
      properties:
        pinned: [shop.payments]
        hidden: [mailer]
        opened: [shop]
        hide-unlinked: true
      text: It hands the payment over.
----

.manifests/view.shop_overview.yaml
[source,yaml]
----
header:
  kind: archicode.morin.io/view
  version: "1"
content:
  id: shop_overview
  name: Shop — Overview
  viewpoint: overview     # overview, detailed or deep: drawn by the command line as well
  layer: application
  properties:
    element: shop
    facet: flow           # optional: the editor draws the view through that facet
    descriptions: true    # the texts of the diagram, when they differ from its default (see the editor)
    wrap: true
----

A step either names a view by its `id`, or carries one: a `viewpoint`, a `layer` and `properties`, as a view has. A named view can be used by several stories and generated by the command line (its `id` is what `--view-ids` takes); a view written in a step is only for that step, and has no file of its own. The text is plain text. A step on a view that is not declared is reported as a warning by the command line, and shown as missing by the editor. The command line ignores the stories, skips the views of the `map` viewpoint (the editor alone draws it), and generates the views of its own viewpoints as it always did.

Workspaces written before stories became manifests keep their views in `views:` of `workspace.yaml`, and may have a `stories:` there too: both are still read. The editor offers to move them to manifests, which keeps `workspace.yaml` small and free of the rewrites an editor save makes to it.

[[stereotypes-and-styles]]
==== Stereotypes and styles

Every box of a diagram is drawn with a list of _stereotypes_.
The stereotypes of an element are, in this order, its `qualifiers` (each one whole: `Spring Boot` is one stereotype) and the words of its `rendering-stereotypes` tag.
The tag is a whitespace-separated list, so that `external changed` gives the two stereotypes `external` and `changed`, and a value of one word gives the one stereotype it always gave.
A stereotype named twice counts once.
The renderer then adds the kind of the element and the way the box is drawn.
The command line and the editor read the stereotypes the same way: they come from the same kernel.

The `styles` of the workspace give a stereotype its look.
`styles.by-tags` and `styles.by-qualifiers` map a stereotype to a style, and a box has the style of every stereotype it is drawn with.
The key is the stereotype itself, not the name of a tag: the keys of `by-tags` are the words of `rendering-stereotypes`, the keys of `by-qualifiers` are the qualifiers.
The two maps are equivalent for the renderer, which only sees stereotypes; use the one that says where the stereotype comes from.
A style sets any of `background-color`, `line-color`, `line-style`, `line-gap`, `line-thickness`, `round-corner`, `font-color`, `font-style` and `shadowing`.
`line-style` is the length of a dash (0 is a solid line) and `line-gap` the gap between two dashes: without `line-gap` the gap is as long as the dash, so that `line-style: 5` is a dash of 5 and a gap of 5 and `line-style: 16` with `line-gap: 3` is long dashes with narrow gaps (PlantUML's `LineStyle: 16-3`).
A `line-gap` means nothing without a `line-style`; when a style overrides the `line-style` of another one, the gap of the other style goes with the dash it replaces.

.Styling the boxes tagged `external` and `changed`
[source,yaml]
----
styles:
  by-tags:
    external:
      background-color: "lightgray"
    changed:
      line-color: "orangered"
      line-thickness: 3
  by-qualifiers:
    PostgreSQL:
      round-corner: 20
----

.An element drawn with the `external` and the `changed` styles
[source,yaml]
----
content:
  id: "mailer"
  name: "Mail Provider"
  tags:
    rendering-stereotypes: "external changed"
----

*In the editor.* The editor draws a box with the style of the stereotypes it is drawn with: `background-color` is the fill, `line-color`, `line-thickness`, `line-style` and `line-gap` the outline (derived from the fill when only the fill is given, see below), and `round-corner`, `font-color`, `font-style` and `shadowing` the rest.
A styled stereotype is also written on its box as a text badge with its name, so that a colour is never the only carrier.
The same badge follows the name of the element in the *Elements* tree and in the tree of the *Map*, and in the header of an element (after its kind, on *Details* and on the diagram tabs; when the header is narrow it shows the badges that fit and the name keeps its room), and the key under the diagram shows the badge of each styled stereotype drawn.
The badges are part of the SVG and PNG exported from a diagram, while the key is not; a badge is not the dot that marks an element as modified and not yet saved.

For the same stereotype, `by-tags` wins over `by-qualifiers`.
When a box has several styled stereotypes, a later one overrides an earlier one property by property: with `rendering-stereotypes: "external changed"`, the fill of `changed` wins, and the properties it does not set come from `external`.
The order is that of the stereotypes of the box, its qualifiers first and then the words of the tag.
The command line follows the same rule: it writes the stereotypes of a box last first, since PlantUML lets the first stereotype of a box win, property by property, whatever the order of the styles.
The `.puml` of a box carrying `external changed` therefore says `+<<changed>> <<external>>+`, and the same workspace always gives the same file, byte for byte.
The one difference: `shadowing` is a flag that is only ever switched on, so a style cannot switch off the shadow another style of the same box switched on (the editor lets `shadowing: false` of a later stereotype do it).

Colours are read as `#rgb`, `#rrggbb`, `rgb(r, g, b)`, `transparent` or a CSS colour name such as `lightgray`; a value the editor cannot read is ignored.
Numbers are whole numbers.

The fill is the colour written in `styles`, in both themes, as in the diagrams of the command line; `styles` has no separate dark colour.
A box with a `background-color` and no `line-color` is outlined with a line derived from its fill: the same colour, darker (each of its channels at 60 %, so the hue is kept), or lighter when the fill is so dark that darkening it would show nothing, as for black.
Without it the outline would be the grey of the theme, lost on the fill, and a box inside a box of the same fill, such as the systems of a solution that are both `external`, would vanish into it.
The derived line is as firm on a box that contains others as on one that does not.
The `line-color` of the style always wins, whatever the fill, and the fill itself is never changed; a box with no fill keeps the outline of the theme, and the outline of the box in focus or selected stays the accent colour.
The same line is drawn on the badge of the stereotype, and in the SVG and PNG exported from a diagram.
In the diagrams of the command line, PlantUML draws a box with the fill of its style and its own thin dark outline, so a box inside a box of the same fill is already told apart there: nothing is derived.
The editor chooses the colour of the text so that it reads on that fill, black or white with a contrast ratio of at least 4.5: the `font-color` of the style is kept when it reads well, and replaced otherwise.
Without a `background-color`, the box and its text keep the colours of the theme, and `font-color` is not used. Except that a box that contains others, with no `background-color` of its own, drawn inside one that has one, lets that fill show: its title is then black or white against that fill, in either theme, so that it never lands on a fill it cannot be read on.

Compared with the command line, `line-style` and `round-corner` are an approximation of what PlantUML draws.
The editor styles only the stereotypes of an element, its qualifiers and the words of `rendering-stereotypes`: it does not use the kind of the element, nor `atomic` and `composite`, as keys, and `styles.atomic` and `styles.composite` are not drawn.

[[plateaus-overview]]
== States of an architecture (plateaus)

An architecture is never finished: it is how it runs today, how it should run next year, and what the year after may bring. ArchiCode calls each of these states a _plateau_ and tells you what changes from one to the next. This section is the story in one place, from the idea to a review of the changes; the rules are in <<plateaus,Plateaus>> and <<plateau-comparison,Comparing two plateaus>> (in the Domain section), the commands in <<plateau-add,Add a plateau>>, <<diff,Compare plateaus>> and <<generate-views,Generate views>>, and the editor in <<editor-plateaus,Plateaus in the editor>> and <<editor-compare,Comparing two plateaus in the editor>>.

IMPORTANT: *Breaking change.* A path of `settings.manifests.paths` may no longer contain `..` nor be absolute, and a reference declared twice is now an error. Read <<plateaus-upgrade>> before you upgrade a workspace; a workspace that does neither is read and drawn exactly as before.

=== The idea

A plateau is a _complete_ folder of manifests: the whole architecture in that state, not a list of differences. You edit the plateau of the future as you would edit any workspace, and nothing has to be kept in sync by hand. The difference between two plateaus is _computed_ from the references of the elements and the relationships, never typed: ArchiCode tells what is new, what changed and what was removed, and the views, the table of changes and the editor all draw the same answer.

One thing cannot be computed: that two elements are the same thing. An element that moves under another parent, or is renamed, has another reference, so it reads as one removed element and one new one. ArchiCode never guesses it; you say it, on the element of the more recent plateau, with `replaces`, and the comparison then reads a _moved_, _split_ or _merged_ element. It proposes the pairs that look like one thing said twice (the _candidates_) and applies none. The editor writes the hint when you accept a candidate, and when you move an element under another parent.

=== The layout

The folder of the architecture holds one `workspace.yaml`, with the settings, the styles and the facets that every plateau shares, and one folder per plateau.

.The folders of an architecture with two plateaus
----
- architecture/
    - plateaus/
        - 10_as-is/ <1>
            - customer.yaml
            - inventory.yaml
            - shop.yaml
            - warehouse.yaml
        - 20_to-be/ <2>
            - customer.yaml
            - inventory.yaml
            - shop.yaml
            - warehouse.yaml
    - workspace.yaml <3>
----
<1> The manifests of the first plateau, directly in the folder (a plateau folder is read like a `manifests` folder: its files, not its sub-folders).
<2> The manifests of the second one: the whole architecture, as it should be.
<3> Lists the plateaus in `settings.plateaus`. This is the example `domain_plateaus` of this manual (`src/doc/examples/domain_plateaus` in the source repository).

=== The settings in short

[cols="1,3"]
|===
| `settings.plateaus` | The ordered list of plateaus, the oldest first. Each entry has an `id` and a `path` (both required), and optionally a `name`, a `horizon` (free text, never interpreted) and a `baseline` (the id of the plateau it is compared with; by default the plateau before it in the list).
| `settings.current` | The plateau that is drawn when none is asked for; the last one by default.
| `from` | Reserved for a later version and refused for now, with a message.
|===

A `path` is mandatory, relative to the folder of `workspace.yaml`, below it (no `..`) and not absolute. The ids and the paths are unique, and `.` is accepted for a single plateau only. Every rule is checked before anything is read, and each problem is reported. The details, with the messages, are in <<plateaus>>.

=== The states

What a plateau changes is told with four states, computed, on elements and on relationships (the fourth is for boxes only), and three more for the elements that say what they replace (see <<plateau-replaces>>):

[cols="1,1,3"]
|===
| State | Mark | Means

| `new` | `+` | the reference is only in the plateau
| `changed` | `~` | the reference is in both and something differs: a property, or a relationship the element declares (an element whose description is the only difference is _wording only_)
| `removed` | `−` | the reference is only in the baseline
| `contains-changes` | `±` | the element did not change by itself, but something inside it did
| `moved` | `→` | the element says that it replaces one element of the baseline (elements only)
| `split` | `⋔` | the element says that it replaces an element that another element replaces too (elements only)
| `merged` | `⊕` | the element says that it replaces several elements (elements only)
|===

Each state has a mark, a line style and a legend, so that nothing relies on colour: see <<plateau-comparison,Comparing two plateaus>> for the command line and <<editor-compare,Comparing two plateaus in the editor>> for the editor.

[[plateau-state-tags]]
*The states and the tags you wrote by hand.* The states are stereotypes of the boxes, the same ones that a `styles.by-tags` entry or a `rendering-stereotypes` tag names (see <<stereotypes-and-styles>>). If you used to mark the boxes of a target by hand with `rendering-stereotypes: "new"` or `"changed"`, nothing breaks, and the command line and the editor draw such a tag the same way. One rule decides it: _a box gets the default look of a state (its mark, its outline, its tint, its struck title) only when the comparison computes that state for it._

* A word you wrote that is the state the box has (a `new` tag on a new element) is one stereotype: the computed state is not written twice, it is the _last_ stereotype of the box, so its look overrides the look of the other stereotypes as a later stereotype always does (the generated `.puml` writes the stereotypes in reverse, so it reads first there). Your `styles.by-tags` entry named like the state wins, property by property, over the default look of ArchiCode: a `new` with only a `background-color` keeps the thick outline of the default.
* A word you wrote that is _not_ the state the box has (a `new` tag on an element that did not change, a `new` tag on an element that changed, any state word when no comparison is made) is only your stereotype (a `.puml` of a comparison writes it `written-new`, so that the default look of `new` cannot reach it). The box has the style you gave to that name in `styles.by-tags` or `styles.by-qualifiers`, if any, and nothing of the default look, whatever else the view shows. On an element that changed, the computed state, which is last, has the last word over it.
* The tags themselves are not read by the comparison (a `rendering-*` tag is never a change), so you can drop them when you like: the computed states say the same, and say it only where it is true.

The command line tells you where a word and the comparison disagree, one line per element and word, on the error output (not in the log, which hides warnings by default), and the files it writes and the table it prints are the same whether you read the lines or not. With the tag `rendering-stereotypes: "new"` added to `customer` in the example, which did not change, `archicode diff` says:

----
warning: the element `customer` carries `new` (`rendering-stereotypes` tag), but the comparison of `to-be` with `as-is` finds that it did not change and holds no change: it is drawn with your own `styles` entry named `new` (if any) and not with the default look of the state. The comparison computes the states, so the word can be dropped.
----

`archicode diff` and `archicode views generate --baseline` check the plateau they compare. `archicode views generate` of a plateau that is not compared says that a state word is a state of a comparison and that nothing is compared here. A workspace without `settings.plateaus` has no comparison to disagree with, and is never told anything: there the words are your own stereotypes, as they always were. A word that agrees with the comparison is never reported. The editor draws the same: a hand-written word is a badge and a style, and the look of a state only where the state is computed. It tells you the same, in the same sentences, when a plateau is compared (*Compare to*): in the panel of the element, under what changed, and in the *Hand-written states* list of the *Changes* panel (see <<editor-compare>>). Nothing is told when nothing is compared, since the comparison is a choice of the page.

[[plateau-replaces]]
=== Saying what an element replaces

A comparison finds an element by its reference. An element that moves under another parent, or is renamed, has another reference: the comparison reads it as one removed element and one new one, with nothing that links them. ArchiCode never guesses that two elements are the same thing; _you_ say it, on the element of the more recent plateau, with the key `replaces`: a list of the full references, in the baseline, of what the element replaces. It is the same hint as the `moved` block of Terraform. The editor can write it for you when it moves an element (see <<editor-move>>).

.The container `inventory` in the plateau `to-be` (`plateaus/20_to-be/inventory.yaml` of the example `domain_plateaus`)
[source,yaml]
----
include::examples/domain_plateaus/plateaus/20_to-be/inventory.yaml[]
----

The inventory used to be a container of the system `shop` and is now one of the system `warehouse`, so its reference went from `shop.inventory` to `warehouse.inventory`. It says what it replaces, and so does the component `levels` inside it.

The key is optional, and a tool that does not know it ignores it. The comparison turns the elements that say what they replace into three states, and the replaced elements are no longer _removed_:

* *moved*: the element replaces one element, which no other element replaces. It is in another place or has another name, and it is the same thing. Whatever else it changes, it keeps it: a name, a description and the relationships it declares are compared with the element it replaces, and the table says which (the `natures`), next to `moved`. A moved element is counted as `moved`, not also as `changed`.
* *split*: several elements replace the same element (`shop.orders` became `shop.cart` and `shop.checkout`). Each of them is `split`, and the table names the other ones.
* *merged*: the element replaces two elements or more (`shop.billing` replaces `shop.invoices` and `shop.receipts`), or an element that is in the baseline and in the plateau at the same time. When an element is both split and merged, it is `merged`.

What the replaced elements held is not carried by itself: a container that moved takes none of its children with it, so each child needs its own `replaces` (`levels` above), or it is read as removed (the box of the replaced container is then drawn as the place it was removed from, with the words "replaced by"). What points at a replaced element follows it when exactly one element replaces it: a relationship to `shop.till` that now points at `stock.till` is not a change of the element that declares it, and nor is a node that deployed `shop.till` and now deploys `stock.till`. What points at a split element is not rewritten, because which half would own it is a guess. The relationships of the halves, and those that end on a half, are therefore not compared with the baseline and read as new, whether the element had them before it was split or not; `archicode diff`, `gap.md` and `gap.json` say so on each of those rows (`of the split shop.report-a`) and count them in the header (see <<diff>>).

[[plateau-candidates]]
*Candidates.* When an element is only in the baseline and another one of the same kind and the same layer is only in the plateau, and nothing replaces or is replaced by either of them, the comparison may find that they look like one thing that was said twice: the same name (ignoring the case), a description with most of its words in common, or the only two elements of that kind under the same parent. A name counts only when no other removed element and no other new element of that kind has it: a `Cache` in every service, or a `Message Broker` in every environment, would pair every removed one with every new one and say nothing about which is which, so such a name proposes nothing (the description and the parent can still). It lists them as candidates and it never applies one. To accept one, write `replaces` on the new element; to refuse it, do nothing. `archicode diff`, `gap.md` and `gap.json` list the candidates once the plateau uses `replaces` (a workspace that does not is written as it always was), each with its reasons. The candidates are not drawn in the views.

[[plateau-replaces-warnings]]
*Warnings.* The comparison does not fail on a `replaces` that it cannot use: it ignores it, and says so on the error output of `archicode diff` and of `archicode views generate --baseline` (not in the log, which hides warnings by default), one line per entry (the example has none; the sample below is from the invented warehouse that <<diff>> uses):

* a reference that is not an element of the baseline (you may be comparing with another baseline than the one you wrote it for);
* a reference that is still an element of the plateau (what is there is not replaced, and an element cannot replace itself);
* a reference listed twice (it counts once);
* an entry that is not a reference (`- 12`, or an empty entry: it is ignored, and it is not read as the reference `12`);
* a `replaces` that is not a list (`replaces: "shop.mailer"`: it is ignored, and the element replaces nothing).

The command line gives the comparison the list as you wrote it, so these lines are the ones the comparison says (the editor refuses a `replaces` that is not a list with a message). A `replaces` that is well written says nothing, and so does an empty list.

----
warning: replaces of shop.report-b (application layer): shop.nowhere is not an element of the base plateau, ignored
----

`replaces` is read from the elements of the plateau that is compared; a `replaces` on an element of the baseline is not read. A plateau that is not compared does not use it.

*What the command line shows.* `archicode diff` has the three states in its table, with the counts of `moved`, `split` and `merged` on a line of their own (`replacing`), and says in the details of each row what the element replaces (see <<diff>>). The views of the comparison draw them with the marks above (see <<plateau-comparison>>). The editor draws them too, lists the candidates, and writes `replaces` for you (see <<editor-replaces>>).

=== A tutorial: from one workspace to a review of the changes

The tutorial builds the example `domain_plateaus` of this manual, an invented bookshop, from the first plateau to a review of the changes in the editor, including the things that change shape. Its commands run in the folder of `workspace.yaml`; the output quoted is the one the commands print.

*Step 1. Start from the architecture you have.* An existing workspace is your first plateau. Create the folder of the plateau under the folder of `workspace.yaml` and move the manifests in it. The files that were in the folder named by `manifests.paths` are the ones to move.

----
mkdir -p plateaus/10_as-is
mv manifests/* plateaus/10_as-is/
----

A plateau is _one_ folder: if `manifests.paths` listed several folders, put their files together in the folder of the plateau (a reference declared twice is an error, see <<duplicate-references>>).

If you already have the two states as two workspaces, a baseline and a target, each with its own `workspace.yaml` and `manifests` folder, make each manifests folder a plateau (`plateaus/10_as-is` and `plateaus/20_to-be`, the oldest first) and keep a single `workspace.yaml`, the one of the target if it is the one you keep working in. Its `settings`, `styles`, `formatters` and facets then apply to every plateau, and the other `workspace.yaml` is not read any more: move into the one you keep what you still need of it. Then list both plateaus as in step 2: `archicode plateau add` is for a new plateau, it never adopts a folder that exists already.

*Step 2. List the plateau.* In `workspace.yaml`, delete `manifests.paths`, the key and its list (a workspace has either that or plateaus, not both, and an empty list counts as written), and list the plateau. The names and the horizon are for people.

.The first plateau, in `workspace.yaml`
[source,yaml]
----
settings:
  name: "Bookshop"
  plateaus:
    - id: "as-is"
      name: "As is"
      horizon: "2026-Q3"
      path: "plateaus/10_as-is"
----

The workspace is read as before, with one visible difference: the commands read the only plateau, and the views of a workspace that has plateaus go to a folder named after the plateau, `views-as-is`, in place of `views` (and `views-as-is-<facet>` for the facets). Move or update what reads the old folder. An unknown `--plateau` is refused with the list of the plateaus that the workspace has, and the editor lists them in its header.

*Step 3. Add the plateau of the future.* `archicode plateau add` copies a plateau into a new folder and appends it to the list, comments of `workspace.yaml` included (see <<plateau-add>>):

----

[[plateaus-upgrade]]
=== Upgrading: what breaks, and what does not

Two things that used to pass now stop with an error that says what to change. Everything else about a workspace that has no `settings.plateaus` is unchanged: it is read, and generates its views in the same folders, byte for byte as before (checked on the views of this repository's workspaces and on a copy of a real workspace of 3,411 views).

. *A path of `settings.manifests.paths` with `..` or an absolute path.* `../shared`, `/srv/manifests` and `C:\data` are refused: one folder holds a whole workspace, so that the editor, which only reaches the folder it opened, reads what the command line reads. Move the folder below the folder of `workspace.yaml`, or move `workspace.yaml` up to a folder that holds both, and change the path to match. A path that stays below the folder (`manifests`, `node_modules/<module>/manifests`) is not affected.
. *A reference declared twice.* Two manifests, a manifest and an element nested in another one, or two elements of one file that share a reference used to pass silently, and which of them was drawn depended on chance. The command line now stops, names the reference and the two files, and writes nothing, and the editor reports the same in the same words (see <<duplicate-references>>). Remove one of the declarations, or give one of them another `id`. Two identical copies count too. This check applies to workspaces without plateaus as well; with plateaus, the same reference in two plateaus is no duplicate, it is what the comparison is about.

Nothing is to be changed in the manifests themselves: their format is the one it always was, with one optional key more, `replaces` (see <<plateau-replaces>>), that an older version of ArchiCode ignores.

One more thing changed for a workspace that has plateaus and that marks its boxes by hand with a state word (`rendering-stereotypes: "new"` or `"changed"`). A word that agrees with the comparison is drawn as before. A word on an element that does not have that state used to give the box the default look of the state in the views of the command line, and the editor did not: it now gives it nothing in both, and the command says so on its error output (see <<plateau-state-tags>>). The files that a workspace without a state word writes are the same, byte for byte.

[[editor]]
== Editor

ArchiCode comes with an editor to browse, edit and draw a workspace without leaving the browser. It is a single page, `standalone.html`, that reads and writes the files of a workspace folder: nothing is uploaded anywhere, the page and the files stay on your machine.

[[editor-open]]
=== Opening the editor

There are two ways to open it:

- *Served by the command line.* `archicode editor serve` serves the editor and opens the folder of the `workspace.yaml` in it, with nothing to pick. It works in any browser. See <<serve-the-editor>>.
- *From the published page.* The page published next to this documentation, at `/editor/` of the same site, asks for a folder. That needs the File System Access API, which Chrome, Edge, Brave and Opera have and Firefox and Safari do not: with one of those, use the command above instead.

[[editor-folders]]
The published page remembers, in the browser, every folder it opened, with the name its workspace gives itself (see <<editor-workspace-name>>). When the page opens again, it opens the last folder directly if the browser still lets it read it; otherwise it asks for a click (*Reopen*), because a browser only gives that permission back on a click. *Close folder*, at the top right, closes the folder and shows the list of the remembered folders: the closed one stays in it, and the next visit does not open it by itself. When no folder is open, the list shows each folder by the name of its workspace, with the name of the folder below it when they differ, most recent first: a click on one opens it, *Remove from the list* makes the browser forget it, and nothing is deleted on disk. Under each folder, the list says what a click will meet, as the browser answers without asking anything: _Opens without asking_, _Will ask for permission_ (the browser shows its prompt), _Blocked by the browser_, or _Could not be reached_ / _Could not be checked_ (the folder may have been moved or deleted). A folder picked again is not added twice, even by two tabs at the same moment: the browser then holds two records for it for an instant, and the editor merges them into one, keeping the name of its workspace and its place in the list. A folder that cannot be opened (the permission refused, the folder moved or deleted) stays in the list, which says why, until it is removed. Served by `archicode editor serve`, the editor has one folder, the one of the server: there is no list and no *Close folder*.

The editor loads `elkjs` (the diagram layout) and CodeMirror (the file editor) from a CDN when it opens. Without network access, it still works, with plainer diagrams and file editor.

The editor reads and writes YAML manifests (`.yaml` and `.yml`) only. The command line also reads TOML and JSON manifests: the editor does not, so what such a file declares is missing from its trees and diagrams, and relationships that point at it show as dangling. It says so, in *Files* (which names the files) and above the trees of *Elements* (which counts them).

A reference declared more than once is reported, not chosen: a red note above the trees of *Elements* and of *Files* gives the same message as the command line, each file that takes part is marked _duplicate_ in *Files* and says so when opened, and no diagram is drawn until each reference is declared once (a view or a story with a duplicated `id` is reported too, and does not stop the diagrams). Nothing else is blocked: the editor still edits and saves, so that the duplicate can be fixed in it.

[[editor-elements]]
=== Elements

The *Elements* perspective is the tree of the workspace on the left, and the selected element in the center. The center has four tabs:

- *Details*: the fields, qualifiers, tags and relationships of the element, with *Edit* to change them (change its id and every reference to it follows; *Move*, in the edit form, puts it under another parent, see <<editor-move>>), and *Delete* (the relationships of other elements that pointed at it are listed first, so that none is left dangling by surprise).
- *Overview*, *Detailed* and *Deep*: the viewpoints of the same names, drawn live from the model, as the command line generates them. *Detailed* is for an element that can contain others. Clicking a box in a diagram selects that element.

The badges and colours of styled stereotypes, on the boxes and in the tree, are explained in <<stereotypes-and-styles>>.

Changes stay in memory, with a mark on the tree for each modified element, until *Save all changes* writes them. A file that changed on disk since the editor read it is not overwritten: the save is refused and says which one. A file that is saved keeps what the changes did not touch: its comments, its blank lines, the quotes of the values and its final line break. Only the lines that changed are rewritten, and a value written anew (a renamed id, a new parent, a reference that follows, a `replaces`) keeps the quoting of the line it replaces, the way its key is written and its trailing comment; a line that is added is written like the lines around it (double quotes, single quotes or none, as the file does), and plain when the file quotes nothing. A list or a map written in square or curly brackets (`replaces: [a, b]`, `tags: {zone: north}`, on one line or on several, nested, as an item of a list of maps) stays as written when the change does not reach it; a change to it writes it as a block, in which the comments that were inside its brackets stay as lines of the block (a comment above a value above it, a comment after a value at the end of its line), and the quotes of its values and of its keys and the words of its booleans (`on`, `yes`) are the ones you wrote, except for a value the change sets. The same words (`yes`, `no`, `on`, `off`, `~`) and a key with no value (`description:`) stay as written in the lines the change does not reach, and a comment or a blank line above a line that is rewritten stays above it. A list written at the same column as its key (`tags:` then `- a` at the same column) is followed too: its items and comments stay, and an item that is added is written at the column the list uses; the comment after `[]`, `{}` or a key with no value stays on the line when a change fills the collection, and the comments inside empty brackets stay under the key. A manifest that uses a YAML anchor, an alias or a tag is not read by the editor: it is listed as unreadable and never written (see tmorin/archicode#74). When a file is laid out in a way the editor does not write (an indentation other than two spaces, for example), it is written again entirely in the editor's own layout, and its comments are lost.

[[editor-map]]
=== Map

The *Map* perspective draws the whole application layer, with no element selected. It opens folded: only the systems and solutions show, and a link is drawn between the boxes its two ends land on, so opening a box splits the links that reached it among its children.

In the tree on the left, each row has two buttons, which appear when the pointer is over the row or the row has the focus:

- *Pin* (the pin) keeps only what touches the element. Pin several to keep what touches any of them. With nothing pinned, the whole layer is drawn.
- *Hide* (the eye) leaves the element, what is inside it and their relationships out of the map.

The pinned and hidden elements are also shown as chips over the map, each removable, with *Clear all* once there are several. In the tree, rows of the elements the map does not draw are greyed. Folding the tree does not change the boxes of the map: use *Fold all* and *Unfold all* in the toolbar of the map, or the buttons of the boxes. *Hide unlinked* leaves out the boxes that no link reaches; it is in the toolbar of the diagrams of Elements too, where the element itself always stays. It is in the URL (`hide-unlinked=1`) and in a saved view.

*Center* puts the selected box in the middle at a readable size (with nothing selected on the Map: the top of the map, centered across), never below 80%, and *Fit* shows the whole diagram, however small. Fit is in the URL (`frame=fit`) and Center, how a diagram opens, is a URL with no `frame`, so a link opens the diagram framed as you left it; a zoom or a move of your own is not part of the link. *PNG* and *SVG*, in the header, download the diagram.

[[editor-inspection]]
=== The inspection panel

Beside a diagram, on the right, a panel shows the data of the selected element without leaving the view: its name and styled stereotypes, its kind, its layer, its id and reference, its description, qualifiers and tags, and the file that declares it. It is there on the *Map*, on the *Overview*, *Detailed* and *Deep* tabs of Elements (where a click on a box moves to that element, and the panel follows) and on the page of a view in the Library (where a click on a box selects it on the page only, see <<editor-stories>>); it is not on *Details* and in the edit form, which show the same things themselves. Nothing is shown, and no room is kept, while nothing is selected. The panel is resized by dragging its edge (the width is remembered; a double click on the edge gives the default back), it goes away with *Maximize*, and on the Map its *x* button deselects the element. On the Map the panel says so when the selected element is not drawn (a pin, a hidden element or a folded box leaves it out), and when it is a technology element, which the Map never draws. A click does what it did before: on the Map it selects, in Elements it moves to the element.

A click on a link of the diagram, or on its caption, selects it instead, and the panel lists each relationship the link stands for: its label, its qualifiers and its tags (`tcp-port`, `doc-exchange`...), with the element that declares it (a button: it selects that element, in the layer of the drawing, as a click on its box does) and the one it points at. What is selected is the pair of boxes the link joins, so a link that groups several relationships lists them all (and says so), a link between folded boxes names the folded end and how many elements it hides (open it to see the relationships one by one), and a link to an unknown element says it points at nothing. The links of that pair are outlined. When several links join the same two boxes, the panel says how many, and marks (with the words _Clicked link_) the relationships of the one you clicked, unless they cannot be told from the others'. The links of a diagram are one stop of the Tab key, however many there are, and so are its boxes (Tab goes from one group to the other): once on a link, the arrow keys move to the next and the previous link, in the order the diagram draws them, and Home and End go to the first and the last. Enter or Space selects the link that has the focus. The stop is where the focus last was among the links, or else the selected link, or else the first one; for the boxes it is where the focus last was, or else the selected box, or else the one in focus of the diagram, or else the first one. *x* or Escape deselects: on the Map the panel goes, in Elements the panel of the element comes back. Selecting a link changes neither the perspective nor the tab, and in Elements the element stays the one being looked at (the tree, the tabs and the URL keep it). On the Map, if the panel that appears leaves the link behind its edge, the view moves by the least it takes to show it, once; a link already in view does not move the view. The selected link is in the URL, after the other parameters of the view (`link-from=customer&link-to=shop`: the two boxes of the drawing), so a copied URL, a reload and Back or Forward bring it back, and bring the view to it if it is not in sight. Selecting a link rewrites the current entry of the history, like a zoom, and does not add one. A link the drawing does not have when the URL is opened (it was renamed, or the boxes it joins are folded differently, which the URL does not carry) is dropped, and the URL with it. The selection ends as soon as the diagram it was made on is no longer the one on screen (another perspective, Details, another element, or a drawing that no longer has the link: a fold, a pin, a facet). A click on a box does what it did before and ends the link selection. A relationship the diagram does not draw (secondary links between deployed applications, unless a facet asks for them) cannot be selected.

Since the panel takes room from the center, the header of the diagram goes to its narrower states sooner (see <<editor-header>>): resize or close the panel to give it back.

[[editor-header]]
=== The header of a diagram

The header over a diagram, on the tabs of Elements and on the Map, adapts to the width of the center panel, which is the window minus the left panel, so dragging the left panel changes it. From wide to narrow:

- *Wide*: every control shows its words.
- *Narrower*: *Show on map* (or *Open in Elements* on the Map), *Name view...*, *Add to story...* and *Maximize* show only their icon; the tooltip says what each one does.
- *Narrower still*: *Show on map* or *Open in Elements*, the *Story* buttons and the *Download* buttons (PNG, SVG) move into the menu of a "⋯" button, which closes with Escape or a click elsewhere. The facet list and *Maximize* stay in the header. The menu items work exactly like the buttons they replace.
- *Very narrow*: the header takes two rows.

[[editor-texts]]
=== The texts of a diagram

Four buttons in the toolbar of a diagram, in the group *Show*, choose what the boxes and the links say. A lit button is a text that is drawn:

- *Labels*: the caption of each link, with its qualifiers in brackets. A long caption does not run over the boxes next to it: it is broken at the spaces into lines of at most 220 pixels (about forty characters at the size of the diagram), centred on the link, and the layout leaves room for all the lines. A word that is wider than a line is cut with an ellipsis, as a name is. The qualifiers are kept in one piece as far as possible, at the end of the last line when they fit and on a line of their own when they do not: the label gives way to them rather than the other way round. They are cut only past two lines without *Wrap*, or when a single qualifier is wider than a line (then its closing bracket is kept). Without *Wrap* a caption has at most four lines, and an ellipsis replaces the end of the label. The caption is broken whether *Wrap* is lit or not, and the tooltip and the accessible name of the link always have all of it. The command line breaks the captions of its PlantUML views too, in narrower lines (PlantUML's own `wrapWidth` of 200).
- *Qualifiers*: the qualifiers of each element, after its kind, as the command line writes them: `[container: rest, public]`.
- *Descriptions*: the description of each element that does not contain others, under its kind, up to three lines.
- *Wrap*: long names, qualifiers and descriptions are broken over several lines, and the box gets taller, instead of being cut with an ellipsis. A box that contains others cuts the qualifiers of its header at any rate. The captions of the links, which are always broken, then show all their lines instead of four at most.

The diagram of an element starts with the labels and the qualifiers, as the command line draws them. The Map starts with none of them, to stay readable. Only a choice that differs from that is remembered: it is in the URL (`labels=0`, `qualifiers=1`, `descriptions=1`, `wrap=1`), and in a saved view (see <<editor-stories>>), so that a link or a step of a story draws the same texts. The tooltip of a box always has the qualifiers and the whole description, and the SVG that is downloaded is the diagram as it is on screen.

[[editor-stories]]
=== Library: stories and views

The *Library* perspective keeps what the workspace says about itself, on two sides: *Stories* (see <<stories>>) and *Views*, the named diagrams that the stories are made of. Each side has its list on the left and its page in the center, and they lead to one another: the view of a step is a link to that view, and a view lists the steps that show it. The URL says which side is open (`#/library/stories`, `#/library/views`; the former `#/stories` still opens the first). A diagram on the Map or in Elements has two buttons in its header:

- *Name view...* keeps the diagram as a view, in a file of its own (`view.<id>.yaml`): the element and the viewpoint (Elements), or what is pinned, hidden and open (Map), with the facet, *Hide unlinked* and the texts it draws. It keeps the recipe, not a picture: the view is drawn again from the model each time. A named view can be put in several stories, and generated by the command line.
- *Add to story...* puts the diagram in a story, as a step after the one being told, or at the end. A dialog asks which story (a list to pick from, or the name of a new one: a name that is already a story's is that story). The step carries its own view (no extra file), unless the diagram is one that was named: then it points at it.

While a story is being walked through, a bar over the diagram says where you are, with *Previous* and *Next*, and the words of the step, to read; *Edit text* turns them into a box to type in (it opens by itself right after *Add to story...*, so that you can write as you go). *Back to this step* draws the saved view again when you moved away from it, and *Leave story* closes the bar. A step that cannot be drawn (its element was deleted) says why in the bar, which stays: *Next* and *Previous* still work. The story is in the URL, so a link or Back lands on the same step.

On the Stories side, a story is open as soon as there is one, and edited in place: its name, its text, the order of its steps (*Up*, *Down*, *Remove*, which can be undone right away) and the words of each step. The step that is showing on the diagrams is marked. *Play* walks through the story from its first step, and *Show on diagram* draws one step. A step that carries its own view says so, and *Keep as named view* gives it a name and a file; a step whose view was deleted offers to point at another one. Renaming an element updates the views and steps that point at it. A change that is not saved yet is marked *modified*.

On the Views side, the page of a view that can be drawn draws it in the center, from the model, with the canvas and the tools of the Map and Elements: zoom, *Center*, *Fit*, *Hide unlinked*, the four texts (see <<editor-texts>>), and *PNG* and *SVG* in the header. The facet of the view is applied: it is drawn here, not picked. There is no folding on this page, since the open boxes of a Map view are part of the view. The zoom and the moves are the page's own and are not changes to the view, and the page changes nothing the Map and Elements show (selection, pins, tab, facet, texts, address). The header keeps *Open on diagram*, which draws the view on the Map or in Elements to explore it with their tools, *Rename* and *Delete*, and has *Maximize*, which hides the list of views and the right-hand panel (`M` maximizes, `Esc` restores; the Map is not touched).

The panel on the right, resized and hidden as the one of the Map (see <<editor-inspection>>), has the view first: what it draws and the file that keeps it, then a field for each attribute of the view, and the steps of the stories that show it, each a link to its story. Once something is selected, the inspection of the selection comes under it; the panel stays where it is when the top of the inspection is in sight, and otherwise scrolls by the least it takes to show its first lines, so that the fields of the view stay in sight as long as there is room. A click on a box, or Enter on the box that has the focus, selects the element and shows its panel, which has a *Show in Elements* button: it leaves the page and selects the element there, on the tab Elements was left on. A click on a link or on its caption shows the relationships it stands for, and the elements named in that panel select on the page too. The selected box is outlined, and *x* or `Esc` deselects. A box for a relationship that points at nothing cannot be clicked here. This selection is the page's own: it does not select anything on the Map or in Elements, it is forgotten when another view is shown, and it is not in the URL, which carries no more than `#/library/views?view=<id>`.

[[editor-view-edit]]
A view is changed by its fields, and the diagram follows at once:

- *Viewpoint*: *Overview*, *Detailed*, *Deep* or *Map*. From an element viewpoint to the Map, the element becomes the pinned element (a technology element gives none: the Map draws the application layer); from the Map to an element viewpoint, the first pinned element that still exists becomes the element, and the hidden and open elements are dropped. What the view showed of the texts is kept. *Cancel* gives the change up as long as it has not been saved.
- *Layer* and *Element* (the element viewpoints): the element is typed, with the references of the layer as suggestions, and applied with `Enter` or by leaving the field. A reference that is not an element of the layer is refused, with the reason under the field, and stays there to be corrected. Changing the layer keeps the element when the other layer has it, and otherwise leaves the view without one: it then says so and cannot be drawn until one is chosen.
- *Pinned*, *Hidden* and *Open* (the Map): each is a list of elements, with a cross to take one out and a field to add one (`Enter`). The drawing of this page is not edited itself, on purpose: a click on a box selects it. To choose pins by clicking, use *Open on diagram*.
- *Facet*: the facets of the workspace, or none. *Hide unlinked*, *Labels*, *Qualifiers*, *Descriptions* and *Wrap* are boxes to tick, and they are the same as the buttons of the tools over the diagram. A text that is what that kind of diagram draws by default is not written to the file, as for any view.

Nothing is written to the disk by an edit. The view gets the mark *modified*, in the header and in the list, and loses it when what you did is put back, as soon as the file of the view would be the one on disk (the last one written); *Save all changes* writes the file of the view and no other (the comments and the layout of the file stay, as for any manifest; a property that an edit takes out and puts back again is written where the editor writes it, element, facet, *Hide unlinked*, then the texts), and *Cancel* gives every unsaved change up: the view, and the diagram with it, are the saved ones again. A view that an edit left impossible to draw (no element, nothing that was pinned exists) says why in the center, with the same fields to correct it, and can still be saved. Renaming an element in Elements still rewrites the views that point at it; the steps of the stories point at the view, so they show the edited view, saved or not.

A view that cannot be drawn (its element was deleted, nothing that was pinned exists any more, the viewpoint is unknown) keeps its message, what it draws, its fields and its steps in the center of the page, with no diagram and no panel.

A story is a file (`story.<id>.yaml`) in the first manifests folder, and so is each named view. They wait in memory, like the other changes, with a mark on the file, for *Save all changes*, and *Cancel* gives them up: only the files that changed are written. When an older workspace still has views or stories in `workspace.yaml`, the Library says so, on both sides, with *Move to manifests*. The Map of a technology layer does not exist: to tell about environments, use views of Elements on the environments or the nodes.

[[editor-facets]]
=== Facets

The facets of the workspace (see <<facets>>) are in a list in the header of the diagrams: the diagram is then drawn as the command line generates it for that facet, with the relationships the facet removes left out, and the elements it removes, with the relationships that pointed at them. In the tree, the elements the facet leaves with nothing to draw are greyed. The facets themselves are edited in the *Settings* perspective, along with the other settings of the workspace (see <<technical-configuration>>).

[[editor-workspace-name]]
=== Name of the workspace

A workspace can have a name, the optional `name` key of its `settings` (see <<workspace>>). *Settings* has a section, *Workspace*, with a *Name* field. Unlike the theme below, the name is a setting of the workspace: it is written to `workspace.yaml`, so it counts as a change to save and lights *Save all changes*.

When the workspace has a name, the editor shows it at the top left of the window, in place of the name of the folder, in the title of the page, in the <<editor-folders,list of remembered folders>> and in the "Opening" messages, which use the name the workspace had when its folder was last opened; the name of the folder is then the tooltip of the name. Without a name, or with a blank one, the editor shows the name of the folder, as before, and an emptied *Name* is left out of the file.

[[editor-plateaus]]
=== Plateaus

When the workspace lists `settings.plateaus` (see <<plateaus>>), the header of the editor has a *Plateau* selector, a group of buttons like the one of the perspectives, in the order of the file: the pressed button is the plateau that Elements, the Map, the Library and the diagrams show. The editor opens the plateau that `settings.current` names, else the last of the list; the plateau you choose is remembered by this browser for this folder (like the sizes of the panels, not in the workspace), and is the one it opens next time as long as the workspace still has it. The buttons show the name of each plateau and its `horizon`, and a tooltip gives its id and its folder.

Choosing another plateau reads its folder from the disk, so the editor asks first when something is not saved. The editor opens the folder of `workspace.yaml`, and that one folder covers every plateau below it: a manifest is saved into the folder of the plateau it was read from, and a new element is written to the folder of the plateau that is drawn. *Settings* lists the plateaus in place of the folders of the manifests: they are written in `workspace.yaml`, and `archicode plateau add` (see <<plateau-add>>) adds one. A save of the settings leaves `plateaus` and `current` exactly as they were written, comments included, and does not add `manifests.paths`.

A `workspace.yaml` that breaks a rule of the plateaus, or a `manifests.paths` that leaves the folder, is not opened: the editor shows the same messages as the command line. A plateau whose folder does not exist is drawn empty, and the header says so.

[[editor-compare]]
=== Comparing two plateaus

With two plateaus or more, the header has a *Compare to* list next to the *Plateau* selector. *Nothing*, the default, draws the plateau alone, exactly as the editor always did. Choosing another plateau draws the plateau together with it: the Map, the diagrams of Elements and the page of a view in the Library tell what is new, what changed and what was removed (and, for the elements that say what they replace, what moved, was split or merged, see <<editor-replaces>>) compared with that plateau, with the same states as `archicode views generate --baseline` (see <<plateau-comparison>>). After *Nothing* the list offers *Baseline: <name>*, the baseline of the plateau that is drawn by the rule of the command line (its `baseline` key, else the plateau before it in the list; the first plateau has none), which follows the plateau when you choose another one, and then each other plateau by name. Like the plateau, the choice is remembered by this browser for this folder (not in the workspace), and it is ignored when the workspace no longer has that plateau. A plateau is never compared with itself: when you choose the plateau that was the baseline, the comparison is *Nothing* until you choose another one, and comes back when you leave that plateau.

The plateau compared with is only _read_. The editor reads its folder through the same folder it has opened (no second picker to use), keeps it apart from the plateau that is drawn, and never writes it: its files are not among the files of the plateau, are never counted as modified, and are not part of *Save all changes* or *Cancel*. It is read when you choose it and when you choose another plateau; *Reload*, next to the list, reads it again from the disk, which is the only way to see a change made to that folder while the page stays open. A reference declared twice in it is reported the way it is for the plateau itself (the diagram says that nothing is drawn, and names both files), and a folder that does not exist is said in the header and compared as empty. A `baseline` key that names an unknown plateau, or the plateau itself, is refused when the workspace is opened, with the message of the command line (see <<plateaus>>).

The diagram is drawn from the union of the two plateaus, and the boxes are laid out on that union: what was removed is drawn where it was, so a box does not move when the comparison is turned on from the other plateau or when you choose the other plateau of the pair (with *Nothing* the plateau is laid out alone, as before). The editor tells the states without relying on colour: each one has a mark in front of the title of the box and of the caption of the link, a line style, and a pill with its name on the box.

[cols="1,1,2,2"]
|===
| State | Mark | Box | Link

| new | `+` | thick solid outline, a pill `new`, a green tint | thick solid line
| changed | `~` | dotted outline, a pill `changed`, an orange tint | dotted line
| removed | `−` | long dashes with narrow gaps, grey outline, grey struck title, a pill `removed`, a grey tint | dashed grey line
| contains changes | `±` | thin dashed outline, a pill `contains-changes` | (none)
| moved | `→` | long dashes with wide gaps, a pill `moved`, a blue tint, `(from shop.till)` after the title | (none)
| split | `⋔` | medium dashes, a pill `split`, a purple tint, `(from shop.report)` after the title | (none)
| merged | `⊕` | short dashes far apart, a pill `merged`, a light blue tint, `(from stock.bin, stock.shelf)` after the title | (none)
|===

The last three states are for the elements that say what they replace, and exist only for a box: a relationship is never moved, split or merged. They are in the table above and in the key only when the drawing has a box in that state.

A box that did not change is drawn as it always was. A removed element is not in the plateau that is drawn, so it is not in the tree and a click on its box does not open it: it shows, in the panel on the right, what the other plateau had (name, kind, properties, the file it is in, the relationships it declared), read-only. A link that changed shows its mark even when the captions are off, as on the Map. The marks and lines are the ones of the command line (a dash and a gap of its own for `removed` 16-3, `moved` 12-12, `split` 8-8 and `merged` 3-9 in both, so that no two of them are alike); the colours are only a help, chosen to read in the light and the dark theme. *Red dashed* keeps its meaning of a dangling reference (an unknown element), and is never used for a removed one.

The look is a default, given to the stereotype of the same name as the state (`new`, `changed`, `removed`, `contains-changes`). A style of your own for that name in `styles` (see <<stereotypes-and-styles>>) wins property by property: your `line-color` replaces the colour of the line and keeps its style and thickness, your `background-color` fills the box and replaces the tint, your `font-color` replaces the grey of a removed title. The state is the last stereotype of a box, so it overrides the style of the others, as a later stereotype always does. A `new` or `changed` tag that you wrote by hand on an element that does not have that state is only your stereotype, with your own style if you gave it one, and the command line draws it the same way (see <<plateau-state-tags>>).

Under the diagram, the key adds an entry for each state the drawing uses, with a sample of its box and its link, its mark, its name, how its line is drawn, and how many boxes and links of that state the drawing shows. The SVG and PNG downloads draw the same marks, lines, struck titles, pills and tints; like the other keys, the key itself is not part of the image.

[[editor-changes-panel]]
==== The Changes panel

While a comparison is on, the panel on the right of the Map and of Elements is never empty. With nothing selected it is the *Changes* panel; with something selected it has two tabs, *Selected* (what is selected, as before) and *Changes* (with the number of rows). It is not in the page of a view in the Library, whose panel is the one of the view.

The panel starts with the counts: elements and relationships, each _new_, _changed_ and _removed_, as chips that carry a mark and a word (`+ 38 new`, `~ 26 changed`, `− 5 removed`), so that they read without colour; the elements add `→ 1 moved`, `⋔ 2 split` and `⊕ 1 merged` when there are some. The same chip is the state on every row below. Two lists follow, *Elements* and *Relationships*, in the order a review reads them: what is new, then what changed, then what moved, was split or merged, then what was removed, and by reference inside each. A row has the chip, the name and the reference of the element (a relationship reads `source → destination “label”`) and, for something that changed, what changed in it in words: `name`, `description (wording only)`, `qualifiers`, `tags`, `deployment`, `relationships added`, `relationships removed`, `relationships changed`, and for a relationship `label`, `qualifiers`, `tags`. A relationship whose label changed is one row that says the label before and after. A row of a moved, split or merged element says where it came from (`from shop.till`, `from shop.report; split with shop.report-b`), as `archicode diff` does.

A click on a row selects the thing as a click on its box or its link does, and shows it. On the Map the boxes around it are opened so that it is drawn, and the view is centred on it (what the *Center* button does); a pin or a hidden element of your own is not undone, and the panel says when the element is not on the map. A removed element opens the read-only panel described above, a relationship selects its link (in Elements, the element that declares it, and its link when that element's diagram is shown). The row of the selection is marked in the list, and the *Changes* tab brings the list back with that row in view.

[[editor-what-changed]]
==== What changed

The panel of a selected element, link or removed box adds a *What changed* block, first, so that a long description does not push it out of sight; it is the same on the page of a view in the Library.

- For a *changed* element, the natures in words, then each property that differs with its value _Before_ and _After_ (name, kind, description, qualifiers, tags, and the applications or `uses` of a node), then its relationships that are new, changed or removed, each a line with its chip. The *Before* and *After* lines carry a sign and a word, and the old value is struck, so nothing relies on colour.
- For a *new* element, "Whole element is new": its properties are the ones listed below the block, and the relationships it declares are listed as new.
- For a *removed* element, the read-only panel above, with "Whole element is removed"; it does not repeat what the panel already lists. A removed element that is only drawn as the place of what was inside it, and that other elements replace, adds _Replaced by_ and lists them.
- For a *moved*, *split* or *merged* element, one sentence that says which, then _Replaces_ with the name and the reference of each element it replaces (one that the other plateau does not have is flagged), then, if the element also changed, _Also changed_ and the properties _Before_ and _After_ as above.
- For a *link*, its state (all of the relationships it groups new, or removed, or changed, or a mixture, which reads _changed_) and, on each relationship it groups, its chip and, for one that changed, what it was and what it is.

[[editor-changes-only]]
==== Changes only and wording-only changes

Next to *Compare to*, while a comparison is on, the group *Everything | Changes only* sets what the diagrams draw: with *Changes only* a diagram keeps what is new, changed or removed, the boxes that enclose them and the ends of the changed links; the links that did not change are left out. The boxes kept only to place the changes, the _context_, are drawn faded, say no state and are told in the key ("context, faded: shown to place the changes", with their number). The focal element of a diagram always stays and is never faded. It works the same on the Map, on the diagrams of Elements and on the page of a view in the Library, and together with the pins, the hidden elements, a facet and *Hide unlinked*.

A change of the description alone is a change of wording, not of structure. The *Changes* panel counts them apart ("10 of the changed elements are changes of wording only") and keeps them visible by default; the checkbox *Hide wording-only changes* sets them aside in one click: those elements are drawn as unchanged (and a box that only they changed is no longer marked `contains-changes`, nor kept by *Changes only*), their rows leave the list, the counts of changed elements drop by their number and the panel says "10 wording-only changes hidden". Relationships are never set aside: a change of a label, a qualifier or a tag is structure.

Both choices are yours and not the workspace's: they are remembered per folder in this browser, like the plateau and *Compare to*, never written to `workspace.yaml`, and they do nothing while *Compare to* is *Nothing*.

[[editor-changes-address]]
==== The address and the trees

The address of the page carries a selection, so that a reload or a shared link reopens it: `ref=` for an element, `link-from=` and `link-to=` for a link, as before, and `removed=` for a removed element (`removed-layer=technology` for one of the technology layer). A removed element exists only next to its comparison, so the address then also carries `compare=` (`@baseline` or the id of a plateau): opening such an address chooses that comparison, as if you had chosen it, even if this browser remembered another one. The other choices of the comparison are not in the address.

While a comparison is on, a row of the tree of Elements and of the tree of the Map has a small mark after its name: `+` for a new element, `~` for a changed one, `→`, `⋔` or `⊕` for a moved, split or merged one, and `±` for one that did not change but has a change below it. The word is in its tooltip and is read by a screen reader. A removed element is not in these trees (it is not an element of the plateau drawn, so it can be neither pinned nor hidden nor edited): the *Changes* panel lists it and opens its panel.

[[editor-replaces]]
==== Moved, split and merged elements, and candidates

An element of the plateau that is drawn can say which elements of the plateau it is compared with it replaces: the key `replaces` (see <<plateau-replaces>>). The editor draws the result with the three states above, counts them and lists them in the *Changes* panel, and the *What changed* block of a moved, split or merged element says what it replaces. A replaced element is not listed as removed. The *Changes only* filter keeps these elements like the others. The hand-written tags still follow the rule of <<plateau-state-tags>>: the look of `moved`, `split` or `merged` is only for a box the comparison says is in that state.

*Candidates.* Under the counts, the *Candidates* section lists the pairs the comparison takes for one thing said twice: an element only the other plateau has, and an element only this one has, of the same kind and the same layer, with the same name (when no other removed and no other new element of that kind has it), a close description, or as the only two of their kind under the same parent, and each with its reasons. Unlike `archicode diff`, which lists them only for a plateau that already uses `replaces`, the editor proposes them for any comparison: it is how an author starts. A candidate is never applied by itself. Each pair has two buttons:

* *Write replaces* adds the reference of the removed element to the `replaces` of the new one, in the manifest of the plateau that is drawn, and nothing else. It is an edit like the others: the file is marked as modified and written by *Save all changes*, the lines you did not touch (comments, blank lines, quotes) stay as they are, a list that was there gets the reference appended once, and a list written on one line (`replaces: [shop.till]`) becomes a list on several lines. The comparison is made again at once, and the new element is now `moved`, `split` or `merged`.
* *Not related* sets the pair aside. It is remembered by the page only, until you close it: nothing is written and the comparison is not changed. The section says how many pairs are set aside, and *Show again* brings them back.

Only the plateau that is drawn is written, and the plateau compared with never is. *Write replaces* is refused, with the reason in the panel and nothing written, when the new element is not an element of the plateau drawn (it belongs to the plateau compared with, which is read-only), when the plateau drawn comes _before_ the one it is compared with in the list of plateaus (`replaces` goes on the more recent plateau: draw that one and compare it with the older), when the replaced element is still in the plateau drawn, or when the `replaces` of the element is not a list.

*By hand.* The edit form of an element has a *Replaces* section as soon as the workspace has several plateaus: the list, each reference with a button to remove it, and a field to add one (it completes with the references of the plateau compared with). A reference the plateau compared with does not have is accepted and flagged ("not in “Base”", with the name of that plateau), because you may have written it for another baseline; one that the plateau drawn still has is flagged "still in this plateau: ignored". An element cannot replace itself, and a reference is listed once. The details of an element that replaces something list it too.

*Warnings.* What the comparison ignored in the `replaces` it was given (see <<plateau-replaces-warnings>>) is a short list in the *Changes* panel, under the candidates, with the sentences of the command line; the editor does not write them to the console. A second list, *Hand-written states*, has one line per element and word for the state words you wrote by hand that the comparison does not give to the element (see <<plateau-state-tags>>), with the sentences of the command line, and the panel of such an element says it too, so that a box with a `new` badge that is not drawn as new tells why.

*Moving an element.* An element that you put under another parent in the editor has another reference: *Move and write replaces* writes the `replaces` for you, for the element and for each element inside it (see <<editor-move>>).

[[editor-move]]
==== Moving an element under another parent

In the edit form of an element, *Move* (after *Delete*, before *Add child*) puts the element, and everything inside it, under another parent, without breaking a reference. It is offered for the elements that can have a parent: a system, a container, a component, a group, a node. A solution, a person or an environment is never put under anything, and has no *Move*; a system can go under a solution, and has no *Move* when the workspace has none. It works on the plateau that is drawn, and never on the one it is compared with, which is read-only.

The dialog has a search field (it keeps the parents that have every word you type in their name, id, reference or kind) and the list of the *valid parents*, in the layer of the element: an element that may hold the kind of this one (the rules that create an element under a parent: a system holds containers and groups, a container holds components and groups, an environment or a node holds nodes), but not the element itself, nor anything inside it, nor the parent it already has, nor a parent that already holds an element with the same id. It says how many elements follow, how many references will be rewritten in how many files, and how many saved views follow.

*What follows.* The reference of the element becomes the reference of the new parent followed by its id, and so does the reference of each element inside it. Every reference to the element or to something inside it is rewritten, in every file of the workspace, by the machinery of an id change:

* the `destination` of the relationships of any element of the same layer;
* the `applications` of the nodes of the technology layer (for an application element) and the `uses` of the environments (for a technology element);
* the `header.parent` of the manifests attached to the element or below it;
* the saved views and the steps of stories of the workspace (the `element` of a view, the pinned, hidden and open elements of a Map view);
* what the page remembers: the selection, the unfolded rows, the modified marks, the pins of the Map.

The facets (their JSONPath is not a reference) are not read, as when an id changes. Nothing else of a file is touched.

*What is written.* How a move is written depends on how the manifest holds the element, and the lines that are not part of it stay as the author wrote them (comments, blank lines, quotes), as for any other edit:

* An element that has a manifest of its own (`app.shop.till.yaml`, with its `header.parent`) stays in its file: only the `header.parent` line changes, and the manifests attached below it follow by their own `header.parent`. The new parent can be in any file.
* An element that is nested in the manifest of another one (in its `content.elements`) is moved as a block inside that manifest: its lines, with the comments just above it and those at the end of its lines, go to the `elements` of the new parent, one level deeper or shallower, and the `elements` it leaves is dropped when it was the last element. The new parent has to be in the same file. A parent in another file would mean cutting the block out of one file and pasting it into another, which the editor does not do: the dialog says how many parents it leaves out for that reason, and the move is refused if you ask for one. Give the element a manifest of its own first, or move it by hand. The comments on lines of their own inside the block go with it. A comment after the last line of the block, before the next element, is the next element's and stays where it was.

*Replaces.* When the workspace has plateaus and a comparison is on (see <<editor-compare>>), the dialog has two buttons: *Move and write replaces* and *Move only*. The first also writes `replaces` (see <<plateau-replaces>>) in the same edit, on the moved element and on each element inside it, each naming its old reference: the comparison then reads one moved element with what it holds, not a removed element and a new one for each. Without the key on the children, a container that moved would be `moved` and its children `removed` and `new`. An element that the plateau compared with does not have (it was added in this plateau) gets none, and the dialog says how many. Without a comparison, or with a plateau compared with that comes after the one drawn, the dialog offers *Move* alone and says why `replaces` is not offered (see <<editor-replaces>>). In a workspace without plateaus there is no mention of it. The key is written to the manifests like the rest of the move; it is a normal edit, so the comparison is made again at once.

*A move that is refused* changes nothing at all, and the reason is told in the dialog, which stays open with what you chose: the new parent is the element or something inside it, it is its parent already, it cannot hold that kind, it already holds an element with that id, the element or the parent is declared twice or belongs to the plateau compared with, a manifest cannot be read (a reference in it could not be rewritten), a reference is written as a number (`destination: 8080`) and cannot be rewritten as the reference of another element, a nested element is asked to go to another file, or (with *Move and write replaces*) an element has a `replaces` that is not a list.

Like every edit, a move is not written until *Save all changes*, and *Cancel* gives it up with the others (the folder is read again). The files it changed are marked as modified, and so is the moved element.

[[editor-theme]]
=== Theme

The editor is drawn in a light or a dark theme. By default it follows the one of the operating system. *Settings* has a section, *Appearance (this browser)*, to choose *Light*, *Dark* or *System* instead: the choice applies at once, to the page, the code editors and the SVG and PNG exported from a diagram.

The choice is a preference of the browser, not of the workspace. It is remembered by the browser alone (nothing is written to `workspace.yaml` or to any file of the folder), it is not a change to save, and it does not light *Save all changes*. A browser that refuses to remember it keeps the choice until the page is closed.

[[errors-and-warnings]]
=== Errors, warnings and exit codes

Every command speaks on its error output in the same way, and keeps its standard output for what it produces (the files it announces, a table, a graph), so that `archicode diff > changes.txt` or `archicode query graph | jq` never mixes the two.

*Errors.* When a command cannot do what you asked, it prints one line for each problem on the error output, starts it with `error: ` and exits with the code 1. It prints no stack trace. The line says what is wrong and where, for instance:

----
error: dangling reference: payments
error: unknown plateau `nope`: the plateaus of this workspace are `as-is`, `to-be`
error: `manifests/shop.yaml` is not valid: the value has the wrong shape (found an array) at `header` (line 1, column 9)
error: the workspace file `/work/workspace.yaml` does not exist (`-w` names another one)
----

An option that does not exist or a missing argument is a usage error: the command prints the problem and how to use the command, as it always did, and exits with the code 2. A failure that nobody expected, a bug, prints `error: unexpected ...` and keeps its stack trace, because a report needs it; the exit code is 1.

*Warnings.* A warning says that the command went on but that something is probably not what you meant. It is one line starting with `warning: ` on the error output, printed when the command has done its work (and before the error, if it fails), once for a sentence the command would say many times. The log is not where to look: the log level of the application is `ERROR`, which hides the warnings of the log. A warning does not change the exit code. The command line warns of:

* a facet written in the old dialect (`anyof`, `noneof`, `== null`): it is rewritten, and the warning gives the standard form (see <<facets>>);
* a step of a story that names a view nobody declares;
* a view of a viewpoint that the command line does not generate (the map is drawn by the editor), skipped by `views generate --view`;
* what a comparison ignored in the `replaces` of a plateau, with `archicode diff` and `archicode views generate --baseline` (see <<plateau-replaces-warnings>>);
* a state word you wrote by hand on an element, where it disagrees with the comparison (see <<plateau-state-tags>>).

A command that has nothing to warn of prints nothing on its error output. Nothing here makes a warning fail a command: the exit code tells whether the command did its work.

[[serve-the-editor]]
=== Serve the editor

.Serve the editor - The command line
[source,shell]
----
archicode editor serve
----

Serves the editor (see <<editor>>) and opens in it the folder of the workspace file, which must be named `workspace.yaml`. The command prints a URL, `http://127.0.0.1:48080/?token=...`: open it in a browser (the page is refused without the token; the editor removes it from the address bar, and a session cookie, which opens the page only and never the API, lets a reload in).

- `--port` (`-p`): the port to listen on, `48080` by default.
- `--host`: the address to bind to, `0.0.0.0` by default, which a Docker `-p` mapping needs.
- `--allowed-host`: a host name, besides `localhost`, `127.0.0.1` and `[::1]`, that a request may be addressed to. Repeat it for several.

The server writes to the folder, so it does not trust the network: the page and every call carry a token that only the printed URL gives, a request must be addressed to one of the allowed host names, a page of another origin is refused, and only the `.yaml`, `.yml` and `.json` files below the folder of the workspace can be reached. With Docker, keep the host side of the port mapping on `127.0.0.1` (`-p 127.0.0.1:48080:48080`).

[[generate-views]]
=== Generate views

.Generate Views - The command line
[source,shell]
----
archicode views generate --help
----

// - The command Generate View triggers the generation of views.
// - By default, the command discovers all possible views based on the elements of the Application Layer and the Technology Layer.
// - By default, the command generate Views for all available Viewpoints.
// - By default, the command generate Views with the built-in Renderer based on Plantuml.
// - By default, the command generate Views in a folder named views in the workspace folder.

// - The command can be customized to render only a given set of views based on their ViewId.

// - The command can be customized to render using a given Renderer Engine.

// - The command can be customized specifying custom View properties.

The "Generate Views" command within ArchiCode serves as a dynamic catalyst for creating comprehensive architectural views. This command is designed to efficiently produce visual representations of your architecture, aiding communication and understanding. Here's a comprehensive breakdown of its functionality:

- Triggering View Generation: The "Generate Views" command is the key that unlocks the process of generating architectural views. Upon invocation, ArchiCode springs into action, initiating the creation of visual artifacts that encapsulate your architectural design.

- Default Behavior: By default, this command leverages the power of discovery. It automatically identifies and generates views based on the elements present within both the Application Layer and the Technology Layer of your architecture.

- Inclusive Viewpoint Generation: The default behavior extends to encompass all available viewpoints. This means that ArchiCode generates views for a comprehensive range of architectural perspectives, enabling a holistic portrayal of your design.

- Built-in Renderer Integration: By default, the "Generate Views" command uses the ArchiCode's Plantuml Renderer. This integration ensures that the generated views are easily understandable and sharable.

- Organized Output: By default, the command orchestrates the organization of generated views within a dedicated "views" folder, nested within your workspace folder. This structured arrangement enhances clarity and enables efficient access to your visual representations.

The command offers also customization Capabilities:

- Plateau: when the workspace lists plateaus (see <<plateaus>>), `--plateau <id>` chooses the one that is read. Without it, it is the plateau `settings.current` names, else the last one. The views of a plateau are written in a folder of its own, `views-<plateau>` (and one folder per facet, `views-<plateau>-<facet>` with the default `directory-name-template`); a workspace without plateaus writes `views` as it always did.

.Generate Views - Plateau
[source,shell]
----
archicode views generate --plateau to-be
----

- Comparison: `--baseline <id>` compares the plateau with another one (see <<plateau-comparison>>). The command then writes the plain views of the plateau, as above, and in addition the views of the comparison, which draw what is new, changed and removed. They are written in `views-<plateau>-vs-<baseline>` (and one folder per facet, `views-<plateau>-vs-<baseline>-<facet>`), next to two files that tell the same in text: `gap.md` and `gap.json`, the table of changes that `archicode diff` prints (see <<diff>>), with the elements that moved, split or merged and the candidates (see <<plateau-replaces>>), and the same warnings about `replaces` on the error output. A workspace that sets `settings.facets.global-enabled: false` has nothing but these two files in `views-<plateau>-vs-<baseline>`: its views are in the folders of its facets. A plateau that has a `baseline` key is compared without `--baseline`; a plateau that has none is not, even though the plateau before it is its baseline for `archicode diff`, because a comparison doubles the number of views, and so about the time it takes (a workspace of 3,400 views goes from about 40 to about 90 seconds), and is not generated by surprise. An unknown baseline, or `--baseline` on a workspace that has no plateaus, stops the command before anything is written. `--output` is, with plateaus, the beginning of the name of these folders.

.Generate Views - Comparison
[source,shell]
----
archicode views generate --plateau to-be --baseline as-is
----

A facet applies to the views of a comparison as it does to the others, and a facet can select on `change` (see <<plateau-comparison>>).

- Selective View Rendering: The power of customization lies in your hands. The command can be tailored to render specific views based on their unique identifier, providing you with control over the scope of generated visualizations.

.Generate Views - Selective View Rendering
[source,shell]
----
archicode views generate --view-id=view_a  --view-id=view_b
----

- Renderer Engine Flexibility: You have the freedom to opt for a preferred Renderer Engine. The command allows you to specify a particular engine, aligning the rendering process with your architectural preferences.

.Generate Views - Renderer Engine Flexibility
[source,shell]
----
archicode views generate --engine=kubernetes-network-policies
----

- Fine-Tuned View Properties: Further customization extends to individual view properties. ArchiCode empowers you to specify custom properties, ensuring that the generated views align precisely with your architectural objectives.

.Generate Views - Fine-Tuned View Properties
[source,shell]
----
archicode views generate --properties='{ "key" : "value" }'
----

*The same workspace gives the same files.*
Generating the views of a workspace twice gives the same files, byte for byte, so that a workspace kept in git only shows a change when the workspace changed.
This does not depend on the folder the workspace is in, on the order a file system lists the manifests in, on the JVM that runs the command, nor on the order in which the author wrote the elements of a list, the relationships of an element or its tags.
Inside a file, the boxes come by reference and then by identifier, the links by their ends, their label, their qualifiers and their tags, and the styles by the name of the stereotype.
What the author writes in an order keeps it: the qualifiers of an element and the words of `rendering-stereotypes` are the order of the stereotypes of its box (see <<stereotypes-and-styles>>), so reordering them is a change of the workspace.
Only a new version of ArchiCode rewrites files that the workspace did not change: the order of the stereotypes of a box changed in 0.10.0 and in 0.11.0, and the order of two links that only differ by the node they end on changed in 0.12.0 (it used to depend on the JVM).
A test (`DeterministicGenerationTest`) generates a workspace twice, with the manifests, the elements, the relationships and the tags declared in the reverse order and in another folder, and compares the files.

=== Query views

.Query Views - The command line
[source,shell]
----
archicode query views --help
----

// - The command Query View is designed to filter views and customize output format.
// - The filtering leverage on JSON Path to deeply query the View model.
// - The command supports the output formats: YAML, TOML, JSON and custom.
// - The custom output format expects a template given as option of the command line.
// - The template engine is Velocity and the filtered data can be accessed with JSON Path.
// - By default, the command doesn't apply any filtering or formatting.

The "Query Views" command within ArchiCode offers a versatile toolkit for precise exploration and customization of architectural views. Here's an in-depth look at the capabilities and features of the "Query Views" command:

- Default Behavior: As a testament to flexibility, the "Query Views" command, by default, refrains from applying any filtering or formatting. This ensures that you have the freedom to explore your architectural views without any predetermined constraints.

- Focused Exploration: The essence of the "Query Views" command lies in its ability to fine-tune your exploration. Designed with precision in mind, this command empowers you to filter and tailor your view output according to your architectural inquiries.

The command offers also customization Capabilities:

- Plateau: like `views generate`, the command takes `--plateau <id>` to choose the plateau that is read (see <<plateaus>>); so does `query graph`.

- Dynamic Filtering: The command harnesses the power of JSON Path, enabling you to apply intricate filters that delve deep into the View model. This dynamic filtering mechanism facilitates targeted extraction of specific architectural insights.

.Query Views - Dynamic Filtering
[source,shell]
----
archicode query views -q '$.[?(@.viewpoint=="deep")]'
----

- Customizable Output Formats: ArchiCode's "Query Views" command extends flexibility by supporting various output formats, including YAML, TOML, JSON, and a customizable option. This ensures that your extracted data aligns seamlessly with your preferred format.

.Query Views - Customizable Output Formats
[source,shell]
----
archicode query views -f toml
----

- Template-Based Customization: The command's customizable output format integrates a template-based approach. By leveraging the Velocity template engine, you can define specific output structures tailored to your architectural needs.

.Query Views - Template-Based Customization
[source,shell]
----
archicode query views -f custom -t '$d.e("$.[*].id")'
----

- Sorted Output: the views come sorted, by identifier and then by layer (application before technology), in every output format and before the JSON Path query is applied, so that `$.[0]` is always the same view. Two runs, on the same machine or not, and two builds of the same version give the same output byte for byte, which lets you diff it or keep it in git. Before 0.14.0 the order of the views was not defined and changed from one build to another; the set of views did not. The order of your scripts' results changes once, when you upgrade; if a script relies on the position of a view, select it by its `id` instead.

- TOML Output: a TOML document is a table, so `-f toml` writes the list of views under the key `views`, as `views = [{ id = '...', ... }, ...]`; a JSON Path query that selects one view writes that view as a table, and one that selects anything else (a list of identifiers, say) is written under `views` too. Before 0.14.0 the list was written as an assignment without a key, which no TOML parser reads. The TOML output changes once, when you upgrade; the YAML, JSON and custom outputs did not change.

[[plateau-add]]
=== Add a plateau

.Add a plateau - The command line
[source,shell]
----
archicode plateau add to-be-2028 --from to-be --name "To be 2028" --horizon 2028-Q1
----

Adds a plateau to the workspace: the folder of the plateau `--from` is copied (all of it, sub-folders included) into a new folder, and the new plateau is appended to the end of `settings.plateaus` in `workspace.yaml`. The file is edited where the list is, by inserting the lines of the new plateau in the style of the ones that are there: its comments, the order of its keys and its layout stay as you wrote them. The command stops, and writes nothing, if the file cannot be edited that way (a `plateaus` list written on one line, for example) and says so.

- `--from`: the id of the plateau to copy. Required. A workspace with no `settings.plateaus` has nothing to copy from: list its folder as the first plateau by hand.
- `--name` and `--horizon`: the optional `name` and `horizon` of the new plateau.
- `--baseline`: the id of a plateau of the list that the new plateau is compared with. It is written as the `baseline` of the new plateau (see <<plateau-comparison>>). Without it nothing is written, and the new plateau is compared with the plateau before it, which is the one it was copied from when that one was the last.
- `--path`: the folder of the new plateau, below the folder of the workspace (the rules of the `path` of a plateau apply). By default the new folder is next to the copied one and named after the id. When the copied folder starts with a number, as `plateaus/10_as-is`, the new one gets the next multiple of ten above the highest number among the plateau folders that share its parent, so `plateaus/10_as-is` and `plateaus/20_to-be` give `plateaus/30_to-be-2028`; a folder with no number gives a folder with none. The number only sorts the folders; the order of the list is the one that counts.
- The command refuses an `id` that exists, a folder that exists already (nothing is ever written over), a folder inside the copied one, and the plateau `.`.

- `--baseline`: the plateau it is compared with: the one named, else the `baseline` key of the plateau, else the plateau before it in the list (see <<plateau-comparison>>).
- `--format` (`-f`): `text` (the default; its lines are as long as the longest reference, several hundred characters on a large workspace, so read them with `less -S` or take `markdown`), `markdown` (a table to paste in a pull request) or `json` (the counts and one object per change, with `before` and `after` for a changed element).
- `--no-wording`: leaves the elements whose description is the only thing that changed out of the table, and says how many are left out. The counts still include them. It changes nothing to the elements that moved, split or merged, nor to the candidates.

The table lists the elements, then the relationships, sorted by layer and reference (the reference of an element that moved, split or merged is its own, not the one it replaces): the same output for the same two plateaus, byte for byte, whatever the machine.

*When elements replace others.* The table above, of the example of the manual, has them already (see <<plateaus-overview>>). A second invented workspace, the warehouse of `src/test/resources/plateau-comparison/replaces` in the source repository, has a till that moved to the stock system and was renamed, a report that was split in two (and its chart, which nothing replaces, so it is removed), a bin and a shelf that were merged into a place, a mailer that was rewritten as a postman without a word about it, and a `replaces` that names an element the baseline never had. `archicode diff --plateau after` prints:

comparing after with before

replacing     1 moved, 2 split, 1 merged
relationships +0 ~0 -0
wording only  0 of the 0 changed elements

- The first line is a warning, on the error output; the rest is the table, on the standard output.
- The `replacing` line, and in the Markdown form the line "Replacing elements: ...", exist only when an element replaces another. The elements that replaced others are in the `replacing` counts and not in the `new`, `changed` or `removed` ones, and the elements they replace have no row and no count: they are not removed.
- The details of a row begin with `from` what the element replaces, then its name, then what differs from what it replaces (`name: "Till" -> "Cash desk"`), and for a split the other elements that replace the same one.
- The candidates are listed after the table, marked _not applied_: write `replaces` on the element in the `TO` column to accept one (see <<plateau-candidates>>). The mailer and the postman are still removed and new.
- In JSON, a row of an element that replaces others has a `replaces` list (the references, sorted), the counts of `elements` have `moved`, `split` and `merged` when there are some, and `candidates` is a list of `layer`, `from`, `to`, `reasons` and `"applied": false`. In Markdown, the candidates are a section, `## Candidates, not applied`.
- The relationships of a split element are not compared with the baseline (which half would own them is a guess), so those of the halves, and those that end on a half, read as new. When there are some, the header has a line `of a split` (in Markdown, a sentence under the counts; in JSON, `counts.relationships.of_split`) that says how many of the new relationships they are, and each of those rows ends with `of the split` and the element or elements concerned (in JSON, `of_split`, a list). Nothing is invented as removed, and the counts of `new` still include them. The editor's *Changes* panel says the same under its counts and on each row.
- A plateau that does not use `replaces` gets the table it always had, byte for byte. A difference is not an error: the exit code is 0. The command stops with an error (exit code 1) that says what to do when the workspace has no `settings.plateaus`, when the plateau is the first one and has no baseline to compare with, and when the baseline is unknown or is the plateau itself.

=== Design Guidelines

==== Incremental and In-Depth Design Approach

// - ArchiCode promotes an incremental and in-depth design approach.
// - Iteratively, the model is refined from the highest level of abstraction to the lowest one.
// - The relationships between elements are also refined iteratively.
// - Relationships covered by those of lower levels can be cleaned for clarity.
// - Moreover, the built-in Viewpoints of ArchiCode have been designed to generate synthetic relationships. So that, views are never polluted by sibling relationships.

ArchiCode advocates an architectural design philosophy characterized by incremental refinement and in-depth exploration. This approach empowers architects to craft well-structured and comprehensive designs that capture the essence of architectural vision. Let's delve into the tenets of this methodology:

- Iterative Refinement: In the journey of architectural creation, ArchiCode encourages an iterative process. The model evolves incrementally, starting from the highest levels of abstraction and cascading down to the minutiae of detail. This iterative refinement ensures a nuanced and coherent architectural representation.

- Layered Depth: With each iteration, the model's depth is progressively enriched. As elements are introduced, relationships between them are also refined, layer by layer. This gradual deepening ensures that architectural intricacies are meticulously captured, leading to a holistic and accurate depiction.

- Relationship Refinement: Just as elements undergo iterative enhancements, relationships between them also follow the same iterative path. The relationships are fine-tuned and perfected, aligning with the evolving architectural narrative.

- Clarity in Relationship Hierarchy: ArchiCode empowers architects to prune relationships for clarity. In instances where higher-level relationships are encompassed by those of lower levels, these higher-level relationships can be refined or omitted, ensuring that the architectural landscape remains lucid and uncluttered.

- Synthetic Relationship Generation: A distinctive feature of ArchiCode's built-in Viewpoints lies in their ability to generate synthetic relationships. This intentional design prevents sibling relationships from infiltrating the views, preserving the purity and coherence of each view's focus.

By embracing ArchiCode's incremental and in-depth design approach, architects embark on a transformative journey of iterative refinement. This methodology ensures that architectural designs are not only comprehensive but also well-structured, intelligible, and unburdened by unnecessary clutter.

==== Tackling view clutter

===== Introduction

// - When the Archicode workspace deeply expresses a model, the views generated become disordered and difficult to understand.
// - This is particularly the case when systematic interactions such as authorization or observability are designed in.
// - As a result, views need to be refined to focus on specific concerns.
// - The facet concept provided by Archicode is a solution for refining views seamlessly.
// - The facet concept automates the generation of secondary workspaces.
// - Generation is based on transformation rules that remove elements and relationships based on JSON Path queries.
// - In this way, it is possible to generate secondary workspaces relevant to a specific subset of elements and relationships, enabling views focused on specific concerns.
// - For example, this makes it easy to generate views dedicated to authorization or observability, leaving the main views to concentrate on the essentials.

Navigating through complex architectural models often presents a challenge for professionals as intricate details and systematic interactions like authorization or observability make the generated views disordered and complex. As these views become overwhelming, there is an evident need for refined, focused, and organized presentation to enhance clarity and understanding. This is where Archicode steps in, offering an innovative solution to transform this complexity into a streamlined and comprehensible format.

Archicode introduces the facet concept, a feature engineered to automate the generation of secondary workspaces and refine views to focus on specific concerns. By employing transformation rules based on JSON Path queries, facets effectively remove certain elements and relationships, offering a cleaner, focused view of specific subsets. This feature serves as a bridge from the chaos of detailed expressions to an organized, easily understandable visualization, paving the way for enhanced insights into complex architectural models.

[NOTE]
.The paths of a facet are standard JSONPath
====
The `json-path` of an action is a JSONPath as standardized by https://www.rfc-editor.org/rfc/rfc9535[RFC 9535]. It selects nodes of the workspace, and the `REMOVE` operator deletes them. The same code evaluates it in the command line and in the editor, so a facet cannot mean one thing in each. Beyond comparisons, a filter can combine tests with `&&`, `||` and `!`, test that a field exists (`?(@.label)`), look inside a list (`?(@.qualifiers[?(@ == 'oidc')])`) and call `length()` or `count()`. The functions `match()` and `search()` (regular expressions) are not available.

The facets written for the previous engine (Jayway) keep working for now, with a warning that gives the standard form. They are going to be removed in a future major version. The command line prints the warning on its error output, one line per rewritten filter (see <<errors-and-warnings>>).

[cols="1,1"]
|===
|Before |Now

|`@.qualifiers anyof ['a', 'b']`
|`@.qualifiers[?(@ == 'a' \|\| @ == 'b')]`

|`@.qualifiers noneof ['a']`
|`(@.qualifiers && !@.qualifiers[?(@ == 'a')])`

|`@.qualifiers == null`
|`!@.qualifiers`

|`@.qualifiers != null`
|`@.qualifiers`
|===

Relationships that have no tag, or no qualifier, simply do not have the field: `@.tags['k'] != 'v'` selects them, `@.tags['k'] == 'v'` does not.
====

[NOTE]
.A facet can remove an element, and what points at it goes with it
====
`REMOVE` is not only for relationships: an action can select elements, such as `$.application..elements[?(@.id == 'catalog')]`. The element is removed with the elements inside it, and so is everything of the workspace that pointed at it or at one of them: the relationships whose `destination` is one of them, the entries of `uses` of an environment, and the entries of `applications` of a node. The views of the facet are then written without them; they do not stop with `dangling reference`. The facet says nothing when it does so, it is what it asked for. The workspace and its other facets are untouched.

[source,yaml]
----
settings:
  facets:
    customs:
      - name: "without-catalog"
        actions:
          - operator: REMOVE
            json-path: "$.application..elements[?(@.id == 'catalog')]"
----

With this facet, the view of `shop.web` in `views-without-catalog` no longer shows a `browses` link to `shop.catalog`, and no view of `shop.catalog` (the element, or a view of the manifests that is about it) is written for the facet. The same goes for a facet that selects on the state of a comparison (`$.application..elements[?(@.change == 'moved')]`). A reference that already pointed nowhere before the facet is not hidden by it: it is still reported as a `dangling reference`.

=== Source Code Organization

// - The best practices to organize the source code of a project using the tool ArchiCode.
// - ArchiCode works with workspace file.
// - The workspace centralizes the data, by default the name is `workspace.yaml`.
// - As the content of workspace file grows, the management of the file becomes complicated.
// - Therefore, the manifest concept have been designed to solve big fat workspace files.
// - A manifest represents a single resource.
// - By default, ArchiCode discover manifests located in the folder "manifests" sibling to the workspace file.

Efficiently organizing your source code is a cornerstone of successful architectural endeavors, and ArchiCode is your companion in this journey. Let's delve into the best practices for structuring your source code using ArchiCode:

- Workspace Dynamics: The workspace file, named `workspace.yaml` by default, serves as a centralized repository for your architectural data.

- Scaling Challenges: As your architectural vision flourishes, the workspace file's contents may expand, leading to management complexities. Recognizing the need for efficient management, ArchiCode introduces the concept of manifests. A manifest embodies a singular architectural resource, enabling focused and structured representation. With manifests, ArchiCode empowers you to break down complex elements into distinct resources, enhancing manageability and granularity. ArchiCode streamlines the process of manifest discovery by default. It effortlessly detects manifests residing in the "manifests" folder, positioned as a sibling to the workspace file.

.Example of an ArchiCode project directory
----
- project_dir/ <1>
    - manifests/ <2>
        - application/ <3>
            - <FILENAME>.{yaml,toml,json} <4>
            - ....
        - technology/ <5>
            - <FILENAME>.{yaml,toml,json}
            - ....
    - views/ <6>
        - <RENDERER NAME>/ <7>
            - application/ <8>
                - <VIEW_ID>.<EXTENSION> <9>
                - ....
            - technoloy/
                - <VIEW_ID>.<EXTENSION>
                - ....
    - workspace.yaml <10>
----
<1> The directory of the project.
<2> The directory containing the manifests.
<3> An arbitrary directory containing the manifest related to the Application layer.
<4> A manifest file.
<5> An arbitrary directory containing the manifest related to the Technology layer.
<6> The directory containing the generated views.
<7> By convention, Render renders their views in subdirectory matching the Render's name.
<8> By convention, Render renders views in directory layers.
<9> By convention, the filename of rendered views is the view identifier. The extension depends on the Renderer.
<10> The workspace file is mandatory even if empty.

//-

* Manifest Diversity: ArchiCode efficiently handles multiple manifest directories, facilitating the seamless incorporation of manifests, including those from package managers like NPM. This versatility enables architects to integrate diverse architectural elements from various sources. This integration showcases ArchiCode's adaptability and its role in enhancing architectural endeavors.

.Example of manifest provided by NPM modules
----
- project_dir/ <1>
    - manifests/ <2>
    - node_modules/ <3>
        - <MODULE_NAME>/ <4>
    - workspace.yaml <5>
----
<1> The directory of the project.
<2> The directory containing the manifests defined in the project.
<3> The directory containing the installed NPM modules.
<4> The directory containing the NPM module importing the other manifests.
<5> The `workspace.yaml` must declare both directories `manifests` and `node_modules/<MODULE_NAME>` to be able to discover all manifests

==== Base Element

All elements share the attributes of the Base Element.

.Attributes of the Base Element
|===
|Name |Type |Comment

|id
|string
|The identifier of the element. Its format should match the variable name in Java or Javascript.

|name
|string
|The human name of the element.

|description
|string
|A short description of the element, usually between 25 and 75 words.

|qualifiers
|string
|A list of specific characteristics that helps define or categorize the element.
They are usually rendered in views.
It can be the name of the main framework used to implement a container: Spring Boot.
Or it can be the name of the RDMS for a database Container : PostgreSQL.

|tags
|string
|A list of key/value pairs that helps to drive the rendering of views.
For instance, to assign a predefined shape to the element or to categorize the element during a threat modeling process.
The tag `rendering-stereotypes` is a whitespace-separated list of stereotypes the styles apply to (see <<stereotypes-and-styles>>).

|relationships
|string
|The list relationships where the current element is the source.
