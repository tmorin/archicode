# Run 0126: patch-takes-a-field-out

Wave 017 (`editor-defects-and-composed-replaces`), item W-8. Focus: a plateau can say that an inherited field is gone, and the editor writes it instead of refusing to clear an inherited text (GitHub issue #94; decision D1 of the wave plan).

Document profile: `single-document`, as W-7 and the runs of waves 015 and 016. The design is one operator, one rule in the kernel and one branch of the editor's write path; a prd/tdd/pln would only copy it. The review passes are answered below.

## Scope

In: the kernel (`src/main/rust/viewpoint-kernel/src/patch.rs`, its tests, `lib.rs` header, README, the re-embedded wasm), the shared patch cases (`patch-cases.json`), the command line (`workspace/LayerLoader`: a `REMOVE` of a field is no removal; `resource/plateau/Patch`: the documentation of the key), the editor (`standalone.html`: the resolution of a plateau, `patchFor`, `newPatchObject`, `updatePatchInPlace`, `writePatchChange`, `plateauPatchesOn`, `planLayerElementEdit`), a shared case file for the two tools (`field-removal-cases.json`), `CLAUDE.md`.

Out: the manual (`src/doc`: W-9), the tutorial, a `where` on a `REMOVE`, a warning for a `SET` and a `REMOVE` of one field in one plateau, `#124` and the other open issues of the wave plan.

## Decisions

- **D1. The operator is `REMOVE` with a `field`, as the plan recommended.** A `SET` with a `null` value is not the way: the kernel (and the Java `Patch`) read a `null` value as no value (`a value of null is no value` is a shared case), and a plateau that wants the text `null`... is still a value. `REMOVE` already means "take out what the selector selects"; with a `field` it takes the field of the selected element out. Additive in contract 5: a `REMOVE` with a `field` was an `error` (`REMOVE takes no field`, which the old shared case pinned), a `REMOVE` without one is what it was, a patch of the old forms reads as before; the number stays 5 (kernel README and the header of `lib.rs` say so). It works with a `target` (the editor's form) and with a `json-path` (bulk).
- **D2. Which fields.** Any field of the selected element except `id`, `parent` and `elements` (refused for every operator, with the sentences they already had) and `kind` (new, REMOVE only: ``kind` cannot be taken out: an element always has a kind``; the kernel does not need a `name`: it is optional in the model and the views fall back on the reference, so `name` can go). A list or an object (`tags`, `qualifiers`, `relationships`, `applications`, `uses`, `replaces`) can go too: the kernel is uniform, the key leaves; the editor does not write that, it keeps the `SET` of an empty list or object for an emptied list (the issue says they are not affected, and every existing patch file stays what the editor wrote).
- **D3. A field the element does not have is already gone: no error.** `matched` counts the nodes selected, as ever. The alternative (a miss, like a `REMOVE` of an element that is not there) makes a plateau fragile: a `REMOVE` of `description` in `saas` would stop `saas` resolving as soon as `baseline` clears the same description, and a bulk `REMOVE` of a field over a `json-path` would have to select exactly the elements that have it. A typo in a field name is not caught, as for `SET`, which creates any field. A selected node that is not an object has no field to take out: the error `SET` gives (`a selected node of x is a list, it has no field ...`).
- **D4. `where` and `value` stay refused for `REMOVE`.** `where goes with SET` is told first, as before; ``REMOVE takes no `value`: it takes a field out of what the selector selects`` (the sentence without a `field` is byte for byte what it was). A `REMOVE` of one relationship found by `where` is a different feature and nobody asked.
- **D5. `expect`** counts the nodes the `json-path` selects, the same as for every operator.
- **D6. The report.** `{ rank, operator, selector, matched, touched }` and nothing else: no `removed`, no `dropped`. Nothing leaves the graph, so there is no cascade (the keys mean "elements that left" and "entries taken out of elements that stay"; putting a field there would put it in the *Cascade of the removals* of `gap.md` and the Changes panel). `touched` is the elements selected, as for `SET`. The command line therefore lists a `Removal` for a `REMOVE` report only when it has `removed` (`LayerLoader`), and the editor reads a `REMOVE` whose sent patch has a `field` as a change of that field (`patched`, `touchedBy`: "taken out by patch 3 of saas (REMOVE target shop)" was already the sentence for the origin of a field a cascade took out).
- **D7. The order of the keys of an element is kept.** The element is a JSON object with `preserve_order`; `Map::remove` is a swap-remove there and would move the last key into the hole. The new code uses `shift_remove` (a Rust test pins it). The old `remove_at` of the facets (a `REMOVE` over a `json-path` that selects a field) is left as it is: changing it could change what a facet writes, and nothing reads the order of the keys of an element.
- **D8. Editor.** `patchFor` answers `{ operator: 'REMOVE' }` when the field is not a list or an object and the plateau no longer has it (the base is known, or not). `newPatchObject` writes `operator`, `target`, `layer?`, `field` and no `value`. The patches of a plateau on (target, field) (`plateauPatchesOn`) now include a `REMOVE` of the field, so the next edit finds it again: a new text changes that patch in place (`REMOVE` becomes `SET`, `value` added), clearing a text a `SET` of the plateau gave becomes a `REMOVE` in place, a text equal to what the plateau inherits takes the patch out (as for the others), and clearing a field the plateau below already has gone takes the `SET` out and writes nothing. Where the editor used to refuse (``comes from another plateau, and a patch can set a value but not take it out``) it writes the patch at the end of the patches of the plateau drawn, under `guardedLayerWrite` (it asks first when a plateau stands on the one drawn, and refuses and restores when the plateau drawn does not give the field back gone). A field the plateau declares itself is still removed from its manifest: no patch.
- **D9. A later plateau that SETs the field again gets it back; a plateau that stands on this one sees it gone.** Both are the kernel's patch order, run by the shared cases F01 to F03 in both tools.

## Findings

- F1. `REMOVE` with a `field` was a pure addition: the only case it changed is `REMOVE takes no field`, which was an error (the shared case became the success case; `REMOVE takes no value` has the same sentence, with `it removes what the selector selects` when there is no field). A `SET` or `ADD` or `MERGE` patch reads as before; `where goes with SET` is still told first.
- F2. serde_json with `preserve_order` makes `Map::remove` a swap-remove: the existing `remove_at` of the facets and of `REMOVE` over a `json-path` moves the last key of an object into the hole of the one taken out. Not changed (it would change what a facet writes, and nothing reads the order of the keys of an element); the new code uses `shift_remove`. Not worth an issue: nothing observable.
- F3. A plateau that `REMOVE`s a field and a plateau below it that clears the same field: the plateau above still resolves (D3, an absent field is no miss). The editor goes further: when a plateau's own `SET` is cleared and the plateau below already has the field gone, the `SET` goes and nothing is written (a REMOVE would say what the plateau below says).
- F4. Left as is, deliberately: `repeatedSets` (command line) and `repeatedSetWarnings` (page) warn for two `SET` of one field in one plateau and say nothing for a `SET` and a `REMOVE` of it; the editor never writes two patches for one target and field, and a hand-written pair is the author's. Also not done: a `REMOVE` with `where` (one relationship found by `(destination, label)`).
- F5. For **W-9**: `src/doc/README.adoc` line 1742 (*A value that comes from another plateau cannot be taken out by a patch ... A list or tags can be emptied*) is now wrong: a text or a number is taken out by a `REMOVE` patch with a `field`, written by the editor; lists and tags are still a `SET` of the empty value; and the manual's section on patches (the operators `REMOVE`, `SET`, `ADD`, `MERGE`; near the `*What a REMOVE takes.*` paragraph at line 410, and the table of what an edit writes at line 1716) needs the form `operator: REMOVE, target, field` and its rules (D2 to D4, D6); the `[[plateau-limits]]` list of `CLAUDE.md` (line 56) still names #94 (and the manual's list); `docs/fixtures/brightcart-spec.md`, if it lists the operators, should say a `REMOVE` takes a field. The origin sentence the Inspector shows for such a field is `taken out by patch N of <plateau> (REMOVE target x)`.
- F6. Files outside `likely_paths`: none.
