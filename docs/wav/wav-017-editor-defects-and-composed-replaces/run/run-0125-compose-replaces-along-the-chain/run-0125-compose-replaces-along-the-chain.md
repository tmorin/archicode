# Run 0125: compose-replaces-along-the-chain

Wave 017 (`editor-defects-and-composed-replaces`), item W-7. Focus: a comparison between two plateaus several steps apart composes the `replaces` of the layers in between, so that a move made in two steps is a move, in both tools (GitHub issue #89; decision T3 of the wave plan).

Document profile: `single-document`, as the runs of waves 015 and 016. This is the first run of the wave that changes what a comparison means, which is why the decisions below are written out; but the whole design fits one page (one rule in the kernel, one chain handed over by each host) and a prd/tdd/pln would only copy it. The review passes are answered below.

## Scope

In: the kernel's `compare` (`src/main/rust/viewpoint-kernel/src/compare.rs`, its README, the re-embedded wasm), the command line (`viewpoint/kernel/PlateauComparer`, `workspace/LayerLoader`, `workspace/WorkspaceFactory`, `workspace/Workspace`, the new `workspace/PlateauStep`, `resource/plateau/PlateauTree.standsOn`), the editor (`replacesChainBetween` and `comparisonInputBetween` in `standalone.html`), the Brightcart fixture (P4 becomes a comparison the tools say), a shared case file, `CLAUDE.md`.

Out: the manual and the tutorial (`src/doc`: W-9), `docs/fixtures/brightcart-spec.md` (W-9), the facets and the views, `Write replaces` (it keeps writing one entry), `layerNodeCounts` (a plateau against its parent: one step).

## Decisions

- **D1. The kernel composes, the hosts hand over the plateaus (T3: "unless the kernel is the smaller place").** The composition needs the elements of the plateaus in between, which each host has to build and hand over anyway; what it does with them is one rule. Written in the hosts it would be written twice (Java and JavaScript) and could drift; written in the kernel it is written once, and the shared cases test the wiring of each host, not two copies of the rule. `compare` takes an optional `chain` (additive to contract 5: the number does not move, the README of the kernel says so, rule 8 of `compare.rs`): the plateaus the target stands on, oldest first, ending with the plateau the target overrides; each element is `{ reference, replaces? }`, `replaces` as the layer that declared the element wrote it. With fewer than two plateaus the answer is what it was.
- **D2. The rule.** Each layer writes `replaces` relative to the plateau it overrides. For an element `e` of the target that carries `replaces` (the host leaves it out when the base says the same of the same element, as before), the entries that are valid at the last step (they name an element of the plateau just above that the target no longer has) are replaced by what that element stands for, and an element the plateau above already holds stands for what it stood for there. "Stands for" is worked out down the chain: an element stands for itself when the plateau under it holds it, and for what its own entries name when its layer wrote them (a word an inherited element repeats is the word of the layer that wrote it, so it is read once, there). The result is a set of elements of the first plateau of the chain; `e` itself and anything the target still holds are taken out. So: a move then a move is a `moved` from the first element; a move then a split, a split then a move of one half, a move then a merge are splits and merges of the first plateau's elements; an element created by a layer in between and moved by the next replaces nothing (`new`, and the entry is no mistake: no warning); an element a layer in between removed ends its own chain. Nothing is guessed: only what a layer wrote is read.
- **D3. What the last step cannot explain is left as written.** An entry that names nothing of the plateau above (or is not a string) goes to rule 6 unchanged, which ignores it with its warning against the base as before. The warning of #89 (`commerce.search is not an element of the base plateau`) goes because the chain explains it. An element whose `replaces` is not a list is not rewritten either (rule 6 says so). A duplicate entry is counted once, silently, when the chain is composed (rule 6 still warns for it with no chain: a corner of a corner).
- **D4. Forks.** The chain starts at the plateau the target and the base have in common (`PlateauTree.standsOn(target, base)`: the deepest common ancestor up to the plateau the target overrides, the target itself not included); the layers of the base's own side are not read (rule 6: `replaces` is read from the target only). The composed entries are then validated against the base like any: an entry the base lacks is ignored with the usual warning, which now names the composed reference (`marketplace` against `saas`: `discovery.search ... shop.app.search is not an element of the base plateau`, where it said `commerce.search`). The table is the same for every fork of the fixture; the sentence of the warning changes for the elements that were moved in two steps. A target that is the past of the base, or the base itself, has nothing under it to compose, and neither has a plateau one layer above what it is compared with: no chain is sent and the answer is byte for byte what it was.
- **D5. Command line.** `LayerLoader` keeps, for each plateau of the chain it loads, the two indexes as they are once the layer is applied (`PlateauStep`, `Workspace.getSteps()`, copied by the union of a comparison); `PlateauComparer.chain` turns the plateaus of `standsOn` into the key. The load is the same load: the steps only keep what it built.
- **D6. Editor.** `replacesChainBetween(baseId, targetId)` does the same from `layerModelOf` (cached per plateau, so no plateau is resolved twice); `comparisonInputBetween` takes the chain as a fourth argument; only `comparisonInput` passes one. `layerNodeCounts` (a plateau with its parent) does not. The comparison cache needs no new key: the chain is a function of the two plateaus, and the models are what `modelsChanged()` already tells it.
- **D7. `Write replaces` is unchanged.** It writes the entry the author chooses, in the manifest of the plateau that declares the element, and `acceptLayeredCandidate` still refuses an element that comes from a plateau above. Between a plateau and the one it overrides (the layer the entry is written for) the entry is a one-step word as it ever was; against a plateau further up the composition reads it like any other. A pair proposed in a comparison several steps apart can name a base element that the plateau the manifest builds on does not have: the word then is valid against the base compared with and is a warning against the parent. That is how it behaved before and is not changed here (filed, see Findings).
- **D8. P4 becomes a comparison the tools say.** `description.mjs` marks it `source: 'tool'` with no warning; `gives` (the tool's one-move-less numbers) goes with the field; `BrightcartLayeredDiffTest.marketplaceAgainstBaselineIsP4ButForTheMoveThatTookTwoSteps` is now `marketplaceAgainstBaselineIsP4BecauseTheReplacesOfTheTwoStepsAreComposed`, and the parameterised tests (counts, text, table row by row, warnings) and the editor's (`brightcart-editor.test.js`, `brightcart-kernel.test.js`, `editor-reads-layers.test.js`, `band-compare-tree.test.js`) read P4 like P1 to P5.

The cost is one optional key on a contract that does not move (`chain`); a host that does not send it (an older editor, a script) gets the answer of before.
- F2.
