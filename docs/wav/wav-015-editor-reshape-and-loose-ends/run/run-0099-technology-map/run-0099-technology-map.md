# Run 0099: Technology map

Wave 015 (`editor-reshape-and-loose-ends`), item W-11 (phase P1). Focus: the page Environments is a Map of the technology layer, like Applications (#92).

Document profile: `single-document`, as runs 0089 to 0098: the scope is settled by the plan (the W-11 row, the fourth criterion of P1), by #92 and by the decision of the author of 2026-10-18 that the issue records; there is no PRD, TDD or pln. The review passes (a read of this document against the code, the open questions, the C scan) are answered below.

## Scope

In: the page Environments of `standalone.html` (a Map of the technology layer, with the layer as the parameter of the code of the Map), the kernel input of such a Map, the saved views of `viewpoint: map` and `layer: technology`, the Changes panel and the chips on it; the `map` viewpoint of the command line (`views generate` draws a view of that viewpoint, of either layer); an example that ships such views (`src/doc/examples/domain_technology_map`) and the contract of the boxes both tools draw; `CLAUDE.md` (the paragraph on the pages and the line on the viewpoints).

Out: the manual and the tutorial (W-18; what they must say is in Findings), the links of the Map of the technology layer that no technology element declares (`uses`, deployed applications: #107), views untied from plateaus (W-12).

## Decisions

- **D1. `environments` is a perspective of its own.** `elementsScope`, `currentPageId()`, `perspectiveIdFromHash()` and `widenElementsScopeToSelection()` are deleted; the page on screen is `currentPerspective`, and an address names it with `pageIdFromHash()`. `mapIsShown()` is true for `map` and `environments`; `mapLayer()` says which layer the Map on screen draws.
- **D2. One state per layer, the old names kept for the application layer.** The application Map keeps `mapPinned`, `mapHidden`, `mapOpened` (about fifty uses in the tests, and nothing gained by renaming); the technology Map has `technologyMapState = { opened, pinned, hidden }`; `mapStateOf(layer)` reads and writes either (`state.pinned = ...`). A pin of a layer means nothing in the other (a reference can exist in both), so a Map never reads the other's lists. Both are in the snapshot of a write (`snapshotWriteState`), reset with the folder (`resetUiState`), and follow a rename (`rewriteUiReferences`) and a delete (`forgetUiReferences`) of the layer they belong to.
- **D3. The kernel input of a map is the layer's own, and nothing else.** `buildKernelInput('map', '', { layer })` takes `layer` (default application) and passes no `app_elements` for a technology map (the applications deployed on nodes are what the viewpoints of an element draw inside a node; the Map draws one layer). No change to the kernel: its `map` already worked on whatever elements it was given. The contract stays 5 and the wasm is the committed one (`embed.sh --check` is green).
- **D4. A Map is a drawing of its layer, in the saved view too.** `currentViewDefinition()` writes `layer: mapLayer()`; `canonicalViewDefinition` keeps the layer of a map (it forced `application`); `viewProblem` checks the pins against the layer of the view; `applySavedView` opens the page of that layer (`environments` for `technology`) with the lists in that Map's state; `libraryDiagramRecipe` reads the lists in the layer of the view; the form of a view has the Layer select for a Map too (the pins, hidden and open elements are refused when they are not elements of that layer; `setViewLayer` on a Map keeps the entries that exist in the other layer; `setViewViewpoint` to the Map pins the element of the view in the layer of the view, and back from it the first pin is the element, the layer stays). A saved Map with no `layer` is the application one, as it was.
- **D5. The tree of the Map is the layer's.** `renderMapScopeHtml` and `renderMapScopeNodeHtml` take the layer from `mapLayer()` (title *Environments*, `data-layer`, the keys of the rows `technology:ref`); the page Elements keeps its tree of both layers and the buttons to add. The title of the page, the status line (*Map of the technology layer*), the label of the canvas for a screen reader, the empty message and the note of the panel (*This map draws the technology layer only.* for an element of the other layer, kept as *The map draws applications only.* on Applications) say the layer.
- **D6. The links between the pages follow the layer.** *Show on map* is offered for an element of either layer and opens the Map of its layer pinned on it (`data-layer` on the button); *Open in Elements* leads to the element with its layer; a row of the Changes panel about the other layer than the Map on screen leaves that Map for the Map of that layer (one entry of the history), as a row on the page Plateaus opens Elements; the Changes panel keeps both layers in its lists (W-15 adds the filter by layer). An element of the other layer that is selected when a Map opens stays selected (it was let go by the old page Environments, since it listed one tree); the panel says it is not on the Map.
- **D7. The command line draws a map, of either layer.** The `map` viewpoint was skipped (`the viewpoint map is not generated by the command line`, a sentence the manual teaches). `MapViewpointService` (registered in `META-INF/services` and `reflect-config.json`) builds no view of its own accord (it has no `createViewBuilder`: a map is a view the author names, so it is generated with `--view-ids`, as the named views of the other viewpoints are) and `KernelViewpointFactory` takes `opened`, `pinned` and `hidden` from the properties of the view, no focal element, and no `app_elements` for a technology map. A list that names an element the kernel cannot find is the kernel's one error line, with the view named (`error: the view x: dangling reference: y`); in the workspace of a facet the entry is dropped, as the editor drops what a facet removes (a facet removes without a word). The drawing of a comparison (`--plateau p --against q`) has the states of the boxes (`<<new>>`, `<<removed>>`, `<<contains-changes>>`), as the other viewpoints do. Not read by the command line, for the Map as for the other viewpoints: `facet`, `hide-unlinked` and the texts of the properties.
- **D8. The example and the contract.** `src/doc/examples/domain_technology_map` (a datacentre and a backup site, nodes that declare relationships, three views of `layer: technology` and `viewpoint: map`) is a workspace of the manual's folder, so `ShippedFilesTest`, `ManualExamplesTest` and `shipped-files.test.js` load it with no entry anywhere; `src/test/resources/technology-map/expected-boxes.json` says the boxes and links of each view and is read by `TechnologyMapTest.java` (the viewpoint of the command line) and `technology-map-shared.test.js` (the page of a view and the page Environments, over the embedded kernel).
