# Run 0150: story-reading-mode

Wave 020, W-5. A story can be read in a mode of its own: full screen, the diagram, the words of the step, the menu of the steps (W-4), *Previous* and *Next*, the key of a comparison and the plateau and comparison the step names, with none of the tools that edit (GitHub issue tmorin/archicode#142, first request; plan decisions T4 to T6). The commit of this run closes #142; the run does not close it. No Java and no Rust change; the command line is not touched (T1).

Profile `single-document`: one layout, one flag, one listener and their tests in a page that already plays stories; the plan's T4 to T7 hold the design, and a prd/tdd/pln would restate them. The review passes are answered below. The wave's design (T4 to T7) was followed, not reopened.

## Decisions

| # | decision | verdict |
|---|---|---|
| 1 | form (T4) | a mode of the editor, same page, full screen: `readingMode` (view state) and `readingModeOn()`, which also asks for a story on a step and a page that draws a diagram (the Map pages or an element's diagram). `renderShellHtml` returns `renderReadingShellHtml()` first when it holds; the editing layout is the code below it, untouched. |
| 2 | what is on screen | `.reading-shell` (`role="region"`, `aria-label="Reading the story <name>"`): a bar (title, "Step n of N" with `aria-live="polite"`, W-4's menu with the class `reading-step-menu`, `stepPlateausHtml`, the words, `story-step-problem` for a step that cannot be drawn, *Previous*, *Next*, *Edit*) over the diagram canvas, its zoom tools and the status line with `#diagram-legend` (the key of a comparison, folded by default, with its *Key* button). Nothing else: the only `data-action` values in the shell are `story-prev`, `story-next`, `story-read-exit`, `diagram-zoom`, `diagram-recenter` (+ `toggle-diagram-key`, drawn into the legend). A dialog that is open is still drawn (`renderAppDialogHtml`), so that state and screen agree (none can be opened from the mode). |
| 3 | the diagram (T5) | zoom, Center, Fit and pan only. `renderDiagramCanvasHtml(record, overlay, host, { reading: true })` draws no editing tool; the tools that were inline are now `renderDiagramEditingToolsHtml`, written exactly as before (tested byte for byte against the page of the tag). `handleAppClick` returns for any click inside `#diagram-canvas` in the mode; `quietDiagramForReading` takes the actions, the fold buttons and the tab stops off the copy on screen (the cached scene is not touched) and makes a box an `img`; `handleDiagramKeydown` keeps only the zoom keys; `markMapSelection`, `markLinkSelection` and the focal box ignore the selection the editor had, which is neither changed nor shown; `changesListIsOnPage()` is false, so J and K (`handleChangesKeydown`) select nothing. |
| 4 | leaving (T5) | *Edit* (`story-read-exit`) and Escape: `leaveReadingMode()` clears the flag, writes an address entry and draws the editing layout on the step that was read, with the plateau, comparison and view that step drew. **Interpretation of "puts the reader back as they were (`storyHome`)":** the mode touches neither `storyHome` nor the plateau; it is a layout. So the reader is back in the editing layout at the step read (as if the step had been walked in the editor), and `storyHome` still holds what they had before the story began, so a step that names none is drawn there and *Leave story* is what it was. A test checks the editing layout after reading to step *k* is the layout walking to *k* gives (bar included), and `storyHome.plateau/against` are those from before entering. |
| 5 | keys (T5) | one listener, `handleReadingKeydown`, on the document, bubbling, the rule of `handleChangesKeydown`: **Left / Right** previous / next, **Home / End** first / last, **Escape** leave. **Up and Down are not taken** (the words scroll; the plan said "the arrows": Left/Right are arrows). Silent for Ctrl/Alt/Meta/Shift, `defaultPrevented`, an input method, a typing target or focused element (input, textarea, **select**, contenteditable, CodeMirror), a dialog, the help, the menu of the header, a rejected YAML text, and the mode off. The select is the menu of the steps, so while it has the focus the arrows are its own (the browser changes its value and the `change` event shows the step; checked in a real browser) and Escape is **not** the mode's either (decision: one rule, a control that owns keys keeps them; Escape on an open select closes its list in some browsers, and leaving the mode as well would be a surprise). The key is kept from the browser only when it did something (not at the ends). |
| 6 | address (T6) | `read=1` after `step=` in `currentRouteHash` (only while `readingModeOn()`); read by `applyDiagramParamsFromHash`, which sets `readingMode = (read === '1') && a valid story and step`. **Rule for a bad `read=1`:** no story, an unknown story, a step out of range or not a number, `read=0`, `true`, or any page that draws no story (Settings, Files, Plateaus, Stories) leave the mode off and the page writes its own address back; no `step=` is step 0 (as before). Entering and leaving write an entry (`location.hash =`), so Back leaves the mode and Forward comes back, and each step is an entry as before. |
| 7 | the comparison of a link | an address carries the plateau but not the comparison (`compare=` only with a removed pick), so a link opened on `read=1` would show the plateau with the wrong comparison. `drawStepOfReadingAddress()`, after the selection is read from the address (at load and on `hashchange`), draws the plateau and the comparison the step names with `drawPlateausOfStep(…, fromAddress = true)`; `homeOfStory(…, fromAddress)` does not take the plateau the address drew for a choice of the reader's, so Back does not move the home. Only with `read=1`: an address without it is read as it was (the same gap exists in the editing layout; see the findings). |
| 8 | focus | opening: `READING_FIRST_FOCUS` (the menu, else *Next* if enabled, else *Edit*); *Previous* / *Next* by click or by a key with that button focused keep it, and the other one takes it at an end (the redraw replaces the buttons); the menu keeps it (`chooseStoryStep`, W-4); a key with the focus on the body leaves it there; leaving: the *Read* button of the bar (`story-read`). |
| 9 | Read buttons | on the bar, after *Next* (`story-read`, no `data-story`: reads the step on screen, draws nothing again, one history entry), and on the Stories page beside *Play* (`data-story`, `data-step="0"`: draws step 1 as Play does, with the flag set first, so `goToStoryStep` writes the address with `read=1` and draws once). A story with no step cannot be read. `story-read` is in `ACTIONS_LEAVING_THE_FORM` (the typed-form question); a key asks it too, a click asks it once. |
| 10 | flag hygiene | `render()` clears the flag when `readingModeOn()` is false (a story that went away leaves nothing behind); `resetUiState` clears it with the folder; no write path is touched. |
| 11 | what it never does | no `modelsChanged()` of its own (entering and leaving: none, tested; a walk calls it exactly as the editing walk does, tested equal), no file written, no `diagramCacheKey` / `modelsKey` / comparison-cache input (the tests compare the cache objects and the key, and the page text of both functions has no mention of the mode). |

## Findings for the wave

- An address carries the plateau of a step but not its comparison (`compare=` is written only with a removed pick), so in the **editing layout** Back or a link to a step told with `against` lands on the right plateau with whatever comparison was there. The reading mode draws the comparison of the step for an address with `read=1` (`drawStepOfReadingAddress`); the editing layout was left as it was (byte identity with 0.18.0). If the author wants the same for the editing layout, it is the same call after `applySelectionFromHashRef`, for any address that carries `story=` and `step=`; a follow-up for the author to decide, not filed.
- `ref=` is set by the steps whose view is an element's (it is the element selected), unlike W-4's note says for every step; harmless, and the tests drop it where addresses are compared.
- The harness has no layout engine and no `<select>`/focus model: the tests call the page's functions and renderers; what a browser does with the focus, the picker and the layout is what the browser look above and the list of things to look at cover.
- Proposed commit subject: `feat: a story can be read full screen, with the tools that edit out of the way, a step menu, keys and an address (#142)`.
