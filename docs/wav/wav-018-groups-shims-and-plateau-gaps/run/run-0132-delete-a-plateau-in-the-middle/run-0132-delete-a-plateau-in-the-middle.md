# Run 0132: delete-a-plateau-in-the-middle

Wave 018, W-5 (`hard_judgment`: data deletion; every task worked inline, none dispatched). Closes GitHub issue tmorin/archicode#112, decision D5 of the author (2026-10-21) and T7 of the plan: a plateau that other plateaus override is deleted in one step, the plateaus that override it go under its parent, what it brought is lost to them, and the dialog lists what each plateau above loses.

## Scope

1. `plateauDeletion` accepts a plateau that others override (the root stays refused).
2. The dialog lists, for each plateau that stands on the deleted one, its new parent and the elements it loses (and what else changes for it), worked out by the kernel.
3. `commitPlateauDelete` rewrites the `override` of the plateaus that override it and queues the files of the deleted plateau in `pendingFileRemovals`, under `guardedLayerWrite`.
4. The refusals of run 0102 stay; a refused delete changes nothing; a leaf is deleted byte for byte as before.

## Reading first

- Run 0102 (#93) refused a plateau with children (`plan.overriding` was a refusal). Everything else (the files that go, `settings.current`, the views and steps that refuse it, the plateau drawn afterwards, the restore of `guardedLayerWrite`) is reused as it was.
- A plateau's parent comes only from `override` in its manifest of kind `archicode.morin.io/plateau` (`buildPlateauTree`): a plateau that only headers name overrides the root. So a plateau that overrides the one deleted (never the root) always has that manifest, and the deleted plateau can be either kind (with a manifest, or headers only, which then overrides the root).
- A file belongs to one plateau: the plateau its header names (`plateauOfManifest`); a view and a story belong to none, and a manifest of kind plateau is never counted among the header files of another plateau. So the files that go (`node.manifest` and `node.headers`) hold nothing of another plateau, and the manifest of a plateau above is never among them.
- The kernel refuses a patch that selects nothing (`patch.rs`: "selects nothing, there is no element ..."), and `resolveLayerStep` returns it as `fatal`; the checks of a layer (`layerProblemsOf`, the parent that does not exist) are `state.problems`. `judgeLayerWrite` refuses a write that makes either appear.
- On the shipped layered Brightcart the one plateau in the middle is `inhouse` (baseline, inhouse, marketplace over inhouse, saas over baseline); `marketplace` patches `commerce.checkout` and declares nodes under `prod.cloud`, both declared by `inhouse`.
- The command line deletes nothing and has no rule to share. The sentences the editor checks against are the ones it shares with the command line already (`layerProblemsOf`, the kernel's, `entryProblemsIn`); the one new check (a step told at a plateau above) is the editor's alone, see the decisions.

## Decisions

- **D-1. What is "lost" is computed, not guessed.** `plateauDeletionAbove(id, goes)` builds the manifests as they would be (the files of the plateau gone, a copy of each child's plateau manifest with `override` rewritten), the tree they make (`buildPlateauTree`), and resolves every plateau that stands on the deleted one again: `resolveLayerStep` over the state of its new parent (`layerStateOf` for a plateau that does not change, the new resolution for one above). Each is compared with its resolution now (`layerStateOf`): `lost` (references it has now and would not have, every nested element named), `back` (references it would have again: the deleted plateau removed them with a `REMOVE`), `changed` (references in both whose own fields differ, the nested `elements` left out: what the patches of the deleted plateau did to them, including the entries a `REMOVE` cascade took), per layer, sorted. The result is kept in `layerCache` (one tree, one text of the manifests). The patches of the deleted plateau are shown by what they did (`changed`, `back`) and by their count ("nor its 2 patches"), not one by one: a patch is lost to every plateau above alike, its effect is what differs. Rejected: listing the elements the deleted plateau declares (it misses the patches, the `REMOVE` that come back, the cascades, and the elements a plateau above removes anyway); rejected: `layerModelOf` for the "after" side (it is keyed on the live tree and would need the write to be made first).
- **D-2. A plateau above that stops resolving refuses the delete.** A patch of a plateau above whose target the deleted plateau declares, a relationship, `uses` or hosted application towards such an element, or an element declared under such a parent, makes that plateau a mistake, not a loss: `plan.breaks` lists the sentences (the kernel's "could no longer be resolved (...)" once, by the plateau whose own patch fails, and every sentence of the layer checks the plateau did not have), the dialog shows them under "It cannot be deleted yet" without a *Delete* button, and `commitPlateauDelete` throws `The plateau \`p\` cannot be deleted: ... (first sentence). Repair it first, or give the plateaus that override \`p\` another parent with Edit.` and writes nothing. The same judgment as `judgeLayerWrite`, which still checks after the write. Rejected: pruning the dangling patches and relationships of the plateaus above (as `prunePatchesNaming` does for a deleted element): it would edit what the author wrote in plateaus that are not deleted, and a patch with `expect` or a `json-path` has no deterministic repair; the author repairs or re-parents first. Consequence: `inhouse` cannot be deleted on the shipped Brightcart (see Reading first); that is the refusal test on the Brightcart.
- **D-3. The new parent is written in `override`, and no manifest is made (T7).** Each plateau that overrides the deleted one gets `override: <parent>` in its manifest of kind plateau, through `setPlateauContentKey` and `touchManifest` (the line-preserving save, as *Edit* writes it); when the parent is the root the key is taken out (an absent `override` means the root, as `commitPlateauEdit` writes it). Since such a plateau always has that manifest (reading first), the alternative of T7, writing a `Kind: Plateau` manifest the key needs, never applies, and the write throws `Not written: the manifest of the plateau ... was not found` if it ever did. Rejected: writing `override: baseline` explicitly (a second spelling of the same tree, and *Edit* does not write it).
- **D-4. Siblings and chains.** Every plateau that overrides the deleted one is rewritten (`plan.rewritten`, in the order of the band); every plateau that stands on it, directly or not, is in `plan.above` (in the order of the tree), each with its parent before and after (a grandchild keeps its parent; what it loses is worked out for it as well, and is usually what its parent loses). The root as the new parent is the case of D-3 that takes the key out.
- **D-5. One yes.** The dialog of the delete lists what each plateau above loses, so its *Delete plateau* is the author's yes to those plateaus: it calls `commitPlateauDelete(id, { listed: true })`, which hands `guardedLayerWrite` the new option `confirmedFor` (the plateaus of `plan.above`). A change of a plateau not listed there still opens the `layer-confirm` dialog, and so does a call with no dialog before it. Rejected: asking twice (the second dialog only says "these plateaus change", less than the first); rejected: `confirmed: true` (it would also skip a change nobody listed).
- **D-6. A step told at a plateau above that would lose what it draws refuses the delete.** For a step with `at: q`, `q` a plateau above, whose view names an element `q` loses (a view's `element`; for a map, the elements it is pinned on, when none of them is left, as `viewProblem` reads it), `plan.blocking` gets ``the story `s` (`file`) step n is told at `q`, which would no longer have `x` ``. The editor's alone: the command line does not look at the plateau of a step (N84), so no shared case. Not checked (see Deferred): a step with no `at` (drawn in whatever plateau the reader has), `against` (the comparison draws the union), and a view (it belongs to no plateau, run 0100; a view whose element no plateau declares any more is the existing sentence "exists in no plateau"). Rejected: refusing on every view that names a lost element (a view drawn in another plateau is no mistake, #100).
- **D-7. Comparison and plateau drawn.** The plateau drawn when it is the deleted one falls back to its parent (as before). A comparison with the past of a plateau that overrode it follows it to the new parent (`normalizedLayerCompare` does it once the `compare` is kept); a comparison with the deleted plateau in any other mode stops (as before). Rejected: stopping every comparison that named the plateau, as run 0102 did (for a leaf no past can name it; for a plateau in the middle the past of its children has an obvious next value, the new parent).
- **D-8. Data deletion (no alternative: the mechanism of run 0102, reused).** The editor only queues the files of the plateau in `pendingFileRemovals` (with `removedFileBaselines`), as run 0102 did; they leave the disk at the next *Save all changes*, with its check that the disk did not change. `snapshotWriteState` already holds the content of every manifest, so a refused write puts the rewritten `override` back with the rest. The tests work on in-memory folders only (`memFolder`); no file of the repository is deleted or written by them.
- **D-9. Other words (no alternative weighed).** The kernel not loaded refuses a delete in the middle (nothing can be worked out); a leaf needs no kernel, as before. The dialog of the files the editor does not read adds "nor rewritten" and `override: <id>` for a delete in the middle (a TOML plateau manifest that overrides it would keep the plateau for the command line). The button of the page no longer says "Cannot be deleted" for a plateau with children: its title says what goes and who goes under which parent.
