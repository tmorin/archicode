## Findings

- `query schemas manifest` describes `content` as `"type": "any"` (an `ObjectNode`); `ManifestKind` already knows the class of each kind's content, and `EditorReadSchemaTest` already cross-checks `READ_SCHEMA` against the classes: both are the base of W-1.
- The generator `jackson-module-jsonSchema` is an older dialect (`"required": true` on the property, no `oneOf`): see Q1.
- Carried from wave 021: `Build` has no `permissions:` block and the repository's default token is write-all (left alone, a follow-up for the author; not in this wave).

- The schema still types two things as `"type": "any"`: a patch `value` (legitimate) and the `properties` of a view. The second matters to an agent: the keys a map or a facetted view takes (`pinned`, `hidden`, `opened`, `facet`, `hide-unlinked`, `applications`, `relationships`) are not in the schema. W-2's guide must say them (from the editor's `VIEW_PROPERTY_ORDER` and the kernel), and W-4's walk must draw a map and a faceted view from the guide alone.
- `save-keeps-quotes-and-comments.test.js` (wave 021) asserts its 2000-file run finishes in 60 s: it takes 12 s alone and 68 s inside the full parallel node run on this 8-core machine. To file as an issue at the end of the wave (a load-sensitive guard; the property it checks is fine).

- A saved overview view with no `properties` at all fails with `error: unexpected java.lang.NullPointerException` and a stack trace (`KernelViewpointFactory.create`), where `properties: {}` gives the proper `has no element` error. Found by W-2; not fixed (T1 forbids changing other commands' output in this wave): to file as an issue at the end of the wave.
- The guide's last line says `init` is not built yet: W-3 changes it and regenerates the golden file. The timing guard of wave 021 (`generated: 2000 files`) is deflaked in W-5, no issue.

- The cold-agent trial found no failure and five gaps of text, all in the guide: how to mark a system external (no flag; `qualifiers: [external]` is a convention), a patch that adds a relationship (`ADD`), the default plateau and the stale `views/` folder, the default of `diff --against`, and that `query graph` is one line of JSON. A scripted walk had not found any of them: the walk asserts what the author thought of, the trial asks what a newcomer needs.
- The schema leaves two things as `any`: a patch `value` and the `properties` of a view. The view properties are in the guide's table, checked against the code by `GuideViewPropertiesTest`.
- Two defects of other commands found and left alone by T1, filed as issues: a saved overview view with no `properties` fails with a NullPointerException; the dangling-reference sentence (`unable to find the element ...`) names no file.
- A `permissions:` block (contents and packages write) was added to `Build` before 0.19.0 (cb4dead); the next push to `main` and the release exercised the snapshot deploy and the image, and the tag run published the website.

## Lessons Learnt

- Carried from wave 021: open the pull request as a draft as soon as a run adds a native resource; a tested script beats a long step; a run that adds a Java class needs `reflect-config.json` in its `likely_paths`; a manual test reads `.adoc`, so a docs-only run needs the whole verification set after its last edit.
- A scripted walk and a cold agent find different things: do both for a tool that is read by a machine. The trial cost one short sub-agent session (about 100k tokens) and found five gaps in text no test could have found.
- Write the dispatch entry of the next run in its own commit, or after the commit of the run before: this wave put it in the previous commit twice.
- Do not stop a stale test run with `pkill -f <name>` from the shell that holds the name in its own command line (it kills itself): kill by PID.
- A time-limit assertion in a generated test is a flake waiting for a loaded machine; the property is the save, not the speed.
