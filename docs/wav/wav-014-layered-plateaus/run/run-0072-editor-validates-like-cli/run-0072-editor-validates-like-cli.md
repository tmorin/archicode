# Run 0072: Editor validates like the command line

Wave 014 (`layered-plateaus`), item W-15 (phase P0). Focus: have the editor and the command line refuse the same manifests with the same sentence (issues tmorin/archicode#75 and #76).
Document profile: `single-document` (the scope is settled by the wave plan and the two issues; what the run decides is the contract between the two readers). This file carries scope, decisions, canonical impact, review passes, tasks, verification and findings. There is no pln: the task list below is the plan, and its state is the state of the run.

## Scope

1. #75. The editor refuses, with the sentence of the command line, a manifest that has a key its element does not have, a nested element whose `kind` is missing or none of those its parent takes, a value of the wrong shape, a key that is required and absent, and a `workspace.yaml` that has a key or a value of the wrong shape in `settings` (and in the rest of the file, `styles`, `formatters`, `application`, `technology`, the top-level keys).
2. #76. An unknown `header.kind` gives one sentence in both tools: the value and the kinds there are, no Java class name.
3. The cases are listed once, in `negative-cases.json`, and read by a Java test and a node test. The table the editor reads with is checked against the classes by a Java test, so that a class that gains a key fails until the page knows it.
4. The messages pinned by waves 012 and 013 are updated where this run changes them; the list is under Verification.

## Decisions

- **D1. The editor reads with a table (`READ_SCHEMA` in `standalone.html`), the command line with its classes, and a test compares the two.** The issue proposed "the kernel, or a schema shared with the command line". A shared schema file would need a build step the page does not have (it is one file, opened from a file or a server), and the kernel (Rust, compiled to WebAssembly) would carry a third copy. The table is a JSON literal between two marker comments in the page; `EditorReadSchemaTest` reads it from the page and, for every type, asks the real reader: the keys it takes (the reader's own `UnrecognizedPropertyException`), the keys it needs and the order it checks them (the non-null failures, one by one), the other names of a key (each is read), the kinds of every polymorphic interface (the `@JsonSubTypes`) and the kinds of manifest (`ManifestKind`). It failed once on the first run, for the one thing the page had missed (`SolutionGroup` also takes `element`, a Lombok `@Singular` adder), which is the proof that the test sees a missing key.
- **D2. The editor finds the problems in the order the reader finds them.** Jackson fails on the first problem in document order: a key is checked where it stands, a `kind` of a nested element is read before the other keys of the object whatever its place, an object that lacks a required key is told when it is finished (so an unknown key later in the object comes first, and a sibling before it comes first too). `readObject` does the same; `manifestProblem` reads the manifest as a header and a content in the order of the file, then the content as the kind says. This also settles two items of #77 that belong to this run's area: a nested element with no `kind` is `missing `kind` (known: ...)` in both tools (it was ``unknown kind `null` `` on the command line), and the editor no longer checks `header.version` before the layered-plateau and unknown-key checks (`kind: plateau` with no `version` gives the layered-plateau sentence in both tools). The rest of #77 is W-17's.
- **D3. The command line's sentences are improved where they said the reader's words.** In `ArchiCodeException.reason`: a text, a number or a boolean where a list, a map or an object is expected is `the value has the wrong shape (found a string)` (it was `Cannot construct instance of ...Builder (although at least one Creator exists): no String-argument constructor...`, with a Java class name); a number is `a number`, with or without a decimal point (it was `an integer` and `a floating-point`, which the page cannot tell apart: `1.0` is `1` once read); a missing `kind` is told as missing, with the kinds there are; an empty text where a collection is expected is the same wrong-shape sentence; a value that is none of the values of an enum (`header.kind`, `layer`, `operator`) is ``unrecognized `path` "value" (known: ...)`` and no class name (#76; the proposal of the issue, with the known values sorted, the full ids for the kinds); the keys the generated builders add (`$fillValuesFrom`) are not listed as keys an author can write. `ManifestParser.missingKey` now also reads `x is marked non-null but is null` without `problem:` (an explicit `id:` with nothing after it, an action without `operator`) and is used for `workspace.yaml` as well: `Missing settings.facets.customs[0].name`.
- **D4. The page accepts what the command line accepts, and refuses it no further than the command line does.** The page was stricter than the command line in one place, and looser in several. Stricter: a kind written with other letters or spaces around it (`ARCHICODE.MORIN.IO/SYSTEM`, which the command line reads) was refused by the page and is now read; `stripArchicodeKindPrefix` does the same. Looser, now aligned: a bare `kind: system` was read by the page and is refused by both (the prefix is required). Not aligned, on purpose and filed: see Findings.
- **D5. `workspace.yaml` is a fatal error of the page, like the command line's.** `Could not read/parse workspace.yaml: <sentence>`, the prefix the page already used for a file it cannot parse; the rules of the plateaus come first (`checkPlateauStructure`), as on the command line, and keep their own heading. The tests that kept an unknown key of `settings` alive through a save (`plateaus.test.js`, `workspace-name.test.js`, `yaml.test.js`) cannot have one any more: they now keep what can exist (the other top-level keys, the managed settings).
- **D6. A group at the root of a manifest (`container-group`, `solution-group`, `system-group`) is not checked by the page.** The command line cannot read them (`unknown kind `_group``, a slip in `ManifestKind.getSubTypeName`, filed as #79 with the `SYSTEM_GROUP` class slip); there is no sentence of the command line to say. They stay `null` in the table.

## Findings

- **F1. The page was stricter than the command line in one place.** `ARCHICODE.MORIN.IO/SYSTEM`, or a kind with spaces around it, is read by the command line (case insensitive enum, trimmed) and was `Unrecognized header.kind` in the page. Both read it now (D4), pinned by `LayeredPlateauRefusalTest` and `editor-reads-like-cli.test.js`.
- **F2. Seven tests of earlier runs held files the command line refuses.** `size: !!str 12`, a list under `tags`, a `person` under a `solution`, a key `name2`, `unknown-section`, `zeta`, a style named `c`: each was valid for the page because the page checked nothing, and none could have been the file of a user whose command line works. They are listed under Verification. This is what #75 meant by "the editor opens the same files without a word", seen from the tests.
- **F3. `known: ...` listed `$fillValuesFrom`** (a method the Lombok `@SuperBuilder` adds to the builder), and listed it first. It is not a key an author writes; it is out of the sentence in the command line and absent from the table.
- **F4. Two items of #77 are done here** (the nested element with no `kind` told as unknown with `null`; the page checking `header.version` before the layered-plateau and unknown-key checks): D2, with the tests `editor-reads-like-cli.test.js` and `LayeredPlateauRefusalTest.shouldTellThePlateauKindBeforeTheVersionThatIsMissing`. W-17 can check them off and keep items 3 to 6.
- **F5. Filed.** #79: the three group kinds at the root of a manifest cannot be read by the command line (`unknown kind _group`: `ManifestKind.getSubTypeName` keeps the underscore, and `SYSTEM_GROUP` is declared with `SolutionGroup`), and the editor reads and can create them. #80: what the two tools still do differently (a `null` where a list or an object is expected crashes the command line with a stack trace and is accepted by the page; an empty `workspace.yaml`; a whole number as `header.kind`; coercions; the sentence lists the Java names `directoryNameTemplate`, `globalEnabled`, `hideUnlinked`, `jsonPath` while the documentation writes the kebab-case ones; the page does not tell lines and columns).
- **F6. Not seen.** The page in a browser (the banner of a refused `workspace.yaml` and the red mark on a refused manifest were read from the state in the node harness, not looked at); the cost of the walk on a very large manifest (it is one pass, linear in the size of the content); the native image (the reflection test passes, the native runner was not run, as in earlier runs).
