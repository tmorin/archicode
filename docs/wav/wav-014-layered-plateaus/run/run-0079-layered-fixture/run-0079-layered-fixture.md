# Run 0079: Layered fixture

Wave 014 (`layered-plateaus`), item W-5 (phase P1). Focus: run the Brightcart layered form on the real tools and have it agree with the complete folders.

Document profile: `single-document`. The design questions of the run are few and settled by the wave plan (the operators, the syntax, `override` in the content), the three facts the plan did not foresee (no `MOVE`, the bulk edit, the `replaces` of inherited elements) are decisions below, and the rest is a fixture, its tests and a document. A TDD would restate the plan and a pln would restate the task list. The review passes are kept (KDMLLC, C scan, open questions) and answered in this file. There is no prd, tdd or pln: the task list below is the plan, and its state is the state of the run.

## Scope

In:

- The generator (`generate.mjs`, `description.mjs`) writes the layered rendition in the syntax the engine reads, and commits it as `src/test/resources/brightcart/layered/`: a folder per plateau with a `Kind: Plateau` manifest (`id`, `name`, `horizon`, `override` when the parent is not `baseline`, `patches` with `REMOVE`, `SET`, `ADD`, `MERGE`), a `plateau: <id>` header on every manifest of a plateau other than `baseline`, and a `workspace.yaml` with `settings.manifests.paths: ["./**"]`. `folders/` stays until W-9. The generator's resolver reads `layered/` back from the committed files and still agrees with `folders/`.
- New tests run `diff`, `query graph`, `plateau list` and `views generate` on `layered/` through the real command line and require what `folders/` gives: P1, P2, P3 and P5 (counts, text, table of changes, warnings), the notable cases, the sizes of the four plateaus, the cascade of a `REMOVE`, the same PlantUML files byte for byte, and a stable output over two runs.
- `layered/` is a shipped file: `ShippedFilesTest` and `shipped-files.test.js` load it (`exceptions.json` stays empty); the editor harness opens it and the test says what it pins.
- `docs/fixtures/brightcart-spec.md` says which results the layered tools now verify, and its section 8 is corrected (`override` is a key of the content of the Plateau manifest, not of its header).
- The Native smoke step of `.github/workflows/ci-build.yaml` gets the `plateau list`, `diff` and `views generate` lines on `layered/` beside the ones on `folders/`.

Out: the editor reading the chain (W-6); a test per negative variant (W-11, the variants V1, V3 to V8 were only tried by hand); the removal of `folders/` and of `--baseline` (W-9); the composition of `replaces` (#89, filed); the manual (W-13).

## Decisions

Given by the wave plan: D1 to D5, A1 to A9. None of the assumptions failed when tried; none was replaced. Decided here (none contradicts the plan):

- **D24. Pattern R replaces the three `MOVE` of the description.** The wave builds no `MOVE` or `RENAME` (non-goals) and a patch never changes an `id` or a `parent`, so `shop.cache` to `commerce.cart-store` (inhouse), `commerce.search` to `discovery.search` and the rename of the system `shop` to `storefront` (marketplace) are written as manifests that say `replaces`, a `REMOVE` of the old element, and the `ADD` of what pointed at it (the cascade of the `REMOVE` takes those links and entries): 8 patches in place of 6, four declared elements more (`commerce.cart-store`, `discovery.search`, `storefront`, `storefront.web`; `shop.mobile` is declared as `storefront.mobile`, the trap of L2 is gone). The resolved plateaus are the same (sizes, counts, notable cases, the generator checks them), the lists of five files of `folders/` change order only (a relationship appended in place of kept in the middle, an application appended): `app.commerce.yaml`, `app.discovery.yaml`, `tec.prod.yaml`, `tec.staging.yaml` of `marketplace`. The model of the generator loses its `MOVE`; V6 (a `MOVE` onto an existing reference) becomes a `SET` of an `id`, which the kernel refuses.
- **D25. `SET` replaces, `MERGE` adds (the note of run 0075).** The bulk edit of N12 (the twelve `Quarkus` containers get the tag `runtime`) is `MERGE` with `json-path` on the elements, `field: tags` and `expect: 12`; no count moves. The model's `SET` of `tags` replaces (A4).
- **D26. The plateau of a manifest is its header, the generator checks the folder.** Every manifest of `saas`, `inhouse` and `marketplace` says `plateau: <id>` (the old fixture had one file that did, to show the header agreed with the folder); `baseline`'s say none. The generator's reader decides by the header, like the tools, and fails if a file sits in the folder of another plateau.
- **D27. The generator writes `layered/` always; `--layered <folder>` is gone.** A rendition that the tools read is a committed folder, like `folders/`; an option that wrote a second copy elsewhere has no reader. The generator takes no argument.
- **D28. `workspace.yaml` of `layered/` reads `./**`.** Every manifest below the folder of `workspace.yaml`, except the folders of generated views (`views-*`, so the tests and the smoke step work on a copy and the next run does not read its own `gap.json`). The tree forks, so no default plateau: every command and test names it (finding F1 of run 0078).
- **D29. The comparison table of the two mechanisms differs by the cascade only.** `gap.json` of the layered tool has one more key (`cascade`) and `gap.md` one more section at its end. The test removes the key and requires the rest equal, and requires the Markdown of `folders/` to be the beginning of the layered one.
- **D30. `expected/comparisons.json` gets the layered questions.** `layeredCommand` (`--against` in place of `--baseline`; null for P6, which is what the old mechanism prints for the question P4 asks), `layeredIgnoredReplaces` and, for P4, `layeredGives`, the counts the layered tool prints (`+39 ~3 -7`, 10 / 2 / 1, `+35 ~1 -9`) next to the model's. `renditions.json` counts both renditions.
- **D31. The editor test pins what the editor does today.** It opens `layered/` (the tree of the four plateaus with the parents of the plan, a Plateau manifest for each, no problem, no warning, every file of the folder read, none unread), draws `baseline` alone (28 application and 22 technology elements, `state.plateaus` empty), and its 50 files go through the line-preserving save as the 73 of `folders/` do (no edit gives the file back, a rename changes one line, a tag only adds lines).

## Findings

- **F1. The two mechanisms agree.** For P1, P2, P3 and P5 the layered tool gives the counts of `expected/` and the table of changes of `folders/`, row by row (the JSON `counts` and `changes` are equal); `query graph` lists the same elements and relationships of the four plateaus; `views generate` writes the same PlantUML files, byte for byte, in the four `views-<plateau>`, the three comparison folders and all the facet folders (3,000 files and more compared), the two `gap` files of a comparison aside. No assumption (A2 to A4, A6, A8, A9) failed.
- **F2. A defect of the engine, fixed here: spurious `replaces` warnings.** `diff --plateau marketplace` printed ten warnings (`replaces of commerce.cart ...: shop.app.cart is not an element of the base plateau, ignored`), `views generate --plateau marketplace` too, with the right counts: an element a plateau inherits from a layer above keeps the `replaces` of the layer that declared it, and the base (the parent) does not have what that layer replaced. The complete folders never warn, they write only the `replaces` of their own plateau. `PlateauComparer` now leaves out of the target of a layered comparison the `replaces` that the base writes the same way for the same element (a dozen lines; only a layered target is touched, so every other output is byte for byte what it was). `BrightcartLayeredDiffTest.theToolWarnsAboutEveryReplacesItIgnoresAndAboutNothingElse` fails on P3 without it (checked: ten warnings) and passes with it; P5 and the comparison with `baseline` keep the warnings the complete folders print (7 and 1: they name what the compared plateau does not have).
- **F3. The composition of `replaces` is not built (L9, P4). Filed: #89.** `diff --plateau marketplace --against baseline` gives `+39 ~3 -7`, 10 moved / 2 split / 1 merged, `+35 ~1 -9`; the model's P4 is `+38 ~3 -6`, 11 / 2 / 1, `+35 ~1 -9`. The tool reads the `replaces` of every layer of the chain relative to the plateau it compares with: `discovery.search` replaces `commerce.search`, which `baseline` does not have, so it reads as new (with a warning) and `shop.app.search` as removed. These are the only two rows that differ. Not an assumption of the plan: the plan does not ask for the composition. Pinned by `marketplaceAgainstBaselineIsP4ButForTheMoveThatTookTwoSteps`; the spec says it in section 10.
- **F4. Variants, tried by hand on a copy of `layered/` (no test: W-11).** V1 `plateau marketplace: patch 13 (SET target commerce.catalogue): selects nothing, there is no element commerce.catalogue in the application layer`; V3 (`override: saas`) ``in the plateau `marketplace`, `prod.cloud.cdn` is declared under `prod.cloud`, which does not exist`` four times (one line for each element declared under a parent the graph lacks: W-11 decides whether that is one sentence); V4 ``in the plateau `baseline`, `commerce.cart` is declared under `commerce`, which does not exist``; V5 two warnings (the plateau `inhous` exists only through one header; one letter from `inhouse`) and an error in `inhouse`; V6 ``plateau marketplace: patch 1 (SET target platform.broker): `id` cannot be changed: a patch never changes an id or a parent``; V7 `plateau marketplace: patch 1 (REMOVE target shop.cache): selects nothing, ...`; V8 `plateau saas: patch 18 (SET target fulfilment.sync): fulfilment.sync has no relationship to shop.db with the label ...` and `plateau inhouse: patch 25 ...`. Each names the plateau and the patch or the element; none prints a stack trace.
- **F5. The layered tool and the complete folders differ by the cascade only** (D29). The cascade of a `REMOVE` is the one thing the layers know and the folders cannot: `gap.md` has a section, `gap.json` a key, and the test for N2 reads `backoffice.console` losing its links to `shop.app.catalog` and `shop.app.promotions`.
- **F6. For W-6 and W-9: how to draw each plateau of `layered/`** (on a copy: `views generate` writes `views-*` next to `workspace.yaml`). `plateau list`; `diff --plateau saas|inhouse|marketplace`; `diff --plateau inhouse --against saas`; `diff --plateau marketplace --against baseline`; `views generate --plateau baseline|saas|inhouse|marketplace` (each writes `views-<plateau>`, its facets and, but for `baseline`, `views-<plateau>-vs-<parent>`); `query graph --plateau <id>`. Outside `likely_paths`:** `src/main/java/io/morin/archicode/viewpoint/kernel/PlateauComparer.java` (F2), `src/test/java/io/morin/archicode/doc/ShippedFilesTest.java` (a layered workspace is loaded once per plateau of its tree, since the tree forks and a default plateau does not exist), `src/test/javascript/viewpoint-kernel/shipped-files.test.js` (one assertion: `layered/workspace.yaml` is among the workspaces), `CLAUDE.md` (two sentences).
