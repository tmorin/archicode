## Decisions

- **D1. One key function, one stamp, per cache.** `modelsKey(comparison, facet)` is the part both keys share: `modelVersion`, the facet as the kernel reads it (`JSON.stringify(toKernelFacet(facet))`, a dozen bytes, so a facet edited in the settings under the same name is a new key), the plateau compared with, `changesOnly` and `hideWording` (only with a comparison drawn), and the text of an empty relationship. `diagramCacheKey` adds what a drawing is made from and the kernel input is not: the viewpoint, the layer as `buildKernelInput` settles it, the element, what the map has opened, pinned and hidden, `hideUnlinked`, the shown texts, the styles, and `viewKey`. The entry also keeps the two indexes it was made from (`modelsNow`, `modelsAreThoseOf`) and is used only while they are the ones now: the net `comparisonCache` already has, under a replacement of a model that forgot `modelsChanged()`. Taken before the drawing is laid out, so an edit that lands during the layout makes the entry stale, not fresh.
- **D2. The cache is asked before any input is built.** `mountDiagramIfNeeded` built the kernel input first (to serialise it); it now builds it after the cache has missed. `quietReferencesThroughFacet` built one input per layer and viewpoint, then asked the cache; it asks first. This is what makes the cost of a render that finds its answer independent of the size of the model, and is what the node test counts (calls of `toKernelElements`, of the kernel's `compute`, serialisations of a model).
- **D3. `diagramModelFingerprint()` is removed.** It walked the index to catch what the input did not carry (names, kinds, descriptions, relationships to unknown elements). All of it comes from `AppState.index`, which is replaced at three places only (the empty state of a load, a load, `rebuildIndexAndRender`), each followed by `modelsChanged()`; the records are rebuilt, not mutated, by every edit. So the version counter covers it, and a test per way to change the model (an edit that renames, a file edited, a deletion, a load) shows the drawing is the one a page without a cache draws.
- **D4. The quiet references' old key left out `only_changes`.** Its key was the kernel inputs minus `only_changes`, so Changes only, which changes what the kernel answers, did not change the key. `modelsKey` holds it. This is a correction, not a regression: noted because the test that pins it fails on the old page for that reason too.
- **D5. A removed environment lists its `uses` in the "What changed" block, Before only.** Same place, same label and same shape as the applications of a removed node (#71) and as the `uses` of a changed environment (the row of the table: Before and After). Read from the baseline's own record, as the file wrote it, like the applications. Nothing to list: no block (the same rule as for the applications, pinned by run 0066). The panel does not say `Uses: none`, which the live panel of an environment does: a removed element's panel lists what it had, and an empty block would say nothing a reader needs.
- **D6. Below 40rem the three regions are stacked, not squeezed.** The cause of the 424 px: the tree has `min-w-48` (12rem, 192 px), the inspection `min-w-56` (14rem, 224 px), and a minimum wins over `max-w-[40vw]`; with the two 4 px handles that is 424 px before the centre panel (`1fr`) has any room, so at 360 px the centre was 56 px wide, its header actions (188 px, `flex-shrink: 0`) went past it, and the document was 424 px wide. Squeezing the minimums to `min(12rem, 40vw)` would have kept the document at 360 and the centre at 64 px, which is not a page one can use. So one `@media (max-width: 40rem)` block, last in the stylesheet: `.app-shell` is a column, the regions are as wide as the window (the inline widths that dragging saved do not apply: `width: auto !important`; the handles are hidden), the tree is at most 30vh, the centre has a height of its own (80vh, 24rem at least: it had the grid's row), the inspection at most 50vh. 40rem is where the three columns leave the centre 216 px (640 - 424), so the stacked layout is used exactly where the centre would be narrower than that. Wider windows keep their rules untouched (a test pins that the rules are only inside the query).
