## Scope

In:

- `WorkspaceFactory` loads a layered plateau as its chain (`LayerLoader`): for each plateau from the root, the elements, views and stories that say `plateau: <layer>` are added to the graph, then the kernel (`apply_patches`) applies the patches of the layer, then the layer is checked and a mistake names the layer (A8, A9).
- `--plateau <id>` draws a layer; `--against <id>` compares (default: the plateau it overrides); `diff` between any two plateaus, siblings included; `views generate` writes the plateau and, for every plateau that overrides another, its comparison.
- The new command `plateau list`.
- The folders `views-<plateau>` and `views-<plateau>-vs-<against>`.
- The cascade of a `REMOVE` (`removed` and `dropped` of the kernel's report) in the table of changes (`gap.md`, `gap.json`, and the three formats of `diff`).
- The old mechanism (`settings.plateaus`, `plateau add`, `--baseline`, `PlateauAdder`, `Plateaus`) works as it did and is not renamed; how the two sets of options relate while both exist is pinned below.

Out: the Brightcart layered fixture (W-5); the editor reading the chain (W-6); the removal of the old mechanism (W-9); the manual (W-13). `MOVE` and `RENAME` do not exist (wave non-goals). The kernel is not changed.

## The shape of the load (the design fork)

The real fork was where the chain meets the graph. (a) **Apply the patches to the JSON of the two layers, layer by layer, and read the model back** (the way a facet is applied): the kernel is the only code that knows what a patch does (its selectors, its cascade, its errors), the Java side only adds manifests, hands over the JSON, reads it back and checks. (b) Keep the model as objects and apply the patches in Java: a second implementation of the four operators, of JSONPath and of the cascade, to keep equal to the kernel's. Chosen (a), as the plan says ("the kernel applies the patches of the layer"). Two consequences:

- A layer **without patches does not leave the objects of the model**: nothing is written as JSON and read back for it. Only a layer that has patches goes through the JSON, and it is the document the kernel takes for a facet: `{application: {elements}, technology: {elements}}`, nothing else of the workspace. A round trip with the mapper of the files is not faithful (it leaves out an empty tag, an empty label, and writes `replaces` as a set, not as the author wrote it), and a plateau whose only patch touches one element would then show false changes on the others; the review found it (finding 1 below). So that call uses a copy of the mapper that keeps the empty texts (`NON_NULL`) and writes `replaces` as it was written (a serializer for `Replaces`, in the copy only: every other output of the tool is written as before).
- The elements of the layer are in the graph **before** its patches run (the index adds them to the roots), so a patch of a layer reaches an element that layer adds (A9; test `setAddAndMergeChangeAFieldAndSetWithWhereChangesOneRelationship`, `MERGE` of the tags of `commerce.cart` in `inhouse`).

The loader keeps the existing indexing (`ElementIndexFactory`) and the existing model; `WorkspaceFactory.load` takes the layered path when `ManifestParser` says the manifests are layered and the workspace has no `settings.plateaus` (`parse(..., layersAllowed)` already refuses both together).

## Decisions

Given by the wave plan: D1 to D5, A1 to A9. None of the assumptions failed when tried; none was replaced. Decided here (none contradicts the plan; each is pinned by a test):

- **D15. Which plateau is read without `--plateau`.** `settings.current` if it is there (it must be a plateau of the tree: ``settings.current` names the plateau `x`, which is not a plateau of this workspace (the plateaus are ...)``), else the last plateau when the tree is one line, else an error that asks for a choice: ``the plateaus of this workspace are not one line (`baseline` is overridden by `inhouse`, `saas`): name the plateau to read with `--plateau`, or with `settings.current` ``. The old mechanism reads the last of the list; a fork has no last one, and picking one silently is the surprise to avoid. `--plateau` wins over `settings.current`.
- **D16. `--against` and `--baseline` while both exist.** `--against` is the option of layers, `--baseline` of `settings.plateaus`; each refuses the other with one line, before anything is written (`LayeredAgainst`):
  - on a layered workspace: ``` `--baseline x` cannot be used: the plateaus of this workspace are layers (`plateau:` in a header, a manifest of kind `archicode.morin.io/plateau`): compare with `--against` ```;
  - on a workspace with `settings.plateaus`: ``` `--against x` cannot be used: the plateaus of this workspace are listed in `settings.plateaus`: compare with `--baseline` ```;
  - on a workspace with no plateau at all, `views generate --against x`: ``` `--against x` cannot be used: the workspace declares no plateau (a `plateau` key in a header, or a manifest of kind `archicode.morin.io/plateau`) ```; `--baseline x` there and `diff` there keep their old sentences (W-9 rewrites them with the key).
  - `--against` names any plateau (siblings, the future, `baseline`); an unknown one is the sentence of `--plateau` (``unknown plateau `nope`: the plateaus of this workspace are `baseline`, `inhouse` and `saas` ``); the plateau itself: ``` `--against inhouse` is the plateau that is compared: choose another plateau to compare it with ```.
- **D17. `views generate` compares every plateau that overrides another.** In the old mechanism a comparison is made when a `baseline` is asked for or written, because "a comparison doubles the views, and is not generated by surprise". In layers `override` is the written baseline (a plateau other than the root always has one), and the P1 gate says `views generate --plateau <id>` comes "with its comparison views". So: a plateau other than the root is compared with `--against` or with its parent; the root is drawn alone (no `views-baseline-vs-...`). `diff --plateau baseline` without `--against` is ``the plateau `baseline` is the root of the plateaus and nothing is before it: there is nothing to compare it with. Name a plateau with `--against` ``.
- **D18. The folders.** `views-<plateau>` for every plateau including `baseline` (the folder of a workspace without plateaus is still `views`); `views-<plateau>-vs-<against>` for the comparison, holding `gap.md`, `gap.json` and `plantuml/`; `-o out` replaces `views` as for the old mechanism (`out-<plateau>`, `out-<plateau>-vs-<against>`). The folders named after `settings.views.path` (`views-*`) are left out of the next read of a `/**` path by the rule of run 0076, and the ones named after `-o` are not (that rule never followed `--output`): a workspace that reads `./**` and generates with `-o out` twice reads its own `gap.json` the second time (finding 4).
- **D19. What is checked after a layer (A8), and in whose words.** Everything below names the plateau, one `error:` line each, all those of the first plateau that is wrong together (sorted by element, then by what it points at); the layers above it are not looked at.
  - ``in the plateau `p`, `a.b` has a relationship towards `x`, which does not exist``; ``... `a.b` uses `x`, which does not exist`` (an environment); ``... `n.m` hosts `x`, which does not exist`` (a node's `applications`); ``... `a.b.c` is declared under `a.b`, which does not exist`` (a manifest with a `parent` the graph does not have). They are the checks of the kernel's `compare` (`dangling reference`) in the author's words, made when the layer is built so that they name the layer that caused them (V8 of the fixture: the stale list copied into a patch). The last one is told **before the patches run** and alone: a patch may remove a parent, and the elements declared under it go with it (a subtree), which is not a mistake; the others are told after the patches.
  - A view placed in the layer (``plateau:`` in its header): the elements its `properties` name (`element`, and the entries of `pinned`, `opened`, `hidden`) must exist in the layer of the view: ``in the plateau `p`, the view `v` (`file`) names `x`, which does not exist``. A story placed in the layer: the same for the steps that carry their own view (``the story `s` (`file`) names ...``). A step that names a view of the workspace which nobody declares stays what it was, a warning of the workspace that is drawn (the final workspace is checked once, on the views of the whole chain).
  - A view or story of a layer is **not** looked at again in the layers above: a layer that removes an element a view of its ancestor names does not break the ancestor's view (views are not patchable in this wave, so the descendant could not repair it; the view is only drawn when asked for with `-i`, and fails there as it always did).
- **D20. The cascade of a `REMOVE`** is what the kernel reports as `removed` (every element that left, the subtree included) except the elements the patch selected (they are rows of the table), plus `dropped` (the entries taken out of elements that stay: ``relationships: shop.cache (flushes)``, `uses: x`, `applications: x`). It is listed for the `REMOVE` patches of every plateau of the target's chain, **among what the plateau it is compared with has**: an element it has and the target no longer has, and an entry its element held (`Removal.effects(base)`). So the cascade is part of the difference between the two plateaus and not of the history of the target: a removal below both plateaus, or of an element that a plateau of the chain added and another removed again, is not in it, and against a descendant it is empty (finding 3 of the review; a first version took the plateaus of the chain that the other plateau does not have, and listed `extra.sub` that was in neither). Format: after the table (and after the candidates), in text, Markdown and JSON (`cascade`), only when there is something to say, so that every other output is byte for byte what it was (`GapReport.render(..., cascade)`). Columns: plateau, `<rank> <operator> <selector>`, effect (`removed` or `dropped`), layer, element, detail.
- **D21. `plateau list`** has its own format, one line per plateau in the order of the tree, columns aligned with two spaces, no trailing space: `PLATEAU  PARENT  SOURCE  NAME  HORIZON`, `-` for what is absent; SOURCE is `manifest <file>`, ``headers only (<files, up to three then and N more>)`` or `implicit` (the root that nothing names). Warnings of the tree go to the error output as for every command. A workspace with `settings.plateaus` gets one line, not a list of the old plateaus (they are not layers and the old mechanism goes in W-9): ``this workspace lists its plateaus in `settings.plateaus`, which are not layers: `plateau list` lists the plateaus of a workspace whose manifests say `plateau: <id>` (the plateaus here are `a`, `b`)``. A workspace with no plateau lists `baseline` alone.
- **D22. `Plateaus.select` no longer decides `--plateau` and `settings.current` for a workspace without `settings.plateaus`.** Whether such a workspace has layers is known when its manifests are read, so the two checks moved after the parse (`Plateaus.requireNoPlateaus`, called by `WorkspaceFactory.load`, `plateauTree` and `PlateauAdder`); the sentences are the same, and a path that cannot be read still brings them with it (as before). The only visible difference: a workspace that has a broken manifest and `--plateau x` (or a `settings.current` that names nothing) now tells the manifest first. On a layered workspace `settings.current` is checked whatever `--plateau` says, as `Plateaus.select` does for `settings.plateaus`.
- **D23. The plateau a layered load gives is a `Settings.Plateau`** (`id`, `name`, `horizon`, `baseline` = the plateau it overrides) so that the comparison, `StateTags` and the diagrams read it as they read the old one; `Workspace.getPlateauTree()` is not null for a layered workspace and is what the commands ask whether it is layered (`LayeredAgainst.isLayered`).
