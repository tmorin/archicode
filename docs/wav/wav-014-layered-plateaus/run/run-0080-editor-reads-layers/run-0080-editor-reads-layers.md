## The design fork: how the chain is resolved in the page

The page holds a model, `AppState.index` (Maps of records), that every panel, the trees, the diagrams and the edits read, and a second model, `AppState.baseline.index`, that the comparison reads. The fork was how a layered plateau becomes such a model.

- (a) **Resolve each plateau as a *state* (a JSON graph), layer by layer, with the kernel, keep the states, and build the index from the state of the plateau drawn** (`resolveLayerStep`, `layerStateOf`, `layerModelOf`). The state of a layer is the state of the plateau it overrides, cloned, plus the manifests of the layer, plus its patches (one `apply_patches` call, the very call `LayerLoader` makes), plus the checks. A plateau reuses the state of its parent, so `marketplace` costs one layer once `inhouse` is resolved, and a click on a node already resolved costs nothing.
- (b) Re-run the old `buildIndex` over the manifests of the chain, and apply the patches to the records in JavaScript: a second implementation of the four operators, of JSONPath and of the cascade, to keep equal to the kernel's.

Chosen (a), as the plan says ("the editor resolves the chain with the kernel"): the kernel is the only code that knows what a patch does. Consequences:

- **The index is built from the JSON the kernel returns**, by the same `indexElementRecursive` as before (one optional parameter, `attachedRoots`, so that the root of a manifest that says `header.parent` keeps its own kind, level and file inside the element it names). An element's `sourceFile` is still the manifest that declares it, so every edit still lands where it always did.
- **The records of a layered model carry where they come from**: `declaredIn` (the plateau of the manifest), `patched` (field -> the last patch that set it) and `touchedBy` (every patch that selected it). A workspace with no layer has none of these, so nothing of its page changes.
- **The comparison is the old machinery**: `AppState.baseline` is the plateau compared with (a model of its own, built from the other plateau's state, never written), and `comparisonState()` asks the kernel's `compare` as before. The plateau drawn is the target, except with the future (see D6).
- **Caching** (`layerCache`): states and models are kept per plateau for as long as the tree of the plateaus (`AppState.plateauTree`, rebuilt by every load and every edit, which end in `rebuildIndexAndRender`) and the text of every manifest are what they were, and the kernel is the one it was. The tree object is the "bump": a new tree is a new cache. A net checks the text of every manifest, so a path that forgot to rebuild is not served from a stale cache (the same net `modelsKey` has). `modelsChanged()` is called by `syncLayers`, which every place that replaces `AppState.index` or `AppState.baseline` ends in (the test `comparison-cache.test.js` checks it).

## Decisions

Given by the wave plan: D1 to D5, A1 to A9. None of the assumptions failed when tried; none was replaced. Decided here (none contradicts the plan; each is pinned by a test of `editor-reads-layers.test.js`):

- **D1. The band is for a workspace without `settings.plateaus`; a workspace with them keeps its selector and has no band.** "Always present" (the plan) is for the layered and the plateau-less workspace; the old mechanism keeps one selector until W-10, and a second one with a lone `baseline` node would be a control that does nothing. Said in the manual.
- **D2. The plateau drawn at the opening** is the one the address names (`plateau=`), else the one this browser last drew in this folder, else `settings.current`, else `baseline`. The command line asks for a name when the plateaus fork; the editor starts at the root, which it can edit. A `settings.current` that is no plateau of the tree is the sentence of the command line (``` `settings.current` names the plateau `x`, which is not a plateau of this workspace (the plateaus are ...) ```); one in a workspace with no layer keeps the old sentence, but is told once the manifests are read (the command line does the same: `Plateaus.requireNoPlateaus` moved after the parse in run 0078), where it was told before.
- **D3. The order of the siblings in the band** (the open question of the plan): the plateaus whose `horizon` reads as a date come first, by date and then by id; the others follow, by id. A horizon reads as a date when it is a year, a month, a day, a quarter (`2026-Q4`) or a half (`2026-H2`); a quarter or a half is its first day. A total order, so the band is the same on every opening. Written in the manual (section *The band of plateaus*). The tree model (`AppState.plateauTree.nodes`, `ids`) keeps the order of run 0077 (siblings by id), pinned by `plateau-model-cases.json`; the band orders for itself (`bandTreeOf`, `compareBandSiblings`).
- **D4. A plateau the command line refuses is drawn all the same, unless the kernel refused its patches.** The command line stops at the first layer whose checks fail (a link to nothing, a parent that is not there, a view that names a missing element). The editor, whose job is to let the mistake be repaired (`baseline` with a dangling link opened and was edited before this run), draws the graph the layer built, tells the sentences of the first layer of the chain that is wrong (`failedAt`, in the words of the command line, ordered as it orders them), and flags the node `!`. A manifest whose `parent` is not there stays at the top under the reference its manifest gives it, as it did. When the kernel refuses the patches of a layer (`apply_patches` returns an error), there is no graph: the plateau, and every plateau above it, is `undrawable`, its index is empty, and the band says why; nothing is compared with it.
- **D5. The mistakes of the tree and the redeclared references keep their banner and block the other plateaus.** With a mistake in the tree (the tree has no nodes), a reference declared twice, or a reference declared again in an ancestor, only `baseline` is drawn (from the manifests, as before this run) and the band says why (`layers.blocked`).
- **D6. The future.** With the future the plateau drawn is the base and the other one the target, so that the counts are `archicode diff --plateau <future> --against <drawn>`'s. The machinery of the comparison reads "removed" as "only in the plateau compared with"; the rule is now by membership (`elementIsOnlyInTheOtherPlateau`): with the past these are the removed elements, with the future whatever the other plateau adds. The boxes, the rows of the Changes panel and the read-only panel follow it, with sentences that say which plateau is which. Not offered with the future: the hand-written state words (`stateWordHintsFor`, they are the target's), the move that writes `replaces` and the *Replaces* field of the form (both old-mechanism, past only; they name the elements of a plateau compared with).
- **D7. Which plateau a comparison follows.** *Past* follows the plateau it overrides when another is drawn; *Future* follows the plateau that overrides it (a chosen target stays while it is still below); a comparison with a plateau that is neither (a sibling, a cousin) stays while it is another plateau. The state is `AppState.layers.compare = { mode: 'past' | 'future' | 'other', other, chosen }`.
- **D8. `replaces` of an inherited element**: the comparison drops, for a layered target, the entries the base writes the same way for the same element (`comparisonInputBetween`, the page's copy of `PlateauComparer.dropInheritedReplaces`), so the editor and the command line warn of the same.
- **D9. A plateau other than `baseline` is read-only for now.** An edit of an element is written in the manifest that declares it, which for an inherited element is a plateau above, and a value a patch set would not change on the page: the rule that makes an edit land in the plateau drawn is W-8's. Until then the writers of an element (`commitElementEdit`, create, delete) and of the lists of views and stories (`createManifestEntry`, `removeEntry`) throw one sentence, the handlers of the fields of a view and of a story (`editSavedView`, `updateStoryField`, `repairStoryStep`) refuse it, and the clicks that write (`WRITE_ACTIONS`) say it in the top bar and change nothing. The one writer left open is the text editor of *Files* (`commitFileEdit`), which writes the text of a file of any plateau: it is how a plateau's own manifest, a patch included, is repaired while the plateau cannot be drawn. `baseline` edits as before (an edit changes every plateau that stands on it; W-8 asks first). The one write allowed in another plateau is *Write replaces*, which writes `replaces` on the new element in the manifest that declares it and refuses an element the target only inherits.
- **D10. What a node of the band says**: its name, its horizon and the counts over the plateau it overrides (`+3 ~5 −11`), computed one node at a time after the drawing (`scheduleBandCounts`) and kept with the models.
- **D11. The address** carries `plateau=<id>` when the plateau is not `baseline`, and the comparison next to a removed element (`compare=`) as the band writes it (`past`, `future:<id>`, `other:<id>`).
