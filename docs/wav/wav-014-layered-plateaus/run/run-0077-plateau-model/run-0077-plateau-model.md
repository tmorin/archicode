## The model (for W-4, W-6 and W-11)

Java, package `io.morin.archicode.resource.plateau` (the model layer; `manifest` and `workspace` depend on it, not the other way):

- `Plateau`: the content of a Plateau manifest. `getId()`, `getName()`, `getHorizon()`, `getOverride()` (null = `baseline`), `getPatches()` (never null; a null item is dropped). `Plateau.BASELINE`. `shapeProblems()`.
- `Patch` (+ `Operator`, `Layer`, `Where`): one patch as data, with the keys the kernel's `apply_patches` takes. `json-path` is the written key, `json_path` an alias. Nothing is applied. **For W-4:** the reader takes an operator and a layer in any case (`remove`, `Technology`) as it does every enum, and the kernel takes `REMOVE` and `technology` only: write `operator.name()` and the lowercase layer when building the kernel's input (`expect: -1` is the kernel's `invalid patch` sentence, with the plateau and the rank).
- `PlateauTree`: the plateaus and how they stack, immutable, built and checked by `PlateauTree.of(declared, headers, layeredBy)` (or `baselineOnly()`).
  - `nodes()` / `ids()`: in the order of the tree (`baseline`, then what overrides it, each followed by what overrides it, siblings by id; the band's horizon order is W-6's).
  - `node(id)`: `Node(id, name, horizon, parent, patches, manifest, headers)`; `parent` is null for `baseline`; `manifest` is the file of the Plateau manifest or null; `headers` are the files whose header names the plateau; `declared()`, `headerOnly()`.
  - **`chain(id)`: the plateaus from `baseline` down to `id`, itself last. This is what W-4 calls**: for each node of the chain, add the candidates / views / stories of `Parsed.ofPlateau(node.id())`, then apply `node.patches()`. `ancestors(id)` (the chain without `id`), `children(id)`, `contains(id)`.
  - `warnings()`, `isLayered()`, `layeredBy()`, `redeclared(declarations)` (a list of sentences), and the static `problems(declared, headers)` (the mistakes of the tree, as a list; `of` throws them).
- `ManifestParser.Parsed` is now `(elements, placedViews, placedStories, plateaus)`: `views()` and `stories()` are the sets of every plateau as before; `ofPlateau(id)` is what one plateau declares on its own (not what it inherits); `Candidate.getPlateau()` is the plateau of an element (`baseline` when the header names none); `Placed<T>(plateau, source, item)` carries a view or a story with its plateau and file.
- Until W-4, `WorkspaceFactory.load` draws `ofPlateau("baseline")` for a layered workspace: the manifests of the other plateaus and the patches are read, checked, kept, and not drawn. The editor does the same (`buildIndex` indexes the manifests of `baseline` alone; the others are walked for what they declare). A workspace that writes no plateau is untouched.

The editor's mirror: `buildPlateauTree(manifestFiles)` returns `{ nodes (Map, tree order), ids, problems, redeclared, warnings, layered, layeredBy }` (`AppState.plateauTree`; when `problems` is not empty `nodes` and `ids` hold nothing: the Java side throws, so W-6 draws no band from a tree that is wrong), `plateauChain(tree, id)`, `checkPlateauRedeclarations`, `layeredAndSettingsPlateausSentence`, and `renderPlateauTreeHtml` (a banner in Elements and Files, next to the duplicates one).

### The shape of the model: the design fork

The one real fork was where the tree lives and what it holds. (a) A tree object in the model layer, built once from "who declares what" and checked at build; the loader asks it for a chain. (b) A flat list of declarations and a resolver the loader calls each time. Chosen (a): the checks (one root, no cycle, known `override`) are properties of the whole tree, they must run before any loading and in the editor too, and W-4 and W-6 both need the chain, the children and the order, which are cheap to answer from a built tree and error-prone to recompute. It holds no element, view or story (those stay in `Parsed`, which is large and changes per load), so the tree is small and the same for every plateau drawn. The placement in `resource/plateau` rather than `workspace` follows the dependency direction (the parser builds it).

- **D9. - **D10. `override: ""` is an unknown plateau** (the sentence shows `` ` ` ``), not "no override"; `plateau: ""` in a header is an id that is not valid; `plateau: ~`, `patches:` empty, `patches: [~]` are absent. No new null crash (#80): nothing reads a null.
- **D11. The mistakes are told together**, one `error:` line each (`ErrorOutput` prefixes every line), in one fixed order, the same in the two tools: the mistakes of the tree (ids not valid, plateaus declared twice, overrides, cycles), then the references declared twice in one plateau (the sentence they always had), then those declared again in an ancestor (only when the tree is right: it needs the chain). A file the reader refuses is told first, alone (the first one in the order of discovery), as today.
- **D12. `settings.plateaus` and layered plateaus are an error, and the only thing told about the layers.** `ManifestParser.parse(..., layersAllowed)` refuses a layered manifest when `WorkspaceFactory` says the workspace has `settings.plateaus` (before the tree is looked at, so a typo in a layer does not hide it); the error names the first layered manifest in the order of discovery. It is found in the folder of the plateau being loaded (the editor: the folder it reads, and the baseline compared with, which it tells in the header); a layered manifest in the folder of another plateau of `settings.plateaus` is told when that plateau is loaded (`diff` loads them all). Not scanning every folder in advance keeps a workspace with a broken folder loading as it did. When a manifest has a file error as well, the command line tells that file first and the editor tells the conflict (the file error shows on the file): after the file is fixed both say the conflict. An edit that adds a layer to a workspace that has `settings.plateaus` shows the conflict in the banner.
- **D13. The checks of the combination of a patch's keys beyond the selector stay with the kernel** (`REMOVE` takes no `value`, `where` goes with `SET`, `expect` goes with a `json-path`...): they are the kernel's `check`, with the plateau and the rank; the model repeats only what makes a patch have no meaning at all (neither or both selectors) because the kernel's sentence for those would name no file.
- **D14. Duplicate-reference detection is per plateau.** Two plateaus that do not stack (alternatives) may each declare `commerce.cart`; the existing sentence for a reference declared twice is unchanged (same plateau); the new one is for an ancestor. A view or a story id follows the same rule (A8 asks for views and stories to be validated after each layer; they are not patchable).
