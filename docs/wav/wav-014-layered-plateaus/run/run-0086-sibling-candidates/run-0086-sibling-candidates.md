# Run 0086: Sibling candidates

Wave 014 (`layered-plateaus`), item W-12 (phase P4). Focus: be offered a pair of replaces only when the two plateaus are one the past of the other (issues #70 and #34). Kernel contract 5.

Document profile: `single-document`, as runs 0075 to 0085. The one real fork (what `compare` does when the host does not say whether the plateaus are on one chain) is decided and pinned below (D56); the decisions are small enough not to need a TDD and a pln. The review passes were kept: a KDMLLC scan of this document and an independent code review of the diff (see *Review passes*).

## Scope

In (the W-12 row of the plan and the second criterion of the P4 gate):

- **#70.** `compare` takes `on_one_chain`, whether one of the two plateaus is the past of the other (an ancestor in the tree of plateaus, which only the host knows). Between siblings the reason `parent` of a candidate is not given, and a pair that has no other reason is not listed.
- **#34.** The state `contains-changes` is explicit in the kernel's output (`contains_changes: true` on an item, only when computed), and the three lists of the seven state words (`ChangeMarks.STATES`, `StateTags.STATES`, the kernel) become one: the kernel's, said by a new entry point `states` and read by Java (`KernelStates`) and by the page. The page had a fourth place that wrote them (four arrays); see D58.
- The kernel contract is **5**; the README of the kernel says what changed; the manual says it in two clauses where a sentence would have lied.

Out: the composition of `replaces` across layers (#89), A1, `Settings.Plateau`, the manual's rewrite (W-13), the CLI's rule that candidates are listed only for a plateau that uses `replaces` (kept, issue #39), the editor's rule that it proposes them for any comparison (kept).

## Decisions

Given by the wave plan: D1 to D5, A1 to A9; none failed. Decided here (none contradicts the plan; each is pinned by a test):

- **D56. `compare` without `on_one_chain` is refused, not defaulted.** The fork: keep the old answer when the input is absent (`true`: the legitimate case of a chain), or refuse. Refused, with one sentence and no partial answer: `invalid input: `on_one_chain` is missing: say whether one of the two plateaus is the past of the other (an ancestor in the tree of plateaus), `true`, or whether they are siblings, `false` (contract 5)`. `null` counts as not given (the kernel's rule for every optional field); a value that is not a boolean is serde's `invalid input: ... expected a boolean`. Reasons, in the README of the kernel ("Comparing two plateaus"): the kernel cannot read the tree of plateaus, so neither answer is right for every caller; a default `true` brings the pairs of issue #70 back to any host that forgets the flag, silently, and a default `false` hides the pairs of a chain; the contract number already tells a host written for 4 (it refuses an answer that says `version: 5`). The price is that every caller of `compare` (Rust tests, node tests, the adapter, the page) was updated once; the test helpers that are not about it say `true`. Pinned by `whether_the_plateaus_are_on_one_chain_is_asked_never_guessed` (Rust), `the kernel asks whether the plateaus are on one chain...` (node) and `theKernelRefusesAComparisonThatDoesNotSayWhetherThePlateausAreOnOneChain` (Java, through Chicory).
- **D57. What "between siblings" takes away: the reason `parent`, and only that.** With `on_one_chain: false` a pair with the reason `parent` and another one (`name`, `description`) stays, listed with the other reason alone; a pair whose only reason was `parent` is not listed. Nothing else moves: the union, the table and the counts are those of a chain (a test compares them). The name and the description are reasons between siblings as anywhere: two alternatives that carry the same name or a close description are still worth a look, and the issue asks for the parent only. "On one chain" is: the same plateau, or one is an ancestor of the other (`PlateauTree.onOneChain`, `plateausOnOneChain` in the page), `baseline` being the ancestor of all; a plateau and its grandparent are on one chain (the pair is legitimate, not a sibling).
- **D58. The state words: the kernel's list, and what became of the others.**
  - The kernel (`lib.rs`) holds `STATES_RELATIONSHIP` (`new`, `changed`, `removed`), `STATES_IDENTITY` (`moved`, `split`, `merged`) and `STEREOTYPE_CONTAINS_CHANGES`; `states` answers `{ version, relationship, identity, container, states }` and reads no input. A test ties it to `Change::parse` and `Change::stereotype`, so a word cannot be added to one without the other.
  - `ChangeMarks.STATES` and `StateTags.STATES` are gone: both read `KernelStates.words()`, which asks the kernel once, on first use (`KernelStates`, `viewpoint/kernel`, in `reflect-config.json`). What `ChangeMarks` keeps is the look of each word (glyph, line), and `ChangeMarksTest.everyStateTheKernelSaysHasALookOfItsOwnHere` fails when a state of the kernel has none (it asserts a glyph and a style of its own for each word, and that an unknown word reads as the marker).
  - The page had the **fourth place**: `RELATIONSHIP_STATES`, `IDENTITY_STATES`, `CHANGE_STATES` and `STATE_WORDS` (four arrays, written by hand), and two literal lists of the same words in the key of a drawing (`['new', 'changed', 'removed']`, twice). The four arrays are now empty `const` arrays that `adoptKernelStates` fills in place when the module is loaded (`loadViewpointKernel`, before the kernel is handed out), and the two literal lists read `RELATIONSHIP_STATES`. They are empty until the kernel is loaded, which is when a comparison exists (the comparison needs the kernel to be built); nothing the page does before then reads them. The look tables (`CHANGE_GLYPHS`, `CHANGE_WORDS`, `CHANGE_DEFAULT_LOOK`, the CSS) stay the page's own, keyed by the word, and `sibling-candidates.test.js` ("the page keeps no list of the state words") fails when a word of the kernel has no entry in one. The page still writes the container's word `'contains-changes'` where the code means it (a test pins it to the kernel's `container`): replacing every occurrence by a variable was out of proportion.
  - Still derived, not asked of the kernel: `StateTags.stateOf` and the page's `referencesAboveChanges` work out `contains-changes` from the union of a comparison by the prefix rule of the references (the kernel's rule), because they work on the output of `compare`, not on a view. They do not read a stereotype. Left as it is and filed as #96: the rule is a few lines, `StateTagRuleTest` and `state-hints.test.js` read the same fixture (`plateau-state-hints`) and must give the same sentences, which exercises both copies, but no test compares them with the kernel's `contains_changes` on the same data.
- **D59. `contains_changes` is the kernel's word that it computed the state.** It is serialised on an item only when true (an input without a comparison gives the bytes it gave), and the stereotype `contains-changes` stays at the end of the list as before (a style can still be given to it). The CLI (`ChangeMarks.stateOf`, `Item.containsChanges`) and the editor (`changeStateOfItem`) read the key and no longer the last stereotype, so a `contains-changes` that an author wrote by hand on a box that holds nothing is drawn as `written-contains-changes` (the author's style and nothing of the default look, the rule of every other state) instead of as the state. Before: both tools drew the mark and the dashed outline.
- **D60. The adapter and the page say it from the tree.** `PlateauComparer.compare(base, target)` asks the tree the two workspaces were loaded from (`onOneChain`); `compare(base, target, onOneChain)` is the explicit form (tests, and a caller that knows). A pair of workspaces that has no tree (no plateau is layered) has no sibling, so it is a chain. The page says `true` for the counts of a node (a plateau and the one it overrides) and asks `plateausOnOneChain(current, other)` for the comparison on screen (past, future and `other` modes alike).
