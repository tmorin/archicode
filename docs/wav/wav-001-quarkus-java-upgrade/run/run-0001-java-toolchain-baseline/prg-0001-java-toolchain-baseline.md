## Findings

- Quarkus 3.21.1 (the version pinned in `pom.xml`, out of this run's scope — reserved for run-0002) predates Quarkus's own "full Java 25 support" milestone, which the Quarkus team shipped in Quarkus 3.31 (per quarkus.io/blog/quarkus-3-31-released). In the event, Quarkus 3.21.1 **does** build and run successfully under a JDK 25 build JVM with `maven.compiler.release=25` — but only after fixing three distinct, real incompatibilities (javac's implicit-annotation-processing deprecation; a JDK 25 JVM security default blocking Byte Buddy's self-attach; and JaCoCo/ASM/Mockito/Byte Buddy versions too old to parse Java 25 class files, including inside Quarkus's own `ClassTransformingBuildStep`). All three were fixable via `pom.xml`-only changes (annotation-processing config, JVM args, and third-party dependency version overrides) without touching `quarkus.platform.version` or any `io.quarkus:*` coordinate. Had `ClassTransformingBuildStep`'s own failure *not* been fixable this way, it would have been a genuine blocker for the wave (contradicting its risk note's "no correctness dependency" assumption) — worth knowing for future waves that pair a JDK bump with an unrelated-looking platform-version bump.
- `.github/workflows/ci-build.yaml` used `distribution: "adopt"` (the retired AdoptOpenJDK identifier) with `actions/setup-java@v2`. Both need to change together: `adopt` has no Java 25 builds, and `actions/setup-java@v2`-`v4` are all deprecated per the action's own README (and `v4` still carries the legacy `adopt` alias, which `v6` removes entirely). Decision: bumped to `actions/setup-java@v6` with `distribution: "temurin"` (TDD DEC-3). Not verified against actual GitHub Actions infrastructure (this run's sandbox has no CI access) — only the workflow file's own correctness (YAML validity, matching the action's documented example) was checked locally.
- A Maven dependency-version override's reach depends on *where* it's declared: a `<dependencies>` override only affects the classpath of whatever directly declares it (a project's own compile/test classpath, or — nested under a `<plugin>` — that plugin's own Maven-resolved execution classpath). Quarkus's own augmentation classloader is built from a *separate* internal re-resolution of the effective POM's `dependencyManagement` (via `quarkus-bootstrap-maven-resolver`), which a plugin-level dependency override does not reach — only a `dependencyManagement` entry, declared ahead of the Quarkus BOM import, does.
- Lombok 1.18.48 (and recent Lombok generally) now detects both Jackson 2 and Jackson 3 on the classpath and emits a non-fatal `[WARNING] Ambiguous: Jackson2 and Jackson3 exist; define which variant(s) you want in 'lombok.config'` for every `@Jacksonized`-adjacent class. This did not block the build and was left as-is (out of this run's stated scope), but is worth a `lombok.config` entry in a future run if the warning volume becomes a CI-log-noise concern.

## Lessons Learnt

- When a wave plan asserts "no correctness dependency" between two runs touching the same pinned dependency (here: Quarkus's own Java-version ceiling vs. this run's JDK bump), verify that claim empirically before trusting it — a framework's own blog post milestone language ("full Java 25 support" landing several minor releases later) is a signal worth checking against an actual local build, not just taking at face value. In this run the claim held, but only after three rounds of real, distinct fixes — it was not a given.
- A pom.xml-level JDK bump's real test is a full `./mvnw verify`, not just `compile`: three of the four failures found here only appeared at `test` or `quarkus:build`, past the point a narrower check would have stopped looking.
- Overriding a transitive dependency's version in Maven is not one mechanism — a project-level `<dependencies>` entry, a plugin-level `<dependencies>` entry, and a `<dependencyManagement>` entry (and *where* it sits relative to an imported BOM) each reach a different classpath. When a build tool builds its own isolated classloader from the project's model (as Quarkus's augmentation phase does), only the `dependencyManagement`-level override reaches it.
