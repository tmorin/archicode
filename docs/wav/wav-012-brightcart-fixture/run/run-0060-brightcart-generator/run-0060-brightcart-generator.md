## Decisions

- **D1. Two source files, not one.** `description.mjs` holds the data (elements, manifests with their file, patches, the document's numbers, variants, notable cases); `generate.mjs` holds the rules (model, emitter, resolver,
  writers, checks). One recipe in two files keeps the data reviewable against the specification without the engine around it.
- **D2. Folders layout.** `folders/workspace.yaml` plus `folders/plateaus/<id>/app.<ref>.yaml` and `tec.<ref>.yaml`, the layout of the Python model (73 manifest files, 1913 lines, 52089 bytes: the numbers of the document).
  `baseline` is written for every plateau but the first (E2); the first has nothing to point at.
- **D3. Layered layout.** `layered/workspace.yaml` (no `settings.plateaus`) and `layered/<id>/plateau.yaml` plus the manifests under `<id>/application/` and `<id>/technology/`, by the file names of the model. `override` only
  on `marketplace` (`inhouse` and `saas` default to `baseline`); one manifest (`inhouse/technology/staging.k8s.yaml`) names its plateau.
- **D4. The resolver is independent of the writer where it matters.** It parses `layered/` and `folders/` back from the disk with a small reader of exactly the YAML the emitter writes, builds the plateaus from the
  files (L0: the manifest belongs to the plateau of its folder), applies the patches read from `plateau.yaml` with the model's operators, and compares element by element (kind, name, description, qualifiers, tags,
  applications, `uses`, relationships in order, `replaces`) with what it reads from `folders/`. It exits 1 on the first difference; shown by tampering with a copy (a qualifier in `layered/saas/plateau.yaml`).
- **D5. The model's checks are the generator's asserts.** The sizes and the nine counts of each of P1 to P6 are written once in `description.mjs` (`DOCUMENT`) as the document's numbers; the notable cases N1 to N17 carry
  machine checks (`checks`) asserted in the model; V1 to V8 are run in the model and must mention the words they expect; M2's 49 declared and 11 + 8 patches are asserted.
- **D6. Variants and merge scenarios are one JSON each** in `variants/` (`V1.json` to `V14.json`, `M1.json` to `M3.json`): change, expected text of the document, class (`error`, `warning`, `error and warning`,
  `refusal`), words the message must contain, and for V1 to V8 what the model reports. Not run by any tool.
- **D7. `expected/`**: `sizes.json`, `renditions.json`, `comparisons.json` (P1 to P6, `verified`, the command, `ignoredReplaces`, the tool's warnings count), `changes.json` (the model's table of changes per comparison: the
  element states and the relationships) and `notable-cases.json`. P6 is marked `verified: archicode diff` (the tool does print its counts, which are what the document says), with the note that it is not the real change
  (P4, model only). See the findings.
- **D8. No view or story manifest.** Section 9 describes five views and two stories per plateau; the document itself says "no manifest views yet" for the generated counts, and the wave's scope for W-1 does not list them.
  Not written; the README says so.

## Findings

- **F1. The P1 gate's third criterion cannot hold with explicit `baseline` keys.** `views generate --plateau <id>` makes the comparison of a plateau that has a `baseline` key, whether `--baseline` is given or not, and for
  `inhouse` and `marketplace` that comparison is E1. The plateau's own views are written first. W-3 fixes it; the wave plan's wording "(no comparison view asked)" assumed the comparison needs `--baseline`.
- **F2. Document corrections.** (a) Layered rendition: 1172 lines and 32237 bytes, not 1171 and 32167: the document's figure left out the line `plateau: "inhouse"` of `staging.k8s.yaml` and the final newline of each file;
  "49 manifests" read as 49 files (45 manifests and 4 `plateau.yaml`). (b) Facet `no-externals` leaves no `Payment provider` system, but the technology nodes `Payment provider (live)` and `(sandbox)` keep the name in theirs.
  (c) V8: the model stops a plateau at its first error; in `inhouse` the failing patch is the relationship, so it does not report the copied list, and `marketplace` is not resolved. (d) Front matter and section 15 say where the
  files are. (e) E1: how it shows on Brightcart.
- **F3. P6 is reproducible by the current tool**, so it is `verified: archicode diff` in `comparisons.json` (what the tool prints, 4 moves and 16 removed), with the note that it is not the real change; the real change of the same two
  plateaus (P4) is the model's alone. The gate wording ("P4 and P6 marked as computed by the model only") is stricter than what is true of P6.
- **F4. The tool's warnings are part of the expected result.** `diff` prints `replaces ... is not an element of the base plateau, ignored` 0 times for P1, P2, P3, 7 times for P5 and once for P6; `expected/comparisons.json`
  records them (`ignoredReplaces`) and the generator computes them from the model.
- **F5. For W-2.** `expected/changes.json` is the model's table of changes and the CLI's `diff -f json` agrees with it for P1, P2, P3, P5, P6 (the label change of N3 is under the new label in the CLI). `contains-changes` is
  not in the `diff` table (it is a state of the drawing), so a test of N13 reads the views or the kernel. The label of the relationships in both is the new one for a label change.
