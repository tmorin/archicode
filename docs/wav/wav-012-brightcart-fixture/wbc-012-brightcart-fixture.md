# Wave 012 — Brightcart Fixture — Business Case

## Context

On 2026-10-17 the author and Claude specified, in `docs/fixtures/brightcart-spec.md`, an invented shopping solution (Brightcart)
that changes over four plateaus: `baseline`, two exclusive alternatives (`saas`, `inhouse`) and `marketplace` on top of
`inhouse`. It is written as manifests, in two renditions: *layered* (a plateau is a layer, its manifests add to the graph,
an ordered array of patches changes it) and *complete folders* (what today's `settings.plateaus` reads). The document has
three jobs: to feed the design of the layered model, to be a worked example, and to be a fixture for tests.

The document was produced by a throwaway model, not written by hand, and the model was cross-checked against the real
`archicode diff` on the complete-folder rendition: five comparisons gave the model's counts exactly. That check also found
a defect in the engine today (E1: `views generate` fails on the comparison views of `inhouse` and `marketplace`, while `diff`
works) and a trap (E2: the `baseline` key must be explicit). The files themselves are not written yet: the document ends
with next steps 2 to 5 (decide the home, write the generator, wire the tests the current tools allow, fix E1) and a sixth that
"waits for decisions that are not taken" (the layered rules L0 to L11, the fold, the migration).

Wave 011 is completed and its pull request (tmorin/archicode#63) carries the document. Nothing in the registers
(`docs/bkg`, `docs/ana`) exists to read; the sources are the document and the issues. #30 ("layered increments over a base") is
the issue that tracks the design question; this wave does not decide it and does not touch it.

## Problems / Opportunities

- The fixture exists only as prose. Nobody can run `archicode diff` on it, open it in the editor, or save its manifests, so
  the first real test of the tools on a case of 40 to 80 elements per plateau is still ahead. The one time it was run (to
  validate the model), it found a defect in a command that its own tests did not catch.
- The layered rendition is the author's design target. Writing it as data, together with the rendition today's tools read and
  a check that both resolve to the same plateaus, turns the target into something a future engine can be tested against, and
  keeps the two from drifting.
- The fixture is also the first realistic example in the repository (the existing ones have a handful of elements). A worked
  example that is also a test cannot go stale without a build failing.
- Everything the layered engine needs that is undecided stays undecided: building the fixture and its checks on the current
  tools does not wait for those decisions, and does not pre-empt them.

## Options & Recommendation

1. **Write the fixture, wire every check the current tools allow, fix what it exposes, look at it in the editor** — four runs
   (recommended). It is next steps 2 to 5 of the document. Each run has its own evidence: the files and their generator, the
   tests, the E1 fix, the look in the editor. It uses only tools that exist.
2. **A wave that also builds the layered engine** (patches, the loader, `migrate`, `merge`), with the fixture inside it.
   Rejected: the rules L0 to L11 are labelled open in the document, the choice between the layered model and the alternative
   under study is not taken, and a public selector contract (L4) is among the open points. Such a wave would stall on its
   first gate or invent the design; it is written once the decisions are recorded, and the fixture is then the test it is
   built against.
3. **Hand-write the files, without a generator.** Rejected: two renditions of about 120 manifest files and 14 variants have
   to stay equal to one description, and the repository already does it with a generator for the harbour pair
   (`src/test/resources/replaces-large-pair/generate.mjs`), regenerated byte for byte.
4. **Keep the fixture as a document only.** Rejected: the document's own method is its limit (one author, one model, one
   cross-check by hand), and the cross-check found a defect. Files that run on every build are the cheapest way to keep finding
   them.

## Vision

The repository holds Brightcart as data: a generator and the files it writes (the layered rendition, the complete-folder
rendition, the variants as descriptions and the expected results), with a check that the two renditions resolve to the same
plateaus. The current tools are tested on it: `diff`, `views generate` (including the comparison views, whose failure is
fixed), facets, the kernel's comparison, the line-preserving save of every manifest, and the native smoke step. The editor has
been opened on it and what it showed is recorded. The document says what was verified by a tool and what is still only the
model's. The layered engine is not built; when it is, it has its test.
