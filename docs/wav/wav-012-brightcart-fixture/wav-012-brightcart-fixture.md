# Wave 012 — Brightcart Fixture

## Purpose

When this wave is done, Brightcart exists as files in the repository, written by one generator: the layered rendition, the
complete-folder rendition, the variants as descriptions and the expected results, and the generator itself shows that the two
renditions resolve to the same four plateaus. The current tools are tested on it (`diff`, `views generate` with its comparison
views, facets, the kernel's comparison, the editor's line-preserving save of every manifest, the native smoke step), the defect
E1 of the document is fixed, the editor has been looked at on it, and `docs/fixtures/brightcart-spec.md` says what a tool now
verifies and what is still only the model's. The layered engine is not built.

## Non-Goals

- Does not build the layered engine: no `patches` in `Kind: Plateau`, no loader of `layered/`, no `plateau migrate`, no
  `plateau merge`. The layered rendition is data that nothing but the generator reads. The variants V1 to V14 and the
  merge scenarios M1 to M3 are written down as descriptions with their expected class of message and are **not run**.
- Does not decide any of the rules L0 to L11, nor the choice between the layered model and the alternative under study, nor
  #30. Those decisions are what the engine's wave waits for; this wave changes none of them and the document keeps them
  labelled open.
- Does not change the format of manifests, `settings.plateaus`, or the output of any command for a workspace that does not hit
  E1 (byte-identity, as in wave 011).
- Does not build `plateau merge`, neither the command nor the editor action, although section 14 notes today's tools could do it
  for complete folders. The author deferred it (tmorin/archicode#65).
- Does not build the large variant (the generator parameter that repeats the bounded contexts); the document says it is not
  needed for a first version.
- Does not ship a subset in `src/doc/examples/` or in the manual: the document says that waits for the layered engine.
- Does not put any text from a real workspace in the repository: Brightcart is invented, and so is everything the generator
  writes.
- Does not cut a release.

## Open Questions

- **The home of the files** (W-1): the document proposes `src/test/resources/brightcart/` with `layered/`, `folders/`, `variants/`,
  `expected/` and `generate.mjs` beside them. The run takes the proposal; moving a folder later is cheap.
- **Whether `layered/` is committed although no tool reads it** (W-1): taken yes, as the document calls it the source of
  truth and the generator's resolver is its test. If the author would rather wait for the engine, W-1 writes it to an ignored
  path and the P1 gate loses its resolver criterion.
- **`plateau merge`, CLI and editor** (not in the wave): deferred by the author on 2026-10-17 and tracked in
  tmorin/archicode#65. The fixture only specifies the scenarios (section 14); no run builds the command or the editor action.
- **What a removed node's references point at in a comparison** (W-3): the fix has to choose between dropping the entries that
  point at a replaced element, pointing them at the replacing one, and keeping the replaced element in the union. The run
  chooses the one that keeps the output shape and says why in its report; the author can overrule it on the pull request.
- **The engine's wave** (after this one): waits for the decisions the document lists (the rules L0 to L11, notably the shape
  of a selector (L4), what a removal takes (L5), whether `MOVE` exists (L6), `replaces` across steps (L9), whether the fold
  exists and how it is produced (L11), and the choice of the layered model itself). It is written once they are recorded.

## Risks

- **Overlap, W-2 and W-3** (`src/test/java/io/morin/archicode/brightcart/**`, `src/test/javascript/viewpoint-kernel/**`):
  `serialize`. They write into the same test folder and run the same `./mvnw verify` in the same working tree and the same
  `target/`. Whoever dispatches runs W-2 first; the batch is one run wide in practice.
- **Overlap, W-3 and W-4** (`standalone.html` if W-3 re-embeds the wasm): resolved by the edge `W-3 -> W-4`. The edge is real,
  not a preference: W-4 reports what the editor does with the union model W-3 changes.
- **Overlap, W-1 and W-4** (`docs/fixtures/brightcart-spec.md`): resolved by the edge `W-1 -> W-4`.
- **Overlap, W-1 and W-2 or W-3**: none by path (`src/test/resources/brightcart/**` against the test folders); the edge
  `W-1 -> W-2, W-3` exists because they read what W-1 writes.
- **Overlap, W-2 and W-4**: none by path, and they are in different phases.
- The generator is a port of a throwaway model that lives outside the repository. If the port differs from the model, the
  checks against the real `diff` (P1, P2, P3, P5) are what catches it; P4 and P6 cannot be checked that way and are flagged
  as the model's. The run says which numbers it could not reproduce rather than adjusting the document silently.
- If a count of the document turns out wrong against the real tool, the document is wrong, not the tool: W-1 corrects the
  document and says so in its report. Nothing in the tools is changed to match a number.
- The fixture adds about 120 small files and their tests to every `verify`. W-2 reports the extra time; if it is more than a
  few seconds the author may move the editor-level tests to a slower tag.
- W-3 touches the kernel. It follows the rule of `CLAUDE.md`: Rust changes end with `embed.sh`, `cargo test`, `embed.sh --check`
  and `node --test`; a contract change is out of scope (#34).
- W-3 cannot see all workspaces that exist; byte-identity is checked on those of the repository and the run lists them.
- W-2 cannot build the native image on the machine that executes the wave if only GraalVM 17 is installed, as in wave 011; the
  smoke step's text is run against the JVM build and the first native run is the pull request's.
- Filing GitHub issues is outward-facing; W-3 and W-4 file issues on tmorin/archicode only, name them in the progress log, and
  comment on no existing issue.
- Branch: wave 012 starts from a tree that contains `docs/fixtures/brightcart-spec.md`, which is on the branch of wave 011
  (pull request #63). If #63 is merged first, branch from `main`; if not, the wave branch is cut from that branch and its pull
  request waits for #63.

## Completion Criteria

The three phase gates verified; `./mvnw -o verify`, `cargo test`, `embed.sh --check`, `node --test` and `npx prettier --check
"src/**/*.java"` pass on the final tree; the generator regenerates `src/test/resources/brightcart` byte for byte; the `Native`
job is green on the wave's pull request (which no run can see); E1 is closed by its commit or re-filed with the reason; the
document says what a tool verifies and what is still the model's; no engine, no new command; every item a run lists as "not
verified" is in the final report.
