## Checks of the claims on HEAD (`61cd8b0`)

- **#108 is true, and smaller than the issue says.** The command line reads `View.Layer` through a mapper with `ACCEPT_CASE_INSENSITIVE_ENUMS`; on a copy of the layered Brightcart with three views of `layer: Technology` / `TECHNOLOGY`, the jar of HEAD draws them on the technology layer (and warns `skip ... which the plateau baseline does not have` for the element only `inhouse` declares). The page had nine strict comparisons on the `layer` of something that comes from a manifest (`viewProblem` twice, `applySavedView` twice, `libraryDiagramRecipe`, `canonicalViewDefinition`, `rewriteRecipeReferences`, `viewLayerOf`); the "about 34" of the issue counts every `'technology'` literal, the others (`opts.layer`, `recipe.layer` in `diagramCacheKey`, `record.layer`) read a layer that is already normalized (`mapLayer()`, a selection, a record), so they stay. A patch's `layer` was already read in any case.
- **#106 is true.** `ElementIndexFactory.create` adds a root candidate to its layer only if it is an `ApplicationElement` / `TechnologyElement`; a container, a component and a node are neither, so they are indexed (so `query graph` lists them) and held by no tree. Without a plateau the final index is the one built from the manifests directly, so they are drawn; with plateaus the layers are built from the trees and a patch cannot select them. On HEAD, K43 to K47 fail in the command line (nothing is thrown) and in the page.
- **#105 is true, and small.** `indexElementRecursive` mapped every item of `relationships`, so `relationships: [null]` gave a relationship with no destination counted as dangling. The places that address a relationship by position all read `data-index` (`renderRelationshipEditRowHtml`, `readElementDraft`, `remove-relationship`): the fix is one `fileIndex` on each relationship of the record and one loop in the form. N87 fails on HEAD in the page (`danglingRelationships`).

## Decisions

The seven places that compared strictly call it. `entryLayerOf` stays as it was (the plateau-free check already used it).

A test pins both (`view-layer-any-case.test.js`: nothing is saved by reading, `mem.writes` is empty).
- **D3. #108: the shared case is N86 of `negative-cases.json`.** On the layered Brightcart: a view of `Technology` on `prod`, a view of `TECHNOLOGY` on `prod.cloud` (only `inhouse` declares it) and a map of `Technology` pinned on both. - **D4. #106: the sentence is the one of the nesting, with the cause in the place of the parent.** ``\`manifests/web.yaml\` is not valid: unknown kind \`container\` with no \`header.parent\` (known: person, solution, system) at \`header.kind\` `` (technology: `known: environment`).
