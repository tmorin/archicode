# Run 0114: Technology map apps and relations

Wave 016 (`band-tree-and-technology-map`), item W-8 (phase P1). Focus: the page Environments shows the application elements and the relationships, and each can be hidden or shown from the toolbar (#107, as the author rewrote it)
Found by run 0099 (wave 015, W-11, #92), which made the page *Environments* a Map of the technology layer and let the command line draw a view of `layer: technology` and `viewpoint: map`.

The kernel's `map` viewpoint drew the links of the relationships that the elements of the layer declare (`relationships`), grouped under the first closed box. For the technology layer that is every link there is: an environment that `uses` another one, and the applications deployed on a node (`applications`), declared no relationship, so they gave no link. On the layered Brightcart fixture (`src/test/resources/brightcart/layered`) the Map of the technology layer was four environments with their nodes and **0 links**; only a workspace whose nodes declare `relationships` had links (the example `src/doc/examples/domain_technology_map` does).

The Overview, Detailed and Deep viewpoints of an environment or a node derive links from the applications deployed in it (the dependencies of an application on another one are relationships of the nodes that host them, and `uses` scopes them). The Map did not, in the editor or on the command line.

**The author's decision (issue #107, 2026-10-20, quoted; the author reads French):** "la map Environment doit montrer les éléments apps et les relations. Les deux peuvent être cachés/montrés depuis la barre d'outils."

Document profile: `single-document`, as runs 0089 to 0113: the scope is settled by the author's decision on #107 and by the plan's decision T3 (the exact set is the run's to settle and to record, below). No PRD, TDD or pln. The review passes (KDMLLC read of this document, the open questions, the C scan against the code, a read-only review of the working tree) are answered below.

## Scope

In: the kernel's `map` (Rust, embedded wasm), the adapter of the command line (`KernelViewpointFactory`), the page Environments and the page of a saved technology Map view in `standalone.html` (kernel input, tools, state, address, saved view, form of a view, selection of an application box), the contract file `expected-boxes.json` and the two tests that read it, the node tests of the Map, `CLAUDE.md`, the README of the kernel.

Out: the manual (W-12's: the lines are in the findings), the relationships that the descendants of a deployed application declare (#124, same limit in the three other viewpoints), the application layer's Map (unchanged), the render cost (W-11 measures it).

## What was found before any change

- The kernel's `map` took `elements` only. Its `Input` has had `app_elements` since the deep viewpoint of the technology layer, `derived_dependencies` (an application whose environment does not host the destination, found in what the environment `uses`) and the item ids of the deployed applications (`<node>_<application>`) are the deep viewpoint's; the page and the command line already draw an item whose id is not its reference (a deployed application: `id !== reference`, `data-layer`, `stereotypes`, `change`, `contains_changes` all read the application layer for it).
- The Brightcart has both ingredients: `prod` and `staging` `uses` another environment, their nodes host applications (`shop.web`, `fulfilment.sync`, ...), and `fulfilment.sync` declares relationships to `carrier` and `erp`, deployed in `partners`.
- `uses` is documented as a scope, never a link of its own (`README.md` of the kernel): nothing is drawn for an entry no relationship rests on. The decision of the author asks for the relationships, not for the `uses` lines.
- The dependencies read the relationships of the deployed element itself only: `shop.app`, whose components declare the relationships to `psp`, `tax` and `mailer`, gives none (the same in the overview, the detailed and the deep viewpoints). Filed as #124.
- The application layer's Map of the editor has never been given `app_elements`; `buildKernelInput` withheld them for every map (D3 of run 0099).

## Decisions

- **D1. The applications (T3).** The applications deployed on the nodes of the technology layer (`applications` of a node: only nodes have them, `Environment` has none), one box each, inside its node, folded as the Map folds: a box is drawn only when its node is visible and open (`opened`, or encloses a pinned element) and, when the map is pinned, inside what is pinned. A node that hosts applications is `expandable` while it is closed (before, only a node with children), so the existing chevron and *Unfold all* open it. An application box has nothing to open. Their ids are the deep viewpoint's (`<last segment of the node>_<application>`, the whole path of the node when that is ambiguous or is the reference of an element), settled over the whole layer, so that opening or hiding a box does not rename another. Why this set: it is what the Overview, Detailed and Deep viewpoints of an environment draw inside a node, the page and the command line already draw such a box, and it is what the author's words ("les éléments apps") name.
- **D2. The relationships (T3).** (a) what the elements of the layer declare (as before); (b) the dependencies between environments that the deployed applications give, the ones the three other viewpoints draw (`derived_dependencies`); not (c) `uses` as a link of its own (a scope, never a link), not (d) the dependencies *inside* one environment (they are "secondary" in the three viewpoints, which draw them only for a flow chosen by a facet), not (e) the relationships of what is inside a deployed application (#124). Smallest consistent set: the one every other viewpoint of the technology layer already agrees on, so the Map says nothing the diagram of an environment does not. A dependency is a link between the boxes of the two applications when both are drawn, else between the boxes the nodes that host them land on, grouped under the first closed box as every relationship of the Map is (the rule stays). Natural when its ends are the applications or the nodes themselves, grouped when an end was brought up to a closed box above. It follows `hidden` (either node hidden: out) and `pinned` (one end inside what is pinned) like any link.
- **D3. Pins, hidden elements and open boxes name technology elements only.** An application is not pinned, hidden or opened on its own (a reference can exist in both layers; the lists of the Map are the layer's, run 0099 D2): hide the node, or turn *Applications* off. The brief said "pinnable/hideable as other elements": the author's decision asks only for the two toggles, and a per-application pin would need a layer-qualified reference in three lists, in the saved views and in the address. Not done; if the author wants it it is a new run, not filed (no one asked).
- **D4. The two properties.** `applications` and `relationships`, booleans, in the properties of a Map view, in kebab-case like the others (single words), **absent means drawn**, the editor writes `false` only (like `hide-unlinked`, which is written only when `true`), in `VIEW_PROPERTY_ORDER` after `hide-unlinked` and before the texts. A value that is not the boolean `false` is no choice, in both tools (the Java side reads `isBoolean() && !asBoolean()`, the page `=== false`): a `"no"` draws both, silently, as `hide-unlinked: "yes"` already does. They mean nothing in a Map of the application layer or any other view: the page's canonical form drops them there, the kernel ignores them there.
- **D5. One implementation, in the kernel; contract 5, additive.** Both tools only pass the properties: the kernel input gets two optional booleans `applications` and `relationships` (absent or null: true), and `app_elements`, the application layer the map was not given. Gate: the applications and the dependencies exist only when `layer` is `technology` and `app_elements` is not empty; an input of a technology map that gives none, and the Map of the application layer whatever it is given (the two keys included), are drawn exactly as before (a Rust test pins it). The number stays 5: no required field, no change of an output shape; a caller that sends nothing new gets nothing new. The kernel's own default, drawn when absent, is the author's default.
- **D6. The toolbar.** Two toggles in a group of the diagram tools, *Applications* and *Relationships* (`aria-pressed`, a `title`, action `toggle-map-part`, no key: none is free and obvious), only where a Map of the technology layer is on screen: the page Environments, and the page of a saved view of that Map, where they edit the view like the texts do (`setViewMapPart`; the form of the view has the two boxes). State: `technologyMapParts` (reset with the folder, `resetUiState`), kept while the editor stays on the page, in the address as `applications=0` and `relationships=0` (what is left out only), part of the key of the diagram cache (`diagramCacheKey`, technology Map only), view state and never model state (a test pins that `modelVersion` does not move), a toggle sets `mapSelectionCheck` so that a selection the redraw no longer draws is dropped. The state does not survive a visit to another page, as the texts and *Hide unlinked* do not (the address of the other pages says nothing of it).
- **D7. A box of an application is an element of the other layer.** Its `data-layer` is `application` on the Map (it was the layer of the drawing for every box, which for a deployed application selected nothing); `scene.drawnApps` says which applications are drawn; the selection check, the outline of the selected box (every box of one application, when it is deployed on several nodes), the panel (no "this map draws the technology layer" for an application that is deployed on some node: `applicationIsDeployed`) and `mapElementIsOnMap(reference, layer)` read it. The sentence for an element the Map does not draw became *This map draws the technology layer, and the applications deployed on its nodes.*; the Elements diagram of a deep technology view keeps its `data-layer` (not touched, see F4).
- **D8. The saved views and the output.** A saved view that says neither key draws both: the output of the saved technology maps of a workspace with deployed applications and dependencies changed (the author accepts it, 0.14.0 being the same day). Byte-identity: see Verification.
- **D9. The contract file.** `expected-boxes.json` has `workspaces`, each with its views (a `plateau` where the workspace has several), the boxes (item ids: the reference of the element, `<node>_<application>` for an application) and the links, and `variants`: the same view with properties put over its own (`applications`, `relationships` false, more `opened`). The example `domain_technology_map` (no application deployed: its variants prove the toggles change nothing there, and that `relationships: false` empties it) and the saved maps `environments_map` and `cloud_map` of the layered Brightcart (the deployed applications, the dependency to `partners`, the pin). 5 views and 9 variants, drawn by the viewpoint of the command line (`TechnologyMapTest`) and by the page of a view and the page Environments (`technology-map-shared.test.js`).
- **D10. A dependency of an application missing from the layer is an error, as in the deep viewpoint** (`dangling application reference: x`, only for a node that is open and an application that is drawn). `LayerLoader` already refuses it at load on the command line; in the editor, a workspace that has it fails on the Map until Applications is turned off or the node is repaired.
