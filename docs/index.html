Introduction

Welcome to the ArchiCode Command Line Tool Documentation. ArchiCode is a powerful tool designed to assist architects in creating models and generating views using an efficient as-code approach. Drawing inspiration from both the C4 Model and the ArchiMate Standard, ArchiCode provides a data model and a command line interface to streamline your architectural workflow.

With ArchiCode, architects can easily design models and produce views while adhering to the principles of the C4 Model. Our built-in viewpoints handle various levels of abstraction, ensuring your architectural vision is accurately represented in your projects.

Incorporating concepts from the ArchiMate Standard, ArchiCode’s model is rooted in the structural Aspect and spans the Application and Technology layers. This integration adds depth and clarity to your architectural creations.

This documentation will guide you through the features, domain, commands, and best practices for utilizing ArchiCode in your architectural projects. Let’s explore how ArchiCode can elevate your architecture-as-code journey.

Availability, License, and Deliverables

ArchiCode is an open-source software hosted on GitHub, fostering transparency and collaboration. It operates under the MIT license, granting users flexibility in its use and modification. The software is distributed as a Maven Artifact and an OCI Image (Docker Image), simplifying integration.

  • Source Code: ArchiCode’s source code is hosted on GitHub at https://github.com/tmorin/archicode, providing access for developers to explore, contribute, and collaborate.

  • Licensing: ArchiCode is licensed under the permissive MIT license, enabling users to freely utilize, modify, and distribute the software.

  • Deliverables: ArchiCode is conveniently available as a Maven Artifact and an OCI Image, facilitating easy integration into development workflows.

  • Access to Deliverables: The practical deliverables can be accessed through the dedicated packages repository at https://github.com/tmorin/archicode/packages.

This accessibility, licensing, and practical distribution emphasize ArchiCode’s commitment to fostering an open and collaborative architectural community.

States of an Architecture

A plateau is a state of the architecture, as it is or as it should be, written as a layer: the manifests that say plateau: <id> in their header, over the plateau they override, with patches (REMOVE, SET, ADD, MERGE) for what they change. ArchiCode computes what is new, changed and removed from one plateau to another and draws it, in the views and in the editor, with marks that never rely on colour. An element can say what it replaces (replaces), so that a move, a split or a merge is one change and not a removal plus an addition; the editor proposes the matches it finds and writes the hint in one click, and moves an element under another parent without breaking a reference (see States of an architecture (plateaus)).

Unraveling Clarity Through Facets

The facet feature in Archicode elegantly simplifies complex architectural views, offering tailored visualizations focused on specific model elements and relationships for enhanced clarity and comprehension.

Domain

The ArchiCode domain serves as the foundational framework for your architectural endeavors, encompassing essential elements that facilitate and enhance your architectural work:

  • Workspace: ArchiCode’s workspace provides the supportive backdrop for all your architecture projects, offering an organized and collaborative environment.

  • Application Layer: Within the ArchiCode domain, the Application layer hosts a rich array of elements coming from the C4 Model, enabling you to meticulously design and model application components with precision and clarity.

  • Technology Layer: Embracing the Technology layer of the ArchiCode domain empowers you to delve into the realm of deployment nodes, strategically configuring your architecture’s technological aspects.

  • Viewpoint and Views: Navigating within the ArchiCode domain grants you access to a spectrum of viewpoints and customizable views, facilitating effective architectural communication and visualization.

  • Technical Configuration: The ArchiCode domain encompasses essential technical configurations, enabling you to tailor the tool to your specific architectural requirements.

As we delve into each facet of the ArchiCode domain, you’ll gain a comprehensive understanding of how each element contributes to your architectural prowess. Let’s embark on a guided exploration through the diverse dimensions of the ArchiCode domain.

Workspace

In ArchiCode, a workspace is a fundamental construct that orchestrates the foundation of your architectural endeavors. It acts as a cohesive hub, streamlining the definition and configuration of your architecture work. Key aspects of the workspace include:

  • Plain Text Format: A workspace is represented as a plain text file, allowing you to choose between YAML, TOML, or JSON formats. This flexibility ensures that the workspace aligns seamlessly with your preferred configuration style.

  • Centralized Definition and Configuration: The workspace serves as a central repository for defining and configuring your architecture work. This consolidation streamlines your workflow and provides a clear reference point for all aspects of your project.

  • Enrichment with Manifests: Workspaces can be enriched through the inclusion of manifests. A manifest, also presented as a plain text file in YAML, JSON or TOML format, further refines and specifies architectural details within the workspace. The command line reads the three; the editor reads YAML only (see [editor-reads]).

  • Manifest for Enhanced Organization: The concept of manifests introduces a structural layer that enhances source code organization. By encapsulating architectural components, manifests contribute to a cleaner and more comprehensible separation of concerns.

  • Collaboration Support: Embracing the manifest concept not only refines source code organization but also provides enhanced collaboration capabilities. Manifests facilitate clearer communication among team members by offering a well-defined structure and purpose.

  • Optional Name: a workspace can be given a name with settings.name. The editor shows it in place of the name of the folder (see Name of the workspace); the command line does not need it. A workspace without a name stays valid.

  • Optional Plateaus: the states of the architecture are layers, written as manifests that say plateau: <id> in their header and, for each plateau, a manifest of kind archicode.morin.io/plateau (see Plateaus). Views and stories belong to no plateau (see [plateau-untied]). A workspace that does not write any plateau keeps the one set of manifests it always had.

A reference is declared once. The reference of an element is its id placed under its parent, whether that parent is the element that contains it in its file or the parent of the manifest’s header, so shop.web is the same reference for an element nested in shop’s file and for a manifest with `parent: shop and id: web. When two declarations share a reference, in two files, in a file and in a manifest placed under its parent, or twice in one file, the command line stops with an error that names the reference and the files, and generates nothing; two identical copies are as much an error as two different ones, because nothing says which file is meant. The same goes for two views, or two stories, that share an id. A reference may exist in both layers (an application and a node of the same name): they are not the same element.

the reference `shop` is declared twice: in `manifests/a.yaml` and `manifests/b.yaml`

The editor reports the same thing, in the same words (see [editor-folders]). With plateaus the rule is the one of [plateau-header]: a reference declared in a plateau and again in a plateau it stands on is the error, and the same reference in two plateaus that do not stand on each other is not.

Manifest formats and kinds

A manifest is a file of YAML (.yaml, .yml), JSON (.json) or TOML (.toml) with a header and a content. The command line reads the three the same way, so that a manifest written in TOML gives the same graph as its YAML twin. This is the TOML twin of manifests/user.yaml above:

The TOML twin of manifests/user.yaml: manifests/user.toml
[header]
kind = "archicode.morin.io/person"
version = "1"

[content]
id = "User"

[[content.relationships]]
destination = "ArchiCode.CommandLineInterface"
qualifiers = ["Console"]

TOML has no null: a key with nothing to say is not written, and is absent. An element nested in another one is a table (a list of tables, as above). The editor reads YAML only: it lists the .toml and .json files it finds as files it does not read (see [editor-reads]).

The kinds. The kind of the header is one of ten, each written archicode.morin.io/<kind>:

person, solution, system, container, component

the elements of the application layer (see Application Layer)

environment, node

the elements of the technology layer

view, story

the views and the stories (see Viewpoints and Views and Stories); they belong to no plateau

plateau

a plateau (see [plateau-manifest])

container-group, solution-group and system-group are no kinds, in the command line and in the editor: a group is an element of kind group, nested in a container, a solution or a system (kind: group in its elements). A manifest of one of those three kinds is refused with the one sentence, which lists the kinds there are:

error: `manifests/grp.yaml` is not valid: unrecognized `header.kind` "archicode.morin.io/system-group" (known: archicode.morin.io/component, archicode.morin.io/container, archicode.morin.io/environment, archicode.morin.io/node, archicode.morin.io/person, archicode.morin.io/plateau, archicode.morin.io/solution, archicode.morin.io/story, archicode.morin.io/system, archicode.morin.io/view) (line 2, column 9)

What a parent holds. A solution holds systems and groups; a system holds containers and groups; a container holds components and groups; an environment and a node hold nodes; a group holds what the element it sits in holds; a person and a component hold nothing. An element declared under a parent that cannot hold its kind (header.parent: a system under a container) is an error in both tools, with or without plateaus, that names the file and says what the parent holds:

error: `manifests/grp.yaml` is not valid: unknown kind `system` under `ArchiCode.CommandLineInterface` (known: component, group) at `header.kind`

An id is a name without a dot, since the dot separates the levels of a reference: a.b is refused by both tools.

error: `manifests/dot.yaml` is not valid: the id `a.b` contains a dot, which separates the levels of a reference, at `content.id`

What a layer holds at its top. In a workspace that has plateaus, a manifest with no header.parent must be of a kind that its layer holds at its root: a person, a solution or a system in the application layer, an environment in the technology layer. A container, a component or a node is held by an element, never by a layer, and a patch could not select one that stands alone, so both tools refuse it with one line that names the file and the kind:

error: `manifests/root-container.yaml` is not valid: unknown kind `container` with no `header.parent` (known: person, solution, system) at `header.kind`

A workspace with no plateau is not concerned: such a root is indexed and drawn as it always was. The editor does not offer these kinds at the top level, and does not move an element there.

Manifests in folders

settings.manifests.paths lists the folders the manifests are read from, manifests by default, and a path read as it is written names one folder: the files directly in it are the manifests, and the files of its sub-folders are not. To keep the manifests in folders of your own (by domain, by team), end a path with /**: the folder and every folder below it are read.

The content of workspace.yaml of a workspace whose manifests are in folders

  name: "Bookshop"
  manifests:
    paths:
      - "manifests/**"
The files of the example domain_manifest_folders

  application/
    shop.yaml
    shop/warehouse.yaml
  people/customer.yaml
  technology/
    reference.yaml
    reference/server.yaml

The command line and the editor read the same files, in the same order, by these rules:

  1. A path that does not end in / is read exactly as it always was: the files directly in the folder. ./ is the folder of workspace.yaml and everything below it, the file workspace.yaml excepted. A folder that does not exist reads nothing, with /** as without.

  2. The files are read in the order of their path from the folder of workspace.yaml, written with / and compared by Unicode code point, whatever the file system or the language of the system: B.yaml comes before a.yaml, and a.yaml before a/b.yaml. A file that two paths find (manifests and manifests/**) is read once. The order tells which file an error names first and the order of the files in the editor; the views do not depend on it.

  3. Below a path that ends in /, these are not read: a file or a folder whose name begins with a dot (.git, .cache); a symbolic link to a folder (a link is never followed, so a link that points to its own folder is no loop; a link to a file is read like the file); and the folders of the generated views, which can hold files that are no manifests (the comparison of two plateaus writes a gap.json). These are the folder that settings.views.path names, as it is written in workspace.yaml, and the folders beside it whose name begins with that name and a dash: with views, the folders views, views-to-be, views-to-be-vs-baseline and views-shop; and any folder that holds both files a comparison writes, gap.json and gap.md, whatever --output named it and whichever command wrote it (a folder with only a gap.json is read, since a manifest may be called so). A folder that is deeper than views.path, or whose name only looks like it (viewsx, views_extra), is read. A path that names such a folder itself (.manifests/, views-notes/) reads it: the rule applies to what is found below a path, not to the path. A path that is a link to a folder is read, as it is without /.

  4. Every .yaml, .yml, .json and .toml file that is found is a manifest, as in a folder read without /**: a YAML file that is not a manifest (a CI file, a values.yaml) is refused with its name, so keep such files out of the folders you name, or in a hidden folder. A TOML manifest is a manifest like the others (see Manifest formats and kinds). The editor reads the YAML ones and says which files it does not read (see [editor-reads]).

  5. A reference declared in two of the files that are found is the error of [duplicate-references], in the same line, with the two files in the order above.

  6. means something only at the end of a path, after a /. manifests//shop, manifests/x, a/b and are refused with one line that names the path and says what is read, in the command line and in the editor (where the Settings screen refuses them too). A path that contains .. or is absolute is refused as before, with / or without. A folder whose name contains ** can no longer be named by a path.

Incorporating workspaces and manifests into your architectural workflow within ArchiCode empowers you with an efficient and organized foundation for your projects. Let’s explore further as we navigate through the various dimensions of the ArchiCode domain.

Plateaus

An architecture goes through states: how it is today, how it should be next year. (States of an architecture (plateaus) tells the story in one place, with a tutorial.) A plateau is one of these states, and it is a layer: it starts from the plateau it overrides, adds the elements of its own, and changes what it inherits with a list of patches. The first plateau, the architecture you have, is the root; it is called baseline, it exists without anything naming it, and it overrides nothing.

Note

There is no settings.plateaus any more. A plateau used to be a complete folder listed under settings.plateaus in workspace.yaml, created by archicode plateau add and compared with --baseline. The key, the command and the option no longer exist. A workspace.yaml that still has the key is refused by every command, and by the editor, with this one line, and nothing is read or written:

error: `settings.plateaus` no longer exists: a plateau is a layer now. Remove the key, write `plateau: <id>` in the header of the manifests of each plateau, and declare each plateau in a manifest of kind `archicode.morin.io/plateau` (`id`, `name`, `override`: the plateau it builds on, `baseline` when absent, and `patches` for what it changes)

--baseline is a usage error (Unknown options: '--baseline', …​, exit code 2) and archicode plateau add too (Unmatched arguments from index 1: 'add', …​); --against and archicode plateau list replace them (see [plateau-choose]). No command converts a workspace: Upgrading: what breaks, and what does not says how to do it by hand.
A workspace with a root and one layer: workspace.yaml
# the plateaus are layers. The manifests in `plateaus/baseline` say no `plateau:`: they are the root, `baseline`, the architecture as it
# is. The manifests in `plateaus/to-be` say `plateau: "to-be"`: they are the layer that builds on it, with the patches of its
# `plateau.to-be.yaml`. The folders are only a habit; the tools read the `plateau:` of the header, not the folder.
settings:
  name: "Bookshop"
  manifests:
    paths: ["plateaus/**"]

  1. The manifests of the root: no plateau: in their header. plateau.baseline.yaml is optional and only gives the root a name and a horizon.

  2. The manifests of the layer to-be: each says plateau: "to-be" in its header. Only what the layer adds; what it inherits from baseline is not copied.

  3. The manifest of the plateau to-be: its name, its horizon, the plateau it overrides and its patches.

The folders are only a habit, and the example (src/doc/examples/domain_plateaus in the source repository) names them after the plateaus to be easy to read. What puts a manifest in a plateau is the plateau key of its header, not the folder it is in. (The editor warns when the two disagree, see Files; the command line says nothing.)

The header. A manifest of an element can say which plateau it belongs to in its header:

header:
  kind: "archicode.morin.io/container"
  version: "1"
  plateau: "to-be"
  parent: "shop"
content:
  id: "ratings"
  name: "Ratings"

Without plateau, the manifest belongs to baseline, the implicit root. A plateau exists as soon as a header names it (a plateau that only headers name has no name, no horizon and overrides baseline: it is told with a warning, see below) or a manifest of kind archicode.morin.io/plateau declares it. The elements of a plateau are added to the ones of the plateau it overrides, so a plateau sees everything its ancestors declare. A reference is declared once in a plateau and in all the plateaus it stands on (see [duplicate-references]): the same reference in a plateau and in its ancestor is an error, and in two plateaus that do not stand on each other (two alternatives) it is no duplicate.

Views and stories belong to no plateau. Only the elements, the patches and the plateaus are layers. A view and a story exist whatever plateau is drawn: the same view or story is the one of every plateau, nothing patches them, and each is declared once in the whole workspace (the error of [duplicate-references], between plateaus that do not stand on each other as well). A plateau: in the header of a view or of a story is accepted and means nothing: no tool reads it, no tool says anything about it (it is no warning and no error, whatever the text is), and it does not make a workspace of plateaus (a plateau that only a story names is no plateau). A header carries the key for every kind, and that is all there is to it.

What a view or a story names is looked at without a plateau, once the layers are read: every element it names must exist in at least one plateau, else it is an error, whichever plateau is asked for (a workspace without plateaus is not checked, and a view is looked at when it is drawn). A name that another plateau has and the plateau drawn lacks is no mistake of the view: that view cannot be drawn in that plateau (see [plateau-views-lacking]).

The manifest of a plateau. A manifest of kind archicode.morin.io/plateau qualifies one plateau; it is optional, and there is at most one for a plateau.

id

Required. What plateau: in a header, override, --plateau and --against name. Lowercase letters, digits, _ and - (no dot, no capital): the identifier is also used in folder names. baseline is the id of the root.

name

Optional. The name shown to people; the id when absent.

horizon

Optional. A free-text label for when the plateau is meant to hold, such as 2027-Q1. ArchiCode does not interpret it, except to order sibling plateaus in the lists of the editor and to warn when it is earlier than the horizon of the parent, when both read as a period (see below).

override

Optional. The one plateau this one is a layer over: baseline when absent. The plateaus form a tree whose root is baseline; two plateaus that override the same one are alternatives. The root overrides nothing.

patches

Optional. What the plateau changes in what it inherits, applied in order (see [plateau-patches]).

The manifest of the example, with all its patches, is in step 3 of the tutorial (see States of an architecture (plateaus)).

What is checked, and the lines you get. The tree is checked when the manifests are read, and each mistake is one error: line that names the plateau and the file, or one warning: (see Errors, warnings and exit codes). A plateau is read as its chain, from the root: for each plateau, the elements that say plateau: <id> are added to the graph, the patches of the plateau are applied, and the result is checked (a relationship, a uses entry, a hosted application and a parent must exist, and an element must be declared under a parent that can hold its kind, see [nesting]). The first plateau that is wrong ends the load, and the plateaus above it are not looked at. The views and the stories are checked once, after the layers (see [plateau-untied]), and so are the plateaus that the steps of a story name (see Stories).

error: the plateau `to-be` (`plateaus/to-be/plateau.to-be.yaml`) overrides `asis`, which is not a plateau of this workspace (the plateaus are `baseline` and `to-be`)
error: the plateau `to-be` is declared twice: in `plateaus/to-be/again.yaml` and `plateaus/to-be/plateau.to-be.yaml`
error: the plateau id `To.Be` in `plateaus/to-be/plateau.to-be.yaml` is not valid: use lowercase letters, digits, `_` and `-`
error: the reference `customer` is declared in the plateau `to-be` (`plateaus/to-be/customer.yaml`) and again in its ancestor `baseline` (`plateaus/baseline/customer.yaml`)
error: in the plateau `to-be`, `shopp.cart` is declared under `shopp`, which does not exist
error: in the plateau `to-be`, `shop.web` has a relationship towards `shop.nowhere`, which does not exist
error: the view `shop_overview` (`manifests/view.shop_overview.yaml`) names `shopp`, which exists in no plateau

The first three are about the tree (an override that names nothing, a plateau declared by two manifests, an id that is not valid). Two more are told the same way: a plateau that overrides itself, directly or through others (error: the plateau `to-be overrides itself`), and a baseline manifest that overrides (error: the plateau `baseline (plateaus/baseline/plateau.baseline.yaml) is the root of the plateaus and cannot override to-be`). The next three are about a plateau: a reference declared again in an ancestor, an element declared under a parent that does not exist, a relationship that leads nowhere. A mistake in a plateau names the plateau, so that the line says which layer to open. The last one is about no plateau: a view that names an element that exists in none.

One cause, one line. When one mistake has many consequences, the tools say the first one (by reference) and count the others. The elements a plateau declares under a parent that is not there are one sentence, whatever the parents are called (here a typo in the parent of three manifests): the first one told is a symptom of the missing layer, and a second wrong parent shows once the first is repaired. The elements that point at one reference that is not there are one sentence for each missing reference (here two relationships added towards shop.nowhere). The views and the stories that name something that is not there keep one line each, since they are not consequences of one another. When a manifest cannot be read, the command line stops at it, before any layer is built, with one line: the file and what is wrong. The editor draws what it can, and says that same line in place of the consequences the missing elements would leave behind.

error: in the plateau `to-be`, `shopp.billing` is declared under `shopp`, which does not exist (2 more elements of the plateau are declared under a parent that does not exist)
error: in the plateau `to-be`, `customer` has a relationship towards `shop.nowhere`, which does not exist (1 more element of the plateau points at it)

Warnings. These go on, and exit with the code 0:

warning: the plateau `to-b` exists only through the `plateau` key of the header of `plateaus/to-be/typo.yaml`: it has no manifest of kind `archicode.morin.io/plateau`, so it overrides `baseline` and has no name
warning: the plateaus `to-b` and `to-be` have ids one letter apart: check that one of them is not a typo

  • A plateau that only headers name is told once, with the files. It is usually a typo in a plateau: key.

  • Two plateaus whose ids are one letter apart (to-b and to-be) are told, so that a typo is seen, only when one of the two has no manifest of kind plateau. Two plateaus that have a manifest each (p1 and p2, to-be and to-bf) are the author’s choice and say nothing.

  • Two SET of the same field of the same target in one plateau: the last one wins, and the warning gives both ranks. A SET with a where is a different one for each destination and label, and a patch with a json-path is not compared (what it selects is not known before the patches run).

  • A horizon that is earlier than the one of the plateau it overrides. A horizon is a free label: two are compared only when both read as a period (2026, 2026-10, 2026-10-18, 2026-Q4, 2026Q4, 2026-H2), and one is earlier when its whole period ends before the period above begins (2026 under 2026-Q4 is not). Any other label is never compared.

The patches. A layer changes what it inherits with the list patches of its manifest. A patch says what it does (operator), to what (a selector), and with what (field, value). The patches are applied in order, each one on the result of the ones before it, and a patch can reach an element that the layer brings with its own manifests (they are in the graph before the patches run). The kernel that applies them is the same one that draws the views and compares the plateaus, in the command line and in the editor.

REMOVE

The element goes, with what is in it and what points at it: the relationships towards it, its entry in a uses or an applications list. The node that hosted the element stays, even when it hosts nothing any more. Takes no field, where or value. What it took besides the element is told after the table of changes (see [plateau-cascade]).

SET

The field is replaced by value, a list or a map as a whole. With where (and field: relationships), value is a map and each of its keys replaces that key of the one relationship found.

ADD

The list field gets value at its end, or each item if value is a list; a missing list is created. Nothing is deduplicated.

MERGE

The keys of value, a map, are set in the map field (the tags, say); the other keys stay. One level only; a missing map is created.

The selector is exactly one of these two:

target

The full reference of exactly one element (shop.web), in the application layer, or in the technology layer with layer: technology. A reference that does not exist is an error, and when the other layer has it, the error says to write layer.

json-path

A JSONPath (RFC 9535) over the document application.elements and technology.elements of the plateau, which selects at least one node (an element or something in it). expect: 3 asks for exactly three: a number of nodes that differs is an error, which turns a silent drift into a message.

field is the field of the element that is changed (name, description, qualifiers, tags, relationships, applications, uses…​); with a json-path, a patch with no field changes the selected nodes themselves. where: {destination: "shop.catalog", label: "reads"} finds one relationship by its destination and its label (a missing label is none); zero or several matches is an error. id, parent and elements cannot be changed: a patch never renames or moves an element, and an element that moved is told with replaces (see Saying what an element replaces). A patch never takes a field out (see Limits of today). Views and stories belong to no plateau, so there is nothing to patch in them (see [plateau-untied]).

patches:
  - operator: SET            # one element, one field
    target: "shop.catalog"
    field: description
    value: "The books that are on sale."
  - operator: SET            # one relationship of an element, found by its destination and its label
    target: "shop.web"
    field: relationships
    where: {destination: "shop.catalog", label: "reads"}
    value: {label: "browses"}
  - operator: MERGE          # every container, and exactly nine of them
    json-path: "$.application..elements[?(@.kind == 'container')]"
    field: tags
    value: {zone: "north"}
    expect: 9
  - operator: REMOVE
    target: "shop.mailer"

Choosing a plateau on the command line. The commands that load a workspace (views generate, diff, query views, query graph) take --plateau <id>. Without it, the plateau is the one settings.current names; else the last one when the plateaus form one line (each overrides the one before it); else the command stops and asks for a choice, since a tree that forks has no last plateau:

--plateau wins over settings.current. The editor does not choose as the command line does when no name is given and the plateaus form one line: with no address, no plateau remembered by the browser and no settings.current, it draws the root, baseline, where the command line draws the last plateau. Write settings.current (the editor has a field for it, see The current plateau) to make the two agree. An unknown id is an error that lists the plateaus (error: unknown plateau `nope: the plateaus of this workspace are baseline and to-be`). archicode plateau list lists the tree, one line per plateau, baseline first, then what overrides it, each plateau followed by what overrides it; plateaus that override the same one come in the order of their ids. - is for what is absent, and SOURCE says where the plateau comes from: its manifest, headers only (a plateau that only headers name, with its files), or implicit (the root that nothing names).

Comparing two plateaus

What a plateau changes is the difference between it and another plateau: ArchiCode compares the two and tells what is new, what changed and what was removed, elements and relationships. The plateau it is compared with is, in this order, the one --against names, else the plateau it overrides. The root, baseline, overrides nothing, so it is compared with nothing unless --against names a plateau. Any plateau of the tree can be named, a sibling or a plateau of the future too (archicode diff --plateau inhouse --against saas compares two alternatives): the comparison is made on the two plateaus as they are resolved, whatever their relation.

Two commands show the comparison: archicode diff writes the table of changes (see Compare plateaus), and archicode views generate draws the views of the comparison (see Generate views).

What counts as a change. An element is the same element in both plateaus when it has the same reference (a reference includes the path of the element, so an element that moves under another parent is a removed one and a new one, unless the new one says that it replaces the old one, see Saying what an element replaces). It is new when its reference is only in the plateau, removed when it is only in the other plateau, and changed when something differs in the element itself or in the relationships it declares: its kind, its name, its description, its qualifiers, its tags (the rendering-* ones do not count), its deployment (applications and uses), or a relationship that was added, removed or changed. A child is judged on its own: a system whose only change is a new container is not changed, it contains changes. The table lists what changed in each element (natures) and tells a change of wording apart: an element whose description is the only thing that differs is wording only. A relationship is identified by its source, its destination and its label; it is new or removed when it is only on one side, and changed when its qualifiers, its tags or, when it is the only one between the two elements, its label differ. The order of a list and the order of the keys of a file are no change.

Using other environments

An application rarely lives alone in its environment: the development environment of a platform talks to an identity provider, to a mail relay, to the integration environment of a partner. Those are environments too, each with the nodes that host the applications modeled for them. An environment says which ones it depends on with uses.

The manifest of an environment that uses another one, and a node of a third one
header:
  kind: archicode.morin.io/environment
  version: "1"
content:
  id: dev
  name: Development
  uses:
    - integration
    - idp.production.openid
  elements:
    - kind: node
      id: cluster
      applications:
        - shop.api

uses is not a relationship and it draws nothing by itself. It tells where to look for what the applications of the environment depend on:

  • When an application deployed in the environment has a relationship towards another application, ArchiCode looks where that other application is deployed. If the environment hosts it, nothing leaves the environment.

  • Otherwise, it is looked for in the environments, or the nodes, listed in uses, and nowhere else. An application deployed in several environments is reached in the ones the environment uses. That is how dev reaches the integration instance of an application, and not the production one.

  • The dependency is then drawn, in the deep view of the technology layer, between the two deployed applications, with the label, the qualifiers and the tags of the relationship of the application. It folds with the nodes: when they are collapsed, the dependencies between them are grouped in one link.

  • The overview and the detailed view of an environment, or of a node, show the same dependencies grouped on the nodes that host the applications: an environment is linked to the environments it uses.

  • The view of an environment shows what it depends on, and the view of a used environment shows who depends on it.

An entry of uses is the reference of an environment, to use all of it, or of one of its nodes, to use a part of it. It has to exist, or the views are not generated.

As the dependencies are derived from the relationships of the applications, a facet that removes some of them removes the dependencies that rest on them. Through a facet, the deep view of an environment also draws the relationships between the applications deployed in it, with their label and qualifiers: a facet that keeps one flow (an authentication, the audit events) shows that flow as it is deployed, on the nodes that host the applications. Without a facet these relationships are not drawn, there would be too many. The overview and the detailed view lift them to the nodes the view is made of. A facet that sets hide-unlinked: true also leaves out, in these views, the elements none of its links goes through, the element the view is about staying; in the editor it is a check box of the facet, in the Settings. The entries of uses can also be selected by a facet, as any other part of the workspace.

ArchiCode places a strong emphasis on the dynamic generation of views, fostering a dynamic and adaptable approach to architectural visualization. Here’s how ArchiCode leverages this dynamic view generation:

  • Pluggable Viewpoint Service: ArchiCode harnesses a pluggable Viewpoint Service architecture, enabling the dynamic generation of views that seamlessly align with the elements of both the Application and Technology layers. This extensible framework empowers architects to tailor viewpoints according to their architectural needs.

  • Diverse Architectural Elements: With ArchiCode, the dynamic view generation process taps into the rich spectrum of architectural elements within the Application and Technology layers. This ensures that views are not only comprehensive but also finely tuned to convey the intricacies of your design.

  • Ad-Hoc View Definition: ArchiCode takes flexibility a step further by allowing architects to define ad-hoc views. This empowers you to create specialized viewpoints that cater to specific architectural inquiries or scenarios, providing an extra layer of customization.

The workspace defined a View representing an overview of the TerminalSession node
technology:
  elements:
    - kind: "environment"
      id: "Reference"
      elements:
        - kind: "node"
          id: "Laptop"
          elements:
            - kind: "node"
              id: "OperatingSystem"
              elements:
                - kind: "node"
                  id: "TerminalSession"
views:
  - kind: "view"
    id: "terminal-session"
    viewpoint: "overview"
    layer: "technology"
    properties:
      element: "Reference.Laptop.OperatingSystem.TerminalSession"

A view that has an id is a named view. Without --view, archicode views generate draws the views it finds from the elements of the model (a named view is drawn when it is asked for); archicode views generate --view terminal-session (or -i) draws the views of that id alone, no other view with them, into views/plantuml/technology/terminal-session.puml. A view can be a manifest of its own, in the folders of the manifests (see Stories); it belongs to no plateau, see [plateau-untied].

The map. A view of the map viewpoint draws a whole layer instead of the surroundings of one element: layer: application (the default) or layer: technology, folded, so that only the top of the layer shows and a link joins the boxes its two ends land on. Three lists of references, in properties, shape it: pinned keeps only what touches these elements, hidden leaves these elements, what is inside them and their relationships out, and opened opens these boxes, so that their children show. A map of the technology layer has two more properties, booleans, that are true when they are absent: applications: false leaves out the applications deployed on the nodes, and relationships: false leaves out the links (see below). The layer of a view (and of a step that carries its own view) is read in any case by both tools: layer: Technology and layer: TECHNOLOGY are the technology layer, and anything else is the application layer; application and technology in lower case remain the form to write. The editor draws the same view on its page Applications (the application layer) and its page Environments (the technology layer, see Applications and Environments: the Map), and both tools draw the same boxes (the example below has the boxes of each view pinned by a test). The command line draws a map when it is asked for it by its id, as for any named view:

settings:

writes views/plantuml/technology/datacentre-map-open.puml. The command line does not read what the editor keeps in a map besides the three lists and the two booleans (facet, hide-unlinked and the texts of the diagram). A list that names an element that does not exist is one error: line that names the view (error: the view datacentre-map-database: dangling reference: datacentre.rack.dbx); in the views of a facet, where the facet may have removed the element, the entry is dropped. A comparison of two plateaus gives a map the states of its boxes, as it does for the other viewpoints.

What a map of the technology layer draws. Besides the nodes and the environments, it draws the applications deployed on the nodes and the relationships:

  • The applications are the applications that the nodes list, one box each, inside its node. Only an open node shows them (a node is open when it is in opened, or when it encloses a pinned element), and a node that is hidden shows none; when the map is pinned, they are drawn only inside what it is pinned on. A node that hosts applications can be opened, so it is no longer drawn as a closed box with nothing in it; an application box has nothing to open. A pinned, hidden or opened entry names a technology element: an application is not pinned, hidden or opened on its own (hide its node, or leave the applications out with applications: false).

  • The relationships are the ones the elements of the layer declare, and the dependencies between environments that the deployed applications give: an application of one environment that depends on an application the environment does not host, found in an environment or a node that the first uses, is a link between the two application boxes when both are drawn, and between the boxes of the nodes that host them otherwise. These are the dependencies that the overview, detailed and deep viewpoints draw; the dependencies inside one environment stay out, as in those viewpoints. uses is a scope and no link of its own. The dependency is read from the relationships of the application that is deployed, not from the ones of what is inside it (see Limits of today).

A saved map of the technology layer that says neither property draws both, so that a saved map of the technology layer draws more than it did in 0.14.0, where it drew neither the applications nor the dependencies between the environments. The properties are applications and relationships, false to leave one out; any other value is no choice, in both tools. They mean nothing in a map of the application layer. A comparison of two plateaus gives the states to the applications as it gives them to the other boxes.

A view in a workspace of plateaus. A view is read against one plateau at a time. A name that the plateau drawn does not have, and another plateau has, is not a mistake of the view, and the two tools say the same: an entry of pinned, opened or hidden is left out of the map (warning: the view `m is drawn without x, which the plateau p does not have`), and a view that cannot be drawn without the name (the element of an overview, a map none of whose pinned elements is there) cannot be drawn in that plateau. archicode views generate --view <id> skips such a view with a warning, and does not fail, since asking for a view in every plateau of a loop is legitimate:

warning: skip `x`: it names `shop.mailer`, which the plateau `to-be` does not have

The editor says it in the view (The element “x” is not in the plateau “p”.). A name that exists in no plateau is the error of [plateau-untied].

A shipped example. The layered Brightcart of the repository (src/test/resources/brightcart/layered, a fixture of the tests, not an example of this manual) keeps seven views and three stories in a folder, shared/, that no plateau owns, so that these cases are checked on it. shop_overview is an overview of shop, which the plateau marketplace renames storefront: archicode views generate --plateau marketplace -i shop_overview skips it with the warning above, and the three other plateaus draw it. marketplace_overview is drawn in one plateau only, and applications_map is drawn everywhere, without shop in marketplace, with a warning. A view is drawn by views generate only when it is named with -i; the plain command draws the built-in views alone.

A view that is about an element that a facet removes is a limit of the command line (#121): views generate --view <id> fails with error: dangling reference: <element>, which names neither the view nor the facet, and does so after the views of the facets before it were written.

By embracing dynamic view generation, leveraging pluggable Viewpoint Services, and facilitating ad-hoc view definitions, ArchiCode equips architects with a toolkit for capturing, communicating, and exploring architectural insights in a dynamic and tailored manner. As we navigate deeper into ArchiCode’s capabilities, you’ll uncover the rendering of views and how they enhance your architectural workflow.

Stories

A story puts views in order, with a sentence for each, to tell how a part of the architecture works. It does not draw anything on its own: each step shows a view, and the editor draws that view live from the model, so a story stays true as the architecture moves.

Stories and views are manifests, like the elements: one file each, in the manifests folders, with the kinds archicode.morin.io/story and archicode.morin.io/view. The editor writes them for you (see Stories: stories and views), but they are plain YAML:

manifests/story.order_flow.yaml
header:
  kind: archicode.morin.io/story
  version: "1"
content:
  id: order_flow
  name: How an order travels
  description: From the shop to the payment provider.
  steps:
    - view: shop_overview          # a view that has a name: see below
      text: The shop receives the order.
    - viewpoint: map               # or a view written right in the step
      layer: application
      properties:
        pinned: [shop.payments]
        hidden: [mailer]
        opened: [shop]
        hide-unlinked: true
      text: It hands the payment over.
manifests/view.shop_overview.yaml
header:
  kind: archicode.morin.io/view
  version: "1"
content:
  id: shop_overview
  name: Shop — Overview
  viewpoint: overview     # overview, detailed or deep: drawn by the command line as well
  layer: application
  properties:
    element: shop
    facet: flow           # optional: the editor draws the view through that facet
    descriptions: true    # the texts of the diagram, when they differ from its default (see the editor)
    wrap: true

A step either names a view by its id, or carries one: a viewpoint, a layer and properties, as a view has. A named view can be used by several stories and generated by the command line (its id is what --view takes); a view written in a step is only for that step, and has no file of its own. The text is plain text. A step on a view that is not declared is reported as a warning by the command line, and shown as missing by the editor. The command line does not draw the stories (see below): it reads them and checks them, and it generates the views of the workspace as it always did, the views of the map viewpoint included (see [map-viewpoint]).

A story belongs to no plateau, like a view (see [plateau-untied]): it is the same story whatever plateau is drawn, and it is declared once in the whole workspace. A plateau: in its header is accepted and means nothing, as it does in a view (see [plateau-untied]).

A step told at a plateau. A step may say which plateau it is told at and which plateau it is compared with, with two optional keys, at and against, each the id of a plateau. They are not the plateau: of a header, which says that a manifest belongs to a plateau: here the story belongs to none and a step says where to look.

  • Without at, the step is told at the plateau the reader has drawn. Without against, nothing is compared. A step that names neither is drawn as the reader had it, the plateau and the comparison.

  • against without at is allowed: the step is told at the plateau drawn and compared with against (what changes from baseline to where I am). When against is the plateau drawn, nothing is compared, which is no mistake.

  • A key with nothing after it, or an empty text (at: ""), names nothing.

plateaus/story.migration.yaml of the example domain_plateaus
# A story belongs to no plateau: it is the same story whatever plateau is drawn. A step may say where it is told (`at`) and what it is
# compared with (`against`), with the id of a plateau; a step that says neither is drawn in the plateau the reader has drawn.
header:
  kind: "archicode.morin.io/story"
  version: "1"
content:
  id: "migration"
  name: "From the shop to the new shop"
  description: "What the new shop changes, one look at a time."
  steps:
    - viewpoint: "overview"
      layer: "application"
      properties:
        element: "shop"
      at: "baseline"
      text: "Today the shop is one system: orders, invoices and receipts, and an inventory of its own."
    - viewpoint: "overview"
      layer: "application"
      properties:
        element: "shop"
      at: "to-be"
      against: "baseline"
      text: "The same system next year, with what changed marked: orders are split in two, invoices and receipts are merged."
    - viewpoint: "overview"
      layer: "application"
      properties:
        element: "warehouse"
      at: "to-be"
      text: "The inventory moved to the warehouse."
    - viewpoint: "overview"
      layer: "application"
      properties:
        element: "shop.web"
      against: "baseline"
      text: "The web site in the plateau that is drawn, compared with where we are today."

Both tools check the keys when the manifests are read, one sentence for each, with the story, the file and the number of the step (from 1), after the layers and before the names the step carries:

error: the story `migration` (`plateaus/story.migration.yaml`) step 1 says `at: tobe`, which is not a plateau of this workspace (the plateaus are `baseline`, `to-be`)
error: the story `migration` (`plateaus/story.migration.yaml`) step 2 says `at: to-be` and `against: to-be`: a plateau is never compared with itself
error: the story `s` (`manifests/story.s.yaml`) step 1 says `at: to-be` but the workspace declares no plateau (a `plateau` key in a header, or a manifest of kind `archicode.morin.io/plateau`)

The last one is told for a workspace that has no plateau too. The command line only checks the steps: it does not draw a story, so a step told at a plateau is never drawn by it (see Limits of today). The fork of the layered Brightcart ships a story that tells one (fork_tour: its steps are told at baseline, at saas and at inhouse, two plateaus that override baseline and do not stand on each other, and compared with baseline, with each other and with the plateaus marketplace stands on), next to order_journey, whose steps name no plateau, and seller_journey, whose steps are all told at marketplace. A name that the plateau of a step lacks is no mistake either, and the command line does not say it. The editor plays the steps, draws their plateaus and tells it (see Stories: stories and views).

Workspaces written before stories became manifests keep their views in views: of workspace.yaml, and may have a stories: there too: both are still read. The editor offers to move them to manifests, which keeps workspace.yaml small and free of the rewrites an editor save makes to it.

Rendering

ArchiCode introduces a systematic approach to rendering views, enriching architectural communication through visualization. Here’s how ArchiCode orchestrates the process of rendering views:

  • View Rendering Mechanism: Within ArchiCode, each View is rendered by a designated "Renderer." This integral component takes the architectural model and translates it into tangible artifacts that resonate with the end user, facilitating a comprehensive understanding of the design.

  • Renderer Definition: A "Renderer" within ArchiCode embodies a set of opinionated and pre-defined rules. These rules are specifically tailored to generate artifacts that eloquently present architectural insights, ensuring consistency and clarity in communication.

  • Pluggable Renderer Service: ArchiCode harnesses a pluggable Renderer Service architecture, enabling seamless integration and utilization of diverse renderers. This extensibility empowers architects to choose the most suitable renderer for the intended audience or purpose.

By introducing a robust rendering mechanism, employing opinionated rules for artifact generation, and facilitating the pluggable Renderer Service, ArchiCode enhances architectural communication by transforming abstract architectural concepts into tangible representations.

Stereotypes and styles

Every box of a diagram is drawn with a list of stereotypes. The stereotypes of an element are, in this order, its qualifiers (each one whole: Spring Boot is one stereotype) and the words of its rendering-stereotypes tag. The tag is a whitespace-separated list, so that external changed gives the two stereotypes external and changed, and a value of one word gives the one stereotype it always gave. A stereotype named twice counts once. The renderer then adds the kind of the element and the way the box is drawn. The command line and the editor read the stereotypes the same way: they come from the same kernel.

The styles of the workspace give a stereotype its look. styles.by-tags and styles.by-qualifiers map a stereotype to a style, and a box has the style of every stereotype it is drawn with. The key is the stereotype itself, not the name of a tag: the keys of by-tags are the words of rendering-stereotypes, the keys of by-qualifiers are the qualifiers. The two maps are equivalent for the renderer, which only sees stereotypes; use the one that says where the stereotype comes from. A style sets any of background-color, line-color, line-style, line-gap, line-thickness, round-corner, font-color, font-style and shadowing. line-style is the length of a dash (0 is a solid line) and line-gap the gap between two dashes: without line-gap the gap is as long as the dash, so that line-style: 5 is a dash of 5 and a gap of 5 and line-style: 16 with line-gap: 3 is long dashes with narrow gaps (PlantUML’s LineStyle: 16-3). A line-gap means nothing without a line-style; when a style overrides the line-style of another one, the gap of the other style goes with the dash it replaces.

Styling the boxes tagged external and changed
styles:
  by-tags:
    external:
      background-color: "lightgray"
    changed:
      line-color: "orangered"
      line-thickness: 3
  by-qualifiers:
    PostgreSQL:
      round-corner: 20
An element drawn with the external and the changed styles
content:
  id: "mailer"
  name: "Mail Provider"
  tags:
    rendering-stereotypes: "external changed"

In the editor. The editor draws a box with the style of the stereotypes it is drawn with: background-color is the fill, line-color, line-thickness, line-style and line-gap the outline (derived from the fill when only the fill is given, see below), and round-corner, font-color, font-style and shadowing the rest. A styled stereotype is also written on its box as a text badge with its name, so that a colour is never the only carrier. The same badge follows the name of the element in the Elements tree and in the tree of the Map, and in the header of an element (after its kind, on Details and on the diagram tabs; when the header is narrow it shows the badges that fit and the name keeps its room), and the key under the diagram shows the badge of each styled stereotype drawn. The badges are part of the SVG and PNG exported from a diagram, while the key is not; a badge is not the dot that marks an element as modified and not yet saved.

For the same stereotype, by-tags wins over by-qualifiers. When a box has several styled stereotypes, a later one overrides an earlier one property by property: with rendering-stereotypes: "external changed", the fill of changed wins, and the properties it does not set come from external. The order is that of the stereotypes of the box, its qualifiers first and then the words of the tag. The command line follows the same rule: it writes the stereotypes of a box last first, since PlantUML lets the first stereotype of a box win, property by property, whatever the order of the styles. The .puml of a box carrying external changed therefore says <<changed>> <<external>>, and the same workspace always gives the same file, byte for byte. The one difference: shadowing is a flag that is only ever switched on, so a style cannot switch off the shadow another style of the same box switched on (the editor lets shadowing: false of a later stereotype do it).

Colours are read as #rgb, #rrggbb, rgb(r, g, b), transparent or a CSS colour name such as lightgray; a value the editor cannot read is ignored. Numbers are whole numbers.

The fill is the colour written in styles, in both themes, as in the diagrams of the command line; styles has no separate dark colour. A box with a background-color and no line-color is outlined with a line derived from its fill: the same colour, darker (each of its channels at 60 %, so the hue is kept), or lighter when the fill is so dark that darkening it would show nothing, as for black. Without it the outline would be the grey of the theme, lost on the fill, and a box inside a box of the same fill, such as the systems of a solution that are both external, would vanish into it. The derived line is as firm on a box that contains others as on one that does not. The line-color of the style always wins, whatever the fill, and the fill itself is never changed; a box with no fill keeps the outline of the theme, and the outline of the box in focus or selected stays the accent colour. The same line is drawn on the badge of the stereotype, and in the SVG and PNG exported from a diagram. In the diagrams of the command line, PlantUML draws a box with the fill of its style and its own thin dark outline, so a box inside a box of the same fill is already told apart there: nothing is derived. The editor chooses the colour of the text so that it reads on that fill, black or white with a contrast ratio of at least 4.5: the font-color of the style is kept when it reads well, and replaced otherwise. Without a background-color, the box and its text keep the colours of the theme, and font-color is not used. Except that a box that contains others, with no background-color of its own, drawn inside one that has one, lets that fill show: its title is then black or white against that fill, in either theme, so that it never lands on a fill it cannot be read on.

Compared with the command line, line-style and round-corner are an approximation of what PlantUML draws. The editor styles only the stereotypes of an element, its qualifiers and the words of rendering-stereotypes: it does not use the kind of the element, nor atomic and composite, as keys, and styles.atomic and styles.composite are not drawn.

States of an architecture (plateaus)

An architecture is never finished: it is how it runs today, how it should run next year, and what the year after may bring. ArchiCode calls each of these states a plateau and tells you what changes from one to the next. This section is the story in one place, from the idea to a review of the changes; the rules are in Plateaus and Comparing two plateaus (in the Domain section), the commands in Choosing a plateau, Compare plateaus and Generate views, and the editor in The pages, The band of plateaus, The Plateaus page, Writing in a plateau and Comparing two plateaus in the editor. What does not work yet is in Limits of today.

Important
 Breaking changes. settings.plateaus, archicode plateau add and --baseline no longer exist: a plateau is a layer (see Plateaus, and Upgrading: what breaks, and what does not to convert a workspace by hand). A path of settings.manifests.paths may no longer contain .. nor be absolute, a reference declared twice is an error, and a plateau id is now lowercase letters, digits, _ and -. A workspace that has no plateau and does neither is read and drawn exactly as before.

The idea

A plateau is a layer: the architecture in that state is the plateau it overrides, plus the elements its own manifests add, changed by its patches. You write what differs and nothing is copied, so nothing has to be kept in sync by hand: when the root changes, every plateau above it changes with it, and a patch that no longer fits tells you so. The difference between two plateaus is computed from the references of the elements and the relationships, never typed: ArchiCode tells what is new, what changed and what was removed, and the views, the table of changes and the editor all draw the same answer.

One thing cannot be computed: that two elements are the same thing. An element that moves under another parent, or is renamed, has another reference, so it reads as one removed element and one new one. ArchiCode never guesses it; you say it, on the element of the more recent plateau, with replaces, and the comparison then reads a moved, split or merged element. It proposes the pairs that look like one thing said twice (the candidates) and applies none. The editor writes the hint when you accept a candidate.

The layout

The folder of the architecture holds one workspace.yaml, with the settings, the styles and the facets that every plateau shares, the manifests of the root, and, for each other plateau, the manifests that say plateau: <id> in their header and a manifest of kind archicode.morin.io/plateau with its patches. The folders of the example domain_plateaus of this manual (src/doc/examples/domain_plateaus in the source repository) are drawn in Plateaus; the tutorial below builds it.

The settings in short

settings.manifests.paths

The folders the manifests are read from. A layered workspace ends a path with /** to read the folders of its plateaus too (see Manifests in folders).

settings.current

The plateau that is drawn when none is asked for; the last one by default when the plateaus form one line. It must be a plateau of the tree. The editor writes it too (see The current plateau), and opens the folder on it when nothing else says which plateau to draw.

settings.plateaus

No longer exists (see the note in Plateaus): a plateau is a plateau: header and a manifest of kind archicode.morin.io/plateau.

A path of manifests.paths is relative to the folder of workspace.yaml, below it (no ..) and not absolute. Every rule is checked before anything is read, and each problem is reported. The details, with the messages, are in Plateaus.

The states

What a plateau changes is told with four states, computed, on elements and on relationships (the fourth is for boxes only), and three more for the elements that say what they replace (see Saying what an element replaces):

State Mark Means

new

+

the reference is only in the plateau

changed

~

the reference is in both and something differs: a property, or a relationship the element declares (an element whose description is the only difference is wording only)

removed

−

the reference is only in the other plateau, the one compared with

contains-changes

±

the element did not change by itself, but something inside it did

moved

→

the element says that it replaces one element of the other plateau (elements only)

split

⋔

the element says that it replaces an element that another element replaces too (elements only)

merged

⊕

the element says that it replaces several elements (elements only)

Each state has a mark, a line style and a legend, so that nothing relies on colour: see Comparing two plateaus for the command line and Comparing two plateaus in the editor for the editor.

The states and the tags you wrote by hand. The states are stereotypes of the boxes, the same ones that a styles.by-tags entry or a rendering-stereotypes tag names (see Stereotypes and styles). If you used to mark the boxes of a target by hand with rendering-stereotypes: "new" or "changed", nothing breaks, and the command line and the editor draw such a tag the same way. One rule decides it: a box gets the default look of a state (its mark, its outline, its tint, its struck title) only when the comparison computes that state for it.

  • A word you wrote that is the state the box has (a new tag on a new element) is one stereotype: the computed state is not written twice, it is the last stereotype of the box, so its look overrides the look of the other stereotypes as a later stereotype always does (the generated .puml writes the stereotypes in reverse, so it reads first there). Your styles.by-tags entry named like the state wins, property by property, over the default look of ArchiCode: a new with only a background-color keeps the thick outline of the default.

  • A word you wrote that is not the state the box has (a new tag on an element that did not change, a new tag on an element that changed, any state word when no comparison is made) is only your stereotype (a .puml of a comparison writes it written-new, so that the default look of new cannot reach it). The box has the style you gave to that name in styles.by-tags or styles.by-qualifiers, if any, and nothing of the default look, whatever else the view shows. On an element that changed, the computed state, which is last, has the last word over it.

  • The tags themselves are not read by the comparison (a rendering-* tag is never a change), so you can drop them when you like: the computed states say the same, and say it only where it is true.

The command line tells you where a word and the comparison disagree, one line per element and word, on the error output (not in the log, which hides warnings by default), and the files it writes and the table it prints are the same whether you read the lines or not. With the tag rendering-stereotypes: "new" added to customer in the example, which did not change, archicode diff says:

warning: the element `customer` carries `new` (`rendering-stereotypes` tag), but the comparison of `to-be` with `baseline` finds that it did not change and holds no change: it is drawn with your own `styles` entry named `new` (if any) and not with the default look of the state. The comparison computes the states, so the word can be dropped.

archicode diff and archicode views generate check the plateau they compare. archicode views generate of a plateau that is not compared says that a state word is a state of a comparison and that nothing is compared here. A workspace with no plateau has no comparison to disagree with, and is never told anything: there the words are your own stereotypes, as they always were. A word that agrees with the comparison is never reported. The editor draws the same: a hand-written word is a badge and a style, and the look of a state only where the state is computed. It tells you the same, in the same sentences, when a plateau is compared (Compare with on the band): in the panel of the element, under what changed, and in the Hand-written states list of the Changes panel (see Comparing two plateaus). Nothing is told when nothing is compared, since the comparison is a choice of the page.

Saying what an element replaces

A comparison finds an element by its reference. An element that moves under another parent, or is renamed, has another reference: the comparison reads it as one removed element and one new one, with nothing that links them. ArchiCode never guesses that two elements are the same thing; you say it, on the element of the more recent plateau, with the key replaces: a list of the full references, in the plateau it is compared with (below, the other plateau: the one it overrides, or the one --against names), of what the element replaces. The key is written where the new element is declared, in its manifest. It is the same hint as the moved block of Terraform. The editor writes it when you accept a candidate (see Moved, split and merged elements, and candidates), and you can edit it in the form of an element. The editor can move an element under another parent without breaking a reference, but a move does not say that the two references are one thing, and nor does a rename (see Moving an element under another parent).

The container inventory in the plateau to-be (plateaus/to-be/inventory.yaml of the example domain_plateaus)
header:
  kind: "archicode.morin.io/container"
  version: "1"
  plateau: "to-be"
  parent: "warehouse"
content:
  id: "inventory"
  name: "Inventory"
  description: "Counts the books on the shelves."
  replaces:
    - "shop.inventory" # the inventory moved from the shop to the warehouse
  elements:
    - kind: "component"
      id: "levels"
      name: "Levels"
      description: "The count of each book."
      replaces:
        - "shop.inventory.levels" # what is inside a moved element says it too

The inventory used to be a container of the system shop and is now one of the system warehouse, so its reference went from shop.inventory to warehouse.inventory. It says what it replaces, and so does the component levels inside it.

The key is optional, and a tool that does not know it ignores it. The comparison turns the elements that say what they replace into three states, and the replaced elements are no longer removed:

  • moved: the element replaces one element, which no other element replaces. It is in another place or has another name, and it is the same thing. Whatever else it changes, it keeps it: a name, a description and the relationships it declares are compared with the element it replaces, and the table says which (the natures), next to moved. A moved element is counted as moved, not also as changed.

  • split: several elements replace the same element (shop.orders became shop.cart and shop.checkout). Each of them is split, and the table names the other ones.

  • merged: the element replaces two elements or more (shop.billing replaces shop.invoices and shop.receipts), or an element that is in the other plateau and in the plateau at the same time. When an element is both split and merged, it is merged.

What the replaced elements held is not carried by itself: a container that moved takes none of its children with it, so each child needs its own replaces (levels above), or it is read as removed (the box of the replaced container is then drawn as the place it was removed from, with the words "replaced by"). What points at a replaced element follows it when exactly one element replaces it: a relationship to shop.till that now points at stock.till is not a change of the element that declares it, and nor is a node that deployed shop.till and now deploys stock.till. What points at a split element is not rewritten, because which half would own it is a guess. The relationships of the halves, and those that end on a half, are therefore not compared with the other plateau and read as new, whether the element had them before it was split or not; archicode diff, gap.md and gap.json say so on each of those rows (of the split shop.report-a) and count them in the header (see Compare plateaus).

Candidates. When an element is only in the other plateau and another one of the same kind and the same layer is only in the plateau, and nothing replaces or is replaced by either of them, the comparison may find that they look like one thing that was said twice: the same name (ignoring the case), a description with most of its words in common, or the only two elements of that kind under the same parent (only when one of the two plateaus is the past of the other, that is, the plateau it overrides or one further down the same line, baseline being the past of all: two plateaus that build on the same one are alternatives, and sharing a parent says nothing between them). A name counts only when no other removed element and no other new element of that kind has it: a Cache in every service, or a Message Broker in every environment, would pair every removed one with every new one and say nothing about which is which, so such a name proposes nothing (the description and the parent can still). It lists them as candidates and it never applies one. To accept one, write replaces on the new element; to refuse it, do nothing. archicode diff, gap.md and gap.json list the candidates once the plateau uses replaces (a workspace that does not is written as it always was), each with its reasons. The candidates are not drawn in the views.

Warnings. The comparison does not fail on a replaces that it cannot use: it ignores it, and says so on the error output of archicode diff and of archicode views generate (not in the log, which hides warnings by default), one line per entry (the example has none; the sample below is from the invented warehouse that Compare plateaus uses):

  • a reference that is not an element of the other plateau (you may be comparing with another plateau than the one you wrote it for);

  • a reference that is still an element of the plateau (what is there is not replaced, and an element cannot replace itself);

  • a reference listed twice (it counts once);

  • an entry that is not a reference (- 12, or an empty entry: it is ignored, and it is not read as the reference 12);

  • a replaces that is not a list (replaces: "shop.mailer": it is ignored, and the element replaces nothing).

The command line gives the comparison the list as you wrote it, so these lines are the ones the comparison says (the editor refuses a replaces that is not a list with a message). A replaces that is well written says nothing, and so does an empty list.

warning: replaces of shop.report-b (application layer): shop.nowhere is not an element of the base plateau, ignored

replaces is read from the elements of the plateau that is compared; a replaces on an element of the other plateau is not read. A plateau that is not compared does not use it.

The replaces of the layers are not composed. A replaces names references of the plateau it is compared with, and the facts of the plateaus in between are not combined (see Limits of today): a move that took two steps, in two layers, is read as one element new and one removed when the plateaus are two layers apart. Compare the plateaus one step at a time to see it as a move.

What the command line shows. archicode diff has the three states in its table, with the counts of moved, split and merged on a line of their own (replacing), and says in the details of each row what the element replaces (see Compare plateaus). The views of the comparison draw them with the marks above (see Comparing two plateaus). The editor draws them too, lists the candidates, and writes replaces for you (see Moved, split and merged elements, and candidates).

A tutorial: from one workspace to a review of the changes

The tutorial builds the example domain_plateaus of this manual, an invented bookshop, from the architecture it has today to a review of the changes in the editor, including the things that change shape. Its commands run in the folder of workspace.yaml; the output quoted is the one the commands print.

Step 1. Start from the architecture you have. An existing workspace is already your first plateau: its manifests are the root, baseline, and nothing in them has to change, not even a header. To keep the next plateaus in folders beside them, move the manifests to a folder of their own and read it with a path that ends in /** (see Manifests in folders); the folder does not have to be called baseline, the name is for the reader.

Step 3. Change what the layer inherits. In the example, shop.payments is added, shop.mailer is removed, shop.web gets the qualifier React and its relationships change, a description is reworded, and four things change shape: the orders are split in two, the invoices and the receipts become one, the reviews are rewritten as the ratings, and the inventory moves from the shop to another system, the warehouse. What is added is manifests (payments.yaml, cart.yaml, checkout.yaml, billing.yaml, ratings.yaml, inventory.yaml); what is removed or changed is the patches of the plateau, which are applied in this order (see [plateau-patches]):

plateaus/to-be/plateau.to-be.yaml
header:
  kind: "archicode.morin.io/plateau"
  version: "1"
content:
  id: "to-be"
  name: "To be"
  horizon: "2027-Q1"
  override: "baseline"
  patches:
    # what the new containers replace, and what is no longer done
    - operator: REMOVE
      target: "shop.mailer"
    - operator: REMOVE
      target: "shop.orders"
    - operator: REMOVE
      target: "shop.invoices"
    - operator: REMOVE
      target: "shop.receipts"
    - operator: REMOVE
      target: "shop.reviews"
    - operator: REMOVE
      target: "shop.inventory" # it moved to the warehouse: `inventory.yaml` says so
    # the web site
    - operator: SET
      target: "shop.web"
      field: qualifiers
      value: ["React"]
    - operator: SET
      target: "shop.web"
      field: relationships
      where: {destination: "shop.catalog", label: "reads"} # the one relationship that has this destination and this label
      value: {label: "browses"}
    - operator: ADD
      target: "shop.web"
      field: relationships
      value: {destination: "shop.payments", label: "pays with"}
    - operator: SET
      target: "shop.catalog"
      field: description
      value: "The books that are on sale."
    # what pointed at the inventory follows it
    - operator: ADD
      target: "warehouse.picking"
      field: relationships
      value: {destination: "warehouse.inventory", label: "counts with"}

  • Six REMOVE: what the new containers replace, and what is no longer done. A REMOVE takes the element with what is in it and what points at it, and archicode diff lists what it took besides the element (step 5).

  • A SET of the qualifiers of shop.web; a SET with where that relabels the one relationship of shop.web towards shop.catalog (the same patch that the editor writes when you change a relationship); an ADD of the relationship towards shop.payments.

  • A SET of the description of shop.catalog: the wording of the description is the only change of that element.

  • An ADD of a relationship to warehouse.picking: what pointed at the inventory follows it. The REMOVE of shop.inventory took the link that picking had, and the inventory is a new container of the warehouse in inventory.yaml.

shop.payments still carries the tag rendering-stereotypes: "new" that its author wrote by hand: it works as before, and the comparison does not need it. In the comparison its word agrees with the state new, so nothing is said; when a hand-written word and the comparison disagree, the command says so on its error output (see [plateau-state-tags]).

A patch that no longer fits is an error that names the plateau, the rank of the patch and its selector. With a typo in the target of the description’s SET (shop.catalogue):

error: plateau to-be: patch 10 (SET target shop.catalogue): selects nothing, there is no element shop.catalogue in the application layer

Step 4. Say what moved, was split or merged. Compare the two plateaus. Read by their references alone, shop.orders, shop.invoices, shop.receipts, shop.reviews and shop.inventory (with its child) are gone, and cart, checkout, billing, ratings and warehouse.inventory (with its child) are new, with nothing that links them. Some of them are the same things, and only you know which, so you say it with replaces on the elements of the more recent plateau (see Saying what an element replaces):

  • shop.orders was split: cart and checkout both say replaces: ["shop.orders"].

  • shop.invoices and shop.receipts were merged: billing lists both in its replaces.

  • shop.inventory moved to the warehouse. It is a manifest of its own, with the parent of its header, and plateaus/to-be/inventory.yaml says parent: "warehouse" and replaces on the container and on its child levels: a container that moves takes none of its children by itself.

  • shop.ratings says nothing, on purpose: it will show a candidate in step 6.

Step 6. Decide about the candidates. Upgrading: what breaks, and what does not

From settings.plateaus to layers. The key no longer exists, and no command converts a workspace: a workspace.yaml that still has it is refused with the one line quoted in Plateaus. To convert one by hand:

  1. Keep the manifests of your first plateau: they are the root, baseline, and need no header. Its id changes: --plateau as-is, settings.current: as-is and scripts that name it must say baseline (a Kind: Plateau manifest with id: baseline and name: "As is" keeps the name for people).

  2. For each later plateau, from the oldest, write a manifest of kind archicode.morin.io/plateau (its id, name, horizon and override: the previous plateau, or baseline for the first). The manifests of elements that are new in that plateau get plateau: "<id>" in their header. What the plateau removes or changes among the elements it inherits becomes a patch (REMOVE, SET, ADD or MERGE, see [plateau-patches]). The copies of the unchanged manifests in the old complete folders are deleted: a manifest that declares again an element of a plateau below it is the error of [plateau-header].

  3. Delete settings.plateaus, and write manifests.paths (a workspace with plateaus could not have one; the default is the folder manifests) with an entry that ends in /** for the folders that hold the plateaus (see Manifests in folders).

  4. Run archicode plateau list and archicode diff --plateau <id> for each plateau: the counts should be the ones you had.

Four differences to know: the views of a plateau are written in views-<plateau> and the views of its comparison in views-<plateau>-vs-<against>; every plateau but the root is now compared with the plateau it overrides when its views are generated; a plateau id is lowercase letters, digits, _ and - (a capital, or a dot as in v1.2, is refused: error: the plateau id `v1.2 in …​ is not valid`); and --baseline is --against. The from key of a plateau, which was reserved, and archicode plateau add, are gone.

Earlier changes. Two things that used to pass stop with an error that says what to change. Everything else about a workspace that has no plateau is unchanged: it is read, and generates its views in the same folders, byte for byte as before (checked on the views of this repository’s workspaces and on a copy of a real workspace of 3,411 views).

  1. A path of settings.manifests.paths with .. or an absolute path. ../shared, /srv/manifests and C:\data are refused: one folder holds a whole workspace, so that the editor, which only reaches the folder it opened, reads what the command line reads. Move the folder below the folder of workspace.yaml, or move workspace.yaml up to a folder that holds both, and change the path to match. A path that stays below the folder (manifests, node_modules/<module>/manifests) is not affected.

  2. A reference declared twice. Two manifests, a manifest and an element nested in another one, or two elements of one file that share a reference used to pass silently, and which of them was drawn depended on chance. The command line now stops, names the reference and the two files, and writes nothing, and the editor reports the same in the same words (see [duplicate-references]). Remove one of the declarations, or give one of them another id. Two identical copies count too. This check applies to workspaces without plateaus as well; with plateaus, the same reference in a plateau and in its ancestor is the same error, and in two plateaus that do not stand on each other it is no duplicate, since they are alternatives.

Nothing is to be changed in the manifests themselves: their format is the one it always was, with two optional keys more, plateau in the header and replaces (see Saying what an element replaces), that an older version of ArchiCode ignores.

Later changes. Layers came with the editor reshaped; a few things moved after them, and what a workspace written for the first version of layers may meet is this:

  1. A view or a story that says plateau:. It is accepted and means nothing, with no message at all (see [plateau-untied]; the warning that earlier versions printed is gone). A workspace whose only plateau: is on a view or a story is no longer a workspace of plateaus, so --plateau and settings.current are errors for it, as for any workspace without plateaus. Two plateaus that each declared a view of one id, or a story of one id, are now one error: a view and a story are declared once.

  2. Kinds. container-group, solution-group and system-group are refused, in both tools: write an element of kind group in the elements of the container, the solution or the system (see [manifest-kinds]). An element declared with header.parent under a parent that cannot hold its kind (a system under a container) is an error, with or without patches, where it used to load in a plateau that had none (see [nesting]); an id with a dot is an error; and the key element of a group in a solution, which was read by mistake, is not read.

  3. Empty values and spellings. A key with nothing after it and an item with no value in a list are absent, in both tools (global-enabled: with nothing is true; an empty workspace.yaml is the default workspace; an item of relationships with no value draws no relationship in the editor either). The keys of settings.facets are global-enabled, directory-name-template, hide-unlinked and json-path; the camel-case spelling is still read. The text of header.parent, header.plateau and header.version is the text as written: parent: yes is the reference yes.

  4. The maps. archicode views generate --view <id> draws a view of the map viewpoint, which it used to skip with a warning (see [map-viewpoint]).

  5. The order of the warnings. The facets are read in the order of the file, so the warnings that name them, and the creation of their folders, come in that order.

  6. Folders of a comparison. A folder that holds both gap.json and gap.md is left out of a /** read, whichever command wrote it (see Manifests in folders).

  7. The editor. The pages are Plateaus, Applications, Environments, Elements, Stories, Files and Settings (see The perspectives and their pages); the band has two lists; Files has no choice of what it lists.

What changes for a reader who knows 0.14.0. Since that release, these things moved; the first two can change a file or an error that a workspace had:

  1. A saved Map of the technology layer draws more. It draws the applications deployed on the open nodes and the dependencies between environments that they give, unless the view says applications: false or relationships: false (see [map-technology]). The views of a workspace that has no such map are written as they were, byte for byte, and so are the other viewpoints.

  2. A root container, component or node in a workspace that has plateaus is an error, with the same line in both tools (see [nesting]). A workspace with no plateau is read as it was.

  3. The band: Compare with shows the tree of the plateaus and has no entries Future any more (see The band of plateaus).

  4. The editor has the field Current plateau in Settings, J and K for the walk through the changes, the box of Add to story…​ that writes at and against, and a dialog before a rename that leaves a view broken in a plateau beside the one drawn (see The current plateau, Keyboard, Stories: stories and views and [editor-rename]).

  5. The command line: archicode diff --width <columns> wraps the text table (see Compare plateaus), and a plateau: in the header of a view or a story says nothing (see [plateau-untied]).

One more thing changed for a workspace that has plateaus and that marks its boxes by hand with a state word (rendering-stereotypes: "new" or "changed"). A word that agrees with the comparison is drawn as before. A word on an element that does not have that state used to give the box the default look of the state in the views of the command line, and the editor did not: it now gives it nothing in both, and the command says so on its error output (see [plateau-state-tags]). The files that a workspace without a state word writes are the same, byte for byte.

Limits of today

These are things that do not work yet, or not the way you might expect. Each is known and filed (the issue is tmorin/archicode#N on GitHub), and the tools say so when they meet one.

Plateaus.

  • The replaces of the layers are not composed (#89). replaces is read relative to the two plateaus compared, and the facts of the plateaus in between are not combined. A move that took two steps (a plateau moves shop.app.search to commerce.search, the next one moves it again to discovery.search) is not seen as a move against a plateau two layers up: the second replaces names commerce.search, which the older plateau does not have, so the element reads as new and the first one as removed. On the layered Brightcart of the repository (src/test/resources/brightcart/layered), archicode diff --plateau marketplace --against baseline prints, besides the table:

    warning: replaces of discovery.search (application layer): commerce.search is not an element of the base plateau, ignored

    and lists discovery.search as new and shop.app.search as removed. Compared with the plateau it overrides, the same plateau reads the move right. Compare the plateaus one step at a time to see a move that took two.

  • A patch cannot take a field out (#94). SET, ADD and MERGE need a value, and REMOVE takes an element, so a plateau cannot say "this inherited description is gone". A list or tags can be emptied (SET of [] or {}), a text can be set to another text. The editor refuses to clear an inherited text with one sentence.

  • The editor does not move an element a plateau inherits (a patch never changes an id or a parent): draw the plateau that declares it. It does not move a group under a parent of a plateau that the plateau drawn overrides either (#114): the group is written inside a file and has no manifest of its own to say where it goes. A Move does not warn of the views it leaves broken in a plateau beside the one drawn, as a rename does (#122).

  • A comparison with the parent cannot stay on the parent. On the band, the parent in the tree of Compare with is read as Past (follows the plateau drawn), so the comparison moves to the new parent when another plateau is drawn. There is no fixed comparison with the parent.

  • A plateau that other plateaus override cannot be deleted in the editor (#112): the dialog says which plateaus override it, and nothing is deleted. Delete the plateaus above it first, or change their override in Edit. The editor draws the plateau of the address, then the one this browser drew last, then settings.current (which Settings writes, see The current plateau), then the root; the command line draws the last plateau when the plateaus form one line and no settings.current says otherwise.

  • A story told at a plateau is never drawn by the command line (#109). archicode checks at and against and draws no story, so there is nothing to draw a step with. The editor plays them.

  • The dependencies that a deployed application gives do not include those of what is inside it (#124). The map of the technology layer, like the overview, the detailed and the deep viewpoints of an environment, reads the relationships of the application that a node lists in applications, not those of its components: a container deployed on a node whose components declare the relationships gives no link to the node that hosts what they depend on.

  • A view whose element a facet removes fails views generate --view (#121) with error: dangling reference: <element>, which names neither the view nor the facet; the views of the facets before it are written already. Name such a view in a workspace where the facet keeps its element, or leave it out of the command.

  • The editor is slow on very large pairs of plateaus (#125). The number of kernel calls does not grow with the elements, but the time of one call does: for the 591 elements and 839 changes of a test pair (replaces-large-pair), in Node, the first call that finds what has nothing to draw takes about half a second where the 82 elements of the layered Brightcart take 16 milliseconds, ten to thirty times longer for seven times more elements. No shipped workspace is that large.

Reading and writing files.

  • The save of the editor writes a file again in its own layout in these cases (#78): an anchor, an alias or a tag inside square or curly brackets (qualifiers: [&a oven, *a]); a tag on a text that goes over several lines, when the tag changes what the text reads as; and a layout the save does not follow (an anchor on a list item whose map starts on the next line); an anchor or a tag on a key (&k name: x) is the other case: the command line reads it and the editor refuses with an anchor or a tag on a key is not supported. In the first two the file is read and the model is what it says, but the comments are lost and the aliases are written as their values; the third is not opened.

  • The two tools read a few plain scalars differently (#103). A plain scalar written as a number in YAML 1.1 that a browser cannot print back as it was written (0x1F, 010, 1_0, 5.0, 1e2) is a number for the command line and a text for the editor; quote it where it is an id or a reference. The editor does not tell the line and the column of a mistake in a file: it names the place by its path in the file, as the command line does (see Errors, warnings and exit codes).

  • The Remove buttons of a qualifier, an application and a use address the file by the position in the list drawn (#120). A list that has an item with no value (qualifiers: [a, null, b]) is drawn without it, and Remove on b takes out the empty item and keeps b. Remove the item in Files.

  • Two small losses of the save (#119): a UTF-8 byte-order mark at the start of a file is dropped when the editor saves it, and when a block is moved to another file a comment after its last line may stay with the next element instead of going with the block.

  • Cancelling a dialog may drop what was typed (#123, not verified in a browser): saving the form of an element can open a dialog before anything is written (the plateaus a write changes, the plateaus that keep the old reference after a rename), and Cancel may rebuild the form from the model.

The command line.

  • archicode diff cannot compare with another version of the workspace in git (--baseline-ref, #25). --width, --fail-on and --only-changes are built (see Compare plateaus and Generate views). views generate writes no text table, so it has no --width.

The editor on a small screen (#82). On a window 360 pixels wide the top bar still wraps onto several lines (about 105 pixels), and the regions under it keep the heights they have on a large screen. Nobody has judged the editor on a phone.

Editor

ArchiCode comes with an editor to browse, edit and draw a workspace without leaving the browser. It is a single page, standalone.html, that reads and writes the files of a workspace folder: nothing is uploaded anywhere, the page and the files stay on your machine.

Opening the editor

There are two ways to open it:

  • Served by the command line. archicode editor serve serves the editor and opens the folder of the workspace.yaml in it, with nothing to pick. It works in any browser. See Serve the editor.

  • From the published page. The page published next to this documentation, at /editor/ of the same site, asks for a folder. That needs the File System Access API, which Chrome, Edge, Brave and Opera have and Firefox and Safari do not: with one of those, use the command above instead.

The published page remembers, in the browser, every folder it opened, with the name its workspace gives itself (see Name of the workspace). When the page opens again, it opens the last folder directly if the browser still lets it read it; otherwise it asks for a click (Reopen), because a browser only gives that permission back on a click. Close folder, at the top right, closes the folder and shows the list of the remembered folders: the closed one stays in it, and the next visit does not open it by itself. When no folder is open, the list shows each folder by the name of its workspace, with the name of the folder below it when they differ, most recent first: a click on one opens it, Remove from the list makes the browser forget it, and nothing is deleted on disk. Under each folder, the list says what a click will meet, as the browser answers without asking anything: Opens without asking, Will ask for permission (the browser shows its prompt), Blocked by the browser, or Could not be reached / Could not be checked (the folder may have been moved or deleted). A folder picked again is not added twice, even by two tabs at the same moment: the browser then holds two records for it for an instant, and the editor merges them into one, keeping the name of its workspace and its place in the list. A folder that cannot be opened (the permission refused, the folder moved or deleted) stays in the list, which says why, until it is removed. Served by archicode editor serve, the editor has one folder, the one of the server: there is no list and no Close folder.

The editor loads elkjs (the diagram layout) and CodeMirror (the file editor) from a CDN when it opens. Without network access, it still works, with plainer diagrams and file editor.

In Settings, the paths of the manifests are one per line, and a path that ends in /** is read with the folders below it (see Manifests in folders); a new element, view or story is written in the folder of the first path. The editor served by archicode editor serve does not list the hidden entries of a folder at all, so a path that names a hidden folder reads nothing there, and does not list a link to a file that points out of the folder, which the command line reads. A browser that lets the page read a folder gives no way to tell a link from a folder: the page stops at a folder that is one it is inside of, but reads a link to another folder, which the command line does not.

The editor reads and writes YAML manifests (.yaml and .yml) only. The command line reads JSON and TOML manifests too (see Manifest formats and kinds): the editor reads neither, so what such a file declares is missing from its trees and diagrams, and relationships that point at it show as dangling. It says so, in Files (which names the files) and above the trees of Elements (which counts them).

A reference declared more than once is reported, not chosen: a red note above the trees of Elements and of Files gives the same message as the command line, each file that takes part is marked duplicate in Files and says so when opened, and no diagram is drawn until each reference is declared once (a view or a story with a duplicated id is reported too, and does not stop the diagrams). Nothing else is blocked: the editor still edits and saves, so that the duplicate can be fixed in it.

The page writes its own address in place of the one that was typed, without adding an entry to the history of the browser. The parameters of an address (ref, tab, pin, facet, story, view, plateau…​) are the ones they were.

The address says the plateau. A link with plateau=<id> draws that plateau, and compare= the comparison it names (see The address and the trees); an address with no plateau= is the root, baseline, which the page never writes. This is also true once the editor is open: an address that is typed in the tab, followed, or reached by Back and Forward draws the plateau it names (an unknown plateau leaves the one that is drawn). A comparison chosen on the band changes no address, so Back between two comparisons of the same plateau does nothing.

Environments is a Map like Applications, on the technology layer: the tree of environments and nodes on the left, the pins, the eye, the chips, the Changes panel and Name view…​ are the ones of Applications. Unlike Applications, it draws the applications deployed on the nodes and the relationships between environments, and its tools can leave each of them out (see Applications and Environments: the Map). The page Elements keeps the tree of both layers, and is where an environment or a node is edited and created, as an application element is. Show on map, on an element of either layer, opens the Map of that layer with the element pinned, and a row of the Changes panel about the other layer leaves the Map on screen for the Map of that layer.

Settings has no section for plateaus: a workspace of layers writes its plateaus in its manifests (see The Plateaus page), and has the paths of its manifests, as a workspace with no plateau does. It has one field about them, Current plateau, which is the key settings.current (see The current plateau). The rest of this chapter says the Map for what Applications and Environments draw, one for each layer. A workspace that writes no layer has the same perspectives and the same pages, and its band has one plateau. Its files are read, drawn and saved as they were.

Elements

The Elements page is the tree of both layers of the workspace on the left, and the selected element in the center. The center has four tabs:

  • Details: the fields, qualifiers, tags and relationships of the element, with Edit to change them (change its id and every reference to it follows; Move, in the edit form, puts it under another parent, see Moving an element under another parent), and Delete (the relationships of other elements that pointed at it are listed first, so that none is left dangling by surprise).

  • Overview, Detailed and Deep: the viewpoints of the same names, drawn live from the model, as the command line generates them. Detailed is for an element that can contain others. Clicking a box in a diagram selects that element.

Renaming an element in a workspace of plateaus. Saving the form of an element with another id rewrites every reference to it. In a workspace that has plateaus the rewrite is made in the files of the plateau that is drawn and of the plateaus that stand on it, since the others do not see the element through it, and in the views and the stories of the workspace, which belong to no plateau and so follow everywhere. A plateau beside the one drawn (one that does not stand on it and does not override it) may still declare the element, or inherit it, under its old reference: a view or a step that names the new reference then cannot be drawn there any more. When that is so, saving the form first opens a dialog before anything is written. It names the plateaus that keep the old reference and the views and the steps of the stories (by story and number) that could no longer be drawn in them, and has two buttons: Cancel, which writes nothing, and Rename anyway, which writes what a rename always wrote. To keep every view whole, cancel, draw each of those plateaus and give the element the same new id there; once every plateau that has it uses the new reference, the views are drawn in all of them. Nothing is asked when no view or step is at risk, when the plateau drawn is baseline (every plateau stands on it), or in a workspace with no plateau. Move changes a reference too and does not warn yet (tmorin/archicode#122).

The badges and colours of styled stereotypes, on the boxes and in the tree, are explained in Stereotypes and styles.

Changes stay in memory, with a mark on the tree for each modified element, until Save all changes writes them. A file that changed on disk since the editor read it is not overwritten: the save is refused and says which one. A file that is saved keeps what the changes did not touch: its comments, its blank lines, the quotes of the values and its final line break. Only the lines that changed are rewritten, and a value written anew (a renamed id, a new parent, a reference that follows, a replaces) keeps the quoting of the line it replaces, the way its key is written and its trailing comment; a line that is added is written like the lines around it (double quotes, single quotes or none, as the file does), and plain when the file quotes nothing. A list or a map written in square or curly brackets (replaces: [a, b], tags: {zone: north}, on one line or on several, nested, as an item of a list of maps) stays as written when the change does not reach it; a change to it writes it as a block, in which the comments that were inside its brackets stay as lines of the block (a comment above a value above it, a comment after a value at the end of its line), and the quotes of its values and of its keys and the words of its booleans (on, yes) are the ones you wrote, except for a value the change sets. The same words (yes, no, on, off, ~) and a key with no value (description:) stay as written in the lines the change does not reach, and a comment or a blank line above a line that is rewritten stays above it. A list written at the same column as its key (tags: then - a at the same column) is followed too: its items and comments stay, and an item that is added is written at the column the list uses; the comment after [], {} or a key with no value stays on the line when a change fills the collection, and the comments inside empty brackets stay under the key. A manifest that uses a YAML anchor, an alias or a tag is read by the editor and by the command line the same way: an alias (description: *n) is the value of the anchor it points at (name: &n "Bakery"), not its name, and a tag qualifies a scalar (!!str 12 is the text 12; !!int, !!float, !!bool and !!null read it as such, any other tag as a text). A merge key (<<: *base) is not a merge: it is a key named <<. The anchor, the alias and the tag stay as written in the lines a change does not touch, and a line a change rewrites keeps its anchor and its tag; an alias stays an alias as long as the line still says what its anchor says, and is written as its value when a change makes them differ. The editor does not follow an anchor, an alias or a tag inside square or curly brackets ([&a one, *a]), nor a tag on a text that goes over several lines: such a file is written again entirely in the editor’s own layout, its comments lost and its aliases written as their values (see tmorin/archicode#78). An anchor or a tag on a key (&k name: x) is read by the command line and refused by the editor, which does not open the file and says so (see Limits of today). When a file is laid out in a way the editor does not write (an indentation other than two spaces, for example), it is written again entirely in the editor’s own layout, and its comments are lost.

Applications and Environments: the Map

The Applications page, which the editor called the Map until wave 014, draws the whole application layer, with no element selected, and the Environments page draws the whole technology layer the same way, with the same tools: one Map for each layer. The tree on the left of each lists the elements of its layer only (Environments in the title of the tree of the technology Map), the pins, hidden elements and open boxes of a layer are that Map’s own (a reference can exist in both layers, and a pin of one means nothing in the other), and a technology element is the pin of the Map of its layer. A Map opens folded: only the top of the layer shows (the solutions and systems, or the environments), and a link is drawn between the boxes its two ends land on, so opening a box splits the links that reached it among its children.

In the tree on the left, each row has two buttons, which appear when the pointer is over the row or the row has the focus:

  • Pin (the pin) keeps only what touches the element. Pin several to keep what touches any of them. With nothing pinned, the whole layer is drawn.

  • Hide (the eye) leaves the element, what is inside it and their relationships out of the map.

The pinned and hidden elements are also shown as chips over the map, each removable, with Clear all once there are more than two. In the tree, rows of the elements the map does not draw are greyed. Folding the tree does not change the boxes of the map: use Fold all and Unfold all in the toolbar of the map, or the buttons of the boxes. Hide unlinked leaves out the boxes that no link reaches; it is in the toolbar of the diagrams of Elements too, where the element itself always stays. It is in the URL (hide-unlinked=1) and in a saved view. A saved view of a Map keeps the layer it draws, and the command line draws it too (see [map-viewpoint]).

What Environments draws besides the technology elements. The Map of the technology layer also draws the applications deployed on the nodes, a box each inside its node, and the relationships: the ones the technology elements declare, and the dependencies between environments that the deployed applications give (an application of an environment that depends on an application hosted in an environment or a node that the first uses). Both are what the command line draws for the same view (see [map-technology], which says exactly which). A node that hosts applications can be opened, with its chevron or Unfold all, and only an open node shows them, so the Map opens as folded as before. A click on an application box selects the application, in the application layer: the panel on the right is the one of that application. An application is not pinned, hidden or opened on its own: pin or hide the node. The group Applications and Relationships in the tools of the diagram turns each of the two parts off and on (a button is lit while its part is drawn): Applications off leaves the application boxes out and the links between the nodes that host them stay, Relationships off leaves every link out. The choice is in the URL, as what is left out only (applications=0, relationships=0), and it is what a saved Map view says in its properties (applications: false, relationships: false; the same two buttons, on the page of a saved view of the technology Map, edit the view like the texts do). It is a choice of the view, not of the model: it writes nothing to the workspace, and it is not kept when you go to another page. On the Map of the application layer there is no such group.

Center puts the selected box in the middle at a readable size (with nothing selected on the Map: the top of the map, centered across), never below 80%, and Fit shows the whole diagram, however small. Fit is in the URL (frame=fit) and Center, how a diagram opens, is a URL with no frame, so a link opens the diagram framed as you left it; a zoom or a move of your own is not part of the link. PNG and SVG, in the header, download the diagram.

The inspection panel

Beside a diagram, on the right, a panel shows the data of the selected element without leaving the view: its name and styled stereotypes, its kind, its layer, its id and reference, its description, qualifiers and tags, and the file that declares it. It is there on the Map (Applications and Environments), on the Overview, Detailed and Deep tabs of Elements (where a click on a box moves to that element, and the panel follows) and on the page of a view in Stories (where a click on a box selects it on the page only, see Stories: stories and views); it is not on Details and in the edit form, which show the same things themselves. Nothing is shown, and no room is kept, while nothing is selected. The panel is resized by dragging its edge (the width is remembered; a double click on the edge gives the default back), it goes away with Maximize, and on the Map its x button deselects the element. On the Map the panel says so when the selected element is not drawn (a pin, a hidden element or a folded box leaves it out), and when it is an element of the other layer, which the Map never draws (This map draws the technology layer only. on Environments, The map draws applications only. on Applications). A click does what it did before: on the Map it selects, in Elements it moves to the element.

A click on a link of the diagram, or on its caption, selects it instead, and the panel lists each relationship the link stands for: its label, its qualifiers and its tags (tcp-port, doc-exchange…​), with the element that declares it (a button: it selects that element, in the layer of the drawing, as a click on its box does) and the one it points at. What is selected is the pair of boxes the link joins, so a link that groups several relationships lists them all (and says so), a link between folded boxes names the folded end and how many elements it hides (open it to see the relationships one by one), and a link to an unknown element says it points at nothing. The links of that pair are outlined. When several links join the same two boxes, the panel says how many, and marks (with the words Clicked link) the relationships of the one you clicked, unless they cannot be told from the others'. The links of a diagram are one stop of the Tab key, however many there are, and so are its boxes (Tab goes from one group to the other): once on a link, the arrow keys move to the next and the previous link, in the order the diagram draws them, and Home and End go to the first and the last. Enter or Space selects the link that has the focus. The stop is where the focus last was among the links, or else the selected link, or else the first one; for the boxes it is where the focus last was, or else the selected box, or else the one in focus of the diagram, or else the first one. x or Escape deselects: on the Map the panel goes, in Elements the panel of the element comes back. Selecting a link changes neither the perspective nor the tab, and in Elements the element stays the one being looked at (the tree, the tabs and the URL keep it). On the Map, if the panel that appears leaves the link behind its edge, the view moves by the least it takes to show it, once; a link already in view does not move the view. The selected link is in the URL, after the other parameters of the view (link-from=customer&link-to=shop: the two boxes of the drawing), so a copied URL, a reload and Back or Forward bring it back, and bring the view to it if it is not in sight. Selecting a link rewrites the current entry of the history, like a zoom, and does not add one. A link the drawing does not have when the URL is opened (it was renamed, or the boxes it joins are folded differently, which the URL does not carry) is dropped, and the URL with it. The selection ends as soon as the diagram it was made on is no longer the one on screen (another perspective, Details, another element, or a drawing that no longer has the link: a fold, a pin, a facet). A click on a box does what it did before and ends the link selection. A relationship the diagram does not draw (secondary links between deployed applications, unless a facet asks for them) cannot be selected.

Since the panel takes room from the center, the header of the diagram goes to its narrower states sooner (see The header of a diagram): resize or close the panel to give it back.

The header of a diagram

The header over a diagram, on the tabs of Elements and on the Map, adapts to the width of the center panel, which is the window minus the left panel, so dragging the left panel changes it. From wide to narrow:

  • Wide: every control shows its words.

  • Narrower: Show on map (or Open in Elements on the Map), Name view…​, Add to story…​ and Maximize show only their icon; the tooltip says what each one does.

  • Narrower still: Show on map or Open in Elements, the Story buttons and the Download buttons (PNG, SVG) move into the menu of a "⋯" button, which closes with Escape or a click elsewhere. The facet list and Maximize stay in the header. The menu items work exactly like the buttons they replace.

  • Very narrow: the header takes two rows.

The texts of a diagram

Four buttons in the toolbar of a diagram, in the group Show, choose what the boxes and the links say. A lit button is a text that is drawn:

  • Labels: the caption of each link, with its qualifiers in brackets. A long caption does not run over the boxes next to it: it is broken at the spaces into lines of at most 220 pixels (about forty characters at the size of the diagram), centred on the link, and the layout leaves room for all the lines. A word that is wider than a line is cut with an ellipsis, as a name is. The qualifiers are kept in one piece as far as possible, at the end of the last line when they fit and on a line of their own when they do not: the label gives way to them rather than the other way round. They are cut only past two lines without Wrap, or when a single qualifier is wider than a line (then its closing bracket is kept). Without Wrap a caption has at most four lines, and an ellipsis replaces the end of the label. The caption is broken whether Wrap is lit or not, and the tooltip and the accessible name of the link always have all of it. The command line breaks the captions of its PlantUML views too, in narrower lines (PlantUML’s own wrapWidth of 200).

  • Qualifiers: the qualifiers of each element, after its kind, as the command line writes them: [container: rest, public].

  • Descriptions: the description of each element that does not contain others, under its kind, up to three lines.

  • Wrap: long names, qualifiers and descriptions are broken over several lines, and the box gets taller, instead of being cut with an ellipsis. A box that contains others cuts the qualifiers of its header at any rate. The captions of the links, which are always broken, then show all their lines instead of four at most.

The diagram of an element starts with the labels and the qualifiers, as the command line draws them. The Map starts with none of them, to stay readable. Only a choice that differs from that is remembered: it is in the URL (labels=0, qualifiers=1, descriptions=1, wrap=1), and in a saved view (see Stories: stories and views), so that a link or a step of a story draws the same texts. The tooltip of a box always has the qualifiers and the whole description, and the SVG that is downloaded is the diagram as it is on screen.

Stories: stories and views

The Stories perspective, which the editor called the Library until wave 014, keeps what the workspace says about itself, on two sides: Stories (see Stories) and Views, the named diagrams that the stories are made of. Each side has its list on the left and its page in the center, and they lead to one another: the view of a step is a link to that view, and a view lists the steps that show it. The URL says which side is open (/stories and /stories/views; the former /library/stories and /library/views still open them). The page lists the same stories and the same views whatever plateau is drawn: a story and a view belong to no plateau (see [plateau-untied]), so there is no list per plateau and no note about other plateaus, and a story or a view is edited, renamed and deleted from any plateau. A new story or view is a manifest in the first folder of manifests.paths, with no plateau: in its header, in a workspace of plateaus as in one without. A diagram on the Applications page, on the Environments page or in Elements has two buttons in its header:

  • Name view…​ keeps the diagram as a view, in a file of its own (view.<id>.yaml): the element and the viewpoint (Elements), or what is pinned, hidden and open, and the layer (Map), with the facet, Hide unlinked and the texts it draws (and, for the Map of the technology layer, applications: false and relationships: false when one of them is turned off). It keeps the recipe, not a picture: the view is drawn again from the model each time. A named view can be put in several stories, and generated by the command line.

  • Add to story…​ puts the diagram in a story, as a step after the one being told, or at the end. A dialog asks which story (a list to pick from, or the name of a new one: a name that is already a story’s is that story). The step carries its own view (no extra file), unless the diagram is one that was named: then it points at it. In a workspace that has plateaus the dialog has a box that keeps the plateaus in the step: Tell the step at to-be, compared with baseline`. It is checked when a comparison is on screen, and not otherwise. Checked, the new step is written with `at (the plateau drawn) and against (the plateau compared with), as the plateau ids they are now: a comparison with the Past, which follows the plateau drawn, is written as the plateau that it is at that moment, and the dialog says so. Unchecked, the step has no key and is drawn as the reader has it, as before. A comparison that has no plateau to name (the plateau drawn itself, a plateau that is gone) leaves against out, and the dialog says why; plateaus that cannot be drawn offer no box. A workspace with no plateau has no box.

While a story is being walked through, a bar over the diagram says where you are, with Previous and Next, and the words of the step, to read; Edit text turns them into a box to type in (it opens by itself right after Add to story…​, so that you can write as you go). Back to this step draws the saved view again when you moved away from it, and Leave story closes the bar. A step that cannot be drawn (its element was deleted) says why in the bar, which stays: Next and Previous still work. The story is in the URL, so a link or Back lands on the same step.

A step told at a plateau. A step that says at or against (see [story-step-plateaus]) draws its plateau and its comparison before it draws its view, in the whole editor: the band, the Changes panel and the diagram are the ones of that plateau, and it is the step, not the plateau, that is an entry of the history. The bar says told at To be, compared with As is. A step that names none is drawn as the reader had it when the story began; a plateau or a comparison that the reader chooses on the band in the middle of the story is the new home of the steps that name none. Back to this step is offered when the plateau or the comparison on screen is not the step’s, and Leave story closes the bar and changes nothing: the diagram stays as it is. A name that the plateau of the step lacks is no mistake of the story: the step says The element “x” is not in the plateau “p”. and cannot be drawn. A step whose plateau is none, or cannot be drawn, changes nothing, says why in the bar, and stays.

On the Stories side, a story is open as soon as there is one, and edited in place: its name, its text, the order of its steps (Up, Down, Remove, which can be undone right away) and the words of each step. In a workspace that has plateaus, each step has two lists, Told at (the plateau drawn, by default) and Compared with (nothing, by default): a choice that is the default takes the key out of the step, a plateau that is none is listed and flagged (not a plateau) so that it is not lost, and Keep as named view keeps the two keys with the step. The step that is showing on the diagrams is marked. Play walks through the story from its first step, and Show on diagram draws one step. A step that carries its own view says so, and Keep as named view gives it a name and a file; a step whose view was deleted offers to point at another one. Renaming an element updates the views and steps that point at it. A change that is not saved yet is marked modified.

On the Views side, the page of a view that can be drawn draws it in the center, from the model, with the canvas and the tools of the Map and Elements: zoom, Center, Fit, Hide unlinked, the four texts (see The texts of a diagram), and PNG and SVG in the header. The facet of the view is applied: it is drawn here, not picked. There is no folding on this page, since the open boxes of a Map view are part of the view. The zoom and the moves are the page’s own and are not changes to the view, and the page changes nothing the Map and Elements show (selection, pins, tab, facet, texts, address). The header keeps Open on diagram, which draws the view on the Map of its layer or in Elements to explore it with their tools, Rename and Delete, and has Maximize, which hides the list of views and the right-hand panel (M maximizes, Esc restores; the Map is not touched).

The panel on the right, resized and hidden as the one of the Map (see The inspection panel), has the view first (while a plateau is compared, it has two tabs, View and Changes, see The Changes panel): what it draws and the file that keeps it, then a field for each attribute of the view, and the steps of the stories that show it, each a link to its story. Once something is selected, the inspection of the selection comes under it; the panel stays where it is when the top of the inspection is in sight, and otherwise scrolls by the least it takes to show its first lines, so that the fields of the view stay in sight as long as there is room. A click on a box, or Enter on the box that has the focus, selects the element and shows its panel, which has a Show in Elements button: it leaves the page and selects the element there, on the tab Elements was left on. A click on a link or on its caption shows the relationships it stands for, and the elements named in that panel select on the page too. The selected box is outlined, and x or Esc deselects. A box for a relationship that points at nothing cannot be clicked here. This selection is the page’s own: it does not select anything on the Map or in Elements, it is forgotten when another view is shown, and it is not in the URL, which carries no more than #/stories/views?view=<id> (and the plateau).

A view is changed by its fields, and the diagram follows at once:

  • Viewpoint: Overview, Detailed, Deep or Map. From an element viewpoint to the Map, the element becomes the pinned element, in the layer the view has (a technology element is the pin of the Map of the technology layer); from the Map to an element viewpoint, the first pinned element that still exists becomes the element, and the hidden and open elements are dropped; the layer stays. What the view showed of the texts is kept. Cancel gives the change up as long as it has not been saved.

  • Layer (every viewpoint: a Map draws the layer it names) and Element (the element viewpoints): the element is typed, with the references of the layer as suggestions, and applied with Enter or by leaving the field. A reference that is not an element of the layer is refused, with the reason under the field, and stays there to be corrected. Changing the layer keeps the element when the other layer has it, and otherwise leaves the view without one: it then says so and cannot be drawn until one is chosen; for a Map it keeps the entries of its three lists that exist in the other layer.

  • Pinned, Hidden and Open (the Map): each is a list of elements of the layer of the view (an element of the other layer is refused), with a cross to take one out and a field to add one (Enter). The drawing of this page is not edited itself, on purpose: a click on a box selects it. To choose pins by clicking, use Open on diagram.

  • Facet: the facets of the workspace, or none. Hide unlinked, Labels, Qualifiers, Descriptions and Wrap are boxes to tick (a Map of the technology layer has two more, Applications and Relationships, ticked when the property is absent: unticking one writes false, see [map-technology]), and they are the same as the buttons of the tools over the diagram. A text that is what that kind of diagram draws by default is not written to the file, as for any view.

Nothing is written to the disk by an edit. The view gets the mark modified, in the header and in the list, and loses it when what you did is put back, as soon as the file of the view would be the one on disk (the last one written); Save all changes writes the file of the view and no other (the comments and the layout of the file stay, as for any manifest; a property that an edit takes out and puts back again is written where the editor writes it, element, facet, Hide unlinked, then the texts), and Cancel gives every unsaved change up: the view, and the diagram with it, are the saved ones again. A view that an edit left impossible to draw (no element, nothing that was pinned exists) says why in the center, with the same fields to correct it, and can still be saved. Renaming an element in Elements still rewrites the views that point at it; the steps of the stories point at the view, so they show the edited view, saved or not.

A view that cannot be drawn (its element was deleted, nothing that was pinned exists any more, the viewpoint is unknown) keeps its message, what it draws, its fields and its steps in the center of the page, with no diagram and no panel.

A story is a file (story.<id>.yaml) in the first manifests folder, and so is each named view. They wait in memory, like the other changes, with a mark on the file, for Save all changes, and Cancel gives them up: only the files that changed are written. When an older workspace still has views or stories in workspace.yaml, Stories says so, on both sides, with Move to manifests, which works whatever plateau is drawn.

Facets

The facets of the workspace (see Tackling view clutter) are in a list in the header of the diagrams: the diagram is then drawn as the command line generates it for that facet, with the relationships the facet removes left out, and the elements it removes, with the relationships that pointed at them. In the tree, the elements the facet leaves with nothing to draw are greyed. The facets themselves are edited in the Settings perspective, along with the other settings of the workspace (see Technical Configuration).

Files

Files lists every manifest of the workspace on the left, and the text of the one that is open in the center, which can be edited (see [editor-reads] for what the editor reads). Whatever plateau is drawn, the list holds every file: there is no choice of what it shows. A workspace that has layers lists them in groups.

A group for each plateau. The heading of a group says the plateau, its name and the number of its files. The groups come in the order of the tree, the root first and then each plateau under the one it overrides. The plateau of a manifest is the one its header names (plateau: saas), baseline when the header names none, and, for a manifest of kind archicode.morin.io/plateau, the plateau it declares. A group that holds no file has no heading. A workspace with no layer lists its files as it always did, with no group and nothing to fold.

Fold and unfold. A click on the heading of a group folds and unfolds it (Enter and Space do the same), and Fold all and Unfold all do every group. A folded group still tells, in its heading, that one of its files has an error or is modified. Opening a file, by its row, by an address or by a link of a message, unfolds its group; a fold that you make afterwards is kept. The folds are the page’s own: they last as long as the editor stays open on the same folder, they are not written in the workspace, and they do not make a file modified.

Files that belong to no plateau. The last group, No plateau, holds the files that belong to no plateau: the views and the stories (they are declared in no plateau, see [plateau-untied]) and a file the editor could not read, which is always listed, with its error. workspace.yaml is not in the list: it is the page Settings.

A plateau that disagrees with the folder. The folder of a manifest does not matter to the tools: the plateau is what the header says. The folders of a project are often named after its plateaus, though, and a file moved from one to the other with its header left alone is read as the plateau of its header, not of its folder. When a manifest sits in a folder that is named like another plateau of the workspace (the deepest such folder counts), its row has a folder mark, a note above the groups counts such files (N files sit in the folder of another plateau), and its page has a warning: a/x.yaml says plateau: b in its header but sits in the folder a; b/y.yaml has no plateau key, so it belongs to baseline, but sits in the folder b. It is only a warning: nothing is refused, the command line says nothing, and the file is where you put it. A folder that is named like no plateau says nothing.

Name of the workspace

A workspace can have a name, the optional name key of its settings (see Workspace). Settings has a section, Workspace, with a Name field. Unlike the theme below, the name is a setting of the workspace: it is written to workspace.yaml, so it counts as a change to save and lights Save all changes.

When the workspace has a name, the editor shows it at the top left of the window, in place of the name of the folder, in the title of the page, in the list of remembered folders and in the "Opening" messages, which use the name the workspace had when its folder was last opened; the name of the folder is then the tooltip of the name. Without a name, or with a blank one, the editor shows the name of the folder, as before, and an emptied Name is left out of the file.

The current plateau

Settings, in its section Workspace, has a field Current plateau when the workspace has at least two plateaus (or when workspace.yaml already says current): a list of the plateaus, in the order of the band, and None. It writes settings.current into workspace.yaml, the plateau the command line draws when --plateau is not given, and the plateau the editor opens the folder on when nothing else says which: no address with plateau=, and no plateau that this browser drew last in this folder. A file that has no settings gets one with that line alone; None takes the line out (and leaves settings: {} when it was the only one). A name that is no plateau is refused with the sentence of the load. Like the other fields of Settings it is a change to save with Save all changes, and it is disabled while the plateaus have mistakes (only what the file says and None can be chosen then).

It does not redraw the plateau on screen: what you chose on the band is not undone by a setting for the next time. With None, the command line draws the last plateau when the plateaus form one line, and asks for --plateau otherwise, while the editor opens the root.

The band of plateaus

Under the top bar, on the four pages of Timeline and nowhere else, the band chooses the plateau that is drawn and the one it is compared with. It is lean and read-only: two lists and, when something is wrong, one button. It writes nothing, and it has no tree, no counts and no sentence of its own (the tree and the counts are on the page Plateaus, see The Plateaus page). The plateau drawn and the comparison are the state of the editor, not of the band: Stories, Files and Settings have no band, and draw the plateau that was chosen. There is no plateau selector, no Compare to list and no section of the Settings for plateaus. A workspace that writes no layer has one plateau, baseline. A workspace of layers (a plateau key in the header of a manifest, or a manifest of kind archicode.morin.io/plateau) has one for each plateau.

  • Plateau draws a plateau in the whole editor. It lists every plateau in the order of the tree, baseline first and then what overrides it, each followed by what overrides it and indented by its depth, with its name and its horizon. A plateau that the command line refuses has a ! in front of its name.

  • Compare with says what the plateau drawn is compared with. It starts with Nothing and Past (follows the plateau drawn) (the plateau it overrides, whichever that is, so it changes when another plateau is drawn; the root has no past, so no such entry), then shows the same tree as Plateau, every plateau in the order of the tree and indented by its depth, with the plateau that is drawn greyed in its place so that it cannot be chosen and the hierarchy reads in both lists. A plateau of the tree is a fixed comparison, as archicode diff --plateau <drawn> --against <other> reads it: the parent, a child, a sibling or a cousin alike. There are no entries Future any more: a plateau above the one drawn is chosen in the tree, and is read as the future of the plateau drawn. A list chooses and does not toggle: choosing again the plateau that is compared already does nothing. Choosing the parent in the tree is read as Past (follows the plateau drawn), as the editor has always read a comparison with the parent: the comparison then moves with the plateau drawn. There is no way, on the band, to compare with the parent and have it stay when another plateau is drawn (see Limits of today). An address with compare=future and several plateaus above the plateau drawn shows a disabled entry, Choose a future plateau, selected, with nothing selected in the tree, until one is chosen.

  • ! N mistakes, when there are some, opens the dialog Mistakes in the plateaus: why only baseline is drawn, the sentences of the plateau drawn and of the plateau compared with that the command line refuses (the sentences of the command line, see Plateaus), the views and the stories that name elements no plateau has, the steps of the stories that name plateaus that are none (see [plateau-untied] and [story-step-plateaus]), and the sentence that nothing is written in a plateau that cannot be drawn.

Everything | Changes only is not on the band: it is among the tools of a diagram, and is shown while a plateau is compared (see Changes only and wording-only changes).

The order of the siblings. Plateaus that override the same plateau are placed by their horizon, when it reads as a date, and by their id otherwise. A horizon reads as a date when it is a year (2027), a month (2027-03), a day (2027-03-18), a quarter (2027-Q4) or a half (2027-H2); the date of a quarter or a half is the first day of the period. The plateaus whose horizon reads as a date come first, from the nearest to the farthest, those with the same date by id; the others follow, by id. The rule is the same every time the folder is opened. (archicode plateau list orders the siblings by id only, and the editor by horizon: the tree is the same.) (The tree does not need a horizon: it is the override of each plateau that places it, the horizon only orders the siblings. Any other text in a horizon is a label that no tool interprets.)

Drawing a plateau. A choice in Plateau draws that plateau, in the whole editor: the trees, Applications, Environments, the diagrams, Stories and the panel on the right show the plateau of the band. The plateau is its chain: the manifests that say plateau: <id> are added to the elements of the plateau it overrides, then its patches change them (REMOVE, SET, ADD, MERGE, applied by the same kernel as the command line), and every plateau of the chain is checked, with the sentences and in the order of the command line: a patch that selects nothing names the plateau, the rank of the patch and what it selected; a relationship, an entry of uses or an application hosted on a node that leads nowhere, a manifest whose parent is not there or cannot hold its kind, name the plateau. The views and the stories belong to no plateau: a name that they have and the plateau lacks is told in the view (see Stories: stories and views), and a name that no plateau has is in the dialog of the mistakes. The choice reads nothing from the disk and loses nothing: the manifests stay as they are, and each plateau is resolved once and kept until a manifest changes. When the kernel refuses the patches of a plateau, that plateau cannot be drawn (the dialog says why, and baseline is one choice away); when only the checks fail, the plateau is drawn all the same, flagged !, with the sentences that the command line would stop on, so that the mistake can be repaired in it. The plateau that opens is the one the address names (plateau=), else the one this browser drew last in this folder, else the one settings.current names (a name that is no plateau is an error with the sentence of the command line; the field Current plateau of Settings writes it, see The current plateau), else baseline. When the plateaus form one line and no settings.current says otherwise, the editor therefore opens the root while the command line, with no --plateau, draws the last plateau.

Comparing. Compare with compares the plateau that is drawn with another one. The comparison is the one of Comparing two plateaus: the Map, the diagrams, Stories and the Changes panel tell what is new, changed, removed, moved, split or merged, with the same counts and the same table as archicode diff for the same two plateaus; Everything and Changes only choose what the diagrams draw. With the past the plateau drawn is the more recent one, with the future it is the older one, and what only the other plateau has is read in the panel on the right, as a removed element is. The choice is remembered by this browser for this folder.

Cascade. Below the lists, the Changes panel has Cascade of the removals when a REMOVE of the more recent plateau took more than what it selects: the elements that went with the selected one, and the entries taken out of elements that stay (a relationship towards it, an entry of uses or of applications), among what the other plateau has, as archicode diff lists them after the table. Write replaces and Not related work on the pairs of any two plateaus; Write replaces writes replaces in the manifest that declares the new element, and refuses an element the plateau only inherits (it is declared in a plateau above, which the key would change).

Where a value comes from. In the panel of an element, each value (name, description, qualifiers, tags, relationships, replaces, uses, applications) says where it comes from: declared in the plateau drawn, inherited from another plateau (the one whose manifest declares the element), or set by patch N of a plateau (with the operator and the selector of the patch, and "inherited" when the patch is one of a plateau above). A block Origin lists the plateau that declares the element and the patches that selected it.

Writing. The plateau that is drawn is the one a write goes to, and the page Plateaus says so (writing in: Buy the commerce platform). What an edit writes, and what is refused, is in Writing in a plateau.

Writing in a plateau

A write goes to the plateau that is drawn, in the files of that plateau, and nowhere else. The page Plateaus says writing in: <plateau> when the workspace has layers. A workspace that writes no layer saves as it always did.

Asking first. A plateau that other plateaus stand on is not written without a word: when an edit changes the resolution of a plateau that overrides the one written, the editor lists those plateaus (the ones that inherit what was written and do not set it themselves) and writes only when you say yes. baseline is the plateau most often in that case. A plateau at the end of the chain, or an edit that no other plateau sees, is written at once.

Only what was meant. Every write is made on the manifests in memory by the same line-preserving save as ever (the lines the edit does not touch, their comments and quotes, stay as they were written; a flow list or map that an edit changes becomes a block), and it is kept only if the plateaus are resolved again and all of this holds: the plateau written gives back the value that was edited; no plateau that resolved before is refused now, and no new mistake appears in the tree of the plateaus or in a plateau (a rename, a delete or a new parent that would make a patch of another plateau select nothing is refused, and says which plateau and which patch). A write that is refused is one sentence in the top bar, and nothing is changed: not a file, not a mark of what is modified. A new patch is always written at the end of the patches, never between two patches of yours, so that a comment above a patch stays above it.

Refused, with one sentence.

  • Renaming (id) or moving an element the plateau inherits: a patch never changes an id or a parent; draw the plateau that declares the element. Renaming or moving an element the plateau declares works as it does in baseline; the target of patches, the relationships they add, and the replaces entries that name it follow the new reference.

  • A value that comes from another plateau cannot be taken out by a patch (a patch sets a value); write a new text, or draw the plateau that declares it. A list or tags can be emptied (SET of an empty list or object).

  • A field that a patch written by hand with a free json-path sets (for instance a MERGE of tags on every element that has a qualifier): the editor shows it, with its origin, and does not edit it field by field. Edit the patch in Files.

  • A plateau cannot be drawn when the kernel refuses its patches: nothing is written in it until they are repaired in Files.

  • A group under an element that the plateau inherits: a group has no manifest of its own, so it cannot be written in the plateau drawn (A group under “shop” (declared in the plateau baseline) cannot be written in a manifest of its own: draw baseline to add it.).

Not written by the editor: patches with a free json-path or an expect (they are written by hand in Files). A new plateau manifest is written next to the other manifests (plateau.<id>.yaml in the first folder of manifests.paths; for a plateau that exists through headers only, in the folder of its files). The text editor of Files writes the text of any file whatever plateau is drawn, and is the way to repair or write what the forms do not.

The Plateaus page

Plateaus, a page of the perspective Timeline (its address is /timeline/plateaus, or /plateaus), lists the plateaus as a tree: one entry for each, in the order of the tree, each indented by its depth. An entry says the name of the plateau, its id, its horizon, whether it is the one drawn or the one compared, and, in a line below, the plateau it overrides, where it is written (described in inhouse/plateau.yaml, or exists only through the plateau key of a header for a plateau that has no manifest of its own), how many patches it has and how many files belong to it. Below that, what it changes over the plateau it overrides, as the chips of the Changes panel, for the elements and for the relationships: new, changed, removed, and moved, split and merged when there are some. They are the counts of archicode diff --plateau <id>; a plateau that the command line refuses, or that overrides one it refuses, says it is not counted (a ! marks it). The root overrides nothing, and says so. A workspace that writes no layer has the page too: one entry, baseline, and a note on what a plateau is. This page is the one place that lists the plateaus as a tree with their counts and the one place that writes a plateau: the band chooses and writes nothing.

The name of a plateau draws it, as a choice in the list Plateau of the band does. Changes draws the plateau and compares it with the plateau it overrides in one step, and the Changes panel opens on the right with the same lists as on the other pages; a click on one of its rows opens the element in Elements, since this page draws none (Next change and Previous change show the change they are at under the buttons, see The Changes panel).

Writing a plateau. New plateau after this (on an entry) and New plateau (above the list, for the plateau drawn, with writing in: <plateau>) make a plateau that overrides it; Edit (Edit plateau beside New plateau) changes its name, horizon or parent. The manifest is written as Writing in a plateau says.

Deleting a plateau. Delete is on the entry of every plateau but the root, and Delete plateau beside New plateau for the plateau drawn. It opens a dialog that says what goes before anything does.

  • What can go. Only a plateau that no other plateau overrides: nothing inherits what it declares or patches, so no other plateau changes with it. The dialog refuses, with one sentence and without a Delete button, the root (every other plateau stands on it), a plateau that others override (it names them, and says to delete them first or to give them another parent with Edit; deleting a plateau that others override is not built, #112), a workspace that has no plateau but baseline, plateaus that cannot be drawn, and a save in flight. The button of a plateau that others override stays, with a tooltip that says why: a button that vanishes says nothing.

  • What goes, and only that. Its manifest of kind archicode.morin.io/plateau and every manifest whose header says its id, listed one by one (a file not saved yet is marked new, not saved yet, and a modified one says its changes go with it). A view or a story that says plateau: <id> belongs to no plateau: it stays, and the dialog says so. The files leave the disk at the next Save all changes, like any change, and Cancel gives the delete up with the others.

  • Files that the editor does not read. A .toml or .json manifest, or a YAML file that the editor cannot read, may say plateau: <id> for the command line: the delete does not touch them, the dialog lists them, and says that the command line still reads the plateau if one of them names it.

  • settings.current. When it names the plateau (or baseline, when the last plateau goes), the key is taken out of workspace.yaml, and the dialog says that the command line then draws the last plateau when the plateaus form one line, and asks for --plateau otherwise. A current that names another plateau, gone already, is left as it is.

  • What blocks it. A step of a story that names the plateau in at or against, and a view or a story step that names an element that only this plateau declares (it would exist in no plateau): the dialog lists the sentences, offers no Delete, and says to change them in Stories first. They are not cleared for you: a step told at a plateau is your statement of which state it shows.

  • After it. The plateau it overrode is drawn, with no comparison, when the plateau drawn was the one deleted; the plateau drawn stays, compared with nothing, when the one deleted was the one compared with. The folders of views that the command line generated (views-<id> and the folders of its comparisons) are not manifests: they stay where they are.

Comparing two plateaus

Compare with, on the band, compares the plateau that is drawn with another one (see The band of plateaus): Past is the plateau it overrides, and the tree lists every other plateau, the one that overrides the plateau drawn (the future of the comparison), a sibling or a cousin included. With nothing compared, which is the default, the plateau is drawn alone, exactly as the editor always did. A comparison draws the plateau together with the other one: Applications, the diagrams of Elements and the page of a view in Stories tell what is new, what changed and what was removed (and, for the elements that say what they replace, what moved, was split or merged, see Moved, split and merged elements, and candidates), with the same states as archicode views generate (see Comparing two plateaus). Like the plateau, the choice is remembered by this browser for this folder (not in the workspace), and it is ignored when the workspace no longer has that plateau. A plateau is never compared with itself. The address carries the plateau (plateau=<id>, when it is not baseline), and the comparison only next to the selection of a removed element (compare=past, compare=future:<id> or compare=other:<id>, see The address and the trees); a link that has compare= draws that comparison, and one that has none leaves the comparison as it is.

The plateau compared with is read, not written: the editor resolves it from the manifests it has already read (there is no second folder to pick), keeps it apart from the plateau that is drawn, and an edit goes to the plateau drawn (see Writing in a plateau). Its elements are not in the trees of the plateau drawn, and what only it has is listed in the Changes panel and read in the panel on the right. A plateau that cannot be resolved cannot be compared, and the dialog of the mistakes (the button of the band) says why. The one write that is made for the comparison is Write replaces (see Moved, split and merged elements, and candidates).

The diagram is drawn from the union of the two plateaus, and the boxes are laid out on that union: what was removed is drawn where it was, so a box does not move when the comparison is turned on from the other plateau or when you choose the other plateau of the pair (when nothing is compared, the plateau is laid out alone, as before). The Changes panel

While a comparison is on, the panel on the right of Plateaus, Applications, Environments and Elements is never empty. With nothing selected it is the Changes panel; with something selected it has two tabs, Selected (what is selected, as before) and Changes (with the number of rows). On Stories the panel is the one of the view, and while a comparison is on and can be drawn it has two tabs, View (what was there) and Changes; a story, or a view that cannot be drawn, had no panel and has the Changes panel alone.

The panel starts with the counts: elements and relationships, each new, changed and removed, as chips that carry a mark and a word (+ 38 new, ~ 26 changed, − 5 removed), so that they read without colour; the elements add → 1 moved, ⋔ 2 split and ⊕ 1 merged when there are some. The same chip is the state on every row below. Two lists follow, Elements and Relationships, in the order a review reads them: what is new, then what changed, then what moved, was split or merged, then what was removed, and by reference inside each. A row has the chip, the name and the reference of the element (a relationship reads source → destination “label”) and, for something that changed, what changed in it in words: name, description (wording only), qualifiers, tags, deployment, relationships added, relationships removed, relationships changed, and for a relationship label, qualifiers, tags. A relationship whose label changed is one row that says the label before and after. A row of a moved, split or merged element says where it came from (from shop.till, from shop.report; split with shop.report-b), as archicode diff does.

Reading a long list. A comparison of a large workspace has hundreds of changes (the pair before and after-declared of the fixture replaces-large-pair has 360). Under the counts, the panel says how many there are (167 changes) and has what it takes to read them without losing the place:

  • Previous change and Next change walk through the list, in the order of the list (the elements, then the relationships). They stop at the ends and do not wrap, and the panel says where you are (3 of 12). With no change selected, Next change goes to the first and Previous change to the last. The walk selects the change as a click on its row does, and leaves the list on screen (the Changes tab stays). Under the buttons the panel shows the What changed block of the change the walk is at (see What changed), so that the page Plateaus, and a story with no view drawn, where no box can be shown, still say what the change is; a click on a row there opens the element in Elements, as before.

  • The lists State (all, then the states that some row has, each with its count) and Layer (both, application, technology) narrow what is listed: the line then reads 12 of 167 changes, each group says n of N, and Show all clears both. contains-changes is not a choice: it is the state of a box that holds a change, never of a row. A filter that leaves out the change you are at moves you to the nearest one that is shown.

  • The filters change the list only, never what the diagrams draw (Changes only does that, see Changes only and wording-only changes), nor the counts above them. They are the editor’s, not the workspace’s: they start again when the pair of plateaus compared changes. The walk has a keyboard shortcut, J and K (see Keyboard).

A click on a row selects the thing as a click on its box or its link does, and shows it. On the Map the boxes around it are opened so that it is drawn, and the view is centred on it (what the Center button does); a pin or a hidden element of your own is not undone, and the panel says when the element is not on the map. A removed element opens the read-only panel described above, a relationship selects its link (in Elements, the element that declares it, and its link when that element’s diagram is shown). The row of the selection is marked in the list, and the Changes tab brings the list back with that row in view.

What changed

The panel of a selected element, link or removed box adds a What changed block, first, so that a long description does not push it out of sight; it is the same on the page of a view in Stories.

  • For a changed element, the natures in words, then each property that differs with its value Before and After (name, kind, description, qualifiers, tags, and the applications or uses of a node), then its relationships that are new, changed or removed, each a line with its chip. The Before and After lines carry a sign and a word, and the old value is struck, so nothing relies on colour.

  • For a new element, "Whole element is new": its properties are the ones listed below the block, and the relationships it declares are listed as new.

  • For a removed element, the read-only panel above, with "Whole element is removed"; it does not repeat what the panel already lists. A removed element that is only drawn as the place of what was inside it, and that other elements replace, adds Replaced by and lists them.

  • For a moved, split or merged element, one sentence that says which, then Replaces with the name and the reference of each element it replaces (one that the other plateau does not have is flagged), then, if the element also changed, Also changed and the properties Before and After as above.

  • For a link, its state (all of the relationships it groups new, or removed, or changed, or a mixture, which reads changed) and, on each relationship it groups, its chip and, for one that changed, what it was and what it is.

Changes only and wording-only changes

Everything | Changes only, among the tools of a diagram and shown while a plateau is compared, sets what the diagrams draw: with Changes only a diagram keeps what is new, changed or removed, the boxes that enclose them and the ends of the changed links; the links that did not change are left out. The boxes kept only to place the changes, the context, are drawn faded, say no state and are told in the key ("context, faded: shown to place the changes", with their number). The focal element of a diagram always stays and is never faded. It works the same on the Map, on the diagrams of Elements and on the page of a view in Stories, and together with the pins, the hidden elements, a facet and Hide unlinked.

A change of the description alone is a change of wording, not of structure. The Changes panel counts them apart ("10 of the changed elements are changes of wording only") and keeps them visible by default; the checkbox Hide wording-only changes sets them aside in one click: those elements are drawn as unchanged (and a box that only they changed is no longer marked contains-changes, nor kept by Changes only), their rows leave the list, the counts of changed elements drop by their number and the panel says "10 wording-only changes hidden". Relationships are never set aside: a change of a label, a qualifier or a tag is structure.

Both choices are yours and not the workspace’s: they are remembered per folder in this browser, like the plateau and the comparison, never written to workspace.yaml, and they do nothing while nothing is compared.

The address and the trees

The address of the page carries a selection, so that a reload or a shared link reopens it: ref= for an element, link-from= and link-to= for a link, as before, and removed= for a removed element (removed-layer=technology for one of the technology layer). A removed element exists only next to its comparison, so the address then also carries compare= (past, the past that follows the plateau drawn; future:<id>, a plateau that overrides the plateau drawn; or other:<id>, any other plateau of the tree: a choice in the tree of Compare with is written as one of the three; compare=future with no id is read as the future to choose, and shown as the disabled entry Choose a future plateau when several plateaus override the plateau drawn): opening such an address chooses that comparison, as if you had chosen it, even if this browser remembered another one. The other choices of the comparison are not in the address.

While a comparison is on, a row of the tree of Elements and of the tree of the Map has a small mark after its name: + for a new element, ~ for a changed one, →, ⋔ or ⊕ for a moved, split or merged one, and ± for one that did not change but has a change below it. The word is in its tooltip and is read by a screen reader. A removed element is not in these trees (it is not an element of the plateau drawn, so it can be neither pinned nor hidden nor edited): the Changes panel lists it and opens its panel.

Moved, split and merged elements, and candidates

An element of the plateau that is drawn can say which elements of the plateau it is compared with it replaces: the key replaces (see Saying what an element replaces). The editor draws the result with the three states above, counts them and lists them in the Changes panel, and the What changed block of a moved, split or merged element says what it replaces. A replaced element is not listed as removed. The Changes only filter keeps these elements like the others. The hand-written tags still follow the rule of [plateau-state-tags]: the look of moved, split or merged is only for a box the comparison says is in that state.

Candidates. Under the counts, the Candidates section lists the pairs the comparison takes for one thing said twice: an element only the other plateau has, and an element only this one has, of the same kind and the same layer, with the same name (when no other removed and no other new element of that kind has it), a close description, or as the only two of their kind under the same parent (not between two plateaus that are not one the past of the other, two alternatives), and each with its reasons. Unlike archicode diff, which lists them only for a plateau that already uses replaces, the editor proposes them for any comparison: it is how an author starts. A candidate is never applied by itself. Each pair has two buttons:

  • Write replaces adds the reference of the removed element to the replaces of the new one, in the manifest that declares the new element, and nothing else. It is an edit like the others: the file is marked as modified and written by Save all changes, the lines you did not touch (comments, blank lines, quotes) stay as they are, a list that was there gets the reference appended once, and a list written on one line (replaces: [shop.till]) becomes a list on several lines. The comparison is made again at once, and the new element is now moved, split or merged.

  • Not related sets the pair aside. It is remembered by the page only, until you close it: nothing is written and the comparison is not changed. The section says how many pairs are set aside, and Show again brings them back.

Write replaces writes the key on the element to of the more recent plateau of the two compared, in the manifest that declares it, and nowhere else; when the plateau compared with is the past of the one drawn (or any plateau the plateau drawn stands on), the more recent plateau is the one drawn, and when it is a plateau above the one drawn, the more recent plateau is the one compared with, which the button writes all the same, since it is the one thing the Changes panel offers. It is refused, with the reason in the panel and nothing written, when the element belongs to the older plateau of the two (replaces goes on the more recent plateau: compare the other way round), when the more recent plateau only inherits the element (it is declared in a plateau above, and the key would change that plateau and the ones that override it: compare that plateau with its past instead), when the replaced element is still in the more recent plateau, when it is not an element of the older one, or when the replaces of the element is not a list.

By hand. The edit form of an element has a Replaces section as soon as the workspace has several plateaus: the list, each reference with a button to remove it, and a field to add one (it completes with the references of the plateau compared with). A reference the plateau compared with does not have is accepted and flagged ("not in “Base”", with the name of that plateau), because you may have written it for another baseline; one that the plateau drawn still has is flagged "still in this plateau: ignored". An element cannot replace itself, and a reference is listed once. The details of an element that replaces something list it too.

Warnings. What the comparison ignored in the replaces it was given (see [plateau-replaces-warnings]) is a short list in the Changes panel, under the candidates, with the sentences of the command line; the editor does not write them to the console. A second list, Hand-written states, has one line per element and word for the state words you wrote by hand that the comparison does not give to the element (see [plateau-state-tags]), with the sentences of the command line, and the panel of such an element says it too, so that a box with a new badge that is not drawn as new tells why.

Moving an element. An element that you put under another parent in the editor has another reference, so it reads as a removed element and a new one when it is compared with the plateau it came from. Move does not write replaces (see Moving an element under another parent): write it from Write replaces in the Changes panel, or in the form of the element.

Moving an element under another parent

In the edit form of an element, Move (after Delete, before Add child) puts the element, and everything inside it, under another parent, or at the top level, without breaking a reference. It is offered when the dialog has at least one place to offer, the top level included: a solution, a person and an environment are at the top already and have nowhere else to go, so they have no Move; a system can go under a solution, and goes to the top level from there. It works on the plateau that is drawn, and never on the one it is compared with, which is read-only. In a plateau of layers it moves an element that plateau declares; an element it inherits is refused (a patch never changes a parent), and says which plateau declares it.

The dialog has a search field (it keeps the places that have every word you type in their name, id, reference or kind) and the list of the places the element can go, in the layer of the element: the top level, when it may be there, then the valid parents, each an element that may hold the kind of this one (the rules that create an element under a parent, see [nesting]). It says how many elements follow, how many references will be rewritten in how many files, and how many saved views follow. Under the places, a closed list says, for every element of the layer that is not offered, why not, with the same search: N places are not offered, and why. The reasons are the sentences that refuse a move: it is the element itself, it is inside the element, it is its parent already, its kind cannot be held by that parent (the sentence says what the parent holds), the parent already holds an element with that id, the parent is declared twice, and a group cannot go under a parent of a plateau that the plateau drawn overrides (#114). A reason that stops every move (an element inside it is declared twice, a manifest cannot be read, a reference cannot be rewritten as text) is told once, at the top, as No move can be written now.

The top level. The kinds that may be at the top level are the ones the layer holds there: a person, a solution and a system in the application layer, an environment in the technology layer; a group is no root. For any other kind the list says so (A container is never at the top level: the application layer holds only person, solution and system there.), and the editor neither offers it nor moves an element there. In practice the top level is offered for a system that sits in a solution.

What follows. The reference of the element becomes the reference of the new parent followed by its id (its id alone, at the top level), and so does the reference of each element inside it. Every reference to the element or to something inside it is rewritten, in every file of the workspace, by the machinery of an id change:

  • the destination of the relationships of any element of the same layer;

  • the applications of the nodes of the technology layer (for an application element) and the uses of the environments (for a technology element);

  • the header.parent of the manifests attached to the element or below it;

  • the saved views and the steps of stories of the workspace (the element of a view, the pinned, hidden and open elements of a Map view);

  • what the page remembers: the selection, the unfolded rows, the modified marks, the pins of the Map.

The facets (their JSONPath is not a reference) are not read, as when an id changes. Nothing else of a file is touched.

What is written. There are four ways, chosen by how the manifest holds the element and where the new parent is declared, and the dialog says which one a place gets. The lines that are not part of the move stay as the author wrote them (comments, blank lines, quotes), as for any other edit:

  • An element that has a manifest of its own (app.shop.till.yaml, with its header.parent) stays in its file: only the header.parent line changes (at the top level the line goes), and the manifests attached below it follow by their own header.parent. The new parent can be in any file.

  • An element that is nested in the manifest of another one (in its content.elements) and goes under a parent of the same file is moved as a block inside that manifest: its lines, with the comments just above it and those at the end of its lines, go to the elements of the new parent, one level deeper or shallower, and the elements it leaves is dropped when it was the last element.

  • A nested element that goes under a parent in another file (declared in another manifest of the plateau written) is cut out of its file and pasted in the other, with its comments and its quotes. Both files are marked as modified, and a refused write changes neither.

  • A nested element that goes to the top level, or under a parent declared in a plateau whose files the plateau drawn does not write (a plateau it overrides), gets a manifest of its own, next to the file it leaves (app.<reference>.yaml, env. for the technology layer, and -2 when the name is taken), with its kind, its version, the plateau drawn when it is not baseline and the parent, none at the top level. A group has no kind of manifest, so a group cannot go there: that is #114.

The comments on lines of their own inside the block go with it. A comment after the last line of the block, before the next element, is the next element’s and stays where it was. A file whose layout the move cannot follow (an anchor, an alias, a tag, a list written at the column of its key) is written by the ordinary save: the move works and the file says the right thing, and the comments of the block are the price. The end of line of each file is its own.

What a move does not tell. A move changes the reference of the element, so the views and the steps of the stories that name it follow it, in every plateau. A plateau beside the one drawn that still declares the old reference can then no longer draw those views, and Move, unlike a rename (see [editor-rename]), does not say so before it writes (tmorin/archicode#122): draw that plateau and move the element there too.

Replaces. Move does not write replaces: the element that a move can reach is declared by the plateau that is drawn, and the plateaus it overrides do not have its old reference, so there is nothing for the key to name. In a workspace of plateaus the dialog says so in one line. To say that an element replaces one of another plateau, use Write replaces in the Changes panel, or the Replaces section of the form of the element (see Moved, split and merged elements, and candidates).

A move that is refused changes nothing at all, and the reason is told in the dialog, which stays open with what you chose: the new parent is the element or something inside it, it is its parent already, it cannot hold that kind, it already holds an element with that id, the element or the parent is declared twice or belongs to the plateau compared with, a manifest cannot be read (a reference in it could not be rewritten), a reference is written as a number (destination: 8080) and cannot be rewritten as the reference of another element, or an id has a / or a \ in it, which cannot be the name of a file (rename the element first).

Like every edit, a move is not written until Save all changes, and Cancel gives it up with the others (the folder is read again). The files it changed are marked as modified, and so is the moved element.

Theme

The editor is drawn in a light or a dark theme. By default it follows the one of the operating system. Settings has a section, Appearance (this browser), to choose Light, Dark or System instead: the choice applies at once, to the page, the code editors and the SVG and PNG exported from a diagram.

The choice is a preference of the browser, not of the workspace. It is remembered by the browser alone (nothing is written to workspace.yaml or to any file of the folder), it is not a change to save, and it does not light Save all changes. A browser that refuses to remember it keeps the choice until the page is closed.

Keyboard

In a tree

  • Up and Down move, Home and End jump to the first and last row.

  • Right unfolds a branch or goes to its first child, Left folds it or goes to its parent.

  • Enter and Space select the element (in the Map, they fold or unfold the branch).

  • In the Map, P pins or unpins the element, and H hides it or shows it again.

In the Changes panel

The buttons tell the key in their tooltips.

In a diagram

  • The arrow keys move between boxes, and Enter opens the one that has the focus.

  • The boxes are one Tab stop, and so are the links: a diagram takes two presses of Tab to cross, however many boxes and links it has. The arrow keys move from the box that has the focus to the neighbouring box, which becomes the stop. On a link, the arrow keys move to the next and the previous link (not to the neighbouring box), Home and End jump to the first and the last, Enter or Space selects it, and Esc deselects it. Tab goes from the boxes to the links and on, and Shift+Tab comes back.

Errors, warnings and exit codes

Every command speaks on its error output in the same way, and keeps its standard output for what it produces (the files it announces, a table, a graph), so that archicode diff > changes.txt or archicode query graph | jq never mixes the two.

Errors. When a command cannot do what you asked, it prints one line for each problem on the error output, starts it with error: ` and exits with the code 1. It prints no stack trace. The exit codes are 0 (done), 1 (an error), 2 (a usage error, below) and 3, which only `archicode diff --fail-on gives, when the comparison holds a change it was asked to fail on (see Compare plateaus). The line says what is wrong and where, for instance:

error: dangling reference: payments
error: unknown plateau `nope`: the plateaus of this workspace are `baseline` and `to-be`
error: `manifests/shop.yaml` is not valid: the value has the wrong shape (found an array) at `header` (line 1, column 9)
error: the workspace file `/work/workspace.yaml` does not exist (`-w` names another one)

The same sentence in the editor. A manifest or a workspace.yaml that the command line refuses, the editor refuses with the same sentence, without the file and the line (the editor shows it beside the file): a key that the element, the setting or the header does not have, a nested element whose kind is missing or none of those its parent takes, a value of the wrong shape, a header.kind that is none of the kinds, a key that is required and absent. An option that does not exist or a missing argument is a usage error: the command prints the problem and how to use the command, as it always did, and exits with the code 2. A failure that nobody expected, a bug, prints error: unexpected …​ and keeps its stack trace, because a report needs it; the exit code is 1.

Warnings. A warning says that the command went on but that something is probably not what you meant. It is one line starting with warning: ` on the error output, printed when the command has done its work (and before the error, if it fails), once for a sentence the command would say many times. The log is not where to look: the log level of the application is `ERROR, which hides the warnings of the log. A warning does not change the exit code. The command line warns of:

  • a facet written in the old dialect (anyof, noneof, == null): it is rewritten, and the warning gives the standard form (see Tackling view clutter);

  • a step of a story that names a view nobody declares;

  • a view that cannot be drawn in the plateau, because it names an element that the plateau does not have and another plateau has: skipped by views generate --view, or, for the entries of the lists of a map, left out (see [plateau-views-lacking]);

  • a viewpoint that the command line has no service for, skipped by views generate --view;

  • what a comparison ignored in the replaces of a plateau, with archicode diff and archicode views generate (see [plateau-replaces-warnings]);

  • a state word you wrote by hand on an element, where it disagrees with the comparison (see [plateau-state-tags]).

A command that has nothing to warn of prints nothing on its error output. Nothing here makes a warning fail a command: the exit code tells whether the command did its work.

ArchiCode advocates an architectural design philosophy characterized by incremental refinement and in-depth exploration. We commence by identifying high-level elements and relationships, progressively breaking down the system into specialized containers and interactions. Notably, while the outlined steps establish a structured foundation, ArchiCode’s true strength lies in its adaptability, enabling architects to customize the process to fit the unique demands of their projects. As we delve into this exploration, ArchiCode emerges as a dynamic instrument, empowering architects to craft intricate architectural designs that seamlessly connect vision with implementation.

Step #1: Shape the highest elements of the application layer

In this initial step, we identify the foundational elements of the application layer:

  • EcommercePlatform: At the core of the system, "EcommercePlatform" is identified as the solution itself, representing the entire e-commerce platform.

  • User: This element represents the users who interact with the e-commerce platform, browse products, and make purchases.

  • SocialIdentityProvider: External services such as Google and Microsoft are designated as "SocialIdentityProvider," responsible for authenticating users.

  • PaymentGateway: The element symbolizes external payment processing services like Stripe and Braintree that facilitate secure financial transactions.

Step #1 - The addition of the elements in workspace.yaml
application:
  elements:
    - kind: "person"
      id: "User"
    - kind: "solution"
      id: "EcommercePlatform"
    - kind: "system"
      id: "SocialIdentityProvider"
    - kind: "system"
      id: "PaymentGateway"

Once the elements are identified, we design the relationships between them:

  • User uses EcommercePlatform: A direct relationship is established from the "User" element to the "EcommercePlatform" element. This relationship signifies that users engage with the platform to explore products, make purchases, and manage their accounts.

  • EcommercePlatform leverages SocialIdentityProvider: A relationship is created from "EcommercePlatform" to "SocialIdentityProvider" to depict the platform’s reliance on external authentication services. This connection ensures a seamless and secure login process for users through trusted identity providers.

  • EcommercePlatform leverages PaymentGateway: Another relationship is formed from "EcommercePlatform" to "PaymentGateway" to illustrate the platform’s integration with external payment processing services. Through this relationship, the platform enables customers to complete transactions using various payment methods.

After establishing the relationships, the next task involves generating a first generation of views:

  • Overview Viewpoint: At this level of abstraction, the "Overview" viewpoint is the most suitable. This viewpoint provides a broad perspective of the relationships and interactions related to the e-commerce platform.

  • Ingress and Egress Relationships: The viewpoint showcases the "Ingress" relationships, highlighting how elements such as "User" enter the platform. Additionally, it depicts "Egress" relationships, illustrating how the platform interact with dependencies.

Step #2: Identify the systems of the solution

In this step, we delve deeper into the systems that compose the e-commerce platform and establish relationships between them.

The first task involves breaking down the "EcommercePlatform" Solution into distinct "System" elements, each responsible for specific functionalities:

  • Product Catalog: Manages product categorization, listings, and details.

  • User Management: Handles user authentication, profiles, and preferences.

  • Order Processing: Facilitates order creation, payment processing, and order tracking.

  • Content Management: Manages website content, including product descriptions and promotional banners.

  • User Interface: Provides personalized product recommendations based on user behavior.

The second task focuses on designing relationships between the newly defined "System" elements:

  • User Interface → Product Catalog: The "User Interface" system interacts with the "Product Catalog" system to present products to users and allow browsing and selection.

  • User Interface → User Management: The "User Interface" system communicates with the "User Management" system to manage user authentication and profile-related interactions.

  • User Interface → Order Processing: The "User Interface" system connects with the "Order Processing" system to handle order creation and transaction processing.

  • User Interface → Content Management: The "User Interface" system engages with the "Content Management" system to display dynamic website content to users.

  • User Management → Social Identity Provider: The "User Management" system integrates with external "Social Identity Providers" to ensure secure user authentication and identity verification.

  • Order Processing → Product Catalog: The "Order Processing" system collaborates with the "Product Catalog" system to validate product availability and manage order-related information.

  • Order Processing → Payment Gateway: The "Order Processing" system interfaces with external "Payment Gateway" services to facilitate secure payment processing and transaction completion.

Step #3: Deep dive into User Management

In this step, we shift our focus to the containers that compose the platform’s systems, starting with the "User Management" system, and establish relationships between them.

The first task involves decomposing the "UserManagement" System into distinct "Container" elements, each responsible for specific functionalities:

  • IdentityAndAccessManagement Container: Manages user authentication, login processes, and role-based access control.

  • UserProfile Container: Handles user profile management, including personal information, preferences, and settings.

  • UserProfile Database: Stores and manages user profile data, providing a reliable data source for the UserProfile Container.

Tackling view clutter

Introduction

Navigating through complex architectural models often presents a challenge for professionals as intricate details and systematic interactions like authorization or observability make the generated views disordered and complex. As these views become overwhelming, there is an evident need for refined, focused, and organized presentation to enhance clarity and understanding. This is where Archicode steps in, offering an innovative solution to transform this complexity into a streamlined and comprehensible format.

Archicode introduces the facet concept, a feature engineered to automate the generation of secondary workspaces and refine views to focus on specific concerns. By employing transformation rules based on JSON Path queries, facets effectively remove certain elements and relationships, offering a cleaner, focused view of specific subsets. This feature serves as a bridge from the chaos of detailed expressions to an organized, easily understandable visualization, paving the way for enhanced insights into complex architectural models.

Note
The paths of a facet are standard JSONPath

The json-path of an action is a JSONPath as standardized by RFC 9535. It selects nodes of the workspace, and the REMOVE operator deletes them. The same code evaluates it in the command line and in the editor, so a facet cannot mean one thing in each. Beyond comparisons, a filter can combine tests with &&, || and !, test that a field exists (?(@.label)), look inside a list (?(@.qualifiers[?(@ == 'oidc')])) and call length() or count(). The functions match() and search() (regular expressions) are not available.

The facets written for the previous engine (Jayway) keep working for now, with a warning that gives the standard form. They are going to be removed in a future major version. The command line prints the warning on its error output, one line per rewritten filter (see Errors, warnings and exit codes).

Before Now

@.qualifiers anyof ['a', 'b']

@.qualifiers[?(@ == 'a' || @ == 'b')]

@.qualifiers noneof ['a']

(@.qualifiers && !@.qualifiers[?(@ == 'a')])

@.qualifiers == null

@.qualifiers

Relationships that have no tag, or no qualifier, simply do not have the field: @.tags['k'] != 'v' selects them, @.tags['k'] == 'v' does not.
Note
A facet can remove an element, and what points at it goes with it

REMOVE is not only for relationships: an action can select elements, such as $.application..elements[?(@.id == 'catalog')]. The element is removed with the elements inside it, and so is everything of the workspace that pointed at it or at one of them: the relationships whose destination is one of them, the entries of uses of an environment, and the entries of applications of a node. The views of the facet are then written without them; they do not stop with dangling reference. The facet says nothing when it does so, it is what it asked for. The workspace and its other facets are untouched.

settings:
  facets:
    customs:
      - name: "without-catalog"
        actions:
          - operator: REMOVE
            json-path: "$.application..elements[?(@.id == 'catalog')]"

With this facet, the view of shop.web in views-without-catalog no longer shows a browses link to shop.catalog, and no view of shop.catalog (the element, or a view of the manifests that is about it) is written for the facet. The same goes for a facet that selects on the state of a comparison ($.application..elements[?(@.change == 'moved')]). A reference that already pointed nowhere before the facet is not hidden by it: it is still reported as a dangling reference.

Source Code Organization

Efficiently organizing your source code is a cornerstone of successful architectural endeavors, and ArchiCode is your companion in this journey. Let’s delve into the best practices for structuring your source code using ArchiCode:

  • Workspace Dynamics: The workspace file, named workspace.yaml by default, serves as a centralized repository for your architectural data.

  • Scaling Challenges: As your architectural vision flourishes, the workspace file’s contents may expand, leading to management complexities. Recognizing the need for efficient management, ArchiCode introduces the concept of manifests. A manifest embodies a singular architectural resource, enabling focused and structured representation. With manifests, ArchiCode empowers you to break down complex elements into distinct resources, enhancing manageability and granularity. ArchiCode streamlines the process of manifest discovery by default. It effortlessly detects manifests residing in the "manifests" folder, positioned as a sibling to the workspace file.

Example of an ArchiCode project directory
- project_dir/ (1)
    - manifests/ (2)
        - application/ (3)
            - <FILENAME>.{yaml,json,toml} (4)
            - ....
        - technology/ (5)
            - <FILENAME>.{yaml,json,toml}
            - ....
    - views/ (6)
        - <RENDERER NAME>/ (7)
            - application/ (8)
                - <VIEW_ID>.<EXTENSION> (9)
                - ....
            - technoloy/
                - <VIEW_ID>.<EXTENSION>
                - ....
    - workspace.yaml (10)

  1. The directory of the project.

  2. The directory containing the manifests.

  3. An arbitrary directory containing the manifest related to the Application layer.

  4. A manifest file.

  5. An arbitrary directory containing the manifest related to the Technology layer.

  6. The directory containing the generated views.

  7. By convention, Render renders their views in subdirectory matching the Render’s name.

  8. By convention, Render renders views in directory layers.

  9. By convention, the filename of rendered views is the view identifier. The extension depends on the Renderer.

  10. The workspace file is mandatory even if empty.

  • Manifest Diversity: ArchiCode efficiently handles multiple manifest directories, facilitating the seamless incorporation of manifests, including those from package managers like NPM. This versatility enables architects to integrate diverse architectural elements from various sources. This integration showcases ArchiCode’s adaptability and its role in enhancing architectural endeavors.

Example of manifest provided by NPM modules
- project_dir/ (1)
    - manifests/ (2)
    - node_modules/ (3)
        - <MODULE_NAME>/ (4)
    - workspace.yaml (5)

  1. The directory of the project.

  2. The directory containing the manifests defined in the project.

  3. The directory containing the installed NPM modules.

  4. The directory containing the NPM module importing the other manifests.

  5. The workspace.yaml must declare both directories manifests and node_modules/<MODULE_NAME> to be able to discover all manifests
