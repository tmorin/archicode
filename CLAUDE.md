# ArchiCode

CLI tool (Quarkus + Picocli) for architecture-as-code: reads a `workspace.yaml` + manifests and renders C4/ArchiMate views (PlantUML).

## Build & Test

```bash
./mvnw clean install       # build
./mvnw test                 # unit tests only
./mvnw verify                # unit tests; the Build job of CI runs this
./mvnw verify -DskipITs=false  # unit tests, then the integration tests against the packaged jar
./mvnw verify -Dnative       # the native image and the integration tests against it, no unit tests (the Native job of CI; needs Mandrel or GraalVM)
```

Integration tests (Failsafe) are skipped by default (`skipITs=true` in pom.xml) unless run with `-DskipITs=false`, `-Dnative` or on the `native` profile (which also skips Surefire: the unit tests are the Build job's). They are the `*IT` classes of `src/test/java/io/morin/archicode/it` (`@QuarkusMainIntegrationTest`, wave 015 run 0105, #62): each launches the packaged application as a process, the jar or the native runner, on copies of the shipped examples (`src/doc/examples`, the Brightcart and bookshop fixtures) in a temp folder, and checks what it prints, its exit code and the files it writes (`views generate`, `query views|schemas|graph`, `diff`, `diff --fail-on`, `--against`, `--only-changes`, a TOML manifest, `editor serve`: started on a free port, one request, stopped). They are what the Native job runs on the native image, so a test must talk to the application through its command line and its HTTP port only. A change to the checks is a change to those classes, not to the workflow; a new class that the application reads by reflection goes to `reflect-config.json`.

Viewpoint kernel (Rust compiled to WebAssembly, shared by the CLI and the standalone editor — see `src/main/rust/viewpoint-kernel/README.md`):

```bash
cargo test --manifest-path src/main/rust/viewpoint-kernel/Cargo.toml
src/main/rust/viewpoint-kernel/embed.sh                  # after changing the Rust: rebuilds and re-embeds the .wasm
node --test "src/test/javascript/**/*.test.js"           # kernel and standalone editor vs. the views the CLI generates
```

Maven needs no Rust: `src/main/wasm/viewpoint_kernel.wasm` is committed.

Format Java sources (no npm script is wired up, so call Prettier directly):

```bash
npx prettier --write "src/**/*.java"
```

## JDK version

This project builds and runs on Java 25 — `.sdkmanrc`, `pom.xml` (`maven.compiler.release`), and CI (`.github/workflows/ci-build.yaml`) all pin or target Java 25 consistently. There is no version drift between them to work around.

## Architecture

Entry point is a Picocli `@TopCommand` (`cli/ArchiCode.java`) with the subcommand groups `ViewsGroup`, `QueryGroup`, `EditorGroup` and `PlateauGroup` and the command `DiffCommand`. Flow:

```
workspace.yaml --> workspace/WorkspaceFactory --> manifest/ManifestParser
                 --> resource/element/{application,technology}, resource/view
                 --> viewpoint/ (view assembly: an adapter around the viewpoint kernel, Rust compiled to WebAssembly); the viewpoints are `overview`, `detailed`, `deep` and `map` (a view of `viewpoint: map` draws a whole layer, application or technology, folded, with the `pinned`, `hidden` and `opened` elements of its properties; the editor draws the same view on its pages Applications and Environments, the command line draws it when it is asked for by its id (`views generate --view`); the Map of the technology layer also draws the applications deployed on the nodes and the relationships, and each can be left out with `applications: false` and `relationships: false` in the properties of the view, see below; `src/test/resources/technology-map/expected-boxes.json` is the contract of the boxes and the links both tools draw on the saved maps of the example `domain_technology_map` and of the layered Brightcart, with the variants that leave the two parts out)
                 --> rendering/plantuml (PlantUML output)
```

Facets (`settings.facets`) are evaluated by the same kernel, as standard JSONPath (RFC 9535, `serde_json_path`): `WorkspaceFactory` hands it the JSON of the workspace (`apply_facet`), the editor hands it the elements of the view. Jayway is still used by the `query` commands only. An action that removes an element removes in the same step what points at it (relationships, `uses`, `applications`), so a facet can hide an element without a `dangling reference`; it is silent about it. The earlier Jayway dialect of facets (`anyof`, `noneof`, `== null`) is rewritten with a warning, until a future major version removes it.

Plateaus are layers (next paragraph; `settings.plateaus`, `plateau add` and `--baseline` no longer exist, and a workspace file that has the key fails on every command with the one `error:` line of `WorkspaceFactory.REMOVED_KEY`, pinned by `RemovedPlateausKeyTest`, and the editor says the same sentence word for word, in its banner, as `REMOVED_PLATEAUS_KEY`, pinned by `plateau-model-cases.json` M50 to M53 and case N41 of `negative-cases.json`; `Settings` has no `plateaus` property and `READ_SCHEMA` no entry for it, so the sentence for an unknown key of `settings` does not list it): `settings.current` and `--plateau` choose the plateau, and `WorkspaceFactory` loads one plateau per call (views go to `views-<plateau>`; a comparison loads its two plateaus once each, parsing the manifests once for each, and `createUnion` is made from a copy of the target already loaded; `--plateau` is looked at before `settings.current`, so it gets past a `current` that names a plateau that is gone; `settings.facets.customs` keeps the order of the file). The kernel has six entry points: `compute` (views), `apply_facet`, `apply_patches` (the patches of a layer), `states` (the seven state words, said once), `quiet` (which elements of a layer have nothing to draw, for all of them in one call: the editor greys them in its tree, one call per layer however many elements, issue #81; the command line has no use for it and `ViewpointKernel` does not expose it) and `compare` (two plateaus in, the union with a `change` on every element and relationship and a sorted table of changes out; `compute` takes that `change` back). An element of the more recent plateau may say `replaces: [ref, ...]` (references of the plateau it is compared with; never guessed, read by `compare` only, kernel contract 4): it is then `moved`, `split` or `merged` and the replaced ones are no longer `removed`. `compare` also lists candidates (same kind and a name that no other removed and no other new element of that kind has, a close description or a lone sibling, the last only when one of the two plateaus is the past of the other: the host tells `compare` with `on_one_chain`, required since kernel contract 5), never applied: the CLI prints them only for a plateau that already uses `replaces`, the editor proposes them for any comparison. The computed states are `new`, `changed`, `removed`, `moved`, `split`, `merged` and, for a box that only contains changes, `contains-changes`: stereotypes added last to the box, with a default style that `styles.by-tags` overrides property by property, and given only to a box that has the state computed (the kernel says so with `contains_changes` on the item and, since wave 015 run 0094 (#96), on the elements of `compare`'s union too, with `contains_more_than_wording` beside it for the editor's wording toggle: `compute` removes both keys from its input, so a facet does not see them, and `StateTags.stateOf` and the page's `comparisonStateOfElement` read the key and derive nothing from the references; A manifest is YAML, JSON or TOML on the command line (`ManifestParser` reads the file with the mapper of its extension, then its `content` again as JSON text with the JSON mapper, so a TOML manifest gives the same model as its YAML twin: `TomlManifestTest`, case D36); the editor reads YAML only and lists the `.toml` and `.json` files it finds as files it does not read. ## Conventions

- Lombok is used pervasively: `@FieldDefaults(makeFinal = true, level = AccessLevel.PRIVATE)` + `@RequiredArgsConstructor` for DI-injected fields, `@Slf4j` for logging, `@SneakyThrows` instead of checked-exception boilerplate.
- SonarCloud is no longer part of CI (removed — see git history). Existing `@SuppressWarnings("java:S____")` annotations are inert leftovers from when it was; no new ones need to follow that pattern.

- Every file, example or fixture the repository ships is loaded by the command line and by the editor in a test. What fails today is pinned by a test that checks the author's error message (one `error:` line, no stack trace), or it is not shipped. A wave that ships such files names, in its plan, the test that does this for each form of them.

## Commit messages

Conventional Commits, no scope except on release commits: `feat: ...`, `fix: ...`, `chore: ...`. (Early history used `feature:`; that was abandoned in favor of `feat:` — don't revive it.) Release commits from `maven-release-plugin` are the only ones with a scope: `chore(release): archicode-X.Y.Z`.
