# ArchiCode

CLI tool (Quarkus + Picocli) for architecture-as-code: reads a `.archicode.yaml` + manifests and renders C4/ArchiMate views (PlantUML).

## Build & Test

```bash
./mvnw clean install       # build
./mvnw test                 # unit tests only
./mvnw verify                # unit tests; the Build job of CI runs this
./mvnw verify -DskipITs=false  # unit tests, then the integration tests against the packaged jar
./mvnw verify -Dnative       # the native image and the integration tests against it, no unit tests (the Native job of CI; needs Mandrel or GraalVM)
```

Integration tests (Failsafe) are skipped by default (`skipITs=true` in pom.xml) unless run with `-DskipITs=false`, `-Dnative` or on the `native` profile (which also skips Surefire: the unit tests are the Build job's). They are the `*IT` classes of `src/test/java/io/morin/archicode/it` (`@QuarkusMainIntegrationTest`, wave 015 run 0105, #62): each launches the packaged application as a process, the jar or the native runner, on copies of the shipped examples (`src/doc/examples`, the Brightcart and bookshop fixtures) in a temp folder, and checks what it prints, its exit code and the files it writes (`views generate`, `query views|schemas|graph`, `diff`, `diff --fail-on`, `--against`, `--only-changes`, a TOML manifest, `editor serve`: started on a free port, one request, stopped, and `--version`, `VersionIT`: `archicode <version>` with the version of the pom, which the build hands to the tests as the property `archicode.version`). They are what the Native job runs on the native image, on each target it builds (and the job keeps the runner, wave 021 run 0155, #149: after the tests `.github/scripts/native-collect.sh` finds the one `target/archicode-<version>-runner` (it fails unless there is exactly one), checks that its `--version` is `archicode <pom version>` (and, for a release, that the pom is the version of the tag), and uploads `native-dist/archicode-<version>-<target>` with its `.sha256` (the format of `sha256sum -c`) as the artifact `archicode-<version>-<target>`, `actions/upload-artifact@v7.0.2`, 7 days: a contributor finds it under Actions, the run of the pull request, Artifacts; it is a zip that loses the executable bit, so `chmod +x` it), so a test must talk to the application through its command line and its HTTP port only. A change to the checks is a change to those classes, not to the workflow; a new class that the application reads by reflection goes to `reflect-config.json`.

Java coverage (wave 023, run 0171, W-8): `./mvnw verify` measures `src/main/java` from every test it runs and fails below the floors. The plain JUnit tests are counted by the agent of `jacoco-maven-plugin`, the `@QuarkusTest` ones by the `quarkus-jacoco` extension (the agent leaves the classes of Quarkus' own class loader to it, `exclClassLoaders`), both into the one file `target/jacoco-quarkus.exec` (`quarkus.jacoco.reuse-data-file` in `src/test/resources/application.properties`; `maven-clean-plugin` deletes the file at the start of a build, so a previous build never adds its lines). `jacoco:check` (execution `check` of the pom) fails `verify` when the line or the instruction coverage of the bundle is 0.90 or below; the branch coverage has a guard-rail at 0.88 (the figure is 0.93: the author raises the floor to 0.90 when asked). The report is `target/jacoco-report` (`index.html`, `jacoco.csv`, `jacoco.xml`), written by the same build locally and in the `Build` job of CI (which runs `./mvnw verify`; no server and no token). At the end of run 0171 the figure is 98.5 % of the lines, 98.6 % of the instructions and 92.9 % of the branches; before it, the only report that existed said 47.8 % of the instructions because it counted the classes the chicory compiler writes from the WebAssembly. The only code outside the measure is what a compiler writes: Lombok (`lombok.addLombokGeneratedAnnotation = true` in `lombok.config` marks it `@Generated`) and `io/morin/archicode/viewpoint/kernel/ViewpointKernelModule*` (no source; excluded in the plugin config). The integration tests (`*IT`) run the packaged application in a process and are not in the figure. A test written for the figure asserts what the code returns, writes or throws (wave 023, T10); a line the tests cannot reach because it is dead is deleted, not excluded. When the kernel has to be made to break its contract (a version, a duplicate id), a test replaces `ViewpointKernel.getInstance()` with `Mockito.mockStatic`.

```bash

```

Lint (ESLint 10, flat config `eslint.config.mjs`, pinned by `package-lock.json`; wave 023 run W-6, #160 step 4, decisions T8 and T9): bug rules only, none that Prettier owns (ESLint's recommended set plus `no-shadow` and `eqeqeq`; `no-unused-vars` ignores arguments and caught errors). `npm run lint` first runs `scripts/extract-editor-script.mjs`, which copies the three executable inline scripts of `standalone.html` (`theme-boot.js`, `module.mjs`, `page.js`) to `target/eslint-editor/` padded with blank lines, so that a finding `page.js:12345` is line 12345 of the HTML, then lints `src/test` (the JavaScript tests and the `.mjs` generators), the copies, the config and `scripts/`, with `--max-warnings 0`. ## JDK version

This project builds and runs on Java 25 — `.sdkmanrc`, `pom.xml` (`maven.compiler.release`), and CI (`.github/workflows/ci-build.yaml`) all pin or target Java 25 consistently. There is no version drift between them to work around.

## Architecture

**The workspace file is `.archicode.yaml`** (wave 019, run 0144, #133, decision T9; it was `workspace.yaml` up to 0.17, a rename with no alias and no migration command): the hidden file that marks a folder as an ArchiCode workspace and holds its `settings`. Only the default of `-w` / `--workspace` changed (`cli/ArchiCode.java`), so `-w workspace.yaml` (an explicit path) still works. A folder that has `workspace.yaml` and no `.archicode.yaml` gets one sentence, the same word for word in both tools (`WorkspaceFactory.FORMER_NAME_SENTENCE` and `FORMER_WORKSPACE_FILE_SENTENCE` in `standalone.html`; the cases are `src/test/javascript/viewpoint-kernel/workspace-file-name-cases.json`, read by `WorkspaceFileNameTest` and `workspace-file-name.test.js`): rename it (`git mv workspace.yaml .archicode.yaml`) or pass `-w workspace.yaml`; the command line prints it as the one `error:` line (exit 1, also from `editor serve`) before anything is loaded, the editor shows it as the reason the folder cannot be opened. The failure to have the workspace file at all is typed (wave 020, run 0147, #146, decision T3): `WorkspaceFileException` (a subclass of `ArchiCodeException`, `workspace/`) with a `Reason`, `MISSING` (no regular file there, a folder where it should be), `FORMER_NAME` (the sentence above) and `UNREADABLE` (the file system refuses it: it was an `unexpected java.io.FileNotFoundException` with a stack trace, it is now `error: the workspace file `<path>` cannot be read: permission denied`, one line, exit 1), raised in `WorkspaceFactory.read` and by `editor serve`; `ErrorOutput` has never reworded a message and still prints it as it is (a test pins that a message which names `.archicode.yaml` for another reason is printed as it is), and the editor keeps the same kinds in `AppState.fatalErrorKind` (`setFatalError(message, kind)`, `'unreadable'` for the file that cannot be had, `'renamed'` for the former name, none for anything read and found wrong: an unknown key, a YAML that is not valid, a document that is not a mapping, `settings.plateaus`, a path or a facet name the settings refuse, which were reworded as "could not be read" because their sentence names the file and are now told as they are): the landing card words only `'unreadable'` as "`.archicode.yaml` could not be read in “folder”" (with the hint), says the sentence of `'renamed'` as it is, and the list of the remembered folders notes both (`landingScreenConfig`, `showRememberedFolders`; no equality test with `FORMER_WORKSPACE_FILE_SENTENCE` is left); the kinds of each case are `expect.failure` of `workspace-file-name-cases.json` (`unreadable`, `renamed`, `content`), read by `WorkspaceFileNameTest` (the type) and `workspace-file-name.test.js` (the kind and the card). The discovery rule finds it as the workspace and never reads it as a manifest, in a folder read without `/**` as in one read with it (hidden, so left out below a `/**` path with every hidden file; `ManifestDiscovery.WORKSPACE_FILE_NAME`, `readManifestFolder`; cases D37 and D38 of `discovery-cases.json`). `archicode editor serve` lists and serves it at the root of the folder only (`EditorHttpServer.WORKSPACE_FILE`: every other hidden entry is still refused, a `.archicode.yaml` in a folder below too). Every shipped example and fixture is renamed with it; the old name stays pinned only by the cases of the sentence above (and by `delete-plateau-as-released.test.js`, which opens the page of the tag `archicode-0.17.0` on a copy under the old name). `CustomRenderingTest` reads the author's git-ignored `.custom/.archicode.yaml`, else `.custom/workspace.yaml`.

Entry point is a Picocli `@TopCommand` (`cli/ArchiCode.java`; `-V`/`--version` is its alone and prints the one line `archicode <version>` through `cli/VersionProvider`, which reads `quarkus.application.version`, the `<version>` of the `pom.xml` fixed by the Quarkus build, so the jar, the image and the native runner each tell what they were built from, with nothing to read at run time and no resource to add to `quarkus.native.resources.includes`; exit 0, no workspace loaded; wave 021, run 0155, #149; the usage of every other command is unchanged) with the subcommand groups `ViewsGroup`, `QueryGroup`, `EditorGroup`, `PlateauGroup` and `StoriesGroup` and the command `DiffCommand`. Flow:

```
.archicode.yaml --> workspace/WorkspaceFactory --> manifest/ManifestParser
                 --> resource/element/{application,technology}, resource/view
                 --> viewpoint/ (view assembly: an adapter around the viewpoint kernel, Rust compiled to WebAssembly); the viewpoints are `overview`, `detailed`, `deep` and `map` (a view of `viewpoint: map` draws a whole layer, application or technology, folded, with the `pinned`, `hidden` and `opened` elements of its properties; the editor draws the same view on its pages Applications and Environments, the command line draws it when it is asked for by its id (`views generate --view`); the Map of the technology layer also draws the applications deployed on the nodes and the relationships, and each can be left out with `applications: false` and `relationships: false` in the properties of the view, see below; `src/test/resources/technology-map/expected-boxes.json` is the contract of the boxes and the links both tools draw on the saved maps of the example `domain_technology_map` and of the layered Brightcart, with the variants that leave the two parts out)
                 --> rendering/plantuml (PlantUML output)
```

Facets (`settings.facets`) are evaluated by the same kernel, as standard JSONPath (RFC 9535, `serde_json_path`): `WorkspaceFactory` hands it the JSON of the workspace (`apply_facet`), the editor hands it the elements of the view. Jayway is still used by the `query` commands only. An action that removes an element removes in the same step what points at it (relationships, `uses`, `applications`), so a facet can hide an element without a `dangling reference`; it is silent about it. The earlier Jayway dialect of facets (`anyof`, `noneof`, `== null`, `!= null`) is no longer read since 0.17 (issue #128, wave 018 run 0129, no legacy): the kernel (`facet::refuse_legacy`) refuses it, in `apply_facet`, `compute` and `quiet`, with one sentence that names the standard form (``the facet path `P` uses `@.qualifiers anyof ['a']`, which is not JSONPath (RFC 9535) and is no longer read: write `@.qualifiers[?(@ == 'a')]` ``), which the command line prints as `error: facet <name>: ...` (exit 1) and the editor shows as the error of the view; no contract number moves (no key or shape changed, and an unreadable path was already the one `error`); the cases are `src/test/javascript/viewpoint-kernel/facet-dialect-cases.json`, read by the kernel's tests, `ViewpointKernelTest` and `conformance.test.js`. **The name of a facet is one folder name** (wave 020, run 0146, #147, decision T2): it goes as written into the folders of the views (`views-<plateau>-<facet>`, `<NN>-<view>-<facet>`, through `directory-name-template`), so a name that is empty, `.`, `..`, or holds `/`, `\`, a NUL or another control character, or one of `<>:"|?*`, or ends with a dot or a space (the names Windows refuses: a workspace is shared across systems; the reserved device names such as `CON` are not looked at) is refused, never rewritten (two facets could share a folder), with one sentence per facet, in the order of the file, the first reason found from the left (``the facet name `a/b` cannot be the name of a folder: it holds `/`, which separates the folders of a path (write a plain word, such as `journey`)``; a control character is written out in the sentence as `\u0000`). The command line refuses it at the load, after the `manifests.paths` check and before any manifest is read, so every command that loads the workspace says it (`views generate`, `stories generate`, `query graph`, `diff`; `plateau list` reads the tree of the plateaus only and does not look at the facets) (`FacetNames`, `WorkspaceFactory.requireFacetsThatAreFolders`; one `error:` line each, exit 1); the editor stops at the same place with the same words under the heading of the settings rules (`facetNameProblem`, `facetNameProblems`; *Add facet* of the settings page refuses the name too, `validateFacetName`). The cases are N94 to N104 of `negative-cases.json` (whole workspaces, run on four commands in N97) and `src/test/javascript/viewpoint-kernel/facet-name-cases.json` (name by name, accepted names too), read by `FacetNamesTest` and `facet-names.test.js`; every shipped example uses plain words, so no output moved.

Plateaus are layers (next paragraph; `settings.plateaus`, `plateau add` and `--baseline` no longer exist, and a workspace file that has the key fails on every command with the one `error:` line of `WorkspaceFactory.REMOVED_KEY`, pinned by `RemovedPlateausKeyTest`, and the editor says the same sentence word for word, in its banner, as `REMOVED_PLATEAUS_KEY`, pinned by `plateau-model-cases.json` M50 to M53 and case N41 of `negative-cases.json`; `Settings` has no `plateaus` property and `READ_SCHEMA` no entry for it, so the sentence for an unknown key of `settings` does not list it): `settings.current` and `--plateau` choose the plateau, and `WorkspaceFactory` loads one plateau per call (views go to `views-<plateau>`; a comparison loads its two plateaus once each, parsing the manifests once for each, and `createUnion` is made from a copy of the target already loaded; `--plateau` is looked at before `settings.current`, so it gets past a `current` that names a plateau that is gone; `settings.facets.customs` keeps the order of the file). The kernel has six entry points: `compute` (views), `apply_facet`, `apply_patches` (the patches of a layer; a `REMOVE` with a `field` takes that field out of the selected elements, wave 017, run 0126, #94: any field but `id`, `parent`, `elements` and `kind`; a field the element lacks is already gone, no error; the report has `matched` and `touched` and no `removed` or `dropped`, so it is no cascade and `LayerLoader` lists no `Removal` for it; additive in contract 5, `REMOVE` without a `field` is as it was), `states` (the seven state words, said once), `quiet` (which elements of a layer have nothing to draw, for all of them in one call: the editor greys them in its tree, one call per layer however many elements, issue #81; the command line has no use for it and `ViewpointKernel` does not expose it) and `compare` (two plateaus in, the union with a `change` on every element and relationship and a sorted table of changes out; `compute` takes that `change` back). An element of the more recent plateau may say `replaces: [ref, ...]` (references of the plateau it is compared with; never guessed, read by `compare` only, kernel contract 4): it is then `moved`, `split` or `merged` and the replaced ones are no longer `removed`. `compare` also lists candidates (same kind and a name that no other removed and no other new element of that kind has, a close description or a lone sibling, the last only when one of the two plateaus is the past of the other: the host tells `compare` with `on_one_chain`, required since kernel contract 5), never applied: the CLI prints them only for a plateau that already uses `replaces`, the editor proposes them for any comparison. ## Conventions

- Lombok is used pervasively: `@FieldDefaults(makeFinal = true, level = AccessLevel.PRIVATE)` + `@RequiredArgsConstructor` for DI-injected fields, `@Slf4j` for logging, `@SneakyThrows` instead of checked-exception boilerplate.
- SonarCloud is no longer part of CI (removed — see git history). Existing `@SuppressWarnings("java:S____")` annotations are inert leftovers from when it was; no new ones need to follow that pattern.

- Every file, example or fixture the repository ships is loaded by the command line and by the editor in a test. What fails today is pinned by a test that checks the author's error message (one `error:` line, no stack trace), or it is not shipped. A wave that ships such files names, in its plan, the test that does this for each form of them.

## Commit messages

Conventional Commits, no scope except on release commits: `feat: ...`, `fix: ...`, `chore: ...`. (Early history used `feature:`; that was abandoned in favor of `feat:` — don't revive it.) Release commits from `maven-release-plugin` are the only ones with a scope: `chore(release): archicode-X.Y.Z`.

## Release

Cut via `maven-release-plugin`. Commit messages use a `chore:` prefix, release commits are `chore(release): archicode-X.Y.Z`. Tag pushes trigger publishing the site to GitHub Pages: the presentation page (`src/site/index.html`) at the root, the Asciidoctor manual (`src/doc`, built to `target/generated-docs`) at `/docs/`, and the editor at `/editor/`.

The binaries go to the GitHub release page (wave 021, run 0156, #149): `.github/workflows/ci-build.yaml` and the scripts of `.github/scripts` (bash 3.2, they run on macOS; tested with fakes by `test-release-scripts.sh` in the job `Targets` of every run). `Targets` (`release-plan.sh`, whose header lists the cases) builds `linux-amd64` only (the check `Native`) for a pull request, a push to `main` and a tag that is not a release, and the three targets of `release_targets` in `release-lib.sh` (`linux-amd64` on `ubuntu-24.04`, `linux-arm64` on `ubuntu-24.04-arm`, `macos-arm64` on `macos-15`, Mandrel for JDK 25 on all three; `Native (<target>)`) for a tag whose head commit message begins `chore(release)` and for a `workflow_dispatch`. Then `Release` puts `archicode-<version>-<os>-<arch>` and `SHA256SUMS` on a DRAFT (`--generate-notes` from the previous release tag, a link to the manual's `[[upgrade-X-Y]]`), `Smoke (<target>)` tests each file as downloaded from the draft (`--version`, `views generate` on `domain_plateaus`, `editor serve`), and `Publish` publishes it (marked "Latest" only when no release tag is newer). `workflow_dispatch -f tag=archicode-X.Y.Z [-f draft=false]` rebuilds a tag and attaches to its draft (a published release is refused); with no `tag` it rehearses on a draft `rehearsal-<pom version>-<run id>` that is never published (`gh release delete <tag> --yes` after). A dispatch skips `Build` (no Maven artifact, image or website); its scripts come from the dispatched commit, the sources from the tag. Never rehearse with a test tag: every tag publishes the website.
