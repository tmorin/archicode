# ArchiCode

CLI tool (Quarkus + Picocli) for architecture-as-code: reads a `workspace.yaml` + manifests and renders C4/ArchiMate views (PlantUML).

## Build & Test

```bash
./mvnw clean install       # build
./mvnw test                 # unit tests only
./mvnw verify                # unit + integration tests (what CI runs)
```

Integration tests (Failsafe) are skipped by default (`skipITs=true` in pom.xml) unless run with `-Dnative` or on the `native` profile.

Viewpoint kernel (Rust compiled to WebAssembly, shared by the CLI and the standalone editor — see `src/main/rust/viewpoint-kernel/README.md`):

```bash
cargo test --manifest-path src/main/rust/viewpoint-kernel/Cargo.toml
src/main/rust/viewpoint-kernel/embed.sh                  # after changing the Rust: rebuilds and re-embeds the .wasm
node --test "src/test/javascript/**/*.test.js"           # kernel and standalone editor vs. the views the CLI generates
```

Maven needs no Rust: `src/main/wasm/viewpoint_kernel.wasm` is committed.

Format Java sources (no npm script is wired up, so call Prettier directly):

```bash
npx prettier --write "src/**/*.java"
```

## JDK version

This project builds and runs on Java 25 — `.sdkmanrc`, `pom.xml` (`maven.compiler.release`), and CI (`.github/workflows/ci-build.yaml`) all pin or target Java 25 consistently. There is no version drift between them to work around.

## Architecture

Entry point is a Picocli `@TopCommand` (`cli/ArchiCode.java`) with the subcommand groups `ViewsGroup`, `QueryGroup`, `EditorGroup` and `PlateauGroup` and the command `DiffCommand`. Flow:

```
workspace.yaml --> workspace/WorkspaceFactory --> manifest/ManifestParser
                 --> resource/element/{application,technology}, resource/view
                 --> viewpoint/ (view assembly: an adapter around the viewpoint kernel, Rust compiled to WebAssembly); the viewpoints are `overview`, `detailed`, `deep` and `map` (a view of `viewpoint: map` draws a whole layer, application or technology, folded, with the `pinned`, `hidden` and `opened` elements of its properties; the editor draws the same view on its pages Applications and Environments, and `src/test/resources/technology-map/expected-boxes.json` is the contract of the boxes both draw on the example `domain_technology_map`)
                 --> rendering/plantuml (PlantUML output)
```

Facets (`settings.facets`) are evaluated by the same kernel, as standard JSONPath (RFC 9535, `serde_json_path`): `WorkspaceFactory` hands it the JSON of the workspace (`apply_facet`), the editor hands it the elements of the view. Jayway is still used by the `query` commands only. An action that removes an element removes in the same step what points at it (relationships, `uses`, `applications`), so a facet can hide an element without a `dangling reference`; it is silent about it. The earlier Jayway dialect of facets (`anyof`, `noneof`, `== null`) is rewritten with a warning, until a future major version removes it.

Plateaus are layers (next paragraph; `settings.plateaus`, `plateau add` and `--baseline` no longer exist, and a workspace file that has the key fails on every command with the one `error:` line of `WorkspaceFactory.REMOVED_KEY`, pinned by `RemovedPlateausKeyTest`, and the editor says the same sentence word for word, in its banner, as `REMOVED_PLATEAUS_KEY`, pinned by `plateau-model-cases.json` M50 to M53 and case N41 of `negative-cases.json`; `Settings` has no `plateaus` property and `READ_SCHEMA` no entry for it, so the sentence for an unknown key of `settings` does not list it): `settings.current` and `--plateau` choose the plateau, and `WorkspaceFactory` loads one plateau per call (views go to `views-<plateau>`; a comparison loads its two plateaus once each, parsing the manifests once for each, and `createUnion` is made from a copy of the target already loaded; `--plateau` is looked at before `settings.current`, so it gets past a `current` that names a plateau that is gone; `settings.facets.customs` keeps the order of the file). The kernel has six entry points: `compute` (views), `apply_facet`, `apply_patches` (the patches of a layer), `states` (the seven state words, said once), `quiet` (which elements of a layer have nothing to draw, for all of them in one call: the editor greys them in its tree, one call per layer however many elements, issue #81; the command line has no use for it and `ViewpointKernel` does not expose it) and `compare` (two plateaus in, the union with a `change` on every element and relationship and a sorted table of changes out; `compute` takes that `change` back). An element of the more recent plateau may say `replaces: [ref, ...]` (references of the plateau it is compared with; never guessed, read by `compare` only, kernel contract 4): it is then `moved`, `split` or `merged` and the replaced ones are no longer `removed`. `compare` also lists candidates (same kind and a name that no other removed and no other new element of that kind has, a close description or a lone sibling, the last only when one of the two plateaus is the past of the other: the host tells `compare` with `on_one_chain`, required since kernel contract 5), never applied: the CLI prints them only for a plateau that already uses `replaces`, the editor proposes them for any comparison. The computed states are `new`, `changed`, `removed`, `moved`, `split`, `merged` and, for a box that only contains changes, `contains-changes`: stereotypes added last to the box, with a default style that `styles.by-tags` overrides property by property, and given only to a box that has the state computed (the kernel says so with `contains_changes` on the item and, since wave 015 run 0094 (#96), on the elements of `compare`'s union too, with `contains_more_than_wording` beside it for the editor's wording toggle: `compute` removes both keys from its input, so a facet does not see them, and `StateTags.stateOf` and the page's `comparisonStateOfElement` read the key and derive nothing from the references; the kernel says the seven words once with its `states` entry point, which `KernelStates` and the page read; a hand-written state word that disagrees is only the author's stereotype, and the command says so on the error output, as it does for the warnings of `replaces`, see below). `archicode diff` and `views generate` write the table (`gap.md`, `gap.json`, with the identity and the candidates) and `views-<plateau>-vs-<against>`; `diff --fail-on <state>[,<state>...]` (the seven words of `KernelStates` and `any`, `cli/FailOn`; the option may be repeated) exits with 3 when the table holds a change of a listed state, 0 otherwise, and prints the table as it does without the option (with `--no-wording` a row that is wording only does not count; an unknown or empty state is one `error:` line, exit 1, before anything is loaded); `views generate --only-changes` passes the kernel's `only_changes` to the views of the comparison only (`views-<plateau>-vs-<against>` and its facets: the views of the plateau and the table are as they were) and is an `error:` line when nothing is compared; the editor compares the drawn plateau with another one (*Compare with* on the band: nothing, the past, the future or any other plateau; the Changes panel with *Write replaces* and *Not related*; Changes only, a switch among the tools of the diagram; there is no other selector and no *Compare to*) and moves an element under another parent (*Move*: children follow, references rewritten in every file; the code can write `replaces` for the element and each element inside it with *Move and write replaces*, offered only when the plateau compared with is one the plateau drawn overrides, directly or not (#95; `replacesAncestorProblem`), but the old reference of a movable element is never in such a plateau, so no page can reach the button (#97): the manual does not teach it, and says that *Move* writes no `replaces`). Every edit goes through the line-preserving save, and anything that changes a model must end in `rebuildIndexAndRender()` or call `modelsChanged()`: the comparison cache, the diagram cache and the cache of the quiet references are keyed on that version counter (plus the small parts that vary: facet, viewpoint, options), not on the serialised models or the kernel input (issues #32 and #37). A workspace without plateaus is byte-identical to before; `..` and absolute paths in `manifests.paths` are refused, and so is a reference declared twice. Where the manifests are: an entry of `settings.manifests.paths` that ends in `/**` is read recursively, any other entry reads the files directly in its folder. `manifest/ManifestDiscovery` (the command line) and `readManifestFolder` in `standalone.html` (the editor) apply one rule, run on one list of cases, `src/test/javascript/viewpoint-kernel/discovery-cases.json`, by `ManifestDiscoveryTest` and `discovery.test.js`: files sorted by their path from the folder of `workspace.yaml`, compared by Unicode code point; below a `/**` path, no hidden file or folder, no link to a folder (`link` in the list of `editor serve`), and no folder of the generated views (`views.path` at its depth, and the folders beside it that begin with its name and a dash), and no folder that holds both files a comparison writes (`gap.json` and `gap.md`, whichever `--output` and whichever command: `ManifestDiscovery.holdsComparison`, `holdsComparisonFiles` in the page; a lone `gap.json` is read, since it may be a manifest); `**` anywhere else in an entry is a one-line error (`ManifestDiscovery.pathProblems`, `manifestsPathProblems` in the page). A change to the rule is a change to the cases file. A manifest is YAML, JSON or TOML on the command line (`ManifestParser` reads the file with the mapper of its extension, then its `content` again as JSON text with the JSON mapper, so a TOML manifest gives the same model as its YAML twin: `TomlManifestTest`, case D36); the editor reads YAML only and lists the `.toml` and `.json` files it finds as files it does not read. The kinds of a manifest are the seven elements, `view`, `story` and `plateau` (`ManifestKind`, `ARCHICODE_KIND_MAP`, `READ_SCHEMA.manifestKinds`): `container-group`, `solution-group` and `system-group` are no kinds, in both tools (a group is an element nested in a container, a solution or a system, kind `group`), and give `unrecognized header.kind` (N56 to N58 of `negative-cases.json`).

Layered plateaus (wave 014): a manifest of an element or a plateau says `plateau: <id>` in its header (none: `baseline`, the implicit root; a view and a story belong to no plateau, see below), and an optional manifest of kind `archicode.morin.io/plateau` (`resource/plateau/Plateau`: `id`, `name`, `horizon`, `override` — one plateau, absent means `baseline` — and `patches`, read by `Patch` and carried as data for the kernel's `apply_patches`) qualifies it. `ManifestParser.parse` builds a `resource/plateau/PlateauTree` from them (ids in `[a-z0-9_-]`, declared once, a known `override`, no cycle: one `error:` line each; a plateau that only headers name, or two ids one letter apart when at least one of the two only has headers to name it (the typo; two plateaus with a manifest each, `p1` and `p2`, give none; decided on 2026-10-18; also two `SET` of one field of one target in one plateau, the last wins, and a horizon earlier than the parent's, both read as periods: a warning through `Warnings`), and `PlateauTree.redeclared` refuses a reference declared in a plateau and again in its ancestor (two plateaus that do not stack may each declare it). `tree.chain(id)` is what a plateau is loaded from (root first): `workspace/LayerLoader` adds, for each plateau of the chain, the elements of `Parsed.ofPlateau(id)` to the graph, then hands the elements of the two layers and the patches of the plateau to the kernel (`apply_patches`, a plateau without patches does not leave the model), then checks the layer (a relationship, a `uses` entry, a hosted application, a parent: one `error:` line each, naming the plateau; the first plateau that is wrong ends the load). **Views and stories belong to no plateau** (wave 015, run 0100, #100 and #86; the assumption A8 of wave 014, that they carry `plateau:` and are validated after each layer, is revised): only elements, patches and plateaus are layers. `Parsed.placedViews`/`placedStories` hold them with their file and no plateau; a view (a story) is declared once in the whole workspace (the existing `declared twice` error, even across plateaus that do not stack); `plateau:` in their header is a warning, the key is ignored and names no plateau (`ManifestParser.ignoredPlateauWarning`, `buildPlateauTree`; M01, M84 to M86 of `plateau-model-cases.json`, N79 of `negative-cases.json`). The check that remains is plateau-free and told once, after the layers (`LayerLoader.entryProblems`, `entryProblemsOf` in the page; K04, K05, K32 to K36 and N80): every element a view or a story step names must be *declared* by a manifest or `workspace.yaml` in some plateau (`Parsed.declared`), else ``the view `v` (`file`) names `x`, which exists in no plateau``; patches are not resolved for it, since a patch never creates an element. Only a workspace that has plateaus is checked. A name that another plateau has and the plateau drawn lacks is no mistake of the view: the command line leaves it out of a map (`KernelViewpointFactory.mapLists`) with a warning, and skips, with a warning, a map none of whose pinned elements is there and a view whose element is not there (`GenerateViewsCommand.canBeDrawnInPlateau`, which asks the plateau a facet was applied to; N81, N82), and the page says the view cannot be drawn in this plateau (`viewProblem`, `viewLacksInPlateau`). The checks of a layer (`LayerLoader` and `layerProblemsOf`/`resolveLayerStep` in the editor) are one file of cases, `src/test/javascript/viewpoint-kernel/layer-checks-cases.json`, read by `LayerLoaderTest` and `layer-checks.test.js`: the command line stops at the first layer that is wrong and draws nothing, the editor tells the same sentences in the same order and draws the plateau all the same, so that it can be repaired. Which kind a parent holds is written once, in the model (`Parent#elementType()`, read by `resource/element/application/Nesting`); `ElementIndexFactory` refuses an element declared with `header.parent` under a parent that cannot hold its kind, in every path and with or without patches in its layer (one sentence per element, sorted by reference, that names the file and says `unknown kind x under p (known: ...) at header.kind`), the page derives `childKindOptionsForLevel` and its check from `READ_SCHEMA`, and `EditorReadSchemaTest` and the table `nesting.holds` of the cases compare both with the classes. An id with a dot is a one-line error in both tools (`ManifestParser.dottedId`, `dottedIdProblem`; M81 to M83 of `plateau-model-cases.json`). `WorkspaceFactory.load` takes this path when the manifests are layered; `--plateau` names the plateau (default `settings.current`, else the last one when the tree is one line), `--against` the plateau to compare with (default the one it overrides; the root has none to default to), `plateau list` lists the tree, `views-<plateau>` and `views-<plateau>-vs-<against>` are the folders, and what a `REMOVE` took besides what it names (`Removal`, from the kernel's `removed` and `dropped`) is listed after the table of changes (`GapReport`, `gap.md`, `gap.json`). `PlateauComparer` leaves out of a layered target the `replaces` that the base writes the same way for the same element, decided from the two elements when the kernel's graph is built (`KernelGraph.of` takes the test) and not by editing the JSON afterwards (an inherited element keeps the `replaces` of the layer that declared it, which would otherwise warn once per element; whether an entry is news depends on the plateau it is compared with, so the load of one plateau cannot take it out: against the root the `replaces` of `inhouse` are kept); the `replaces` of the layers are not composed, so a move that took two steps reads as new and removed against a plateau two layers up (P4 of the Brightcart fixture). The Brightcart fixture ships only its layered form, `src/test/resources/brightcart/layered/`, written by `generate.mjs`; the converted fixtures of the old plateaus (`plateau-comparison`, `plateau-state-*`, `split-relationships`, `replaces-large-pair`) keep their first state as the manifests of the root with an empty layer of its name over it, so their numbers did not change; the manual's example `domain_plateaus` (the bookshop of the tutorial) is written as a reader would write it, a root named `As is` by its own `Kind: Plateau` manifest (`id: baseline`) and the one layer `to-be`, and is loaded by `ManualExamplesTest`, `ShippedFilesTest`, `PlateauComparisonTest` (the tables the manual quotes), `FacetRemovesElementTest` and, in the editor, `shipped-files.test.js` and `example-identity.test.js` (what the layers add: every plateau but the root is compared with the one it overrides when its views are generated, and `diff` ends with the cascade of the removals; a tree that forks needs `--plateau`). The editor builds the same tree with the same sentences (`buildPlateauTree` in `standalone.html`, `READ_SCHEMA` for the kind); `plateau-model-cases.json` is read by `PlateauModelTest` and `plateau-model.test.js`. The manual says what the tools do and what they do not yet (`[[plateau-limits]]`: #89, #94, #84, #78, #88, and #86, #97); change it with the tools.

Errors and warnings: `cli/ErrorOutput` is the error path of every command (installed on the Quarkus `CommandLine` by `cli/CommandLineConfiguration`, and by the tests through `errorOutput.install(commandLine)`): a failure the author can act on (`ArchiCodeException`, a manifest or workspace file that is not valid or absent, a file or folder the file system refuses, a port in use; the most precise cause in the chain wins, and an `IOException` that is not about a file is a bug) is `error: <one line>` on the error output with exit code 1 and no stack trace, a usage error keeps picocli's code 2, `archicode diff --fail-on` is the one command that exits with 3 (`ErrorOutput.CHANGES_FOUND`), and an unexpected exception keeps its trace. Nothing uses `log.warn` for the user, since `quarkus.log.level=ERROR` hides it: a warning goes through the `Warnings` bean (`warn`, `warnAll`), de-duplicated, and `ErrorOutput` prints it as `warning: ...` when the command ends (before the error, if it fails). Facet rewrites, a story step on an undeclared view, a skipped viewpoint, `Comparison.getWarnings()` and `StateTags` use it. The editor refuses the same manifests and `workspace.yaml` with the same sentences (`READ_SCHEMA` in `standalone.html`: the keys, shapes and kinds of each class; `EditorReadSchemaTest` compares it with the classes, so a class that gains a key fails until the page knows it; the cases both tools run are in `src/test/resources/brightcart/negative-cases.json`). `AbstractElement.replaces` is read as a `Replaces` (a set of the references that also keeps the JSON as written), which `KernelGraph` hands to the kernel, so that the kernel's warnings about a duplicate, a non-reference entry and a non-list fire from the CLI. Both tools read the same way what is empty or odd (wave 015 run 0092, #80 and #85; `MapperFactory.reading`, the cases N59 to N77 of `negative-cases.json` and M65 to M80 of `plateau-model-cases.json`): a key with nothing after it and an item with no value in a list are absent, so the default is read (`global-enabled:` empty is `true`; a `JsonNode` such as a patch `value` keeps its null; a map keeps a null value; the page leaves the item out of `elements`, `paths`, `qualifiers`, `applications` and `uses` but keeps it in `relationships`, #105), a manifest that holds only `null` has no header, an empty or comment-only `workspace.yaml` is the default workspace, `settings.current: ""` names no plateau, a number is no value of an enum (`header.kind: 5`, `layer: 1`) and an item of `elements` that is a list is the wrong shape; the keys of `settings.facets` are told in kebab-case (`global-enabled`, `directory-name-template`, `hide-unlinked`, `json-path`; the camel-case spelling is an alias, still read); the fields of a header that the command line types as text (`parent`, `plateau`, `version`) are the text as written, so `parent: yes` is the reference `yes` in both (`parseYamlAsModel` in the page), while the content reads a YAML 1.1 boolean as the boolean in both (`id: yes` is `true`). Known differences, pinned and filed as #103 and #105: a plain scalar written as a YAML 1.1 number the page cannot print back as it was written (`0x1F`, `010`, `1_0`, `5.0`, `1e2`) is a number for the command line and a text for the page; the page does not tell the line and the column of a file.

## Conventions

- Lombok is used pervasively: `@FieldDefaults(makeFinal = true, level = AccessLevel.PRIVATE)` + `@RequiredArgsConstructor` for DI-injected fields, `@Slf4j` for logging, `@SneakyThrows` instead of checked-exception boilerplate.
- SonarCloud is no longer part of CI (removed — see git history). Existing `@SuppressWarnings("java:S____")` annotations are inert leftovers from when it was; no new ones need to follow that pattern.

- Every file, example or fixture the repository ships is loaded by the command line and by the editor in a test. What fails today is pinned by a test that checks the author's error message (one `error:` line, no stack trace), or it is not shipped. A wave that ships such files names, in its plan, the test that does this for each form of them.

## Commit messages

Conventional Commits, no scope except on release commits: `feat: ...`, `fix: ...`, `chore: ...`. (Early history used `feature:`; that was abandoned in favor of `feat:` — don't revive it.) Release commits from `maven-release-plugin` are the only ones with a scope: `chore(release): archicode-X.Y.Z`.

## Release

Cut via `maven-release-plugin`. Commit messages use a `chore:` prefix, release commits are `chore(release): archicode-X.Y.Z`. Tag pushes trigger publishing the site to GitHub Pages: the presentation page (`src/site/index.html`) at the root, the Asciidoctor manual (`src/doc`, built to `target/generated-docs`) at `/docs/`, and the editor at `/editor/`.
